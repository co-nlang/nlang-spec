## 1. 創世自舉流程 (Genesis Bootstrapping) **[Core Requirement]**

為了解決語言初期的「冷啟動」問題，引擎必須實作嚴格的自舉流程。

1.  **初次啟動檢測**：當引擎啟動且本地不存在 `.oo/` 目錄時，觸發自舉。
2.  **種子解壓縮**：引擎將內建的官方標準庫（如 `~%List`, `~%Math`）寫入本地存儲。
3.  **創世 Commit 產生**：
    *   計算種子原始碼的 CAID。
    *   驗證 CAID 是否與引擎硬編碼的「官方種子 CAID」一致。
    *   產生宇宙的第一個 Commit $C_0$（創世 Commit）。
4.  **建立根宇宙 `_`**：將 `_` 指向 $C_0$，完成工作區初始化。

## 3. L1 物理層：傳輸載體 (The Carrier Layer)

`~%Discovery./fetch` 在語言層是抽象態射，實際的網路行為由引擎實作。

### 3.1 傳輸優先順序

```
1. 本地快取 (.oo/objects/)     ← 最快，無網路請求
2. 工作區已知節點              ← 團隊內部共享
3. 設定的 registry 節點        ← 類似 npm registry，但非強制中央
4. IPFS / Git HTTP             ← 公開後備來源
```

引擎按順序嘗試，第一個回應有效內容的來源獲勝。
來源不影響收斂結果——相同的 hash 無論從哪裡取得，內容必然相同。

### 3.2 OODP 基礎封包格式

**角色，不是指令名**：任何以 OODP 暴露投影與取物能力的程序都是發現／取物
節點。CLI 拼法是 `oo node serve`（REAL_01 §1.2 宇宙節點）；`serve-discovery`
不是獨立子命令。同一封包承載三種 `%op`；本引擎目前**實作** `#fetch` 與 `#advertise`（§4.2），
對 `#discover` 回傳明確的「本節點未實作」狀態（不得以靜默代答）。

**Request 結構**（n/ Cocoon 或等價 JSON；線上鍵名帶 `%`）：
```nlang
{{
    %op:   #discover | #fetch | #advertise | #find_node
    %hash:   "hash:sha256:v1:9f86d081..."  ;; 目標 CAID（#fetch 必填）
    %from:   @caid                         ;; 請求節點 ID（節點身分弧起攜帶）
    %ad:     @ServiceAdvertisement         ;; #advertise 必填（§4.2）
    %target: @caid | @str                  ;; #discover 為 CAID（§4.3）；
                                           ;; #find_node 為 40 hex 之節點 ID（§4.4）
}}
```

**`%from`【2026-07-27 更新,規範性】**:請求**必須**攜帶請求方之 `node_id`(§4.1)。**但它是主張,不是認證**——本版不簽名,任何對等點皆可填入任意值。因此**不得有任何判定依賴它**:服務、驗證與四向結果,無論 `%from` 為何皆須完全相同(與本節「對等點的 `%status` 是主張,不是驗證」同一律)。其用途為可觀測性,以及為 `#advertise`(宣告者)與 `#discover`(DHT 路由)鋪路。`#fetch` 本身不依賴「誰在問」:物件自驗證(REAL_03 §6.6)。

**【2026-07-28 補】** 上述「屆時另訂」於 `#advertise` 已定:該 op 的 `%from` **必須**與 `%ad.node_id` 相符,且身分由廣告自身的簽章認證(§4.2.1–§4.2.2)。**這不使 `%from` 在 `#fetch` 上變成認證**——`#fetch` 的服務與四向結果仍必須與 `%from` 無關。同一個欄位在一個 op 上被簽署、在另一個 op 上仍是主張,並無矛盾:承擔認證的從來不是欄位,是簽章。

**【2026-07-28 再補,`#discover` 定案】** 上文「`#discover` 仍待定」現已裁定:**`#discover` 上的 `%from` 與 `#fetch` 同,是主張而非認證**,**不得有任何判定依賴它**(§4.3.6)。理由:一次發現回答只是把**已簽署之公開記錄**再廣播一次,使答案取決於誰在問,買不到任何安全性,卻造出一個分區面(同一個問題對不同提問者給不同答案)。

**Response 結構**（JSON 物件；鍵名字面為 `%status` 等）：
```nlang
{
    %status: #success | #not_found | #conflict | #not_implemented | #rejected
    %result: _         ;; 僅 #success 時承載值；缺席不得視為成功
    %reason: #tag      ;; 每一個非 #success 皆必須攜帶（§3.2.1）
    %source: @str      ;; 回應節點的識別碼
    %hops:   @int      ;; 本記錄在抵達你之前被轉發過幾次；直答為 0（§4.3.4）
    %peers:  [@RelayedAdvert]   ;; 僅 #discover；可為空列表（§4.3.3）
}
```

**`#rejected` 與 `%reason`【2026-07-28 新設;2026-07-29 擴及全部非成功狀態,規範性】**:`#rejected` 意為「請求可理解,但本節點拒絕受理」,與 `#conflict`(格式錯或完整性裁決)、`#not_implemented`(不辦此 op)皆不同。其**判別理由必須**由 `%reason` 攜帶。

> **原條文寫「`%reason` 當且僅當 `%status` 為 `#rejected` 時出現」,已刪除。** 該限制與同段下一句自相矛盾:下一句主張「狀態集合維持小,**可分性住在 `%reason`**」,而「當且僅當 `#rejected`」正好使可分性**只能**住在狀態碼裡。本節在同一段裡主張一個修法又禁止它。**現行規則見 §3.2.1。**

理由不得收攏成單一標籤:一個以「四件事必須可分」為論旨的協定,若把四種拒絕收成一個 `#conflict`,即是 §1.2 `#timeout` 那個錯誤降一層重演。狀態集合維持小而跨 op 穩定,可分性住在 `%reason`——新增 op 不得為此膨脹共用狀態集。

#### 3.2.1 每一個非成功回應都必須說出為什麼 **[Core Requirement,2026-07-29 新設]**

*   **`%reason` 於 `%status` 非 `#success` 時必須出現(MUST)**,於 `#success` 時**不得**出現。
*   **`%status` 集合不得為此增長(MUST NOT)**:仍為 `#success` / `#not_found` / `#conflict` / `#not_implemented` / `#rejected` 五者。新增 op 或新增可分情況一律以 `%reason` 承載。
*   **本節點不服務之 op 回 `#not_implemented`(MUST)**,而非 `#conflict`——不論該 op 名是「未知」或「已知而未實作」。二者對提問者是同一件事:**換一台問**。而 `#conflict` 說的是另一件事:**修你自己的封包**。
*   **未知的 `%reason` 標籤不得使回應失效(MUST NOT)**:收方遇到不認得的理由,**必須**依 `%status` 行事並將該理由視為不透明字串。理由集得增長;狀態集不得。

**跨 op 之共用理由集**(此表為規範性;`#rejected` 另有 §4.2.2 之集合):

| `%status` | `%reason` | 意義 |
| :-- | :--- | :--- |
| `#not_implemented` | `#unknown_op` | 本節點不服務此 op |
| `#not_found` | `#not_held` | 明確的缺席 |
| `#conflict` | **`#caid_mismatch`** | **持有,而位址重算不符——本表上唯一的完整性裁決** |
| `#conflict` | `#malformed` | 封包不成形(含無 `%op`、空行、`%target` 形狀錯) |
| `#conflict` | `#missing_field` | op 可辨識,而必填欄缺席 |
| `#conflict` | `#unparseable_caid` | `%hash` / `%target` 存在但不是 CAID |

> **`#caid_mismatch` 是這張表的重點,不是其中一列。** `#conflict` 此前同時表示「你的請求有問題」與「我這裡的位元組壞了」,而只有後者是關於**內容**的裁決。收方據此決定要不要在對方名下記一筆完整性事件——見 §3.2.2。**一個無法被佐證的指控不該寫進聲譽紀錄。**

#### 3.2.2 協定層的回答不是完整性裁決 **[Core Requirement,2026-07-29 新設]**

收方**必須**區分「對端關於**內容**的裁決」與「對端關於**這次交談**的回答」,且**只有前者得記入完整性紀錄**(REAL_03 §6.6)。

| 對端所言 | 客戶端 `%cause` | 記入完整性紀錄? |
| :-- | :--- | :--- |
| `#conflict` + `%reason: #caid_mismatch` | `#caid_mismatch` | **是** |
| `#conflict` + 其他理由,或**無**理由 | `#peer_refused` | 否 |
| `#not_implemented` | `#peer_not_implemented` | 否 |
| `#rejected` | `#peer_refused` | 否 |
| **本引擎不認得的 `%status`** | `#peer_unknown_status` | **否** |
| `#not_found` | `#missing_key` | 否 |

*   **未知狀態碼不得被當作損壞(MUST NOT)**。**一個比你新的節點不是一個被弄壞的節點。** 若違反此條,協定的**每一次**未來擴充都會使舊實作指控新實作損壞——而完整性紀錄正是操作者用來判斷誰在供應壞資料的東西,污染它即使其失去用途。此為 REAL_03 §6.6「裁決必須為真」在網路面的形。
*   **無理由之 `#conflict` 判為拒絕(MUST)**:舊實作不攜帶 `%reason`,而**無法佐證的指控不得寫入**。其代價明列於此並被接受:舊對等點**自身偵測到**的完整性問題,於收方讀作拒絕。代價有界——收方本就對其接受的每一個位元組重算位址(REAL_03 §6.6),失去的是對方的**報告**,不是自己的**檢查**。

| 對等點狀態 | `%status` | 客戶端可見 |
| :-- | :--- | :--- |
| 持有且位址驗證通過 | `#success` | 值（客戶端仍須重算 CAID） |
| 未持有 | `#not_found` | 缺席（`⊥ #missing_key`），**不是** conflict |
| 持有但本地位址驗證失敗 | `#conflict` | 具名完整性裁決（客戶端側為 `#caid_mismatch` 等） |
| 接受連線後無回應 / 逾時 | （無回應） | `⊥ #peer_timeout`，與上三者可分 |

**對等點的 `%status` 是主張，不是驗證**。即使對端宣稱 `#success`，客戶端仍
必須對 `%result` 重算內容位址；不符則為 `#caid_mismatch`（REAL_03 §6.6），
與對端說法無關。

**禁止以靜默代替狀態**：缺物、腐敗、未知 op、未實作 op 皆須有可區分的
`%status`（或明確逾時）；不得以 0-byte 回應讓客戶端把四種情況收成同一結果。

> **【2026-07-29 已結案】** 下述缺口由 §3.2.1 補上:未知 op 改回 `#not_implemented`(修法 a)**且**全部非成功狀態攜帶 `%reason`(修法 b)——**兩解皆採,因其各答一半**。實測七格全可分(值/損壞/缺席/未知 op/缺欄/格式錯/CAID 不可解)。本條自此**得**被引用。以下為原始記錄,保留其量測。

**傳輸協定**：OODP 封包可跑在任何傳輸層上：Unix socket、TCP、HTTPS、或作為 libp2p 的擴展。預設讀取逾時由引擎約定（現行實作 10s）。

## 4. L2-L3 介面：節點發現與路由

### 4.1 Kademlia DHT 基礎路由 **[Core Requirement]**

L2 使用 **Kademlia XOR 路由**尋找物理節點。這是工程妥協——純粹的譜路由在離散 DHT 中難以實作。

**路由表結構【2026-07-28 落地並精確化】**：

*   **節點 ID** = `node_id` CAID 之**內容摘要前 160 bit**,即**前 20 個位元組**(原始位元組,非十六進位字元)。該 CAID 定址何物見 §4.1.1。
    > **欄位名更正**:原文作 `content_digest`,而該欄位名為 `digest`。此非文字瑕疵——宇宙決定性弧曾有一次比對讀了不存在的鍵而**兩側恆得 None**,於是空洞通過。**規格寫錯欄位名,會製造出綠色的空洞量測。**
*   **距離度量** = `XOR(a, b)`,以大端序整數比較。
*   **桶索引** *i* = `XOR(self, peer)` 的**前導零位元數**;等價地,與自身共享恰好 *i* 個前導位元者入桶 *i*。`i == 160` 意為該對等點**即是自己**,**不得**存入。
*   **每桶容量 k = 20**。
*   **160 個固定桶**。桶分裂(標準 Kademlia 二叉樹)為後續優化,本版不做:在可觸及的深度上它不改變任何可量測行為。

#### 4.1.1 節點身分 **[Core Requirement,2026-07-27 新設]**

前條說了如何由一個 CAID 導出節點 ID,卻從未說**那是什麼東西的 CAID**。本節補上。

*   **材質(MUST)**:節點身分是一組**金鑰對**;`node_id` 為其**公鑰**之 CAID,DHT 位址取其前 160 bit。**不得**由宇宙內容導出——**[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)** §4.1.2 義務 #1 要求同源宇宙在任何行程、任何工作區得到相同的根 CAID(實測:兩個全新工作區、同一份原始碼 ⟹ 同一個根 digest),而那正是節點位址**不能**具備的性質:所有服務同一宇宙的節點將佔據同一個槽位。**讓宇宙可聯邦的性質,恰好取消它作為節點位址的資格**——內容定址回答「是什麼」,節點位址回答「眾多持有者中的哪一個」。且 §4.2 之 `signature` 本就需要私鑰。
*   **與操作者身分之別(MUST NOT)**:節點金鑰**不得**與 **[REAL_01](./REAL_01_Ouroboros_Engineering.md)** §7.5 之操作者金鑰為同一把。二者回答不同問題:操作者金鑰回答**誰授權**(治理、`#refine` 簽署,屬人),節點金鑰回答**哪一台在服務**(屬工作區)。以操作者金鑰為節點金鑰,將使複製工作區等同複製操作者的簽署能力——正是 §7.5 存在的理由。
*   **住所與作用域(MUST)**:節點金鑰**不得**置於工作區儲存(`.oo/`)之內,理由同 §7.5.1(該樹是設計來被取用與複製的成品)。其**工作區絕對路徑為身分的一部分**:引擎**無法**區分「工作區被搬移」與「工作區被複製」——它只觀察到路徑改變——故令路徑參與身分,使**複製在結構上即為另一個節點**,無需偵測、無需啟發式、無需詢問操作者。代價是搬移工作區即更換節點身分,此為明知之取捨。

    **該路徑必須先正規化(MUST,2026-07-28 補)**:符號連結、`.`/`..` 與重複分隔符**必須**於導出身分前解析完畢。原文只寫「絕對路徑」,而**絕對不蘊涵正規**:未正規化的實作會使**同一個目錄的兩個名字成為兩個節點**——例如工作區搬家後在原處留下一條指向新址的符號連結,兩邊皆可用,卻各自取得身分並各自簽章。這恰好違反本條自己的理由:本條令路徑參與身分,是為了讓**複製**在結構上成為另一個節點;**兩個名字不是一份複本**,把它判成複本,與判不出複本是同一類錯誤的兩面。
*   **保管(MUST)**:適用 §7.5.3 全部條款(僅存 PKCS#8、自建立即擁有者專屬、既有目錄不得改權限、不得靜默取代、併發產生須恰有一個結果且各行程回報者即為被持久化者、**必須在語言層路徑邊界之內且該保護不得依賴路徑恰好含儲存目錄名之元件**)。
*   **惰性(SHOULD)**:於首次網路使用時產生即可;從未接觸網路的工作區不必先有節點身分。

#### 4.1.2 填充、驅逐與其誠實界限 **[Core Requirement,2026-07-28 新設]**

*   **只由已認證的廣告填充(MUST)**:僅在 §4.2.2 五道檢查**全數通過**之後插入。**不得**由 `%from` 或任何未簽署欄位學習節點。
    > 標準 Kademlia 從它收到的**每一則訊息**學習節點,因為它沒有更好的東西。本協定有簽署的廣告,故可以免費地更嚴格;而若照抄那個做法,`%from` 是未簽的主張(§3.2),等於把任意插入白送給任何人。
*   **重複出現即更新(MUST)**:已在表中者再次廣告只更新其記錄,**不佔用新槽位、不驅逐任何人、不改變其在既有者中的位置**。
*   **桶滿:偵守優先(MUST)**:桶已達 k 時,**新對等點不入表**,並記錄該次丟棄。**不得**於插入路徑進行網路 I/O——ping-and-replace 會使「受理一則廣告」變成可在陌生人指定時機向外撥號,那是為了一項本版不需要的精緻化而新開的放大向量。
*   **自己不入表(MUST)**。

**偵守優先買到什麼,以及沒買到什麼**:

`node_id = sha256(公鑰)`,而磨鑰匙是可平行、可預算的(成本模型見 **[SPEC_15](./SPEC_15_Anti_Patterns.md)** §7.1)。偵守優先使**事後**磨鑰匙一文不值:對一個已滿的桶,再多的算力買到零。

**但它同時是「事前磨」的攻擊面,且本規格必須照實說**:先到者填滿某桶之後,其後所有誠實節點於該桶**一律被拒**(實測:攻擊者先填滿桶 0,隨後 20 個誠實節點全數被拒)。標準 Kademlia 以**活性驅逐**(ping 最舊者,不回應才替換)緩解此事,而本版明文不做。

⟹ **偵守優先是一個競速條件,不是一項防禦**。它使攻擊者必須**早到**,而非僅僅有錢。任何把它讀成女巫防禦的敘述都是錯的:ORDER_00 §1.1 已論證框架內部供不出女巫抗性。

*   **本版不持久化(MUST NOT,2026-07-28)**:路由表與對等點目錄皆為**行程記憶體**。**不得**因本版之路由功能而於工作區產生任何耐久檔案。
    > **理由不是保守,是分界**。耐久的 OODP 狀態會一併帶來:回收(何時忘記一個對等點)、遷移(跨版本讀舊檔)、§5.1 的新檔條款,以及**一項安全性質的改變**——記憶體內的表在重啟時清空,故上述「先到者鎖死某桶」目前**止於重啟**;一旦落磁碟,那個意外的緩解就消失。**那是一次應當被裁定的變更,不是某次實作的順手產物。**

**與譜幾何的分層**：
- **L2 (Kademlia)**：解決「這台機器在哪裡」
- **L3+ (譜感知)**：解決「這個子空間由誰服務」

### 4.2 服務廣告基礎格式 **[Core Requirement,2026-07-28 落地]**

節點向網路宣告其承載的服務（L3 基礎版）：

```nlang
@ServiceAdvertisement: {{
    node_id:     @caid     ;; 公鑰之 CAID（§4.1.1）
    public_key:  @str      ;; 公鑰本體,hex【新設】
    services:    [@caid]   ;; 該節點宣稱可服務的子空間 CAID 列表
    listen_port: @int      ;; 宣告之監聽埠【新設】
    capacity:    @int      ;; 當前負載容量（相對值）
    ts:          @int      ;; Unix 秒【新設】
    ttl:         @int & ..15
    affiliation: ?@Affiliation  ;; 可選。操作者簽署之歸屬聲明（§4.2.8）
    signature:   @str      ;; 對本體之簽章,hex（§4.2.1）
}}
```

`affiliation` 為**可選**:其缺席合法,且不改變本節其餘一切。它位於簽章所涵蓋的本體之內,故節點亦簽署之。

#### 4.2.1 公鑰隨廣告同行,與簽章之所簽 **[Core Requirement]**

*   **公鑰必須內嵌(MUST)**:`node_id` 是**雜湊**,Ed25519 無從對雜湊驗簽,故廣告**必須**攜帶公鑰本體,收方重算其 CAID 與 `node_id` 比對。**不得**改以取物(`#fetch node_id`)代之:驗證廣告的目的正是為了得知對等點是誰、在哪裡,一條預設「對端已可達」的路線是自舉迴圈。

    > 此前 §7.2 義務 #1 要求「驗證 `signature` 與 `node_id` 對應的公鑰匹配」,而本節格式從未攜帶公鑰,亦無取得路徑(實測:節點對自身 `node_id` 之 `#fetch` 回 `#not_found`)。**該義務自 2026-05-14 寫下起即無法被滿足**;無法被滿足的檢查不是更嚴格的檢查,是沒有檢查。**[REAL_01](./REAL_01_Ouroboros_Engineering.md)** §7 的操作者面第一天就是這樣做的(`%authority` 攜帶公鑰本體而非其 CAID),線上面未跟上。

*   **簽章之所簽(MUST)**:令**本體**為本廣告**未加入 `signature` 欄位前**之值,則

    ```
    payload   = "oodp-advert:v1:" ++ CAID(本體)
    signature = Ed25519(節點私鑰, payload)
    ```

    收方**必須**移除且僅移除 `signature` 欄位後重算 `CAID(本體)`。域分隔前綴為**必須**,使廣告簽章不得被挪用為其他以值為對象之簽章(同 §7 操作者面 `refine:` 之分隔)。

*   **簽章承諾的是值,不是編碼**:因所簽為內容位址,對等點得重新編碼(JSON ↔ cocoon、任意欄位順序)而不破壞簽章。多數協定須靠正準序列化才有此性質,內容定址免費給出。惟**列表順序有義**(改變順序即改變 CAID),故收方**不得**在計算位址前對 `services` 排序、去重或正規化。

#### 4.2.2 收方驗證階梯 **[Core Requirement]**

順序具規範性:

| # | 檢查 | 失敗 |
| :-- | :--- | :--- |
| 1 | `%ad` 存在、為 combo、必填欄位齊備(含 `public_key` 與 `signature`) | `#rejected` `%reason: #malformed` |
| 2 | `CAID(public_key) == node_id` | `#rejected` `%reason: #identity_mismatch` |
| 3 | `%from == %ad.node_id` | `#rejected` `%reason: #identity_mismatch` |
| 4 | 簽章以 `public_key` 驗證 §4.2.1 之 payload | `#rejected` `%reason: #bad_signature` |
| 5 | `|now − ts| ≤ 60s` | `#rejected` `%reason: #stale` |
| — | 以上皆過 | `#success` |

第 2 步**必須**先於第 4 步,且其失敗**必須**具名為 `#identity_mismatch`:只問「簽章對不對得上封包裡的公鑰」的引擎會接受每一份偽造,因為偽造者兩樣都供給。第 3 步同理——一個對「誰在說話」給出兩種說法的封包,不得由收方靜默擇一。

#### 4.2.3 廣告本體是數據,不是程式 **[Core Requirement]**

引擎**不得**對廣告本體求值。本體是數據:僅字面量原子、列表與字面量所組成之 combo;其餘一切(態射、應用、路徑、算術、插值……)**必須**判為 `#malformed`,且該判定**必須**先於任何求值。判別**應以白名單為之**,使日後新增之語法形在有人明確決定它得上線之前預設被拒;遞迴**必須**有深度上限。

> **承重量測(2026-07-27)**:實作曾以求值本體為受理廣告的**第一個動作**,早於本節五道檢查。一個未帶簽章、未帶金鑰、未帶身分的封包令節點在攻擊者指定路徑寫下攻擊者指定內容,而後才回以 `#rejected #malformed`——**裁決是對的,效果已經發生了**。此為 **[SPEC_08](./SPEC_08_Meta_and_Runtime.md)** §6.1.2「授權須於施加特權效果的當下出示」在線上的對應面:此處根本沒有授權,效果照樣施加。

#### 4.2.4 未被驗證者 **[Core Requirement]**

`services` 與 `capacity` 是**主張**。收方無從知道對端持有什麼,故廣告一個宣告者並不持有的 CAID **必須**受理(`#success`);拒絕它等於宣稱自己知道一件無從知道的事。謊報的代價由後續 `#fetch` 支付——那裡取回的物件自我認證(REAL_03 §6.6),或取不回。簽章不使清單為真,它使說謊者可歸責。

此即 §6.1「Hash 保證完整性,不保證可信度」在廣告上的分工:**公鑰是自我認證的物件**(誰遞給你的不相干,雜湊得到 `node_id` 它就是那把鑰匙),**服務清單是斷言**(可認證其出處,無從驗證其內容)。

#### 4.2.5 位址:主機觀察,埠宣告 **[Core Requirement]**

廣告**不攜帶主機**。收方**必須**以承載該廣告之連線的來源主機為對等點主機,並以廣告內**經簽署**的 `listen_port` 為其埠——監聽埠無從觀察(來源埠是臨時埠,不是它),主機則無從偽造成另一台機器。

於是**一份廣告只能描述你已經在跟他講話的那一台**:一個有效簽章永遠無法指名第三方,反射與放大向量**在結構上**關閉,不靠檢查。代價是 NAT 之後的節點宣告不出可達位址——**那是事實,不得粉飾**。

#### 4.2.6 對等點目錄之地位 **[Core Requirement,2026-07-28 改寫]**

受理之廣告存於引擎本地的**對等點目錄**。其地位逐條如下:

*   **得**由 `#discover` 搜尋並轉發(§4.3)。
*   **不得**成為取物來源:持有某對等點之廣告,**不使** `~%Discovery./fetch`/`./find` 去連它。取物的來源集合只由操作者顯式建立(`./connect`)。**理由**:讓本地取物去撥號給一台只是「有人跟你提過」的主機,是一個同意權問題,不是一個路由優化;它應當被單獨裁定,而非作為發現的副作用發生。
*   **不得**進入宇宙(**[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)** §4.1.2 義務 #3)。判定法:兩個工作區演化同一份原始碼,一個從未接觸網路、一個受理廣告並服務發現,其**根 CAID 必須相等**。
*   **不得**因收到未經請求之封包而寫入物件儲存。

**與 LADD 的區分**：
- 本文 (L3 基礎)：簡單的服務列表廣告
- APP_05 (L4 優化)：譜幾何廣告 (GBB)，包含質量、譜指紋、引力場

#### 4.2.7 `ttl` 的語義,與它為何沒有單位 **[Core Requirement,2026-07-28 新設]**

`ttl` **不是時長**。它是一個**格論量**:**[APP_05](./APP_05_LADD_Global_Logic_Lattice.md)** §4.1 的第一級路由過濾是
$MASA_{overlap} = MASA_Q \sqcap MASA_{N_i}$——**每一跳都是一個 meet**,而 meet 沿格序下降
($A \sqcap B \sqsubseteq A$);APP_05 §3.1 的質量 $m(C)=\mathrm{Tr}(P_C)$ 是整數(投影的秩)。
一個**整數、隨 meet 下降、自然有上界**的量,正是 `@int & ..15` 的形狀。

> **它沒有單位,是因為格論的秩本來就沒有秒或跳這種單位。而且沒有任何節點遞減它——數學在遞減它。**

此設計的關鍵性質是:因為每個節點各自從**內容定址資料重算**它,原始的 `ttl` 是**自我認證的**——
**[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)** §6.1.1 意義下的**度數 0** 量,不需要信任任何中繼者。

**但本層算不出它**,理由見 §4.3.7。故本版對 `ttl` 的規範限於它撐得住的部分:

*   **範圍(MUST)**:`0..=15`。逾範圍者於 §4.2.2 之階梯判為 `#malformed`。
*   **`ttl: 0` 意為「不要轉發我」**(MUST)。此值在兩種讀法下皆有定義(秩預算已無可 meet;轉發深度為零),故可安全實作。
*   **不得修改(MUST NOT)**:`ttl` 在簽章之內,任何節點遞減它都會毀掉簽章。**跳數計數器不能住在簽章裡;跳數預算可以。**
*   **不得與 `%hops` 相比(MUST NOT)**:見 §4.3.4。

#### 4.2.8 歸屬聲明 **[Core Requirement,2026-07-30 新設]**

§4.1.1 給每個工作區一把自己的節點金鑰,§4.1.1 之附註又**禁止**該金鑰與操作者金鑰為同一把。二者合起來的後果是:**一位操作者的數台機器彼此是陌生人**,而操作者既無從說「這幾台是我的」,也無從收回。

**歸屬聲明**是操作者對「某節點屬於我」所簽的一句話。它住在廣告本體之內,故節點自己也簽了它。

```nlang
affiliation: {{              ;; 可選欄位,位於 @ServiceAdvertisement 之內
    operator_key: @str       ;; 操作者公鑰,hex
    signature:    @str       ;; hex
    expires:      @int       ;; Unix 秒
}}
```

*   **所簽之 payload(MUST)**:

    ```
    payload = "oodp-affiliation:v1:" ++ node_id ++ ":" ++ expires
    ```

    此為本規格第三個簽章域(另二為 §4.2.1 之 `oodp-advert:v1:` 與 §7 操作者面之 `refine:`)。**兩個被綁進 payload 的東西都是承重的**:少了 `node_id`,一份真實的聲明可被任何節點穿戴;少了 `expires`,持有者自行續期。域前綴帶 `:v1:`,因為 `refine:` 未帶版本是不重犯的缺陷。

*   **最長效期(MUST)**:`expires - now` **不得**逾 **30 日**;逾者不予採信。**沒有上限則本節的撤銷模型什麼也沒買到**——操作者大可簽一份百年聲明並稱之為短命。

*   **撤銷即到期(MUST NOT 另設撤銷清單)**:OODP 除廣告自身的 `ts`/`ttl` 外沒有任何分發通道,而憑空生一個撤銷通道所引入的失效模式比它治的還多。撤銷因此**由短效期加續簽承擔**。此非將就:公開網路上**有**撤銷通道的一方也在往這裡走——CA/Browser Forum 逐年壓低憑證上限(825 → 398 日且續降),理由正是撤銷在實務上不可靠(CRL/OCSP 常態 fail-soft)。ORDER_01 §7.4 對委任所取的「除非顯式標註否則自動屆期」是同一個直覺,低一層。

*   **只能加,不能減(MUST)**:歸屬聲明是**斷言**(SPEC_13 §6.1.1 意義下的度數 ≥1),它**不得**使任何本會被拒者被接受,亦**不得**使任何本會被受理者被拒。**故它不在 §4.2.2 的驗證階梯之內,也不新增任何 `%reason`**:一份驗不過的聲明只是「歸屬未經證實」,而不是廣告有問題——節點自己的簽章仍然有效,**它是誰從未有疑問**。與 §4.2.4「未被驗證者」同一條紀律,施於一個新欄位。

*   **三條路徑,全有或全無(MUST)**:一份聲明有三種抵達方式,而**只驗其中一部分,等於沒驗**:

    | 抵達方式 | 何時判 |
    | :-- | :--- |
    | 直接 `#advertise` | 受理當下 |
    | 隨 `#discover` 逐字轉發(§4.3.3) | 收方自行重判,**不採信中繼者的裁決**(§3.2.2) |
    | 自耐久對等目錄載入(§5.1.2) | 每次載入重判 |

    第三條**不是形式**:`expires` 是對**當下**的判斷,而一份受理時有效的聲明可以在檔案躺在磁碟上的期間死去。**裁決不得被持久化**;它是衍生物,依 §5.1.2 之原則於載入時重算。實作若把裁決存下再讀回,便是在重播一個過期的答案。

*   **鑄造需要操作者私鑰,服務不需要(MUST)**:聲明是一次鑄成、隨廣告出貨的靜態物件。**這是本設計唯一的安全支點**:若服務時需要操作者私鑰,則一台有歸屬的機器就是一台握有操作者簽署能力的機器,而複製工作區即複製該能力——正是 §4.1.1 附註存在的理由。私鑰之保管與位置依 **[REAL_01](./REAL_01_Ouroboros_Engineering.md)** §7.5;聲明本身**只含公開材料**,但仍**不得**置於 `.oo/` 之內,理由同 §7.5.1:那棵樹是為了被複製而存在的。

*   **它買不到女巫抗性(說明,但規範性地不得被讀成別的)**:攻擊者**不簽就是了**。本機制只約束**選擇加入**的一方,故它買到的是誠實操作者自願揭露所帶來的**女巫可辨識性**,不是抗性。**[REAL_01](./REAL_01_Ouroboros_Engineering.md)** §7.6 第 5 列(女巫抗性須外部物理錨點)**不因本節而被回答**,第 6 列才是本節。

*   **本版不做**:「我在乎哪些操作者」——即歸屬的**信任根**——不在本節。其歸宿已由 **[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)** §4.1.2 義務 #3 裁定:信任配置屬**斷言層**、經帶外通道供給,與 REAL_01 §7.2 之 `~/.oo/authorized_keys` 同處,**不得**鑄入宇宙。它是**第三份**名單,與治理面的建築師白名單、§6.2 之套件根信任清單並列而不合一——三者回答三個不同問題,依 REAL_01 §7.6 之紀律不得共用一個詞或一份清單。

### 4.3 `#discover`:服務索引 **[Core Requirement,2026-07-28 新設]**

`#advertise`(§4.2)使節點說得出「我在哪、我承載什麼」。`#discover` 使**別的節點問得出**「誰承載這個」。

#### 4.3.1 請求

```nlang
{{ %op: #discover, %from: @caid, %target: @caid }}
```

`%target` **必填**;缺席或不可解析 ⟹ `#conflict`。`%from` 為主張(§3.2)。

#### 4.3.2 回應方搜尋什麼

**僅搜尋對等點目錄**(§4.2.6),取其**經簽署**之 `services` 列表中與 `%target` **完全字串相符**者。

*   **不得**查詢自身物件儲存。持有該物件卻從未向你廣告過的節點,在此問不出來——那是 `#fetch` 的問題,直接問它即可。此限制**必須**照實記錄,不得以查儲存粉飾。
*   **不得**在比對前對 `services` 排序、去重或正規化(§4.2.1:列表順序在位址之內)。
*   排除**必須**先於封頂(§4.3.5):`ttl == 0` 者、以及超出收方陳舊上限(§4.3.6)者。

命中之意義**僅為**「有人聲稱服務此物」(§4.2.4)。不多於此。

#### 4.3.3 回應與**逐字轉發**

```nlang
{{ %status: #success, %source: @caid, %hops: 1,
   %peers: [ {{ %ad: @str, %observed_host: @str }} ] }}
```

*   **`%ad` 是字串,承載廣告之 n/ 原始碼,逐位元組如其抵達時**(MUST)。回應信封為 JSON,n/ combo 無法以結構嵌入其中;改攜原始文本,使「逐字」**字面可查**,而非某個重新編碼器的性質。§4.2.1 已言簽章承諾的是值而非編碼,故重新編碼**仍會**驗過——但那也意味著**沒有人分辨得出忠實的轉發與有損的轉發**。故:**不得**重新編碼,不得增刪、重排或改寫任何欄位,`ttl` 尤然。
*   **`%observed_host` 是 `%ad` 的兄弟,不是它的欄位**(MUST);`%hops` 在信封中,在每個 `%ad` 之外。**簽章不覆蓋的東西,不得坐在簽章覆蓋的東西裡面**——信任邊界必須看得見於封包的形狀,而非藏在散文裡。
*   **空結果為 `#success` 配 `%peers: []`,不得為 `#not_found`**(MUST)。「我不知道有誰」是一個答案;`#not_found` 會把它與「我沒有索引」壓成同一個值,而客戶端據此無法決定該改問別人還是別再問這台。

#### 4.3.4 一筆被轉發的記錄,其信任沿記錄內部裂開 **[Core Requirement]**

§4.2.5 以**結構**買到反射與放大的關閉:「一個有效簽章永遠無法指名第三方」。
而 **`#discover` 就是指名第三方那個操作**。它按構造重新打開 §4.2.5 關上的向量,
且此協定的任何安排都無法再以結構關上它。存活下來的,是**每一筆記錄內部的裂縫**:

| 欄位 | 地位 |
| :--- | :--- |
| `node_id`, `public_key`, `services`, `listen_port`, `ts`, `ttl` | **自我認證**——在簽章之內。誰遞給你的不相干。 |
| `%observed_host` | **斷言**——中繼者的**觀察**。永遠無法被簽:§4.2.5 的要旨正是主機出於觀察而非宣告,而**觀察無法旅行**。 |
| `%hops` | **斷言**——中繼者自己的**計數**。 |

⟹ 一筆被轉發的記錄是**一個自我認證的物件,裹在斷言的指標裡**。

**`%hops` 的規範**:直答為 `0`,經索引轉發一次為 `1`(§3.2)。它是**可觀測性,不是閘**:

*   **不得**以 `%hops` 與 `ttl` 相比作為檢查(MUST NOT)。兩者是**不同的量**——一個是轉發計數,一個是秩預算——恰好共用一個範圍;以其一閘另一,**看起來像防禦,實為範疇錯誤**。
*   且 `%hops` **不可驗證**:說謊的中繼者永遠報 `0`。任何以它為據的界只約束誠實的一方。收方的保護是**它自己的**預算(§4.3.5)與陳舊上限(§4.3.6),二者皆為本地,且**不得**被宣稱為多於此。

#### 4.3.5 放大:由結構關閉改為由預算關閉 **[Core Requirement]**

§4.2.5 以構造關上了放大器。一個單行請求換回一個長列表就是放大器,故此處**必須**改以明確的界關上:

*   `%peers` 每則回應至多 **8** 筆(排除之後施加);
*   回應本體至多 **64 KiB**;若封頂後之筆數仍超出,**必須**再減。

**且此界必須由雙方各自持守**(MUST,2026-07-28 驗收所加)。只做在回應方的界保護的是**別的節點不被你放大**,對**你的節點被別人放大**毫無作用:實測一個從不停頓的對端送出 67.1 MB,收方全數緩衝、峰值 143 MB、解析出 8156 筆——而讀取逾時**從未觸發**,因為逾時針對的是**停頓**,不是**總量**。

故收方**必須**對 `#discover` 回應施加同一個 64 KiB 上限,且逾限**必須**具名(建議 `#oversize`)而**不得**把截斷的前綴當作一個短答案處理。

> 此非新政策,是同一條界由**真正會受傷的那一側**持守。(`#fetch` 的回應不在此列:物件無規定之大小上限,對其封頂需要另行裁定。)

#### 4.3.5.1 哪八個:溢出時的選擇 **[Core Requirement,2026-07-30 新設]**

§4.3.5 定了**至多 8 筆**,卻從未說是**哪** 8 筆。這一節補上。

*   **未溢出時,全數回傳(MUST)**:存活候選不多於上限時,**全部**回傳,且每次皆同。選擇只發生在溢出處。
*   **溢出時,每次查詢**獨立**抽一次均勻不放回樣本(MUST)**。
*   **不得加權(MUST NOT)**:特別是 `capacity`——§4.2.4 已言它是**無從驗證的主張**,以它加權等於把說謊的誘因從排序搬進抽樣。
*   **不得依提問者(MUST NOT)**:§3.2 之 2026-07-28 裁定已定 `#discover` 的 `%from` 為主張且**不得有任何判定依賴它**。此處重申,因為「依提問者鍵控」正是實作抽樣時最容易滑進去的形。
*   **排除先於選擇(MUST)**:§4.3.2 之 `ttl == 0` 與陳舊排除在抽樣**之前**施行,不在之後。
*   **不得靜默退回固定序(MUST NOT)**:實作若因任何理由取不到隨機性,**不得**默默回退為某個內部迭代序的前綴——那正是本節所修的缺陷,而靜默的回退使它不可察覺。

##### 為何是抽樣而不是排序

**任何決定性、與提問者無關的排序 $f(\text{peer}, \text{target})$ 都可被磨。** 要把 8 個身分擠到 $N$ 個誠實節點之上約需 $O(N)$ 次嘗試,而 **[SPEC_15](./SPEC_15_Anti_Patterns.md)** §7.1 實測鑄鑰速率為 3,500 把/秒——$N=1000$ 時不到一秒;且依 §5.1.2 之耐久目錄,買到的席位是**永久**的。

> **決定性的規則,是攻擊者也能離線算的規則。** 防守方每次查詢算一次;攻擊者每個目標算一次,然後把贏的鑰匙永久留著。不對稱在此。

##### 這不是本規格放棄決定性

`n/` 是決定性的(CAID、觀測、權威),而此處要的是相反的東西。張力在注意到下面這件事時解消:**§4.3.5 的封頂本來就已經是一次截斷**,答案從來不是整份目錄。把**某一次任意截斷**擺出穩定得像正準答案的樣子,那才是偽造;誠實地說「這是一次抽樣」不是說謊的那一邊。

**且原本的不確定性是意外的。** 修訂前的實作以雜湊表迭代序取前 8,故答案是逐行程隨機種子的函數——**同一行程內問幾次都是同樣的 8 個**(實測),重啟才換一組。它既非決定性亦非抽樣,而**沒有人選擇過它**。意外的性質不是性質:第一個來修這個不穩定性的人會順手拆掉它,而且不知道自己拆了什麼。

##### 誠實的代價:目錄因此可被遠端列舉

**「重試得以觸及任何人」與「反覆詢問終將觸及所有人」是同一件事。** 實測:20 筆目錄於 **8 次查詢、0.03 秒**內被完整列出;修訂前則需等待對方重啟。

此代價**被接受**,理由是它不洩漏任何秘密:目錄所存者為**已簽署的公開廣告**,而節點轉發它們正是本節的用途(§4.2.4、§4.3.3)。**且退出機制早已存在且為規範性的**——`ttl: 0` 意為「不要轉發我」(§4.2.7),該廣告自此不進入任何回答。修訂前的不可列舉性是**模糊性**,不是政策,而模糊性同樣屬於「意外的性質」。

##### 與 `#find_node` 的不對稱,及其理由

`#find_node` **必須維持決定性**(§4.4:XOR 序,Kademlia 之查找收斂倚賴它)。二者的差別不是慣例:

> **`#find_node` 的答案,提問者自己算得出來因而可查證**——他握有目標與各節點 ID,可自行驗算那些節點確實最近。**`#discover` 的答案不能**:命中之意義僅為「有人聲稱服務此物」(§4.3.2),任何 8 個與任何另外 8 個一樣可信。
>
> **決定性屬於答案可被查證之處;在不可查證之處,它是偽造的。**

兩個 op 共用同一個回應編碼(§4.3.3),故實作**不得**因其形狀相同而統一其選擇規則。

##### 本節不宣稱女巫抗性

以上皆為**執行軌的成本整形**。**[ORDER_00](./ORDER_00_Interim_Constitution.md)** §1.1 與 SPEC_15 §7.1 之結論不變:內部機制供不出女巫抗性,錨在外部。本節所買到的,**僅為使重試有意義**——修訂前,一個拿到 8 個女巫節點的客戶端再問幾次都是同樣那 8 個。

#### 4.3.6 收方驗證階梯 **[Core Requirement]**

對 `%peers` 之**每一則**獨立施行;失敗**丟棄該則,不丟棄整份回應**:

| # | 檢查 | 失敗 |
| :-- | :--- | :--- |
| 1 | `%ad` 可解析、為 combo、§4.2 必填欄位齊備 | 丟棄該則 |
| 2 | `CAID(public_key) == node_id` | 丟棄該則 |
| 3 | 簽章以 `public_key` 驗證 §4.2.1 之 payload | 丟棄該則 |
| 4 | `0 <= ttl <= 15` | 丟棄該則 |
| 5 | `ts` 在收方陳舊上限之內 | 丟棄該則 |
| — | 皆過 | 可用之候選 |

*   **丟則不丟份**之理由同 **[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)** §6.1.1:來源在度數 0 上對等,跳過說謊者並繼續。一則不可驗證的記錄**不得**使同一份回應中可驗證者一併失效。
*   **此處無 `%from` 檢查**:§4.2.2 步驟 3 問的是 `#advertise` 的**說話者**;在一筆被轉發的記錄上,說話者是中繼者,而記錄不是關於他的。
*   步驟 2 **必須**先於步驟 3,理由同 §4.2.2:只問「簽章對不對得上封包裡的公鑰」的引擎會接受每一份偽造,因為偽造者兩樣都供給。
*   **廣告本體是數據不是程式**(§4.2.3)**逐字適用於每一則 `%ad`,且白名單判定必須先於任何求值**。發現回應是**你自己發起的請求所換回的遠端輸入**——正是最容易被忘記要不信任的那一類。

**陳舊上限(收方本地政策)**:`ttl` 既已用於傳播界,廣告**不宣告任何壽命**;`ts` 是記錄中唯一的時間。故收方**必須**自行施加陳舊上限,此屬 SPEC_13 §6.1.1 允許的**可用性政策**(得組態;**不得**藉此關閉驗證),且**必須**可為操作者所見。建議值 **15 分鐘**。**引擎不得自行於廣告格式增設壽命欄位**——那是規格改動。

#### 4.3.7 為何本層算不出 `ttl` 的原設計 **[說明]**

$d_L$ 與 GBB 住在 L3+ 的譜幾何側,`ttl` 住在 L2/線上的廣告格式裡,而**兩者從未相交**。
本層剩下的只能是**跳數**——即算不出距離時的退化影子:一個**斷言的指標**(度數 ≥1),
落在 §4.3.4 那道裂縫的**錯誤一側**。**欄位留下了機制的名字,失去了機制。**

此非新的妥協,而是 **[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)** §0 開宗明義所宣告之混合設計的後果——§0 列出「純粹譜路由的三項困難」,本節與 §4.1.1、§4.2.5 恰為其三:
無離散可驗證的預算(困難一)、$d_L$ 難建確定性路由表(困難二)、物理節點需穩定標識而譜指紋隨內容變動(困難三)。

**但須分辨**:§0 宣告的妥協畫在**層界**上(L2 走 Kademlia、L3+ 走譜感知,各司其職)。
一個 L3+ 的量出現在 L2 的線上格式裡,是那條線**沒有被守住**,不是妥協本身。
補救是說清楚它屬於哪一側、另一側不在時它是什麼意思(§4.2.7),不是重新設計協定。

多跳閘門屬後續路由弧——真正的機制(自內容定址資料重算距離)在那裡才拿得到。

### 4.4 `#find_node`:路由表查詢 **[Core Requirement,2026-07-28 新設]**

`#discover`(§4.3)問「誰**服務**這個 CAID」,答案來自服務索引。
`#find_node` 問「誰在這個**節點 ID** 附近」,答案來自路由表(§4.1)。
**兩個不同的問題、兩張不同的表,故兩個 op**——共用一個 op 正是本規格連續三弧在拆解的病。

#### 4.4.1 請求

```nlang
{{ %op: #find_node, %from: @caid, %target: @str }}
```

*   **`%target` 是 160-bit 節點 ID,不是 CAID(MUST)**:恰好 **40 個小寫十六進位字元**。長度不符、含大寫、為 CAID、缺席——皆 `#conflict`。
    > 把 CAID 也收下,就是讓「附近是誰」與「誰服務這個」重新變回同一個問題。由 CAID 導出目標(取其摘要前 20 位元組)是**呼叫方**的事。
*   `%from` 為主張(§3.2),**不得**有任何判定依賴它,且**不得**因此請求而被填入路由表(§4.1.2)。

#### 4.4.2 回應

與 §4.3.3 **同形**,刻意如此——收方以同一道階梯(§4.3.6)驗證每一則:

```nlang
{{ %status: #success, %source: @caid, %hops: 1,
   %peers: [ {{ %ad: @str, %observed_host: @str }} ] }}
```

*   內容為**已知對等點中距 `%target` 最近的 k 個**,依 XOR 距離**遞增**排序,同距者以 ID 自身決勝,使順序為全序且可重現。
*   **必須搜尋整張表,不得只搜目標所落之桶(MUST)**:對任意目標,最近的 k 個可能散在數個桶中。只回「目標那個桶」的實作在多數輸入上看起來是對的,而它是錯的。
*   空表 ⟹ `#success` 配 `%peers: []`。
*   **上限**:每則回應至多 **k = 20** 筆,且本體至多 **64 KiB**;**二者皆須由雙方各自持守**(§4.3.5 同律——只有誠實一方在守的預算不是預算)。

**放大比之記錄**:滿載回應實測 20 筆 / 10,347 位元組,對 87 位元組之請求為 **118.9×**——在位元組預算之內,但**約為 `#discover` 之四倍**(k=20 對上限 8)。OODP 走 TCP,來源位址無法偽造,故此為**已連線對等點的頻寬乘數,不是反射向量**;真正的界是位元組預算而非筆數。

#### 4.4.3 本版不做

疊代查找與多跳(α 平行、逐輪逼近)、活性 ping 與其驅逐、桶分裂、持久化(§4.1.2)。
本 op 一跳作答一次;**發現到的對等點仍不成為取物來源**(§4.2.6)。

#### 5.1.1 佈局格式版本 **[Core Requirement,2026-07-29 新設]**

#### 5.1.2 耐久對等目錄 **[Core Requirement,2026-07-29 新設]**

`#advertise`(§4.2)受理的記錄**得**跨行程留存。留存的是**目錄**,不是 §4.1 的桶索引。

*   **索引為衍生物,不得持久化(MUST NOT)**:桶索引是目錄上的第二層索引,其內容為 `leading_zeros(XOR(self, peer))` 之函數,而 `self` 為本節點身分(§4.1.1)。持久化它會產生**第二個真相來源**,而兩者一旦分歧,**沒有任何東西能說哪一個對**。索引**必須**於載入時由目錄重建。

*   **重建序(MUST)**:按本節點觀測到的收受時刻遞增重放;無該時刻者(見下)退回簽章中的 `ts`。§4.1 的**佔位者優先**是插入序的函數而非別的,故重放即複現之。

*   **一則記錄有兩半,且它們分屬不同層(MUST)**。此即 §4.2.5 之切分落在儲存上:

    | 半邊 | 內容 | 隨複本旅行? |
    |---|---|---|
    | **自我認證** | 逐字 `%ad` 原文(含 `node_id`/`public_key`/`services`/`listen_port`/`capacity`/`ts`/`ttl`/簽章) | **是** |
    | **斷言** | 觀測到的主機、跳數、收受時刻,及由前者導出的位址 | **否** |

    「旅行」指**被複製到另一個節點**,不指撐過一次重啟。重啟原地是同一個節點在記得自己看過什麼——那不是旅行,是記憶。故耐久檔**必須**記載它所屬的節點身分;身分相符時斷言半邊一併還原,不符時**只還原自我認證的半邊**,該節點**必須**重新觀測後方能撥號,但**得**轉發(轉發送出的是逐字簽章本體,§4.2 已言簽章承諾的是值不是編碼)。

    > **一個觀測不能旅行,一份簽章可以。** 複本得**複述**它被告知的事,不得**聲稱**它看見過。

*   **儲存記錄必須於載入時重新驗證(MUST)**:每則自檔案讀入的記錄**必須**通過與轉發記錄相同的階梯(§4.3.3:字面本體、欄位完備、`ttl` 範圍、`CAID(公鑰) == node_id`、簽章),未通過者**必須**丟棄並計數。

    > **理由**:上表「自我認證」一欄之所以能寫「是」,靠的不是記錄帶著簽章,而是**有人去檢查那個簽章**。一份沒人檢查的簽章記錄不是自我認證的事實,是一份**穿著簽章的斷言**——恰是本節費力分開的兩層又合回去。且 SPEC_08 §6.3 已裁 `.oo/` 的斷言層無從驗證而只能信任;耐久目錄**不屬於**該層,因為它**驗得了**。能驗而不驗,是把度數 0 的東西當度數 ≥1 對待。
    >
    > 代價由 SPEC_15 §7.1 計價:該節把路由表席位標價為**鑄造身分**,而一行未經檢查的檔案內容一個都不用花。

*   **寫入量必須為記錄數之線性(MUST)**:每次受理重寫全檔是 O(N²)。實測對照:150 則廣告下,全檔重寫式累計寫入 **14,380,000 位元組**,而追加式為 **131,568 位元組**(877 B/筆),**109×**。

*   **自動移除的界線(MUST)**:被**取代**的記錄(同一 `node_id` 之較新簽章廣告)**得**自動移除,無須出示任何能力。SPEC_08 §6.2「遺忘不得自動發生」治的是**使已記錄事實的內容不可達**;一則廣告從未被提交、無任何已記錄事實指向它、移除它不使任何 `#rollback` 變為不可逆。**該紅線不覆蓋整個 `.oo/`**,此處即其界線。

## 6. 信任模型與安全

### 6.1 Hash 保證完整性，不保證可信度

`hash:sha256:xxx` 只保證「你拿到的內容和發布者當初的內容一致」。
它**不保證**：發布者善意、套件無漏洞、符合使用場景。

### 6.2 幾何信任鏈 (Recursive Trust Geometry)

信任在 `n/` 中被轉化為對 **CAID 的偏好選擇**。

**1. 顯式別名優先**
若多個來源對同一個別名提供不同 CAID，引擎依據 `discovery.n` 中的來源順序進行收斂。

**2. 根信任清單 (Root of Trust)**
引擎應允許設定「根信任清單」。只有在此清單授權範圍內的黑名單更新才會被合併。

**3. 簽章驗證 (建議實作)**
```nlang
{
    %content: { ... }
    %sig:     b"..."     ;; Ed25519 簽章
    %pubkey:  b"..."     ;; 發布者公鑰
}
```

### 6.3 惡意套件處理

- **本地黑名單**：`oo block <hash>` 加入本地拒絕清單。
- **社群黑名單**：黑名單本身也是 n/ Combo，可被發現和合併。
- **隔離執行**：沙箱機制限制套件的路徑存取權限（見 SPEC_08）。

**重要**：黑名單是工程機制，不是語言規格。

*   **本節之最終去向**:見本章 §7 篇首之過渡聲明。

## 8. L3 收斂層：基礎分散式收斂

### 8.1 基礎 `&` 運算協議 **[Core Requirement]**

當節點收到遠端的合併請求時，執行基礎格論運算：

1.  **接收請求**：`{ %op: #unify, %target: CAID_A, %with: CAID_B }`
2.  **本地計算**：嘗試計算 `CAID_A & CAID_B` 的結果
3.  **回傳結果**：
    - 成功：回傳合併後的 CAID 與內容
    - 衝突：回傳 `_|_` 與 `%cause` 結構（見 REAL_04）

### 8.2 與 LADD 優化的介接

基礎 L3 收斂（本文）：
- 直接對 CAID 進行合併運算
- 無額外路由優化
- 適用於小規模或區域網路

LADD 優化收斂（APP_05）：
- 利用譜引力預測合併可能性
- 熱帶剪枝避免無意義的衝突
- 測地線路由選擇最優節點進行合併

**兩者關係**：LADD 是 L3 的**優化擴充**，基礎收斂必須先正確實作，才能導入 LADD 優化。

## 9. 版本管理與遷移

### 9.1 Hash-based 版本控制

在 n/ 中，「升級套件」= 把 `deps` 中的 hash 換成新的 hash，然後觀測收斂結果是否有 `_|_`。

```bash
# 預覽升級是否產生衝突
oo upgrade @ai.agent <new-hash> --dry-run

# 確認無衝突後執行
oo upgrade @ai.agent <new-hash>
```

### 9.2 雜湊演算法未來相容性 **[Core Requirement]**

n/ 的 hash 格式天然帶有演算法前綴：

```nlang
hash:sha256:v1:9f86d081...
hash:blake3:v2:1234abcd...
```

本地儲存必須將演算法納入路徑（見 §5.2）。
