## 1. 承重結論(候選)

### 1.1 差別不在儲存,在合併算子

> **更正(2026-08-04,用戶與他人討論後帶回):本節初稿寫「git 是補丁模型」,那是錯的。**
> **git 的物件模型就是快照**(blob/tree/commit 存完整狀態),delta 只存在 packfile 的
> 壓縮層;補丁是**心智模型與 porcelain**(`format-patch`/`rebase`/`cherry-pick`),
> 不是資料模型。
>
> 而這個錯誤在本文件內部就自相矛盾:**§1.5.4 的整個論證靠「● 是完整狀態不是差量」,
> 而那句話對 git 一樣成立。** 標題已改。

**真正的軸:合併算子是不是一個全域決定性的全函數。**

| | 儲存 | 合併 | 需要合併節點嗎 |
| :-- | :-- | :-- | :-- |
| **git** | 快照 | 三方合併,**不決定性**,要人介入 | **要**——「這兩條在此匯合」得記在圖上 |
| **DB(OCC)** | — | 衝突則**中止晚到者** | — |
| **n/** | 快照 | **meet,全域且決定性** | **不要**——衝突是一個**值**(⊥) |

⟹ **git 需要合併節點,是因為它的合併不是函數;n/ 不需要,是因為它是。**
而 n/ 與 DB 的差別在另一邊:**DB 中止晚到者,n/ 合併晚到者**——因為它有一個能把
兩個寫入合起來的代數,而 DB 沒有。

SPEC_10 §4.1 逐字寫的就是資料庫的樂觀併發控制:

> `n/` 採用基於格論與內容雜湊的**樂觀併發模型**
> `#commit` 必須具備**強原子性 (Strong Atomicity)**
> **晚到者自動收斂**:$C_{new} = HEAD_{current} \sqcap Staged_{incoming}$

ACID 四格都有落點,而 **C(一致性)** 那一格特別乾淨:資料庫的一致性是「不違反約束」,
而 n/ 的約束**就是格本身**,`_|_` 就是違反。

而 n/ 做到一件資料庫做不到的事:**衝突時不中止晚到者,而是合併晚到者**——
因為 meet 是全域且決定性的。DB 必須 abort-and-retry,是因為它沒有一個能把兩個寫入
合起來的代數。

(用戶口述:版本控制的直覺來自資料庫的 Transaction 與 ACID,不是來自 git。)

### 1.1.1 CRDT:同一個代數,相反的方向約定

(2026-08-04 用戶提出比較。CRDT 的數學核心是 **join-semilattice**。)

**CvRDT(狀態式)** 要求:狀態空間是半格,merge = **join(⊔)**,而 join 天然
**交換、結合、冪等**;更新必須**單調**(只能往上)。這三條加單調性 ⟹ **強最終一致性**
(同一組更新,無論順序與重複,收斂到同一狀態)。

**與 n/ 對照:**

| CRDT | n/ |
| :-- | :-- |
| merge = **join ⊔**,資訊**往上**增加 | merge = **meet ⊓**,資訊**往下**增加(`E ⊑ B`) |
| 單調性(只能往上) | **Invariant 2 資訊單調性** |
| 交換 / 結合 / 冪等 | SPEC_01 交換+冪等;conformance L1-28 測 `x ∨ x = x` |

⟹ **方向約定相反,代數是同一個。** n/ 的 ⊓ 就是 CRDT 的 ⊔ 在序反轉之下。
**而 Invariant 2 就是 CRDT 的收斂條件**——這不是類比,是同一條要求。

**而 n/ 已經有一個部件字面上就是 CRDT**:`%effect`。CHANGELOG(v0.2.26 一帶)記著
效果格「遷至**集合半格**」,SPEC_08 §372 明文「**效果冪等律** $E \mid E = E$」,
而 `EffectTag` 在引擎裡是位元場、合成用 join。

#### 1.1.2 三處差異,每一處都是我們已經發現過的事的另一種說法

1. **⊥ 是吸收元,而 CRDT 的格是被設計成不會有那種元素的。**
   CRDT 選格的時候刻意讓**任何一對的 merge 都是有意義的**(LWW、G-Set、MV-Register);
   n/ 保留 ⊥ 且它吸收。⟹ **這正是 §2.1.1 給 §4.1.2 的理由**:問題不是衝突,
   是「自動 + 不可逆」。

2. **`pin` 不可交換 ⟹ 它把 n/ 踢出 CRDT 的體制。**
   CRDT 要交換律;`pin` 是覆蓋不是 meet,兩次 pin 換順序結果不同。
   ⟹ **§1.7.3 的 CRDT 版說法:特權就是那個破壞收斂的操作。**
   而 §1.7.3 已量到它在序上不留邊——**兩件事是同一件事的兩面。**

3. **CRDT 不需要歷史,因為 merge 收斂,當前狀態就夠。**
   ⟹ 對照 §1.8:**非特權的部分(可重算那一列)確實不需要日誌;
   只有特權的部分需要。** 同一條分界第三次出現。

**而 §1.5.4 的日誌為什麼必須有序,也由此得解:** op-based CRDT(CmRDT)要求操作
在因果投遞下**可交換**;我們的日誌含 `#pin`,不可交換 ⟹ **它只能是一條有序的
REDO log,不能是一組可交換的操作集。**

#### 1.1.3 SPEC_13 §5.3 是一個 MV-Register

兩個來源對同一別名給出不相容的值 → **兩個都留著**(`ID_1 | ID_2`)→ 讀取時由
消費者的約束消融 → 仍有殘留就標 `#ambiguous_alias`。

**那是多值暫存器(Multi-Value Register)加讀時解析**,一個標準 CRDT。

⟹ **n/ 在別名層已經是 CRDT,在值層不是**(因為值層有 ⊥ 與 pin)。
而 **B1/B2 那個開放問題,用 CRDT 的話問就是:值層要不要也變成 CRDT?**

#### 1.1.4 n/ 拒絕付的那個代價

CRDT 用「**讓衝突在構造上不可能**」買到收斂——代價是**它必須替你決定**:
LWW 丟掉一邊,集合聯集兩邊都留但不說哪個對。

**n/ 保留 ⊥,是拒絕捏造一個答案。** ⊥ 是它對「這兩件事不能同時為真」的誠實回答。

⟹ 所以 §1.1.2 的三處差異不是 n/ 做得不夠 CRDT,**是它在同一個代數上選了另一個
關於誠實的位置**。而 SPEC_13 §5.3 說明它**在該讓步的地方讓步了**
(「宇宙不需要知道哪個 `pkg` 是正確的」)——**兩層各取所需,不是不一致。**

#### 1.1.5 規格既有的 CRDT 觸點

* **APP_07 §74**:最終一致性的修復(**CRDT merge**、read-repair、補償交易)
  「就是字面上的**相位補償**」——分區→癒合迴圈的 monodromy 是 $H^1$。
* **GUIDE_03 §98**:事件流可經 CRDT 協議跨節點複製。

⟹ **碰過上同調層,從沒碰過設計層。** 本節是第一次把它接到設計上,
而接點是「Invariant 2 = 收斂條件」與「pin = 破壞交換律者」。

#### 1.1.6 外掛特權的 CvRDT

(用戶,2026-08-04。本節是 §1.1.1–§1.1.5 的收束。)

> **n/ 是一個外掛了特權功能的 CvRDT。** 核心(meet、單調、收斂)是 CvRDT;
> 非單調的變更走外掛層;而**外掛層在不同的共享度上是不同的東西**。

**① 那不是兩套機制,是同一條規則的兩個點**

| 層 | 這個格**誰在站** | 非單調變更 | 代價 |
| :-- | :-- | :-- | :-- |
| **規格**(Combo 化之後) | **所有人** | ORDER_01 **Epoch+1**,躍遷 | 極大,綁治理——**故意的** |
| **一般 n/ 程式的值** | **沒有別人**(單寫者) | `pin` | 小,綁權限 + 審計 |

> **推翻一個格的代價,正比於有多少人正站在那個格上。**

而它**預測中間那一格**:被幾個人共享的宇宙,代價應落在中間——那正是多寫者的情形,
需要的東西介於 `pin` 與 Epoch 之間(帶權威的 epoch)。**框架沒有洞。**

**〔量〕事實校正:規格書 Combo 化目前 0%**(`meta/ROADMAP.md` 列為「引擎 SPEC_17
支援(現 0%)」;`spec/` 底下零個 `.n` 檔)。⟹ 上表第一列是**設計意圖不是現況**,
ORDER_01 的 Epoch 今天治的是治理流程,還不是一個 CRDT 的 reset。
**值那一列現在就能定,規格那一列要等 Combo 化落地才驗得了。**

**② 核心為什麼保得住:單寫者是前提,不是性質**

一個站在 CvRDT 外面的外掛,照理應該讓兩個副本在一次 pin 之後永久分岔——除非有一個
「取代信號」告訴別人「我蓋過你了」,而那個信號自己又必須單調 ⟹ 繞回去又是 epoch。

**外掛之所以不需要它:值層只有一個寫者。** 一個 `.oo/`、一個 HEAD;pin 從不必跟
任何東西收斂。而節點之間流動的是 **● —— 一個完整狀態加一個 CAID,收到它不是 merge,
是 fetch**。SPEC_10 §4.1 的「平行提交」是**行程內並發**(OCC 處理),不是分散式多寫者。

⟹ **「值層單寫者」是這個模型的前提條件,不是它的性質。** 這句話的用處在於它說出了
**什麼時候會失效**(見 ④)。

> **〔量〕更正(2026-08-05,控制面主題):那個前提比本節初稿寫的更弱——
> 它不只是「不是性質」,它根本沒有被機制強制。**
>
> 同一工作區 40 個並行 `oo evolve` → 應有 41 欄,**實得 2 欄,遺失 39,零錯誤**。
> `save_staged` 是無條件 `fs::write`,全樹 0 個鎖、0 處樂觀併發痕跡。
>
> ⟹ **準確句:單寫者是「使用假設」,不是機制。沒有任何東西阻止第二個寫者
> ——第二個寫者只是靜靜地弄丟資料。** 而 SPEC_10 §4.1 承諾的「晚到者自動收斂」
> 從未實作。詳見 `control_plane.md` §1.1。

**③ 有沒有一個統一的代數?有,而且不奇特——但它要的價錢我們不付**

用戶問:「外掛」是不是繞過了某個其實存在的數學模型,能不能跟 CRDT 合成一個單純模型。

**答案是有,而且是標準品:**

* **epoch 化的 reset 是一個字典積**——狀態 `(epoch, payload)`,epoch 主導,
  reset = bump epoch。那**仍然是 join-semilattice**,單調性沒被破壞,只是**搬高了一層**。
  ORDER_01 的 Epoch 走的就是這條。
* **覆寫本身也有標準 CRDT 形式:LWW-Register**——狀態 `(timestamp, value)`,
  merge 取時間戳大的。它**確實實現了 pin 的效果,而且是純 CRDT。**

⟹ **所以外掛不是因為代數不存在。可用的代數存在,而且很普通。**

**不用它的理由是它換走了什麼:**

> **CRDT 是定義在「值」上的代數。而 `pin` 的判準是「誰做的」,那不是值的性質。**

LWW 讓贏家是**誰比較晚**的函數;n/ 要的是**誰有權**。任何能表達 pin 的代數,都得把
「行動者」編碼進值裡,而一旦編進去,「誰說了算」就變成**代數決定的**,
不再是**有人負責的**——**那正是 §1.1.4 說 n/ 拒絕付的那筆錢**,
也是 SPEC_13 §7 權威與信任格論存在的理由。

**而 §5.1.2 已經在另一個脈絡下擋過同一形狀**:LWW 需要寫入的全序,同時間戳要打平手,
而**用身分打平手是可磨的、且逐受害者無關**——seat_order 弧的裁定直接可轉。

**④ 失效條件(本節的重點)**

用戶的話:「pin 看起來就是一個很人為/工程的設計,所以解釋『為什麼這個模型有用』
不如記得『什麼時候會失效』。」**同意,所以本節的中心是這一段。**

**兩個失效條件,一個是執行期的,一個是設計期的:**

1. **值層出現第二個寫者。** 外掛失去它的前提(② )。可能的觸發:離線優先的
   多裝置編輯同一個宇宙——與 container 那條線相容,所以不是天方夜譚。
   一旦發生,外掛就需要一個 epoch,代價結構往表格中間那格移動。
   **這一題該掛在那個產品決定底下,不是獨立的技術題。**
2. **有人提議把 `pin` 做成 CRDT。** 那在數學上**做得到**(③ ),所以它會看起來像
   一個純粹的改進,而它實際換掉的是「誰有權」→「誰比較晚」。
   **寫下來是為了讓下一個提議的人知道那不是免費的優雅化。**

> **附:上一輪那個「值層要不要也變成 CRDT?」在本框架下不是獨立問題**——
> 它就是失效條件 1 的另一種問法。答案取決於「會不會有兩個寫者」,而那是產品決定。

#### 1.1.7 CALM:判準存在,而 ⊥ 讓它退化

(2026-08-15 用戶提出。CALM = Consistency As Logical Monotonicity。)

§1.1.1–§1.1.6 把 n/ 定位成「外掛特權的 CvRDT」,而 §1.1.6 ② 徒手推出了一段論證:
外掛之所以不需要「取代信號」,是因為值層單寫者;而那個信號自己**又必須單調**,
所以繞回去又是 epoch。

**那段論證有名字,而且是個定理。**

##### ① 2013 版搬不過來,理由具體

Hellerstein 猜想、Ameloot–Neven–Van den Bussche 證明的 CALM,模型是
**relational transducer network**:

* 狀態**全部是關係**,monotone 定義在 **fact set 的 ⊆** 上;
* **確定性**;
* 側條件 **network-topology independence**:對**任何**連通圖、**任何**輸入的水平分割都要算對;
* coordination-free 的定義:**存在**一個分割與一次執行,**只靠 heartbeat transition**
  即到達靜止點——亦即**你從不需要等著聽別人說「我沒話要說了」**。

**它從頭到尾沒有提 join、沒有提格。** ⟹ §1.1.1 那座橋(CvRDT 收斂 ⟺ Invariant 2)
與 CALM 是**兩座不同的橋**,後者不會順著前者過來。n/ 的單調住在**精煉序**上,
2013 版的住在**事實集合的包含**上,不是同一個映射。

##### ② 但那個側條件,就是 §1.1.6 ② 的形式化

topology-independence 要求對**每一種輸入分割**都正確。

**單寫者 ⟹ 只有一種分割(全部在一個節點)⟹ 該條件退化為空 ⟹ 非單調操作
免費就是 coordination-free。** 多寫者一出現,條件立刻咬人。

⟹ **「值層單寫者是前提,不是性質」由直覺升格為定理的一格**;而 §1.1.6 那句
「推翻一個格的代價正比於有多少人站在那個格上」的機制也有名字了:
**人數 ＝ 你必須算對的分割類**。

**修正一句**:要不要協調是**二值**的(它只看操作單不單調),隨人數變的是協調
**多貴**——但那個二值是**相對於你必須正確的分割類**而言。§1.1.6 預測的中間格
因此不是「介於兩者之間的機制」,而是「同一種協調,跑起來便宜」;
**這是一個可證偽的差別。**

##### ③ 2026 有一版把 ① 的防火牆拆了

**Complete CALM**(arXiv 2602.09435)把定理推廣到**規格**層:
`Spec = (E, Obs, ⪯)`,其中 `Obs: ℋ → 𝒫(O)` 把歷史映到可接受結果集,`⪯` 是結果上的偏序。

* **對 ⪯ 的要求只有偏序**——論文明說無需 join、meet 或格結構,並把
  「lattice order for domain values」列為**預設而非規則**;
* **非確定性**由 `Obs(H)` 的多重結果承載;
* **單調**:對所有 `H₁ ⊑_h H₂` 與所有 `o ∈ Obs(H₁)`,存在 `o' ∈ Obs(H₂)` 使 `o ⪯ o'`;
* **coordination-free**:對每個行程與每次呼叫,**回應必須立即可產生**——只用內部與
  輸出動作,**不需要任何進一步的輸入**。

最後一條翻成 n/ 就是:**`observe` 必須只靠本地狀態答得出來**,即 CbO 加單寫者前提。

##### ④ 承重結論:判準在值層不退化,在歷史層退化,而後者已被 B1 裁過

**〔本節 2026-08-15 改寫兩次。初稿的推導是錯的,錯法記在 ④′。〕**

**值層:不退化。** 〔量 v0.22.0〕塌陷是**局部**的:

```
{ a: 1, b: (1 & 2), c: 3 }  →  { a: 1, b: _|_(#conflict), c: 3 }   Combo 沒被吃掉
(1 & 2) | 7                 →  7                                    ⊥ 支被丟掉
5 & (1 & 2)                 →  _|_                                  只有 meet 吸收
```

聯集那格比「局部」更強:**⊥ 在 join 方向是中性元,直接消失**。⟹ 要讓整個宇宙成為 ⊥,
必須在**每一個座標**上都撞出矛盾,而引擎從不自發那樣做。故在無矛盾的歷史上
**`⊥ ∉ Obs(H)`**,平凡化那一步**不在可選項裡**。**局部塌陷就是 `Obs` 的銳化本身**,
不必外加。

**歷史層:退化,而且是耐久的。** 〔量 v0.22.0〕`app: { ok: 1, bad: 1 & 2 }` 提交**成功**,
`Bottom` 落在磁碟上的根裡,`log` 讀得回來,**全程無任何提示**。而一旦
`⊥ ∈ Obs(H)`,由於 `o ⪯ ⊥` 恆成立,**判準永遠無法抱怨進入 ⊥ 的那一格**——
它分不出「該塌的塌了」與「不該塌卻塌了」。

> **〔帳〕上面那次量測不是新發現**,是 **D32／D33／D38** 在 v0.22.0 上的重新確認
> (原量測 2026-08-06／08-08)。

**而這一格已經裁過了。** **D33(B1,用戶 2026-08-06)**:SPEC_10 §4.1.2 綁了兩件事——
**收斂撞 ⊥ 必須停下並回報**(觀測的責任)/**要不要固化由操作者決定**。
⟹ **n/ 的答案是「⊥ 可以入歷史」**,那是操作者的權利,不是疏漏。

##### ④′ 本節的推導錯了兩次,錯法值得留著

**第一版**斷言「⊥ 是 ⪯ 最大元 ⟹ 判準平凡地被滿足」。
**錯在把序上的可用性當成 `Obs` 的成員資格**——Complete CALM 的單調性量化的是
`Obs(H)`,不是序裡存不存在那個元素。序上「可以精煉成 ⊥」不蘊涵動力學上「⊥ 是一個
可接受結果」。

**第二版**(用戶指出 ⊥ 就是空集合後)把它改成「⊥ = ∅ 所以被指稱逼出來」。
**同一個錯的第二種說法**——⊥ 是不是 ∅ 決定它在序裡的位置,決定不了它在不在 `Obs(H)` 裡。

**真正的判別問題從來不是「⊥ 是什麼」,是「⊥ 進不進歷史」。** 而那是一則裁定,不是一個
數學事實——這也是為什麼兩版都在數學那邊找答案而找不到。

D33 把回報列為責任。**Complete CALM 說那不只是責任,是唯一的位置。**

* **格**說不出來——⊥ 是 ⪯ 最大元,任何值都合法地精煉到它;

這使 **W3′-b(提交時報告 ⊥ 座標)** 的定位改變:它現在阻塞於 W12 且被當成周到之舉,

#### 1.1.8 Serializability 與格是同一個問題的兩個相反解法

(用戶 2026-08-27 提問:「Serializability Theory 是不是也建構在 poset 與 graph theory 上?
最後會繞回 lattice 嗎? Isolation 是不是也是同一套語言?」本節是那次回答的收錄。
**它是 §1.1.6 的第二個證人,而且給 Q-016 的兩條路徑一個理論理由。**)

**① 那套理論確實是 poset ＋ graph,而且是定義層級的字面。**

*   BHG(Bernstein–Hadzilacos–Goodman 1987)對 history 的定義逐字是一對
    $(\Sigma_H, <_H)$,其中 $<_H$ 是**偏序**,且必須排序每一對**衝突**操作
    ——**不衝突者刻意不被排序**,那正是它是偏序而非全序的理由。
*   基本定理是純圖論的:**H 為 conflict-serializable ⟺ 其 serialization graph 無環。**
*   而這兩件事是同一句話:DAG 的傳遞閉包**就是**偏序,環**就是**「成不了偏序」的障礙。
    ⟹ **serializable ＝ 衝突關係擴張得成偏序 ＝ 它有線性延拓**,
    而那是 **Szpilrajn 延拓定理**(1930)。**整個理論的心臟是這一句。**
*   對照可以說明為什麼大家只用圖論那版:*view*-serializability 的判定是
    **NP-complete**(Papadimitriou 1979),conflict 版是判 DAG 有無環。

**② 但它不繞回 lattice,而「為什麼不繞回」才是答案。**

serializable histories 對任何自然的 meet／join 都不封閉(兩個可序列化的歷史合起來
不是一個歷史);且**障礙是「環」**——那是連通性的障礙,不是序完備性的障礙。

| | 做法 | 數學 |
| :-- | :-- | :-- |
| **Serializability** | 保留不交換的操作,**限制哪些交錯合法** | 序 ＋ 圖:找線性延拓,障礙是環 |
| **Lattice / CRDT** | **限制操作必須交換**,然後**所有**交錯都合法 | 代數:ACI ⟹ 序不再重要 |

**兩邊問的是同一句話:「什麼時候順序不重要?」** 一邊答「衝突圖無環」,
一邊答「操作是 join 態射」。**CALM 是連接兩者的定理**(§1.1.7)。

**③ 格真正出現的地方有三個,都不在古典理論的核心。**

*   **isolation levels 自己是偏序,而且不是鏈**:Adya(MIT 1999)把每個 level
    形式化為「禁止哪一組現象」;**Snapshot Isolation 與 Repeatable Read 不可比。**
*   **Adya 的分類法是圖論的**:DSG 有 ww／wr／rw 三種邊,**每個 level ＝ 禁止哪一類環**;
    Fekete 等(TODS 2005)證得 SI 底下非序列化的環**必含兩條相鄰的 rw 邊**。
*   **格出現在放棄「存在一個全域排程」之後**——CRDT／Bloom／Datalog。
    **那個世界沒有 isolation 問題。**

**④ Isolation 與 Consistency 不是同一套語言,是同一個格的兩條軸。**

Consistency(linearizability)管**單一物件**跨副本、管**實時序**;
Isolation(ACID)管**一組操作跨多物件**。標準分解式:

$$\text{Strict Serializability} = \text{Serializability (isolation)} + \text{Linearizability (consistency)}$$

⟹ 常見的「一致性階層圖」其實是**這兩條軸的乘積偏序的 Hasse 圖**
(Viotti & Vukolić 2016 的 survey 把約 50 個模型排進同一張)。

**⑤ 對 n/ 的後果:§1.5.1 那個 Isolation 借用是正當的,但它借的是結論不是機器。**

ACID 的 Isolation 困難,是因為並行交易有**衝突操作**;整套理論就是為了判定
哪些交錯安全。而 n/ 的值層是**單一寫者**(§0.1 第 1 句)＋ **meet 可交換可結合**
⟹ **沒有衝突操作可排序,衝突圖沒有邊,每個歷史都平凡地可序列化。**

⟹ **n/ 白拿 Isolation 的理由,與 CALM 說它不需要協調是同一個理由:
不是解決了隔離問題,是根本沒有那個問題。**

**⑥ 而這指出 n/ 真的有隔離問題的唯一位置:`pin`。**

§0.1 第 1 句已記:`pin` 就是破壞交換律、把 n/ 踢出 CvRDT 體制的那個操作。⟹

> **meet 所在之處,n/ 在格的世界,isolation 是空的。
> `pin` 所在之處,n/ 在 serializability 的世界,isolation 是一個真問題
> ——而還沒有人問過它。**

**工程直覺早就分對了**:Q-016(W12)逐字是「**meet 路徑 CAS＋重試;pin 路徑序列化**」。
本節不改那個結論,它說明**為什麼那個分法是必然的而不是務實的**:
兩條路徑住在兩套不同的數學裡。**做 `pin` 那一弧時應回頭讀本節。**

**兩個對應,同批記下:**

*   **`#blur` ≈ SI 的 snapshot。** SI 給每個交易一個一致快照;n/ 給每次觀測一個
    `#blur`,而其 CAID **必須含視界參數**(`SPEC_08` §3.2.1)。
    **兩邊做的是同一件事:把「我看到的是什麼」烘進身分裡,讓讀可重現。**
*   **write skew 在 meet 底下不可能。** 它需要兩個交易各寫不相交之物而**聯合**
    違反不變量;在只會收窄的 meet 底下**離不開**一個約束。
    ⟹ **write skew 只在 `pin` 底下可能** ——同一條分裂線的第三個證人。

**⑦ 旁證(用戶)**:lock-free 的文獻常從 isolation level 那塊補起——這不是巧合,
**linearizability 正是從這一支長出來的**(Herlihy & Wing 1990),
而 lock-free／wait-free 是疊在它上面的進展條件。

**⑧ 兩個 Isolation,兩套理論——而分界線就是 commit point。**

(用戶 2026-08-27:「虛擬化講的 Isolation 不是同一件事,因為一個目的在消滅共享,
另一個卻是在共享資源。」)

| | **ACID Isolation** | **虛擬化 Isolation** |
| :-- | :-- | :-- |
| 共享 | **邏輯上共享,而且是刻意的** | **物理上共享,但要藏起來** |
| 承諾 | 交錯之後等價於某個序列 | 你察覺不到別人存在 |
| 「彷彿獨自一人」的**範圍** | **到 commit 為止** | **永遠** |
| 有沒有合流點 | **有——而且合流才是目的** | **沒有** |
| 理論 | Serializability(序 ＋ 圖;Szpilrajn) | **Non-interference**(Goguen & Meseguer 1982);觀測等價／bisimulation |
| 失效模式 | 異常(dirty read、write skew…)**＝環** | **side channel** ＝ 物理共享從抽象層漏出 |

⟹ **兩者用同一個字,是因為那個字命名的是「彷彿獨自一人」這個承諾,不是機制;
而承諾的作用域相反,機制就必然相反。**

**這也是為什麼虛擬化那邊沒有對應的序列化理論:沒有東西可以序列化。**
Serializability 的全部內容是「這個交錯**等價於**哪個序列」,它需要效果會合流。
虛擬化的衝突圖不是無環,是**空的,而且永遠空**——那套機器搬過去沒有主詞。

**⑨ n/ 兩種都有,而分界不在共享,在被隔離的是「值」還是「容器」。**

| | 隔離的東西 | 哪一種 | 為什麼 |
| :-- | :-- | :-- | :-- |
| **○(savepoint)** | **值** | **ACID 的** | **有 commit point**——○ 遲早轉 ●,加入共享世界 |
| **`.oo/`(節點／容器)** | **容器** | **虛擬化的** | 同一台機器上兩個節點**永遠不會合併成一個節點** |

⟹ **§1.5.1 借的是第一種,而它借對了**(⑤)。**但第二條軸沒有家**——見 O81。

**那四個安全級缺陷全部住在第二條軸上,一個都不是序列化問題**:
Q-029(拒絕只蓋住讀)、Q-030(47 位元組遠端終止節點)、Q-031(持有但開不起來)、
Q-035(名字不是憑證)——四者問的都是「**低完整性的資料能不能影響高完整性的動作或觀測**」,
那是**資訊流**問句。

**而佇列早就注意到它們不對勁,只是沒有名字**:`WORK_QUEUE` §9.1 逐字
「這條線的偵察掉出來三個安全級缺陷……**它們不是這條線的進度**」。
⟹ **它們不是那條線的進度,因為它們根本不在那條軸上。**

**對稱得值得記的一筆**:Q-035 的偵察結論是「這是**課責**缺陷不是提權缺陷」。
**課責 ＝ 事後追得出是誰做的;non-interference ＝ 事前就看不出有別人**
——**同一條軸的兩端**。那則結論當時是憑量測下的,現在它有理論位置了。

**⑩ 兩種 Isolation 的代數:它們差一條公理,而那條公理是冪等。**

(用戶 2026-08-28 帶回 `separation algebras` 這個關鍵字。本節是對 ⑧⑨ 的代數化,
**也給了 O81「不變量該怎麼寫」一個候選答案**。)

**Separation algebra**(Calcagno–O'Hearn–Yang 2007)＝ **可消去的偏交換么半群**
$(\Sigma, \bullet, u)$:$\bullet$ **偏**——$x \bullet y$ 只在兩者**不相交**時有定義
(偏性就是「分離」的編碼);交換、結合、有單位元;且**可消去**
($x \bullet y = x \bullet z \Rightarrow y = z$)。

**一條公理把它與格分開。** 可消去么半群裡若 $x \bullet x = x$,因 $x \bullet u = x$,
消去得 $x = u$ ⟹ **separation algebra 裡除單位元外沒有冪等元**
(偏的版本更直接:$x \bullet x$ 對非單位元根本無定義——一塊 heap 不能和自己相加)。
而 join-semilattice 的 $\sqcup$ **全定義且冪等**。

⟹ **兩者在冪等這一軸上互斥,非平凡地兼有不可能。**
共同母體是**偏交換么半群(PCM)**,而格與 separation algebra 是它分岔的兩支,
**分岔點只有一條公理**,且那條公理的意思恰好是 ⑧ 那張表:

| | 冪等(格／CRDT) | 可消去(分離) |
| :-- | :-- | :-- |
| 被組合的是 | **資訊** | **資源** |
| 知道兩次 | 等於知道一次 | 不等於有一個 |
| 共享 | **免費** | **禁止** |

**冪等就是 contraction。** Linear logic 丟掉的 $A \to A \otimes A$ 就是
$x \sqcup x = x$ 的邏輯面 ⟹ **n/ 的值層是 linear 的反面:極度 contractive。**
**這與 ⑤ 是同一件事的兩種說法**——「meet 可交換 ⟹ 衝突圖沒有邊 ⟹ isolation 是空的」,
代數版本是「值層 contractive ⟹ 共享免費 ⟹ 沒有東西要隔離」。

**旁證一則,對 Q-016 有用**:`pin` 破壞交換律,但它**應是冪等的**
(pin 同一個值兩次等於一次)⟹ **`pin` 是從交換律那扇門離開 CvRDT 體制的,
不是從冪等那扇門** ⟹ **pin 路徑需要的是排序,不是分離**。

**真正「兩個都有」的框架叫 BI**(Bunched Implications;O'Hearn & Pym):
它**同時有兩個合取**——$\wedge$ 加性、contractive(共享)與 $*$ 乘性、分離(不相交);
separation logic 是 BI 在 heap 上的模型。⟹ **不是「separation algebra 是格的對偶」,
而是 BI 承認「有兩種『而且』」。**

**⟹ O81 的不變量有候選形狀了:frame rule。**

$$\frac{\{P\}\ C\ \{Q\}}{\{P * R\}\ C\ \{Q * R\}}$$

「若 $C$ 只碰 $P$ 的資源,旁邊那塊 $R$ 不受干擾。」
**而 O81 底下那四個已出貨的安全缺陷,每一個都是 frame 沒守住**——Q-035 逐字是
「使用者資料取得了宿主內建能力」,即 $C$ 碰到了 $P$ 以外的東西;Q-029／030／031 同型。
⟹ **四個個案第一次有了一條共同的規範形狀可寫**,而不是四條各自的修法。

**誠實的限制(不得略去)**:separation logic 整套是為**可變狀態**造的,
而 **n/ 的值層沒有 mutation**(值不可變、只有 meet)⟹ 在那一層 frame rule 是**平凡的**。
**它真正咬得到的只有兩處:容器(`.oo/` ＝ 節點)與 `pin`**
——而那兩處正好是 n/ 裡唯二「東西是資源不是資訊」的地方。**這不是巧合,是 ⑨ 的分表。**

#### 1.1.9 值住在格裡,邏輯住在 topos 裡,而規格從沒說過這兩者是什麼關係

(用戶 2026-08-29 帶回一個外部提問:有人讀完語法,認為 n/ 是以 map 結構做 list／tree
——**這個判讀沒錯**——接著問「**Inductive Types 怎麼做?**」。
用戶的定位是本節的主張:「全域轉量子邏輯、正交模格之後,**規格書沒有仔細說局部是什麼**,
反而都放在附錄章節。」
本節是那次回答的收錄。**它是 §1.1.8 ⑩ 的續篇——同一條冪等律,第二個否定結果。**)

**① 對方會走到 proof theory,是因為「運算即證明」邀請他走。** 而 n/ 的「運算即證明」是
**偏序版**的——證明就是 `⊑`——那個版本天生**證明無關 (proof-irrelevant)**。
這才是 μ 不在的真正原因;§1.1.8 ⑩ 那條冪等律只是它的一個推論。

**② 問題不是「歸納型缺席」,是「局部是什麼」有三個答案。**

〔量 2026-08-29,`grep` 規範層 = `SPEC_*`／`REAL_*`／`SYNTAX_*`／`GLOSSARY`／`TAG_REGISTRY`〕
**`Heyting` 0 次。`Topos` 0 次。`直覺主義` 0 次。**

| 家 | 位階 | 說局部是什麼 |
| :-- | :-- | :-- |
| `SPEC_06` §1.3.1 | **規範** | **分配格**(「在同一個觀測視角下,邏輯表現如經典分配格」) |
| `APP_04` §2.2 | 附錄 | **Heyting 代數**(Sheaf Topos 的內在邏輯) |
| `COSMOLOGY/02` §1–§2 | **[思辨性]** | 「分配格 **(Heyting 代數)**」——當成同一個東西 |

這三個不是同一個東西:分配格沒有蘊含箭頭,Heyting 是分配格加相對偽補。
而**單一 MASA 的投影格其實是 Boolean 的**——比三者都強,排中律成立。
⟹ **三個互不相同的答案,住在三個位階不同的家,從沒被對齊過;
而兩個非規範的家講得比規範的家多。**

**③ 這三個答案對「有沒有 μ」給出相反的結果。**

| 局部是什麼 | 有沒有 μ | 為什麼 |
| :-- | :-- | :-- |
| Boolean 代數 | ✗ | 還是偏序 |
| Heyting 代數 | ✗ | 還是偏序 |
| **Sheaf Topos 的物件層** | **✓** | 不交餘積 ＋ NNO ⟹ W-types(Moerdijk–Palmgren 2000) |

前兩個仍是偏序 ⟹ §1.1.8 ⑩ 的結論原封不動。**只有第三個給歸納型,
而那正是規格從沒宣稱過的那個。**

**④ 因為規格把邏輯與值放進了不同的範疇。**

*   `APP_04` §2.2 逐字:「n/ 的**邏輯**實質上是建立在 $\mathcal{C}(\mathcal{A})$ 之上的
    Sheaf Topos 的**內在邏輯**。」——**邏輯**在 topos 裡。
*   `APP_04` §1.2 逐字:「每一個 Combo 或節點 $A$ 對應一個**封閉子空間** $\mathcal{S}_A$。」
    ——**值**在格裡。

**Curry–Howard–Lambek 要求這兩者是同一個範疇。在 n/ 裡它們不是。**
命題被放進了一個有物件層的地方,值被留在真值層。

**⑤ 而 `APP_04` 自己就對不齊,對不齊的正是決定 μ 的那條線。**

| 節 | Data 是什麼 |
| :-- | :-- |
| §1.2 | 節點 ↦ **子空間** $\mathcal{S}_A$ |
| §6.2 | Data ↦ **向量** $v \in \mathcal{S}_A \subseteq \mathcal{H}$ |

**物件 vs 子物件。** Trinity(`SPEC_05`)的「同構」把這條線抹平了,
但兩者只在 rank-1 時重合,而 `@int` 顯然不是 rank-1。

**⑥ 真正的理由是證明無關,而且它是被裁定的,不是缺席的。**

`SPEC_12` §1.1 帶因 Top 的守欄(2026-07-16 裁):

> **守欄 1 格律中立**:`=`／CAID／合併／去重一律**視同裸 Top**……
> **與 `_|_` 帶因不參與等值同款**。
> **守欄 2 不傳播**:任何運算消費帶因 Top 即視同裸 Top,**來歷隨之蒸發**。

**n/ 攜帶見證(`%cause`、因果鏈、`%obstruction_degree`),然後明文把見證逐出代數。**
那就是證明無關,寫成了規範守欄。而**證明無關 ＋ 偏序 ⟹ 任兩物件間至多一支箭頭
⟹ 沒有項可以歸納**。

⟹ **結構歸納不是「還沒做」,是被一條已生效的裁定擋在門外。**

n/ **有**的那個歸納原理是完備格白送的 **Knaster–Tarski／Park 規則**
($F(x) \le x \Rightarrow \mu F \le x$),那正是拿來證 `#recursive_lazy` 性質時會用的東西
——**但它嚴格弱於結構歸納**,差別就在有沒有項。
⚠ **順帶量到**:Park 規則要**完備**格,而 `SPEC_01` 說的是正交模格、非分配(§2.5.1),
**沒有任何一處宣稱任意 join／meet 存在**。投影格模型本身完備 ⟹
**這是文件缺口不是數學缺口**,但 `SPEC_12` 整章的不動點語言,其存在性保證沒有被寫下來過。

**⑦ 而 n/ 的遞迴型預設是 ν 不是 μ,方向與 ML／Coq 對調。**

`SPEC_12` §3.2 結構遞迴逐字:「定義幾何結構的**無窮可能性**……
在語義上**不具備停機問題**,因為其本體是靜止的幾何定義」,惰性觀測。
**那是最大不動點的描述。** `List: {..., next: List}` 在 n/ 裡容納無窮串列,
在 Coq 的 `Inductive list` 裡不容納。
⟹ 在 ML／Coq 裡 coinductive 是要額外費事的那一個,在 n/ 是 inductive。
而這**不是選的**:`SPEC_04` §6.3 已把它推到底——無全域截面(KS)⟹ 觀測是構成性的
⟹ 惰性是被逼出來的。μ 要的那句「就這些,沒別的」是封閉世界宣稱,
而值層在憲法層級是開放的(`_` ＝「在當前資訊下可以是任何東西」)。

**⑧ `#blur` 的直覺主義理由目前掛在錯的樓層。**

`COSMOLOGY/02` §3:「由於內在邏輯是 Heyting 代數,n/ 天然符合直覺主義邏輯」,
然後把排中律失效**放在單一視角內**示範。**但單一視角是 Boolean 的
——在那一層排中律不失效。**

正確的來源是 **Kripke／層語義**:真值必須對**所有未來的視角精煉**保持穩定。
**那就是 Invariant 2 資訊單調性。**
⟹ `#blur` 的直覺主義理由其實比寫下來的**更強、更 n/ 原生**
——它不是從外面借的量子邏輯,**它就是單調性本身**,而視角偏序就是 Kripke frame。

**限制(不得略去)**:`COSMOLOGY` 帶 [思辨性] 警告 ⟹ 不是合規缺陷;
`#blur` 的規範定義在 `SPEC_08`／`TAG_REGISTRY`,不依賴這段。
**這是地基敘事的缺陷,不是引擎的。**

**⑨ 落點:D44,以及 v0.38.0 蓋了一層不是為此蓋的地板。**

D44(2026-08-27 裁)要求「⊥ 的觀測結果也必須產生一個 ○,因為 `%cause` 需要指涉對象」。
本節給它一個結構性理由:**⊥ 需要落點,正是因為見證在格內被立法為不可見**
(⑥ 的守欄 1)。格裡只有一個 ⊥;n/ 的 ⊥ 卻帶著「為什麼」。
那個「為什麼」在格內無處可放,所以它必須落在格**外**——而 ○ 鏈就是格外。

⟹ **v0.38.0 出貨的 savepoint 層,是證明相關的東西第一次有地方站。當時不是為這個做的。**
同一句話也是 §1.1.7 ④′「⊥ 的爭點不是『⊥ 是什麼』而是『⊥ 進不進歷史』」的另一種說法:
**證明無關的 ⊥ 沒有歷史;證明相關的 ⊥ 必須有。**

**⑩ 這不開新線,是既有那條線上的一格。** `disc 030` 已裁「n/ 的值不是任何 CTT 的型別」
(非 Kan ＋ 有向 ＋ 脈絡),而**證明相關正是 HoTT 那條軸**。
本節把「有沒有歸納型」「`#blur` 憑什麼直覺主義」「`%cause` 為什麼進不了等值」
**證明成同一個問題的三張臉** ⟹ **O82**。

### 1.2 local 與 published 是兩個不同的態射,不是同一個東西的兩份拷貝

用戶對 git 的診斷:**難用是因為它把 local repo 與 remote repo 都當成一個完整自洽的
repo 來處理**,而兩邊的語義要求根本不同——local 只想記錄歷史與隨時退回,
published 則要求完整、可執行、經過多層檢查。

n/ 已經把這兩件事拆成兩個態射了,只是沒人把它寫成「這就是那條界線」:

| | `commit` | `refine` |
| :-- | :-- | :-- |
| CLI | 無 `--sign` 〔量〕 | **有 `--sign`** 〔量〕 |
| 語義 | 記錄自己的歷史 | 對別人宣稱 $E \sqsubseteq B$ |
| 背書 | 無 | SPEC_13 §5.2.1:「其正確性由 **#refine Commit 的簽署權威**背書」 |

而 SPEC_13 §5.2.3 把同一條界線畫在同一個地方:自動重定向**允許**發生在
Live Observation 與 Staged,對**已固化的歷史 Commit 嚴禁**。

#### 1.2.1 這條界線有四個獨立的證人

(2026-08-02 收攏。§1.5 的設計討論做完之後才看出來這四條是同一條。)

| 面向 | local | published |
| :-- | :-- | :-- |
| **簽章** | `commit` 不簽 | `refine` 簽,權威背書 |
| **定址** | ○ 可含 `#incomplete`(SPEC_08 §3.2.1:不具備內容定址的合法性) | ● **必須**可定址 |
| **身分** | 本地鑄造的隨機 / patch id —— **斷言層** | CAID —— **自我認證層** |
| **撤銷** | drop 一個 ○ **不留痕** | 放棄一個 ● **必須**留痕(`abandoned`) |

**四條線畫在同一個位置,而且沒有一條是為了配合另一條設計的**——簽章那條在 v0.2.x
就在了,定址那條出自 SPEC_08 §3.2.1,撤銷那條出自 `CommitMeta.abandoned`,
身分那條是 2026-08-02 的討論推出來的。**這種收斂是「這面牆是承重牆」的證據。**

**缺口:** 「published 必須完整、可執行、經過多層檢查」這件事,今天 `refine`
只驗兩樣——$E \sqsubseteq B$ 與簽章。**「可執行 / 通過檢查」那一格是空的。**

#### 1.2.2 這條界線與 §1.1.8 的兩個 Isolation 是同一條

(用戶 2026-08-29:「合併的衝突可能會要分是 local 還是 publish……會不會是同一個問題,
只是還沒被展開?」**是同一個,而且引擎兩半都已經做了,只是沒有人寫下那句話。**)

**① 先把兩張表疊起來。**

| | **local** | **published** |
| :-- | :-- | :-- |
| 態射(§1.2) | `commit` | `refine` |
| **動作**〔量〕 | **meet** | **檢查 `⊑`** |
| 對方是誰 | 都是我 | **可能是敵手** |
| 理論(§1.1.8 ⑧) | serializability | non-interference |
| 衝突問的是 | 「值是什麼」 | 「**該不該讓你的位元組影響我**」 |
| 會不會合流 | 會(有 commit point) | **不會**——檢查通過也只是接受一個斷言 |
| **⊥** | **正當答案** | **⊥ 就是攻擊本身** |
| 失效模式 | 排程 | side channel／DoS |

**② 引擎已經實作了兩半。**〔讀 2026-08-29,`universe.rs:1254`〕`refine` 的第一步逐字是
`// Step 1: verify geometric monotonicity (new & old = new)`——那是 **`A ⊑ B ⟺ A ⊓ B = A`
的檢查**(SPEC_06 §1.5 的特異性關係),**驗證並拒絕,不把 ⊥ 放進你的狀態**。
而 `commit` 走 meet,**會**產生 ⊥。

⟹ **兩個態射早就各自帶著兩種衝突語義,而規格從沒說過那正是它們的分別。**
同一段原始碼還記著一則舊缺陷:「Tampering bought a skip of the geometric check」
——**那個檢查是安全邊界,而它曾經可以被繞過**。這是 §2.5 那一類
(引擎做對了一件規格沒描述的事),不是 §2.4。

**③ 為什麼 published 側的 ⊥ 不是答案而是攻擊。**

若一個已發布的衝突產出 ⊥,那麼**任何人都能遞給你一個值,把你的狀態變成 ⊥**。
那不是「誠實地回報不相容」,那是**由構造而來的阻斷服務**——
而它與 **Q-029／Q-030／Q-031／Q-035** 是同一軸(O81 的四個安全級缺陷,
Q-030 逐字是「47 位元組遠端終止節點」)。**⊥ 中毒就是那條軸在值層的長相。**

⟹ **local 用 meet,published 用檢查。meet 會中毒,檢查不會。**
這一句是本節的全部內容,其餘是證據。

**④ 它解釋了 §0.1 那個「最大的一處對不上」。**

`SPEC_10` §4.1.2「衝突必須立即終止」出自規格的**第一個提交**、從未修訂、
**而引擎今天已經不遵守它**。現在有理由了:**它用一條規則回答一個需要兩條規則的問題**
——它寫於 local／published 這條界線存在之前。不是引擎背叛了規格,
是那條規則從來沒有辦法同時對兩側成立。

**⑤ 它也給 §1.1.7 ④′ 那個 CALM 退化一個名字。**

CALM 的判準分不出「該塌的塌了」與「不該塌卻塌了」。**在 local 那是記帳問題;
在 published,「不該塌卻塌了」有一個名字——有人讓你的值變成 ⊥。**
同一個退化,一側良性,一側是漏洞。

**⑥ 它是 O81 的第二個結構候選,而且與第一個(frame rule)同構。**

frame rule 說 $C$ 不得碰 $P$ 以外的資源。**一個已發布的精煉不得碰它所證明之外的東西**
——⊥ 中毒逐字就是 frame 沒守住。⟹ §1.1.8 ⑩ 的 frame rule 與本節是同一句話的兩種說法,
一個從代數來,一個從態射來。

**⑦ 對 Q-014 候選丙的後果(這是本節今天的用處)。**

丙把衝突的答案從「先到者贏」換成 ⊥。〔量 2026-08-29〕今天 `a: 1` 然後 `a: "x"`:
第二筆 **rc=1**、被拒、**不進工作集**,staged 留 `{ a: 1 }`;反序留 `{ a: "x" }`。

**那個語義改變整個落在 local 側**——丙動的是 `evolve`,不動 `refine`。而 local 側
**D33 已裁 ⊥ 可以入歷史,由操作者決定**。⟹ **丙看似最可怕的那一格,
在已裁的帳上其實是允許的。**

**丙在 local 側真正留下的問題不是 ⊥,是 `rc` 變 0**——那是 D33 同一則裁定的另一半
(**收斂撞 ⊥ 必須停下並回報**),而它**今天就已經是未兌現的欠帳**
(§6 Inbox「提交撞 ⊥ 時 `commit` 逐字回報 Commit successful 且 exit=0」)。
⟹ **丙不製造新問題,它讓一則已經欠著的裁定變得非付不可。**

### 1.5 最小單位不是 commit —— savepoint 與 commit

(用戶設計,2026-08-02;符號 ○ = savepoint,● = commit。)

**模型:**

* 每一次**改變 combo** 的演化產生一個 ○;不改變 combo 的演化不產生
  (例:對已是 `1` 的 `a` 再演化 `a: 1`)。
* **pin(覆蓋模式)也歸類在演化底下**,一樣產生 ○。
* ○ 之間的關係來自**演化順序**;`checkout` / `rollback` 到較早的 ○ 之後再演化,
  就造出旁支。
* `commit` 把當前 HEAD 的 ○ 轉成 ●,**中間的 ○ 歷史併入該 ●**。
* 第一個節點一定是 ●。

```
●#0 → ○#1
    ↘ ○#2 → ○#3        commit ⟹  ●#0 → ●#3
                                   (#3 記得中間經歷 pin a:3 與 evolve c)
```

#### 1.5.1 命名:`snapshot` 不能用

SPEC_10 §1.2 有一條白紙黑字的裁決:

> **裁決:快照 ＝ Commit／CAID,不新增 source-level 語法。**

**推薦 `savepoint`**,理由不只是「還沒被佔用」:

1. 資料庫的 savepoint 就是**開著的交易裡的一個標記**,可回退——正是 ○;
2. **它在交易提交時消失**——正是「中間的 ○ 歷史併入 commit point」;
3. 最有價值的一點:**§1.2 那個 local/published 的界線,用這個詞就變成 ACID 的
   I(隔離性)**——未提交的狀態對別人不可見。**不需要為 local/remote 發明規則,
   那是隔離性白送的。**
   **⟵ 2026-08-27 補(§1.1.8):這個借用是正當的,但借的是結論不是機器,
   而 n/ 不需要那台機器——值層單一寫者 ＋ meet 可交換 ⟹ 衝突圖沒有邊,
   每個歷史都平凡地可序列化。「白送」的理由與 CALM 說它不需要協調是同一個:
   不是解決了隔離問題,是沒有那個問題。而這也指出唯一有隔離問題的位置是 `pin`。**

誠實的差異:DB 的 savepoint 在回退時**丟棄**後面的工作;此處是**保留到被顯式 drop
為止**(而 drop 不留痕,見 §1.5.5)。

#### 1.5.2 ● 不是另一種物件,是 ○ 上的一個謂詞

用戶原本擔心「savepoint 可能無法產生 CAID」。實際的判準用戶自己已經給了
(§1.5.6 的第二個差異):**只有可內容定址的 combo 才能 commit。**

而 SPEC_08 §3.2.1 說明了為什麼有些不合格:`#incomplete`「**不具備內容定址的
合法性**」,因為其值隨燃料變動。一個**全部固化完**的 ○ 是可以被定址的。

⟹ **● = 一個「可定址」且「被宣告為可分享」的 ○。** 不是兩種型別。

**實作面撞在同一點上(用戶,2026-08-03):** ○ 與 ● **共用一個結構**,只是各自
有些欄位不去使用。這是從「實作成本」推出來的,而上一段是從「語義」推出來的——
**兩條路到同一個結論。**

但要加一條紀律,而且**有量過的前科**:seat_order 弧的掛帳是「排序欄位『缺席』
與『不可解析』共用退回值 `0`」——**一個槽兩個意思,讀的人分不出來**。
「某些欄位不去使用」正是同一個形狀。

**防線:結構共用,雜湊不共用。**

* ○ **不需要 `content_hash`**(§1.5.3:身分住斷言層,是本地鑄的 id);
* 雜湊只在翻牌成 ● 的那一刻算,輸入必須是**正面列舉的白名單**,
  不是「結構裡的所有欄位」;
* 好消息:`Commit::content_hash` **今天就是手寫白名單**,所以這是既有形狀。

#### 1.5.3 兩個身分層

○ 需要一個穩定把手,但不需要 CAID。用戶提議「類似 jj 的 patch id」。

**這是對的答案,而且理由比「退而求其次」強**:**savepoint 永遠不旅行**,
所以本地鑄一個隨機 ID 的代價是零——**自我認證只在有第二方要說服時才有價值,
而這裡沒有第二方。**

⟹ 用 disc 025 的話:**○ 的身分住斷言層,● 的身分住自我認證層。** 各安其位。

#### 1.5.4 中間歷史是 REDO,不是 UNDO

用戶原話「類似 UNDO Log」,但給的草圖 `[(#pin, a, 3), (#evolve, c)]` 記的是
**做了什麼**(操作 / after-image),不是**怎麼倒回去**(before-image)——那是 REDO。

而 **REDO 就夠了**,理由是設計自己送的:**● 是完整狀態,不是差量。**
要重建 ○#2,從 ●#0 **往前重放**即可;永遠不需要 before-image,因為檢查點一直在。
資料庫需要 UNDO 是因為它在提交前就地修改資料頁——**n/ 沒有這個問題。**

⟹ 準確說法:**「從檢查點往前重放的 REDO log」**。
(用戶確認:一直在想反向的箭頭,而 UNDO 所需的 logical logging 極難寫。)

**但有一個必須補的欄位。** logical logging 的前提是**重放必須決定性**。
n/ 在這件事上異常有利(meet 全域決定性),**但 `(#evolve, c)` 不決定性**:
若固化 `c` 撞到燃料上限,結果取決於 `%fuel`,換預算重放會得到不同的值。

⟹ **每一筆觀測型的日誌條目必須攜帶視界參數。** 這與 SPEC_08 §3.2.1 要求
`#blur` 的 CAID 必須含視界參數**是同一條規則的第二個實例**:
一個沒說清楚「在什麼條件下停的」觀測,不是一個穩定的東西。

#### 1.5.5 兩種 diff,該共存

| | 是什麼 | 現況 |
| :-- | :-- | :-- |
| SPEC_10 §5 `#diff` | 「所有狀態皆由內容雜湊決定,可精確**計算**兩 Commit 的幾何差異」 | **從狀態重算** = physical logging(git 的模型) |
| `~%Diff./diff` `/patch` `/is_compatible` | 值層 combo 對 combo | **引擎 genesis 已種,規格零字** |
| 用戶要的 | `[(#pin, a, 3), (#evolve, c)]` | **被記錄的操作** = logical logging |

重算回答「差在哪」,日誌回答「做了什麼」。

**而引擎早就承認過重算不夠了。** `CommitMeta.privileged_effect: Option<bool>`
存在,正是因為「這次提交動用了特權」**無法從狀態還原**——從 `_`(top)pin 到 `3`
是單調的,與一次正常演化在狀態上**完全不可分**。

⟹ **引擎已經為了一個事實破例做了 logical logging,只是只做了一格布林。
本設計是把那一格推廣。**

**存放位置:`~%Engine` 底下**(見 §1.6;中途曾提過 `~%Version`,已收掉)。
要求是不管怎麼 `checkout` 都能讀取。

* **〔量〕這個要求是滿足的:`~%` 軸不在被提交的 root 裡。** 對一個提交過的宇宙
  `oo inspect <commit>`,root 內 `~%` 出現次數為 **0** ⟹ 系統軸是每次啟動鑄造的,
  不隨版本走,所以放在那裡的日誌不會被 checkout 換掉。
* **鍵應該是 CAID 對,不要用本地序號。** `3_0` 這種序號是本地的、提交後 ○ 的
  編號本來就沒了、重建不保證還原成同號。而**§1.2 的推論要求 diff 隨 ● 一起旅行**
  ——用本地序號當鍵的 diff 傳不出去。
* **住哪一層有答案**:它在被版本化的宇宙**之外**(DB:WAL 不是一張表)。
  與 Invariant 4(萬物皆 Combo)不衝突——**它是 Combo,只是不從根可達**,
  即 disc 025 的**斷言層**,與完整性日誌、對等目錄同層。
  而**讓它對程式唯讀的機制已經在跑**:`BottomCause::SystemReserved` 已在拒絕
  使用者對 `~%` 軸的左值寫入,不需要新機制。

#### 1.5.6 drop 的不對稱,以及它給 `abandoned` 的理由

| | 留不留痕 | 為什麼 |
| :-- | :-- | :-- |
| drop 一個 **○** | **不留** | 它從沒旅行過,**不可能有人正握著它** |
| 放棄一個 **●** | **必須留** | 它**可能已經被發表**,別人手上可能有那個 CAID |

⟹ **你不能悄悄地取消發表。** 這就是 `CommitMeta.abandoned` 在解的事,
而它從來不是為 ○ 設計的。

也因此 `commit` 那一刻需要跟使用者確認:若 HEAD 的 ○ 不是上一個 ● 的唯一子樹,
旁支的 ○ 會**無痕消失**——所以要在還能問的時候問。

#### 1.5.7 承重量測:固化狀態會改變 CAID

同一支程式,唯一差別是 `c` 有沒有被固化(同檔 vs 拆檔),提交後比較 root CAID:

```
c 已固化 (c: 3)           digest 42c1aa7dfb1599…
c 未固化 (c: Thunk(a+b))  digest 1aeb5c4d703984…
sketch                    兩者逐位元組相同
控制組:兩個獨立工作區、同程式、同固化 → digest 逐位元組相同 42c1aa7d…
```

**「同 sketch 異 digest」在這裡的意思:sketch 看見結構,digest 看見固化到哪裡。**

**後果:** 若 ● 繼承的是當地恰好演化到的固化狀態,兩個人跑同一支程式、演化順序不同,
**會產出 CAID 不同的 ●** ⟹ 共享的不是「這支程式」,而是「這支程式 + 某人的觀測深度」。

**而 §1.5.2 的判準剛好把它關掉**:只要 ● 要求全部固化(或以 `#blur` 顯式凍結,
而 `#blur` 的 CAID 依 SPEC_08 §3.2.1 必須含視界參數),固化狀態就成為正準的,
**● 重新是 (程式, 宣告的視界) 的函數,不再是本地歷史的函數。**

⟹ **「最小單位是 ○」與「只有可定址者能 commit」不是並列的兩點——
第二個是第一個能成立的前提。**

> **⚠ 補充(2026-08-27,用戶)——本節的量測還說了第二件事,而且結論可能相反。**
> 「同 sketch 異 digest」不只是「● 該不該要求全固化」,它是**注入與觀測
> 各自留下的痕跡不同**(§1.10.1)。而用戶的切法把本節的結論**倒過來**:
> 固化深度**不進 ●**,● 記注入的 sketch,thunk 就讓它是 thunk。
> 兩者都堵得住這個洞(病灶是**部分**固化,全固化與全不固化都正準),
> 但那是**推翻一則已寫下的裁定**,不是補一格空白。
> **⟵ 2026-08-27 更新:D43 已裁「● 的前提是能不能算出 CAID」,
> 而未求值的 thunk 算得出 digest(本節自己量過 `1aeb5c4d…`),
> 真正不可定址的是 `#incomplete` ⟹ 本節舊結論的「論據」已不成立,
> 但替代它的是什麼仍未裁 ＝ O79。**

### 1.6 命名空間:全部歸 `~%Engine`

SPEC_10 講的是同一件事(演化、提交與因果邊界),但它的態射散在兩個家族:
`/observe` `/evolve` `/collapse` `/refine` 在 `~%Engine`,而 **`/commit` 在 `~%Repl`**。

**〔量〕而這場爭論的對象大部分還不存在:**

| SPEC_10 §2 | 引擎 |
| :-- | :-- |
| `~%Engine./observe` | **✓ 有** |
| `~%Engine./evolve` | **✗** |

`/set_strategy` `/check_oml` `/equivalence_map` `/resolve`;其中後五個
**以 `~%Engine./` 拼法在規格中查無**。

⟹ **版本控制那一組今天只活在 CLI**(`oo evolve`/`oo commit`/`oo refine`),
語言層一個都沒有 ⟹ **整併零遷移成本。**

**裁定(用戶,2026-08-03):全部歸 `~%Engine`,理由就是「引擎能做的所有事」**
——不需要用「演化與提交」去論證它;最直觀的答案就是對的答案。
`~%Diff` 的三個概念保留,重新設計後併入(中途曾考慮獨立的 `~%Version`,已收掉:
多開一個家族又是一次「同一件事兩個家」)。

**預設是 observe;`/collapse` 拔除。** 併入後 `~%Engine` 應含
`/observe` `/evolve` `/commit` `/refine`,以及今天沒有的
`/checkout` `/rollback` `/diff` `/log` `/status`。

**兩個要接受的後果:**

1. `~%Repl` 這個名字**把介面寫進了語義**。REPL 只是三個面之一(對人),
   而 commit 不是只有 REPL 能做——CLI 在做,控制面將來也該做。
   用介面命名一個語義操作,與 REAL_01 §1 把 CLI 拼法寫進規範性條文是同一個錯。
2. 併入後 `~%Engine` 會裝著 `/project_down`(Bohrification 投影)、`/check_oml`
   (邏輯驗證)、`/equivalence_map`(狀態)這些**不是版本控制**的東西 ⟹
   **SPEC_10 不再是 `~%Engine` 的規格,只是其中一段。**

(`~%Ouroboros` 已排除:名字長,且「Ouroboros」在規格裡至少指四個東西——
引擎、協定 OODP、工程 REAL_01、哲學意象。)

### 1.7 兩張圖:本地時間序,全球邏輯格

用戶 2026-08-03 提出:`#refine` 在新圖景下不只是 blur→exact,而是
**從 ⊑ 關係造出關聯**。設 LADD 上有兩個彼此無共同歷史的 commit:

```
def = { a: 1 | 2 }        ghi = { a: 1 }
```

`diff CAID(def) CAID(ghi)` 判得出 **`CAID(ghi) ⊑ CAID(def)`**,
於是 `refine CAID(ghi) CAID(def)` 可以把它們接起來。

**這件事的份量:它把「歷史」從宣告變成計算。** git 的父邊是造 commit 的人
**斷言**的;`ghi ⊑ def` 是**任何人都算得出來的事實**,不需要相信誰。

#### 1.7.1 那是兩張圖,不是一張

| | 本地 | 全球 |
| :-- | :-- | :-- |
| 關係 | **時間序** ○→● | **特化序 ⊑** |
| 由誰決定 | 你造的 | 內容決定的 |
| 說的是 | **發生了什麼** | **什麼是什麼的實例** |

`ghi` 並不是**從** `def` 來的,它只是**在** `def` 底下。把兩者畫成一條線的代價:
`diff def ghi` 在歷史意義下該答「無共同祖先」,在序意義下該答「ghi ⊑ def」,
**兩個都真、都有用**,合成一張就少掉第一個。

而 ⊑ 會連上一堆沒打算連的:`{a: 1, b: 2}` ⊑ `{a: 1}`,「多寫一個欄位」自動成為
誰的精煉。**——而這反而是好消息:「這個具體的東西滿足那個約束嗎」就是 ⊑,
而 LADD 本來就是為套件發佈生的。**

⟹ **承重結論候選:版本圖與依賴解析圖是同一張圖。**

正確的說法:**本地圖記錄「發生了什麼」,全球圖記錄「什麼滿足什麼」,
`refine` 是把一條本地事實發表成全球圖上的一條邊。**

#### 1.7.2 直接後果:`Savepoint` 有 `.parent`,`Commit` 沒有

(用戶 2026-08-03。)時間序住 ○,全球序是內容的函數、不需要被儲存。

⟹ **與今日引擎正面衝突**:`Commit.parent: Option<ContentHash>` 存在,
且 `oo inspect` 會印出 `parent: (none)`。那個欄位記的是本地時間序,
而本地時間序在新模型裡屬於 ○。

#### 1.7.3 特權是「格表達不出來的那一步」

用戶觀察:⊑ 很可能讓本地有時間序的兩個 commit **在全球格上毫無關聯**,
**尤其是特權模式操作**。

**〔量〕證實,而且分界剛好落在特權上:**

```
old: { a: 1 }
pin:  { a: 3 }          is_compatible(old, pin)  → #false   old & pin  = _|_ #conflict
norm: { a: 1, b: 2 }    is_compatible(old, norm) → #true    old & norm = 正常收斂
```

* **普通演化**是 meet ⟹ 新狀態必 ⊑ 舊狀態(Invariant 2)⟹ **全球邊存在,
  且與本地邊一致**。
* **pin** 產生的新狀態與舊狀態**不可比** ⟹ **全球圖上沒有那條邊。**

⟹ **本地圖與全球圖在非特權歷史上完全一致,恰好在特權處分岔。**
換句話說:**全球邏輯格 = 本地歷史扣掉特權邊。**

而由此可以說出特權在 n/ 裡到底是什麼:

> **特權 = 做一個格表達不出來的動作。**

這回頭解釋了兩件既有的事:

1. **為什麼特權必須留審計痕**——因為**值不會記得**。格裡沒有那條邊,
   `CommitMeta.privileged_effect` 是唯一記得的地方。
2. **§1.5.4 的 REDO log 不是便利設施,是那條邊唯一的載體。**
   非特權的歷史可以從內容重算;特權的不行。

#### 1.7.4 refine 的簽章在新圖景下大多不需要

SPEC_13 §5.2.1 自己說了簽章是為什麼存在的——**不透明目標**:

> 當 `CAID_source` 指向 `CAID_target` 且兩者使用不同雜湊演算法時……
> `CAID_target` 被視為**不透明字串**,其正確性由 #refine Commit 的簽署權威背書。

⟹ **兩邊內容都在手上時,自己算 ⊑ 即可,不需要相信任何人。**
簽章只在**算不出來**時才需要(跨演算法,或只有 CAID 沒有內容)。

**這是強化不是削弱**:refine 在兩邊在場時是**自我認證的**,一邊不透明時才落到
斷言層。⟹ **§1.2.1 表格第一列須加註:`refine` 有兩個模式。**

#### 1.7.5 兩個殘留問題

* **⊑ 是偏序,父不唯一。** 若 `ghi ⊑ def` 且 `ghi ⊑ jkl`,兩者都合法 ⟹
  推導出來的**不是樹,是格**。最徹底的形式正是 §1.7.2:根本不存父邊。
* **原本的 blur→exact 是特例。** `exact ⊑ blur` 就是 ⊑,所以最初的設計不是
  另一件事,是**「你剛好知道為什麼」的那個特例**。而它也**不是 merge**——
  `ghi` 本來就是 `def ⊓ 更多約束`,refine 只是**把一個已經發生的 meet 認出來**
  (與 §1.3「merge 被值語言吸收」同一句話)。
* **027 在全球圖裡永遠無解,而這次是確定的。** 全球圖依構造單調,只能往下 ⟹
  **撤回在這張圖裡沒有位置,那不是缺陷,是這張圖的定義。** 撤回只能住審計行。

#### 1.7.6 全球圖存不存:外部裁定與三處修正

(2026-08-03。用戶向兩個持早期規格的模型分別提問,答覆大致相同。)

**採納的主結論:**

> **真值層嚴禁儲存邊,檢索層(LADD)必須物化。**
> 全球圖是資料庫意義的**物化檢視**——就像 B-Tree / R-Tree,只是為了加速幾何查詢
> 而建的索引。

**採納的命名:邊有兩型** ——`DERIVED`(算出來的)/ `DECLARED`(refine 簽章背書的)。
這正好把 §1.7.4 的兩個模式命名了,比本文原本的寫法乾淨。

**〔量〕外部答覆的一項事實查證屬實:** `~%Discovery` 的原語是
`/advertise` `/alias` `/fetch` `/find` `/identify`,**沒有一個是序查詢**;
⊑ 在 10 份規格檔裡出現,但都是語義關係(SPEC_01 格、SPEC_06 unify、
SPEC_13 §5.2.2 refine),**從未作為路由/檢索原語**。

**——但有三處要修。**

**① 承重:「檢索層丟失無損」對 pin 是假的。**
外部答覆的表寫著檢索層「遺失的後果:無損(重新掃描所有 CAID 即可 100% 重建)」。
**這對 ⊑ 邊成立,對操作日誌不成立**——理由就是 §1.7.3 量到的:pin 在序上不留
任何邊,所以掃遍全世界的 CAID 也**推不出「這裡發生過一次 pin」**。
⟹ **日誌不是索引**,不能當可重建的快取來設計(詳見 §1.8)。

**② `parent` 不是 CAID 污染的成因,而想要的東西已經存在。**
外部答覆說「同內容不同 parent ⟹ 不同 CAID」。真,但**不完整**:
`content_hash` 也吃 `meta`,而 `CommitMeta` 的 Debug 含 **author / timestamp /
message** ⟹ **拿掉 `parent` 之後,兩人提交同一份內容仍得到不同的 commit CAID。**

而純內容的身分**本來就在結構裡**:`Commit.root`。
**用戶自己的例子說的其實就是 root**——「def 的內容 `{a: 1 | 2}`」是 root 的內容,
不是 commit 物件的內容。

⟹ **要先問的是:全球圖索引的是 commit 的 CAID,還是 `root`?**
若是 `root`(而它必須是,那是唯一純內容的身分),則 ⊑ 在 root 之間計算、
毫無污染,而 **`Commit.parent` 對全球圖完全不相干**。

**③ 兩個小的。**
*複雜度*:依賴解析是 $O(N)$(一個 `C_spec` 對所有人 meet),$O(N^2)$ 是**建整張
索引**的成本。而物化的真正理由不是速度,**是那個查詢在分散式下根本做不到**
——你手上沒有全世界的 CAID。
*相等測試不健全*:草圖寫 `meet_res == caid_sub`,實際要比的是
`CAID(meet_res) == caid_sub`,而 **CAID 依賴固化狀態**(§1.5.7)⟹
**兩側必須都是正準固化的**,否則靜默漏判。這正是 §1.5.2 的判準在索引層的對應。

#### 1.7.7 `Commit.parent` 可以免費棄用

〔讀 `value.rs:2764`〕`if let Some(p) = &self.parent { … }` ⟹
**`parent: None` 貢獻零位元組。**

所以一個新模型的 ● 只要**從不設定** `parent`,雜湊就與「這個欄位不存在」
**逐位元組相同**;而既有的 commit 早已算過落盤,CAID 原封不動。

⟹ **「移除」要付紀元,「不再設定」不用付。** 保留為 deprecated 是嚴格更便宜的路。
(要接受的後果:歷史會是混的——舊 commit 有 parent、新的沒有,`oo log` 走回鏈到
切換點就停。遍歷本來就要搬到日誌,屬弧 A。)

### 1.8 三個層,不是兩個

外部答覆用「metadata vs data」來分 refine 與 commit;用戶補充「從圖看點與邊都是
data,從索引看 refine 比較像 metadata,這也是它為何像 advert」。

**方向對,但用 metadata 會漏掉一格。真正的軸是:你能不能不靠信任誰就確認它?**

| | 驗證方式 | 丟了會怎樣 | 例 |
| :-- | :-- | :-- | :-- |
| **自我認證** | 雜湊它自己 | **不可逆** | ● / `root` / `.oo/objects` |
| **可重算** | 需要兩端,但**不需要信任誰** | **無損** | `DERIVED` 的 ⊑ 邊 |
| **斷言** | 只能信任簽章 | **不可逆** | `DECLARED` 邊、**pin 日誌**、廣告 |

> **更正(2026-08-03):這不是一條軸上的三點,是兩個獨立的布林,而上表漏了一格。**
> 見 `observation_result.md` §9:
>
> | | 能驗證它是它宣稱的嗎? | 能再產生一次嗎? |
> | :-- | :-- | :-- |
> | `#pure` 值 · `DERIVED` 邊 | ✓ | ✓ |
> | **`#io` / `#nondet` / `#state` 值** | **✓** | **✗** ← 漏掉的一格 |
> | `DECLARED` 邊 · pin 日誌 · 廣告 | ✗ | ✗ |
>
> **`%effect` 就是那一格的標記**:可被定址,但不可被重現。
> 這也是為什麼 `#io` 值可以合法被提交(SPEC_10 §1.1「由因果邊界固化,
> 而非由真理固化」),以及為什麼效果會傳染(那是該格的封閉性)。

**§1.7.6 ① 的錯誤在此一般化:第二列與第三列被放進同一個盒子,因為兩者都「住檢索
層」。但軸不是「在哪一層」,是「重不重算得回來」。**

⟹ **點與邊的乾淨說法:**

* **點** = 值(自我認證)
* **`DERIVED` 邊** = **根本不是物件**,是一個可計算的關係
* **`DECLARED` 邊** = 物件,而且是斷言

**全球「圖」= 一組點 + 一個可計算的關係 + 一組被斷言的邊。只有第三樣是 data。**

而 **`refine` 不是一種東西**:`DERIVED` 的住第二列,`DECLARED` 的住第三列,
**兩者畫在圖上一模一樣,耐久性要求卻相反** ⟹ `edge_type` 不是方便欄位,
**它是兩層之間的界線,不得被靜默跨越**。

#### 1.8.1 延伸:`DECLARED` refine 看起來像 advert,不像 commit

它的性質:一則**簽章的、關於某個 CAID 的陳述**,要**傳播**、要在**斷言層持久化**、
要有**誰的簽章算數**的信任根、而且該有**時效**。

**那是 `%ad` 的形狀,不是 commit 的形狀。** 而那套機制 v0.2.54 就出貨了
(耐久對等目錄、簽章面隨行、`ttl`),信任根的模式 v0.7.0 也在了
(`affiliation_roots`)。

⟹ **值得評估:`CommitKind::Refine` 這個位置是不是放錯了。**

### 1.9 沒有位址字面,所以東西只能住在根裡

> 2026-08-19,由 Q-033 D2 的裁定討論長出來。**這一節解釋的是 Q-033 為什麼存在。**

#### 1.9.1 量到的三件事

〔量,引擎 v0.26.1〕

1.  **語言裡沒有任何寫法能指名一個位址。** `PathAnchor` 只有
    `Root`／`Current`／`Parent`／`Bare` 四種。`@"hash:…"`、`<<hash:…>>`、`~"hash:…"`
    皆為 parse error;`"hash:…"` 只是字串。`<</f>>` 有效,但它引用的是**名字**
    ——回傳具現化的態射(`%code`／`%closure`),不是位址。
2.  **`~%Discovery./fetch(CAID)` 真的取回值,而且它是一次本地 CAS 讀取。**
    對本地存過的 CAID 取回整個根(含其使用者欄位);對不存在的 CAID **立刻**回
    `⊥ #missing_key`,零 peer 設定、不等網路。**它住在網路模組裡並被標成 `#io`,
    但那是擺放位置,不是它的性質**——位址→值是確定性的(同一個 CAID 恆得同一個值),
    那正是純的定義。
3.  **匯入使匯入者變成 `#io`,而效果自 v0.26.0 起進位址。** `~%Discovery./fetch(…)`
    的結果被投影後,外層 combo 帶 `%effect: #io`;同一格的 `~%Math./add` 是純的。

#### 1.9.2 承重推論

**每一個庫都得靠名字才拿得到;每一個名字都得在某處被綁定;唯一永遠都在的綁定處
就是標準根。** ⟹ 拆模組不會讓東西離開根,因為**沒有別的地方能掛**。

⟹ **最小的創世根是空的。** 若名字經由父提交鏈解析,根就一個值都不需要——
查找本來就是引擎機具,今天讀 `ctx.standard_root`,換個來源讀父提交是同一套機具。
而空的創世根有一個別的值都沒有的性質:**它是唯一一個所有實作不必靠規格列清單
就能同意的值。**

#### 1.9.3 撞牆的位置就是那把尺

若引擎的庫只是一個普通提交,兩個獨立實作會造出**不同的**那一筆 ⟹ 同一份程式碼
在不同引擎上得到不同位址。**fetch 救不了**:可以抓引擎甲的庫來重現甲的位址,
但那樣乙就不是獨立實作,而是甲的庫的客戶。

⟹ 規範核心仍然需要,但**它必須多大是可以算的**:

> **一個東西該進規範核心,當且僅當程式以「符號名」指涉它,
> 而兩個獨立實作必須對它取得一致,程式的位址才可重現。**

推論(可操作):**凡是能以位址取得的都不必進核心**——兩邊抓到逐位元組相同的東西,
一致是構造保證的。核心恰好是**只能靠名字**的那些殘留。

⟹ 縮小核心的手段不是刪模組,是**補上位址字面**。這是 §1.9.1 第 1 項為什麼承重。

#### 1.9.4 三提交的 `init`(用戶 2026-08-19)

`init` 不必只做一個提交:

| | 內容 | 使用者可否調整 |
| :-- | :-- | :-- |
| 第一 | 標準根 | 否 |
| 第二 | 引擎自帶的標準庫／客製功能 | **可挑、可整個拔除** |
| 第三 | 使用者自己的 | — |

**這個模型讓 REAL_03 §6.8 的特例消失**:「認不得的標準根」變成「認不得的父提交」,
而已裁的 丁-c(認不得就靠 OODP 取回)由特例升為通則。它也讓「這是哪一台引擎做的」
第一次成為**歷史裡有答案的問題**。

**用戶 2026-08-19 裁定:自動補進第二個提交並記錄。** 我原先提的「具名拒絕」
過嚴——它會逼使用者不斷走特權模式重鑄歷史。

**而這與 §6.8 第三條 MUST 不衝突,因為兩者管的不是同一件事**(我原先把它們混為一談):
該條逐字管的是「引擎讀到自己**不具備的標準根摘要**時」——**解不開的位址**,
不是**沒綁定的名字**。

| 情形 | 答覆 |
| :--- | :--- |
| **名字未綁定**(`~%Math` 不在第二個提交裡) | **自動補進第二個提交並記錄** ⟹ 歷史裡有痕,位址仍由歷史決定、仍可重現 |
| **位址取不到**(`_"sha256:…"` 不具備) | **具名拒絕**——一個具體位址在定義上無可代入 |

兩列的共同點仍是:**不可靜默替代**。那會讓兩個設定不同的使用者得到不可比較的宇宙
而無人察覺,即 §6.8 立節時寫下的第三個後果,也是它說「這是安全性質不是效率性質」
的那一項。

**未定**:自動補**發生在哪一層**(解析／演化／提交),以及那一筆**是否需要使用者同意**。

### 1.10 注入與觀測是兩個動作,而「固化」同時指著它們

(用戶 2026-08-27。本節是 §1.4 的更正與展開,並改寫 A4;§1.4 那句
「演化 ＝ 觀測 ＋ 固化」**留著,但它的兩個加項各自要換名字**。)

> **✅ A4 已裁(用戶,2026-08-27)→ D42–D45。** **拆**——先拆成兩個獨立動作。
> **一次做兩步的複合入口(CLI 或 API)容許存在,但那是 UX 層,不得是語義層。**
> 用戶原話:「最後要不要有個 cli 指令(或 api 也能有)可以一次做兩步,
> 那就只是 UX 的問題。」
> **同批未裁而被逼出來的兩題:O79**(固化深度進不進 ●)、**O80**(○ 的產生判準)。

#### 1.10.1 那一刀

| | 是什麼 | 動到什麼 |
| :-- | :-- | :-- |
| **注入** | 與當前宇宙節點做 `&`,**不求值** | **sketch**(連帶 digest) |
| **觀測** | 給一條已定的路徑,消耗燃料收斂它 | **只有 digest** |

例:`a: @int` 注入 `a: 3` 得到的是 `a: @int & 3`,**不是** `a: 3`;
要到觀測 `a` 那一刻才收斂成 `a: 3`。

**這條界線 §1.5.7 已經量到了,只是當時沒認出來**:同一支程式,`c` 固化與否
digest 不同(`42c1aa7d…` vs `1aeb5c4d…`)而 **sketch 逐位元組相同**。
⟹ 「sketch 看見結構,digest 看見固化到哪裡」就是這兩個動作各自的痕跡。

**注入不是新詞,核心規格早就寫對了。** `SPEC_10` §2.2 逐字:「將新的定義**注入**
當前宇宙的 Staged」,公式 $Staged_{new} = Staged_{old} \sqcap Definition$。
⟹ **A4 寫下「注入」時沒有回頭引 SPEC_10 §2.2**,於是這個詞在設計帳上看起來
像個未定義的新詞,而它在規格裡有家、有公式。這是 §5.1 那種病的第三個實例
(對的東西寫在一個地方,別處不知道它存在)。

#### 1.10.2 ○ 的鏈,以及「持久 ≠ 固化」

```
○(1) ──注入──▶ ○(2) ──觀測──▶ ○(3) ──commit──▶ ●(4)
a: @int        a: @int & 3      a: 3
```

**每一個 ○ 都已經是持久的。** ⟹ **持久 ≠ 固化**:
「持久」是寫下來了,「固化」(用戶此處的用法)是轉成 ●。

**而 ● 的真正前提不是「可分享」,是「能不能算出 CAID」。**
可分享是**要不要**(意志),可定址是**能不能**(事實);§1.5.2 的兩個條件因此分工明確,
而會失敗的是後者。

#### 1.10.3 那個前提已經有答案,而且有一個動詞

接 `observation_result.md` §5 / `SPEC_08` §3.2.1:

| | 可否內容定址 |
| :-- | :-- |
| **`#incomplete`**(掛起) | **不可**——值隨燃料變動 |
| **`#blur`**(凍結) | **可**,且 CAID **必須**含視界參數 |

⟹ **○／● 的界線就是 `#incomplete`／`#blur` 的界線。**
且 `SPEC_08` §172 已經有那個動詞:**提升(Lift)**——`#incomplete` 依
`%strategy: #blur` 提升為 `#blur`。

⟹ **○ → ● 分解成三步,三步都已經有名字:Lift(使可定址) → 鑄 CAID → 宣告可分享。**

#### 1.10.4 ⊥ 的觀測結果也必須產生 ○

(用戶:「即使產生 `_|_` 觀測的結果也應該產生一個 ○,因為後續才能觀測 `%cause`。」)

**這補的是 B1(§2.1.3)已裁但沒有落點的那一半。** B1 裁的是「收斂撞 ⊥ **必須停下
並回報**,要不要固化由操作者決定」,而偵察量到引擎**連前半都沒做**。
⟹ **回報就是那個 ○**,理由不是體驗:`%cause` 掛在那個 ⊥ 值上,
**若失敗的觀測不產生任何東西,`%cause` 就沒有可指的對象,那次失敗不可檢查。**
一個能被後續觀測的 ○ 與一行 stderr 的差別,是**前者在格裡**。

**順帶**:⊥ 帶著確定的 `%cause` 不隨燃料變動 ⟹ **可定址** ⟹ 承載 ⊥ 的 ○
**有資格**轉 ●。這正面撞上 §2.3 那條「local 側衝突 → 立即終止」
(`SPEC_10` §4.1.2,創世遺物、無理由)。

#### 1.10.5 開放:○ 的產生判準不能用 CAID 表述

舊判準(§1.5)是「**改變 combo** 才產生 ○」。新切法可以統一成
「**digest 變了才產生 ○**」——注入改 sketch 連帶改 digest,觀測只改 digest,
兩者都涵蓋,而重複注入同一個值、重複觀測已算完者也都自動不產生。

**但它對 `#incomplete` 不成立,而 `#incomplete` 正是 ○ 存在的理由之一。**
`#incomplete` 沒有 CAID,「digest 變了」在那一格問不出答案;
而 ○ 這一層的身分是本地鑄的 id(§1.5.3),**不能拿只有 ● 那層才有的東西當判準**。

⟹ **待答**:燃料燒完、只前進了一半的那次觀測,算不算「有變化」?
若算(本文傾向算,否則就失去「我看到哪裡」這個記錄,而那正是 ○ 的職責),
判準得用**局部收斂結果**表述——而那個東西今天住在 `BlurDetail.partial` 裡,

### 2.1 「提交必須立即終止」從來沒有人裁定過,而且今天不成立

>                    Value::Combo(self.staged.clone())) {

#### 2.1.3 裁定(用戶,2026-08-06):一條規則裡有兩件事,拆開

> **收斂遇到 bottom 該停並回報是對的,但要不要固化是使用者能決定的。**

| | 誰的責任 | 條文該說 |
| :-- | :-- | :-- |

#### 2.1.1 它為什麼只長在合併路徑上

(2026-08-02:由另一個持早期規格的 agent 提出,本文採納——它比「§4.1.2 只治合併」
這個純觀察更進一步,給出了理由。)

**問題不是衝突本身,是「自動 + 不可逆」的組合。**

* `⊥` 在 meet 下是**吸收的**;Invariant 2 只保證單調遞增,而 `&` 沒有減法語義。
  一旦坍縮成 `⊥`,除非動用特權改寫歷史,否則回不來。
* 合併路徑是**唯一一個「你沒有做任何決定,卻會落到 ⊥」的地方**——晚到者的
  staged 與別人的 HEAD 相遇,是並發時序造成的,不是誰選的。
* 所以中斷不是為了排斥衝突,是為了不讓引擎**替你**按下一個不可逆的按鈕。
  §4.1.2 同時要求揭露競爭 Commit 的 CAID,正是把診斷線索交還給觀測者。

⟹ **這條規則的正當範圍是「自動且不可逆」,不是「衝突」。** 顯式提交一個
`_|_` 不落在它的射程內——而那與 §2.1 的實測一致。

### 2.4 固化只固化「當下搆得到的」,而且從不回頭 —— pin 不傳播

**〔量〕同一支程式,拆檔方式不同,`c` 的命運不同:**

```
;; 情形 A:a/b/c 同一個檔
a: 1 / b: 2 / c: a + b
$ oo evolve a.n ; oo status  →  c: 3            ← evolve 當下就被固化

;; 情形 B:c 先,a 後
$ oo evolve s1.n   (b: 2 / c: a + b)
$ oo evolve s2.n   (a: 1)
$ oo status        →  c: Thunk { … }            ← 補上 a 之後也沒回頭固化
```

而在 Combo 封閉性底下,**拆檔應該是語義無關的**。

**〔量〕後果——pin 不傳播:**

```
$ oo evolve a.n                          (a:1 b:2 c:3)
$ oo evolve p.n --pin --grant pin        (a: 3)
$ oo status  →  a: 3   b: 2   c: 3       ← c 沒跟著動,期待是 5
```

反事實已做:**從未觀測過、直接 pin,`c` 仍是 3** ⟹ 固化點是 evolve,不是 observe。

而且**不可能靠再 evolve 修好**,因為 `3 & 5` 是 `_|_`。
⟹ **覆寫一個座標,等於必須覆寫每一個由它導出的座標。今天不會。**

### 2.7 Phase 44 的 `~%Diff`:形狀對,語義相反

`crates/interpreter/src/builtins/diff.rs`,25 個測試,**規格零字**。
問題是「§1.5.4 的重放機制是不是已經有一半」——**答案是否定的,而且比「不夠用」更糟。**

**〔量〕`patch` 是覆蓋,不是 meet:**

```
c: { x: 1 }   d: { x: 5 }
~%Diff./patch (c, ~%Diff./diff (c, d))   →   { x: 5 }      ;; meet 會是 _|_
```

原始碼對得上:`set_at_path` 走無條件 `insert_field`,葉節點直接 `return new_val`。

⟹ **`diff.patch` 在每個路徑上都是 pin 的語義** ⟹ **拿它當重放引擎,會把每一次
普通演化都靜默地變成一次 pin。** 而 pin 與普通演化的可分性(§1.7.3)正是那條日誌
存在的理由。它不是少功能,是**語義相反**。

它也**只讀 `path` 與 `to`,忽略 `from`**——沒有基底檢查。REDO 確實盲套 after-image,
但 DB 的 REDO 錨在 LSN 上;這裡**沒有錨**,套錯基底會靜默產生垃圾。

**三個缺陷:**

* **①〔量〕相同的輸入會報出差異。** `{x: 1|3}` 對 `{x: 1|3}` →
  `[{path:"x", from: 1|3, to: 1|3}]`。成因:`same_value` 只有
  `Top`/`Bottom`/`Atom`/`Combo` 四個分支,**`Union`/`Thunk`/`Blur`/`Range`/`Code`/
  `Ref`/`TopCaused` 全落到 `_ => false`**;加上巢狀欄位本來就存成未強制 thunk。
* **②〔讀〕所有 bottom 一律相等**:`(Bottom(_), Bottom(_)) => true` ⟹
  `#conflict` 與 `#fuel_exhausted` 對 diff 是同一個值。
  **與 `observation_result.md` 的主論旨正面衝突**(原因是第二條軸)。
* **③〔讀〕Atom 相等用 Debug 字串比**:`format!("{:?}", ka) == format!("{:?}", kb)`。
  與既有掛帳「`to_nlang` 用 `Debug` 印未強制 thunk」同一家族。

**可沿用的兩塊:**

* `is_compatible` 的 `deep_merge_values` **葉節點走 `oo.unify_internal`,那是真正的
  meet** ⟹「這兩個合得起來嗎」這個閘是誠實的,而那正是套用前該問的問題,
  **也正是 §1.7 判定 ⊑ 所需要的原語**。
* `/diff` 吐出的 `{path, from, to}` **`from` 是有的,只是 `patch` 不看** ⟹
  形狀對,修法局部:套用前比對 `from`、預設用 meet、**除非該筆條目標記為 pin**。
