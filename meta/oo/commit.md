## 0. 這份文件回答什麼

不是「commit 這個指令怎麼用」,而是:**版本控制這件事在 n/ 裡站在哪、承重的是什麼、
哪些現有的磚不屬於這棟樓。**

判別法:一句話屬於這裡,當且僅當**拿掉它所描述的部分,別的句子會變成假的**。
刪掉不影響任何東西的,是歷史或目錄,不是這裡的內容。

### 0.1 這棟樓的樣子(承重摘要)

底下八句是這份文件的全部主張;其餘是證據。每句後面是它住的節。

1. **n/ 的版本控制是交易模型,不是補丁模型。** SPEC_10 §4.1 逐字就是資料庫的
   樂觀併發控制,而 git 的補丁/三方合併才是外來的。〔§1.1〕
2. **local 與 published 是兩個不同的態射,不是同一個東西的兩份拷貝。**
   這條界線有**四個獨立的證人**(簽章 / 定址 / 身分 / 撤銷),而且沒有一個是為了
   配合另一個設計的。〔§1.2、§1.2.1〕
3. **git 的圖結構被值語言吸收掉了。** branch → 聯集值,merge → meet,
   **只剩時間上的撤回沒有落點**。〔§1.3〕
4. **最小單位是 savepoint(○),不是 commit(●);而 ● 不是另一種物件,
   是 ○ 上的一個謂詞**——可定址,且被宣告為可分享。〔§1.5、§1.5.2〕
5. **中間歷史是從檢查點往前重放的 REDO log**,不是 UNDO;
   而**每一筆觀測型條目必須攜帶視界參數**,否則重放不決定性。〔§1.5.4〕
6. **有兩張圖:本地時間序、全球特化序。** 而**版本圖與依賴解析圖是同一張圖**
   ——「這個具體的東西滿足那個約束嗎」就是 ⊑。〔§1.7、§1.7.1〕
7. **全球邏輯格 = 本地歷史扣掉特權邊。** 實測:普通演化必 ⊑ 前一版,
   pin 產生的兩個狀態**不可比** ⟹ **特權 = 做一個格表達不出來的動作**,
   而這正是它必須留審計痕的理由——**值不會記得**。〔§1.7.3〕
8. **軸不是「在哪一層」,是「重不重算得回來」。** 由此:`DERIVED` 邊根本不是
   物件而是一個可計算的關係,pin 日誌**不是索引**不能當快取設計,
   而 `%effect` 標的是「可定址但不可重現」那一格。〔§1.8〕

**最大的一處對不上:** SPEC_10 §4.1.2「衝突必須立即終止」出自規格的**第一個提交**,
從未被修訂,**五條語義不變性沒有一條強制它,而引擎今天已經不遵守它**;
同一個現象在 SPEC_13 §5.3 被裁成相反的答案(保留聯集、按需消融),
而兩節從不互相引用。〔§2.1、§2.2、§2.3〕

## 1. 承重結論(候選)

### 1.1 n/ 的版本控制是交易模型,不是補丁模型

SPEC_10 §4.1 逐字寫的就是資料庫的樂觀併發控制:

> `n/` 採用基於格論與內容雜湊的**樂觀併發模型**
> `#commit` 必須具備**強原子性 (Strong Atomicity)**
> **晚到者自動收斂**:$C_{new} = HEAD_{current} \sqcap Staged_{incoming}$

ACID 四格都有落點,而 **C(一致性)** 那一格特別乾淨:資料庫的一致性是「不違反約束」,
而 n/ 的約束**就是格本身**,`_|_` 就是違反。

而 n/ 做到一件資料庫做不到的事:**衝突時不中止晚到者,而是合併晚到者**——
因為 meet 是全域且決定性的。DB 必須 abort-and-retry,是因為它沒有一個能把兩個寫入
合起來的代數。

> **git 才是那個外來的模型。** git 用補丁/三方合併,它的合併不決定性、要人介入。
> (用戶口述:版本控制的直覺來自資料庫的 Transaction 與 ACID,不是來自 git。)

### 1.2 local 與 published 是兩個不同的態射,不是同一個東西的兩份拷貝

用戶對 git 的診斷:**難用是因為它把 local repo 與 remote repo 都當成一個完整自洽的
repo 來處理**,而兩邊的語義要求根本不同——local 只想記錄歷史與隨時退回,
published 則要求完整、可執行、經過多層檢查。

n/ 已經把這兩件事拆成兩個態射了,只是沒人把它寫成「這就是那條界線」:

| | `commit` | `refine` |
| :-- | :-- | :-- |
| CLI | 無 `--sign` 〔量〕 | **有 `--sign`** 〔量〕 |
| 語義 | 記錄自己的歷史 | 對別人宣稱 $E \sqsubseteq B$ |
| 背書 | 無 | SPEC_13 §5.2.1:「其正確性由 **#refine Commit 的簽署權威**背書」 |

而 SPEC_13 §5.2.3 把同一條界線畫在同一個地方:自動重定向**允許**發生在
Live Observation 與 Staged,對**已固化的歷史 Commit 嚴禁**。

#### 1.2.1 這條界線有四個獨立的證人

(2026-08-02 收攏。§1.5 的設計討論做完之後才看出來這四條是同一條。)

| 面向 | local | published |
| :-- | :-- | :-- |
| **簽章** | `commit` 不簽 | `refine` 簽,權威背書 |
| **定址** | ○ 可含 `#incomplete`(SPEC_08 §3.2.1:不具備內容定址的合法性) | ● **必須**可定址 |
| **身分** | 本地鑄造的隨機 / patch id —— **斷言層** | CAID —— **自我認證層** |
| **撤銷** | drop 一個 ○ **不留痕** | 放棄一個 ● **必須**留痕(`abandoned`) |

**四條線畫在同一個位置,而且沒有一條是為了配合另一條設計的**——簽章那條在 v0.2.x
就在了,定址那條出自 SPEC_08 §3.2.1,撤銷那條出自 `CommitMeta.abandoned`,
身分那條是 2026-08-02 的討論推出來的。**這種收斂是「這面牆是承重牆」的證據。**

**缺口:** 「published 必須完整、可執行、經過多層檢查」這件事,今天 `refine`
只驗兩樣——$E \sqsubseteq B$ 與簽章。**「可執行 / 通過檢查」那一格是空的。**

### 1.3 git 的圖結構被值語言吸收掉了

| git 的圖結構 | n/ 把它放到哪 |
| :-- | :-- |
| branch(同時養兩個未來) | **值語言**——聯集 / 別名疊加(SPEC_13 §5.3) |
| merge(兩條歷史匯合) | **值語言**——meet,決定性,不需要節點 |
| **undo / savepoint** | **沒有落點** |

用戶補的關鍵句:**「Combo 之間是包含關係,他們本來就已經能自己描述這個關係了。」**
所以 git 拼成 branch 的那個東西,n/ 拼成一個聯集值。

**〔量〕實測聯集穿過算術:**

```
a: 1 | 3
b: 2
c: a + b
$ oo run --observe a  →  1 | 3
$ oo run --observe c  →  3 | 5
```

⟹ **使用者想像中的 branch/merge 不是提案,是一個已經在跑的機制。**

而剩下沒有家的那一件——時間上的撤回——**本來就不是值之間的關係**。
discussion 027 已推到同一結論(「撤回是審計行裡的事實,不是值間關係」);
jj 的 operation log 就是它的實作。

**用戶要的是 savepoint,不是 branch**:「去試 / 隨時退回」,單一現在,
沒有「同時養兩個未來」。

### 1.4 演化 = 觀測 + 固化;觀測是 dry run

用戶更正(2026-08-02):**觀測不改變宇宙,演化才會。**
由此:evolve 會 force 是**定義**,不是實作偏離。

推論(待確認):**REPL 預設應該是演化而非純觀測,所以缺一個切換機制。**

### 1.5 最小單位不是 commit —— savepoint 與 commit

(用戶設計,2026-08-02;符號 ○ = savepoint,● = commit。)

**模型:**

* 每一次**改變 combo** 的演化產生一個 ○;不改變 combo 的演化不產生
  (例:對已是 `1` 的 `a` 再演化 `a: 1`)。
* **pin(覆蓋模式)也歸類在演化底下**,一樣產生 ○。
* ○ 之間的關係來自**演化順序**;`checkout` / `rollback` 到較早的 ○ 之後再演化,
  就造出旁支。
* `commit` 把當前 HEAD 的 ○ 轉成 ●,**中間的 ○ 歷史併入該 ●**。
* 第一個節點一定是 ●。

```
●#0 → ○#1
    ↘ ○#2 → ○#3        commit ⟹  ●#0 → ●#3
                                   (#3 記得中間經歷 pin a:3 與 evolve c)
```

#### 1.5.1 命名:`snapshot` 不能用

SPEC_10 §1.2 有一條白紙黑字的裁決:

> **裁決:快照 ＝ Commit／CAID,不新增 source-level 語法。**

**推薦 `savepoint`**,理由不只是「還沒被佔用」:

1. 資料庫的 savepoint 就是**開著的交易裡的一個標記**,可回退——正是 ○;
2. **它在交易提交時消失**——正是「中間的 ○ 歷史併入 commit point」;
3. 最有價值的一點:**§1.2 那個 local/published 的界線,用這個詞就變成 ACID 的
   I(隔離性)**——未提交的狀態對別人不可見。**不需要為 local/remote 發明規則,
   那是隔離性白送的。**

誠實的差異:DB 的 savepoint 在回退時**丟棄**後面的工作;此處是**保留到被顯式 drop
為止**(而 drop 不留痕,見 §1.5.5)。

#### 1.5.2 ● 不是另一種物件,是 ○ 上的一個謂詞

用戶原本擔心「savepoint 可能無法產生 CAID」。實際的判準用戶自己已經給了
(§1.5.6 的第二個差異):**只有可內容定址的 combo 才能 commit。**

而 SPEC_08 §3.2.1 說明了為什麼有些不合格:`#incomplete`「**不具備內容定址的
合法性**」,因為其值隨燃料變動。一個**全部固化完**的 ○ 是可以被定址的。

⟹ **● = 一個「可定址」且「被宣告為可分享」的 ○。** 不是兩種型別。

**實作面撞在同一點上(用戶,2026-08-03):** ○ 與 ● **共用一個結構**,只是各自
有些欄位不去使用。這是從「實作成本」推出來的,而上一段是從「語義」推出來的——
**兩條路到同一個結論。**

但要加一條紀律,而且**有量過的前科**:seat_order 弧的掛帳是「排序欄位『缺席』
與『不可解析』共用退回值 `0`」——**一個槽兩個意思,讀的人分不出來**。
「某些欄位不去使用」正是同一個形狀。

**防線:結構共用,雜湊不共用。**

* ○ **不需要 `content_hash`**(§1.5.3:身分住斷言層,是本地鑄的 id);
* 雜湊只在翻牌成 ● 的那一刻算,輸入必須是**正面列舉的白名單**,
  不是「結構裡的所有欄位」;
* 好消息:`Commit::content_hash` **今天就是手寫白名單**,所以這是既有形狀。

#### 1.5.3 兩個身分層

○ 需要一個穩定把手,但不需要 CAID。用戶提議「類似 jj 的 patch id」。

**這是對的答案,而且理由比「退而求其次」強**:**savepoint 永遠不旅行**,
所以本地鑄一個隨機 ID 的代價是零——**自我認證只在有第二方要說服時才有價值,
而這裡沒有第二方。**

⟹ 用 disc 025 的話:**○ 的身分住斷言層,● 的身分住自我認證層。** 各安其位。

#### 1.5.4 中間歷史是 REDO,不是 UNDO

用戶原話「類似 UNDO Log」,但給的草圖 `[(#pin, a, 3), (#evolve, c)]` 記的是
**做了什麼**(操作 / after-image),不是**怎麼倒回去**(before-image)——那是 REDO。

而 **REDO 就夠了**,理由是設計自己送的:**● 是完整狀態,不是差量。**
要重建 ○#2,從 ●#0 **往前重放**即可;永遠不需要 before-image,因為檢查點一直在。
資料庫需要 UNDO 是因為它在提交前就地修改資料頁——**n/ 沒有這個問題。**

⟹ 準確說法:**「從檢查點往前重放的 REDO log」**。
(用戶確認:一直在想反向的箭頭,而 UNDO 所需的 logical logging 極難寫。)

**但有一個必須補的欄位。** logical logging 的前提是**重放必須決定性**。
n/ 在這件事上異常有利(meet 全域決定性),**但 `(#evolve, c)` 不決定性**:
若固化 `c` 撞到燃料上限,結果取決於 `%fuel`,換預算重放會得到不同的值。

⟹ **每一筆觀測型的日誌條目必須攜帶視界參數。** 這與 SPEC_08 §3.2.1 要求
`#blur` 的 CAID 必須含視界參數**是同一條規則的第二個實例**:
一個沒說清楚「在什麼條件下停的」觀測,不是一個穩定的東西。

#### 1.5.5 兩種 diff,該共存

| | 是什麼 | 現況 |
| :-- | :-- | :-- |
| SPEC_10 §5 `#diff` | 「所有狀態皆由內容雜湊決定,可精確**計算**兩 Commit 的幾何差異」 | **從狀態重算** = physical logging(git 的模型) |
| `~%Diff./diff` `/patch` `/is_compatible` | 值層 combo 對 combo | **引擎 genesis 已種,規格零字** |
| 用戶要的 | `[(#pin, a, 3), (#evolve, c)]` | **被記錄的操作** = logical logging |

重算回答「差在哪」,日誌回答「做了什麼」。

**而引擎早就承認過重算不夠了。** `CommitMeta.privileged_effect: Option<bool>`
存在,正是因為「這次提交動用了特權」**無法從狀態還原**——從 `_`(top)pin 到 `3`
是單調的,與一次正常演化在狀態上**完全不可分**。

⟹ **引擎已經為了一個事實破例做了 logical logging,只是只做了一格布林。
本設計是把那一格推廣。**

**存放位置:`~%Engine` 底下**(見 §1.6;中途曾提過 `~%Version`,已收掉)。
要求是不管怎麼 `checkout` 都能讀取。

* **〔量〕這個要求是滿足的:`~%` 軸不在被提交的 root 裡。** 對一個提交過的宇宙
  `oo inspect <commit>`,root 內 `~%` 出現次數為 **0** ⟹ 系統軸是每次啟動鑄造的,
  不隨版本走,所以放在那裡的日誌不會被 checkout 換掉。
* **鍵應該是 CAID 對,不要用本地序號。** `3_0` 這種序號是本地的、提交後 ○ 的
  編號本來就沒了、重建不保證還原成同號。而**§1.2 的推論要求 diff 隨 ● 一起旅行**
  ——用本地序號當鍵的 diff 傳不出去。
* **住哪一層有答案**:它在被版本化的宇宙**之外**(DB:WAL 不是一張表)。
  與 Invariant 4(萬物皆 Combo)不衝突——**它是 Combo,只是不從根可達**,
  即 disc 025 的**斷言層**,與完整性日誌、對等目錄同層。
  而**讓它對程式唯讀的機制已經在跑**:`BottomCause::SystemReserved` 已在拒絕
  使用者對 `~%` 軸的左值寫入,不需要新機制。

#### 1.5.6 drop 的不對稱,以及它給 `abandoned` 的理由

| | 留不留痕 | 為什麼 |
| :-- | :-- | :-- |
| drop 一個 **○** | **不留** | 它從沒旅行過,**不可能有人正握著它** |
| 放棄一個 **●** | **必須留** | 它**可能已經被發表**,別人手上可能有那個 CAID |

⟹ **你不能悄悄地取消發表。** 這就是 `CommitMeta.abandoned` 在解的事,
而它從來不是為 ○ 設計的。

也因此 `commit` 那一刻需要跟使用者確認:若 HEAD 的 ○ 不是上一個 ● 的唯一子樹,
旁支的 ○ 會**無痕消失**——所以要在還能問的時候問。

#### 1.5.7 承重量測:固化狀態會改變 CAID

同一支程式,唯一差別是 `c` 有沒有被固化(同檔 vs 拆檔),提交後比較 root CAID:

```
c 已固化 (c: 3)           digest 42c1aa7dfb1599…
c 未固化 (c: Thunk(a+b))  digest 1aeb5c4d703984…
sketch                    兩者逐位元組相同
控制組:兩個獨立工作區、同程式、同固化 → digest 逐位元組相同 42c1aa7d…
```

**「同 sketch 異 digest」在這裡的意思:sketch 看見結構,digest 看見固化到哪裡。**

**後果:** 若 ● 繼承的是當地恰好演化到的固化狀態,兩個人跑同一支程式、演化順序不同,
**會產出 CAID 不同的 ●** ⟹ 共享的不是「這支程式」,而是「這支程式 + 某人的觀測深度」。

**而 §1.5.2 的判準剛好把它關掉**:只要 ● 要求全部固化(或以 `#blur` 顯式凍結,
而 `#blur` 的 CAID 依 SPEC_08 §3.2.1 必須含視界參數),固化狀態就成為正準的,
**● 重新是 (程式, 宣告的視界) 的函數,不再是本地歷史的函數。**

⟹ **「最小單位是 ○」與「只有可定址者能 commit」不是並列的兩點——
第二個是第一個能成立的前提。**

### 1.6 命名空間:全部歸 `~%Engine`

SPEC_10 講的是同一件事(演化、提交與因果邊界),但它的態射散在兩個家族:
`/observe` `/evolve` `/collapse` `/refine` 在 `~%Engine`,而 **`/commit` 在 `~%Repl`**。

**〔量〕而這場爭論的對象大部分還不存在:**

| SPEC_10 §2 | 引擎 |
| :-- | :-- |
| `~%Engine./observe` | **✓ 有** |
| `~%Engine./evolve` | **✗** |
| `~%Repl./commit` | **✗**,且 **`~%Repl` 整個家族不存在**(genesis 種了 23 個,無此名) |
| `~%Engine./collapse` | **✗** |
| `~%Engine./refine` | **✗**(`~%Refine` 家族亦不存在) |

`~%Engine` 實際裝八個:`/observe` `/save` `/project_down` `/project_up`
`/set_strategy` `/check_oml` `/equivalence_map` `/resolve`;其中後五個
**以 `~%Engine./` 拼法在規格中查無**。

⟹ **版本控制那一組今天只活在 CLI**(`oo evolve`/`oo commit`/`oo refine`),
語言層一個都沒有 ⟹ **整併零遷移成本。**

**裁定(用戶,2026-08-03):全部歸 `~%Engine`,理由就是「引擎能做的所有事」**
——不需要用「演化與提交」去論證它;最直觀的答案就是對的答案。
`~%Diff` 的三個概念保留,重新設計後併入(中途曾考慮獨立的 `~%Version`,已收掉:
多開一個家族又是一次「同一件事兩個家」)。

**預設是 observe;`/collapse` 拔除。** 併入後 `~%Engine` 應含
`/observe` `/evolve` `/commit` `/refine`,以及今天沒有的
`/checkout` `/rollback` `/diff` `/log` `/status`。

**兩個要接受的後果:**

1. `~%Repl` 這個名字**把介面寫進了語義**。REPL 只是三個面之一(對人),
   而 commit 不是只有 REPL 能做——CLI 在做,控制面將來也該做。
   用介面命名一個語義操作,與 REAL_01 §1 把 CLI 拼法寫進規範性條文是同一個錯。
2. 併入後 `~%Engine` 會裝著 `/project_down`(Bohrification 投影)、`/check_oml`
   (邏輯驗證)、`/equivalence_map`(狀態)這些**不是版本控制**的東西 ⟹
   **SPEC_10 不再是 `~%Engine` 的規格,只是其中一段。**

(`~%Ouroboros` 已排除:名字長,且「Ouroboros」在規格裡至少指四個東西——
引擎、協定 OODP、工程 REAL_01、哲學意象。)

### 1.7 兩張圖:本地時間序,全球邏輯格

用戶 2026-08-03 提出:`#refine` 在新圖景下不只是 blur→exact,而是
**從 ⊑ 關係造出關聯**。設 LADD 上有兩個彼此無共同歷史的 commit:

```
def = { a: 1 | 2 }        ghi = { a: 1 }
```

`diff CAID(def) CAID(ghi)` 判得出 **`CAID(ghi) ⊑ CAID(def)`**,
於是 `refine CAID(ghi) CAID(def)` 可以把它們接起來。

**這件事的份量:它把「歷史」從宣告變成計算。** git 的父邊是造 commit 的人
**斷言**的;`ghi ⊑ def` 是**任何人都算得出來的事實**,不需要相信誰。

#### 1.7.1 那是兩張圖,不是一張

| | 本地 | 全球 |
| :-- | :-- | :-- |
| 關係 | **時間序** ○→● | **特化序 ⊑** |
| 由誰決定 | 你造的 | 內容決定的 |
| 說的是 | **發生了什麼** | **什麼是什麼的實例** |

`ghi` 並不是**從** `def` 來的,它只是**在** `def` 底下。把兩者畫成一條線的代價:
`diff def ghi` 在歷史意義下該答「無共同祖先」,在序意義下該答「ghi ⊑ def」,
**兩個都真、都有用**,合成一張就少掉第一個。

而 ⊑ 會連上一堆沒打算連的:`{a: 1, b: 2}` ⊑ `{a: 1}`,「多寫一個欄位」自動成為
誰的精煉。**——而這反而是好消息:「這個具體的東西滿足那個約束嗎」就是 ⊑,
而 LADD 本來就是為套件發佈生的。**

⟹ **承重結論候選:版本圖與依賴解析圖是同一張圖。**

正確的說法:**本地圖記錄「發生了什麼」,全球圖記錄「什麼滿足什麼」,
`refine` 是把一條本地事實發表成全球圖上的一條邊。**

#### 1.7.2 直接後果:`Savepoint` 有 `.parent`,`Commit` 沒有

(用戶 2026-08-03。)時間序住 ○,全球序是內容的函數、不需要被儲存。

⟹ **與今日引擎正面衝突**:`Commit.parent: Option<ContentHash>` 存在,
且 `oo inspect` 會印出 `parent: (none)`。那個欄位記的是本地時間序,
而本地時間序在新模型裡屬於 ○。

#### 1.7.3 特權是「格表達不出來的那一步」

用戶觀察:⊑ 很可能讓本地有時間序的兩個 commit **在全球格上毫無關聯**,
**尤其是特權模式操作**。

**〔量〕證實,而且分界剛好落在特權上:**

```
old: { a: 1 }
pin:  { a: 3 }          is_compatible(old, pin)  → #false   old & pin  = _|_ #conflict
norm: { a: 1, b: 2 }    is_compatible(old, norm) → #true    old & norm = 正常收斂
```

* **普通演化**是 meet ⟹ 新狀態必 ⊑ 舊狀態(Invariant 2)⟹ **全球邊存在,
  且與本地邊一致**。
* **pin** 產生的新狀態與舊狀態**不可比** ⟹ **全球圖上沒有那條邊。**

⟹ **本地圖與全球圖在非特權歷史上完全一致,恰好在特權處分岔。**
換句話說:**全球邏輯格 = 本地歷史扣掉特權邊。**

而由此可以說出特權在 n/ 裡到底是什麼:

> **特權 = 做一個格表達不出來的動作。**

這回頭解釋了兩件既有的事:

1. **為什麼特權必須留審計痕**——因為**值不會記得**。格裡沒有那條邊,
   `CommitMeta.privileged_effect` 是唯一記得的地方。
2. **§1.5.4 的 REDO log 不是便利設施,是那條邊唯一的載體。**
   非特權的歷史可以從內容重算;特權的不行。

#### 1.7.4 refine 的簽章在新圖景下大多不需要

SPEC_13 §5.2.1 自己說了簽章是為什麼存在的——**不透明目標**:

> 當 `CAID_source` 指向 `CAID_target` 且兩者使用不同雜湊演算法時……
> `CAID_target` 被視為**不透明字串**,其正確性由 #refine Commit 的簽署權威背書。

⟹ **兩邊內容都在手上時,自己算 ⊑ 即可,不需要相信任何人。**
簽章只在**算不出來**時才需要(跨演算法,或只有 CAID 沒有內容)。

**這是強化不是削弱**:refine 在兩邊在場時是**自我認證的**,一邊不透明時才落到
斷言層。⟹ **§1.2.1 表格第一列須加註:`refine` 有兩個模式。**

#### 1.7.5 兩個殘留問題

* **⊑ 是偏序,父不唯一。** 若 `ghi ⊑ def` 且 `ghi ⊑ jkl`,兩者都合法 ⟹
  推導出來的**不是樹,是格**。最徹底的形式正是 §1.7.2:根本不存父邊。
* **原本的 blur→exact 是特例。** `exact ⊑ blur` 就是 ⊑,所以最初的設計不是
  另一件事,是**「你剛好知道為什麼」的那個特例**。而它也**不是 merge**——
  `ghi` 本來就是 `def ⊓ 更多約束`,refine 只是**把一個已經發生的 meet 認出來**
  (與 §1.3「merge 被值語言吸收」同一句話)。
* **027 在全球圖裡永遠無解,而這次是確定的。** 全球圖依構造單調,只能往下 ⟹
  **撤回在這張圖裡沒有位置,那不是缺陷,是這張圖的定義。** 撤回只能住審計行。

#### 1.7.6 全球圖存不存:外部裁定與三處修正

(2026-08-03。用戶向兩個持早期規格的模型分別提問,答覆大致相同。)

**採納的主結論:**

> **真值層嚴禁儲存邊,檢索層(LADD)必須物化。**
> 全球圖是資料庫意義的**物化檢視**——就像 B-Tree / R-Tree,只是為了加速幾何查詢
> 而建的索引。

**採納的命名:邊有兩型** ——`DERIVED`(算出來的)/ `DECLARED`(refine 簽章背書的)。
這正好把 §1.7.4 的兩個模式命名了,比本文原本的寫法乾淨。

**〔量〕外部答覆的一項事實查證屬實:** `~%Discovery` 的原語是
`/advertise` `/alias` `/fetch` `/find` `/identify`,**沒有一個是序查詢**;
⊑ 在 10 份規格檔裡出現,但都是語義關係(SPEC_01 格、SPEC_06 unify、
SPEC_13 §5.2.2 refine),**從未作為路由/檢索原語**。

**——但有三處要修。**

**① 承重:「檢索層丟失無損」對 pin 是假的。**
外部答覆的表寫著檢索層「遺失的後果:無損(重新掃描所有 CAID 即可 100% 重建)」。
**這對 ⊑ 邊成立,對操作日誌不成立**——理由就是 §1.7.3 量到的:pin 在序上不留
任何邊,所以掃遍全世界的 CAID 也**推不出「這裡發生過一次 pin」**。
⟹ **日誌不是索引**,不能當可重建的快取來設計(詳見 §1.8)。

**② `parent` 不是 CAID 污染的成因,而想要的東西已經存在。**
外部答覆說「同內容不同 parent ⟹ 不同 CAID」。真,但**不完整**:
`content_hash` 也吃 `meta`,而 `CommitMeta` 的 Debug 含 **author / timestamp /
message** ⟹ **拿掉 `parent` 之後,兩人提交同一份內容仍得到不同的 commit CAID。**

而純內容的身分**本來就在結構裡**:`Commit.root`。
**用戶自己的例子說的其實就是 root**——「def 的內容 `{a: 1 | 2}`」是 root 的內容,
不是 commit 物件的內容。

⟹ **要先問的是:全球圖索引的是 commit 的 CAID,還是 `root`?**
若是 `root`(而它必須是,那是唯一純內容的身分),則 ⊑ 在 root 之間計算、
毫無污染,而 **`Commit.parent` 對全球圖完全不相干**。

**③ 兩個小的。**
*複雜度*:依賴解析是 $O(N)$(一個 `C_spec` 對所有人 meet),$O(N^2)$ 是**建整張
索引**的成本。而物化的真正理由不是速度,**是那個查詢在分散式下根本做不到**
——你手上沒有全世界的 CAID。
*相等測試不健全*:草圖寫 `meet_res == caid_sub`,實際要比的是
`CAID(meet_res) == caid_sub`,而 **CAID 依賴固化狀態**(§1.5.7)⟹
**兩側必須都是正準固化的**,否則靜默漏判。這正是 §1.5.2 的判準在索引層的對應。

#### 1.7.7 `Commit.parent` 可以免費棄用

〔讀 `value.rs:2764`〕`if let Some(p) = &self.parent { … }` ⟹
**`parent: None` 貢獻零位元組。**

所以一個新模型的 ● 只要**從不設定** `parent`,雜湊就與「這個欄位不存在」
**逐位元組相同**;而既有的 commit 早已算過落盤,CAID 原封不動。

⟹ **「移除」要付紀元,「不再設定」不用付。** 保留為 deprecated 是嚴格更便宜的路。
(要接受的後果:歷史會是混的——舊 commit 有 parent、新的沒有,`oo log` 走回鏈到
切換點就停。遍歷本來就要搬到日誌,屬弧 A。)

### 1.8 三個層,不是兩個

外部答覆用「metadata vs data」來分 refine 與 commit;用戶補充「從圖看點與邊都是
data,從索引看 refine 比較像 metadata,這也是它為何像 advert」。

**方向對,但用 metadata 會漏掉一格。真正的軸是:你能不能不靠信任誰就確認它?**

| | 驗證方式 | 丟了會怎樣 | 例 |
| :-- | :-- | :-- | :-- |
| **自我認證** | 雜湊它自己 | **不可逆** | ● / `root` / `.oo/objects` |
| **可重算** | 需要兩端,但**不需要信任誰** | **無損** | `DERIVED` 的 ⊑ 邊 |
| **斷言** | 只能信任簽章 | **不可逆** | `DECLARED` 邊、**pin 日誌**、廣告 |

> **更正(2026-08-03):這不是一條軸上的三點,是兩個獨立的布林,而上表漏了一格。**
> 見 `observation_result.md` §9:
>
> | | 能驗證它是它宣稱的嗎? | 能再產生一次嗎? |
> | :-- | :-- | :-- |
> | `#pure` 值 · `DERIVED` 邊 | ✓ | ✓ |
> | **`#io` / `#nondet` / `#state` 值** | **✓** | **✗** ← 漏掉的一格 |
> | `DECLARED` 邊 · pin 日誌 · 廣告 | ✗ | ✗ |
>
> **`%effect` 就是那一格的標記**:可被定址,但不可被重現。
> 這也是為什麼 `#io` 值可以合法被提交(SPEC_10 §1.1「由因果邊界固化,
> 而非由真理固化」),以及為什麼效果會傳染(那是該格的封閉性)。

**§1.7.6 ① 的錯誤在此一般化:第二列與第三列被放進同一個盒子,因為兩者都「住檢索
層」。但軸不是「在哪一層」,是「重不重算得回來」。**

⟹ **點與邊的乾淨說法:**

* **點** = 值(自我認證)
* **`DERIVED` 邊** = **根本不是物件**,是一個可計算的關係
* **`DECLARED` 邊** = 物件,而且是斷言

**全球「圖」= 一組點 + 一個可計算的關係 + 一組被斷言的邊。只有第三樣是 data。**

而 **`refine` 不是一種東西**:`DERIVED` 的住第二列,`DECLARED` 的住第三列,
**兩者畫在圖上一模一樣,耐久性要求卻相反** ⟹ `edge_type` 不是方便欄位,
**它是兩層之間的界線,不得被靜默跨越**。

#### 1.8.1 延伸:`DECLARED` refine 看起來像 advert,不像 commit

它的性質:一則**簽章的、關於某個 CAID 的陳述**,要**傳播**、要在**斷言層持久化**、
要有**誰的簽章算數**的信任根、而且該有**時效**。

**那是 `%ad` 的形狀,不是 commit 的形狀。** 而那套機制 v0.2.54 就出貨了
(耐久對等目錄、簽章面隨行、`ttl`),信任根的模式 v0.7.0 也在了
(`affiliation_roots`)。

⟹ **值得評估:`CommitKind::Refine` 這個位置是不是放錯了。**

## 2. 圖與現況對不上的地方

### 2.1 「提交必須立即終止」從來沒有人裁定過,而且今天不成立

SPEC_10 §4.1.2:「若自動收斂產生 `_|_`,提交必須立即終止。」

**〔量〕出處追溯:**

```
git log -S "衝突中斷與因果揭露" -- spec/zh_TW/SPEC_10_Evolution_and_Commit.md
→ 43ecd54  Genesis: Discovery of Element Zero
```

**規格的第一個提交,之後從未被任何修訂碰過。**

**〔量〕而且引擎已經不遵守它:**

```
x: 1 & 2
$ oo run --observe x        →  _|_ (%cause: #conflict)
$ oo commit -m "a conflict" →  Commit successful: hash:sha256:v1:c04e77b7…
$ oo log                    →  它在那裡
```

§4.1.2 實際只治「**並行合併產生的** `_|_`」,不治「值本身是 `_|_`」。

#### 2.1.1 它為什麼只長在合併路徑上

(2026-08-02:由另一個持早期規格的 agent 提出,本文採納——它比「§4.1.2 只治合併」
這個純觀察更進一步,給出了理由。)

**問題不是衝突本身,是「自動 + 不可逆」的組合。**

* `⊥` 在 meet 下是**吸收的**;Invariant 2 只保證單調遞增,而 `&` 沒有減法語義。
  一旦坍縮成 `⊥`,除非動用特權改寫歷史,否則回不來。
* 合併路徑是**唯一一個「你沒有做任何決定,卻會落到 ⊥」的地方**——晚到者的
  staged 與別人的 HEAD 相遇,是並發時序造成的,不是誰選的。
* 所以中斷不是為了排斥衝突,是為了不讓引擎**替你**按下一個不可逆的按鈕。
  §4.1.2 同時要求揭露競爭 Commit 的 CAID,正是把診斷線索交還給觀測者。

⟹ **這條規則的正當範圍是「自動且不可逆」,不是「衝突」。** 顯式提交一個
`_|_` 不落在它的射程內——而那與 §2.1 的實測一致。

#### 2.1.2 兩個未經查證的機制(記錄以免再被引用)

同一份答覆另外提到兩個「若真想提交衝突歷史該怎麼做」的機制,**查證後兩個都不成立**:

* **「特權強制提交」**:稱需動用 `%privilege_token` 以 `#commit` 特權操作強制提交
  含 `_|_` 的 staged,並打上 `#privileged_commit` 標籤。
  **〔量〕假**——提交一個 `_|_` **不需要任何 grant**,實測兩次:
  `x: 1 & 2` 與 `k: { ok: 1, bad: 1 & 2 }` 皆直接 `Commit successful`。
  而 `#privileged_commit` 在 SPEC_08 §3.2.1 確實存在,但它治的是
  **`#incomplete`**,不是 `_|_`(見 `observation_result.md` §5)。
* **「局部衝突保留(非嚴格性)」**:此詞在規格全庫**查無**。
  **〔量〕**巢狀測試 `k: { ok: 1, bad: 1 & 2 }` 的 combo 確實沒崩,
  但原因是 `k.bad` **根本沒被求值**(存進去的是 Thunk)——是**惰性**,
  不是對衝突的容忍。順帶修正 §2.4:**固化發生在頂層欄位,不進入巢狀 combo。**
* 附帶:「邏輯奇點」一詞只出現在 `COSMOLOGY/05`(直覺層),不在規範性條文中。

### 2.2 五條語義不變性,一條都沒被違反

| SPEC_00 §5 | 提交一個衝突會不會違反 |
| :-- | :-- |
| 1 收斂決定論 | 不會。`⊥` 是決定性的,有 CAID |
| 2 資訊單調性 | 不會。`⊥` 是格的下界,走向它是單調的**極致** |
| 3 觀測純粹性 | 無關 |
| 4 複合封閉性 | 不會。`⊥` 是一個值 |
| 5 邊界一致性 | 唯一候選,而該節**全文只有一句「界定了宇宙的邏輯極限」,沒有內容** |

⟹ **禁止提交衝突不是從公設推出來的。**

### 2.3 鬆緊放反了

| | 裁定 | 出處 |
| :-- | :-- | :-- |
| **local 側** | 衝突 → **立即終止** | SPEC_10 §4.1.2(創世遺物,無理由) |
| **全球側** | 衝突 → **保留聯集,按需消融** | SPEC_13 §5.3(有理由,有機制) |

同一個現象(對一個名字有兩個不相容的主張)、兩個相反的答案、兩份文件、從不互相引用。

而 §5.3 的理由寫得比 jj 自己還清楚:

> **語義效果**:這實現了「基於需求的衝突解決」。**宇宙不需要知道哪個 `pkg` 是
> 「正確」的,它只需要知道哪個 `pkg` 能滿足當前的幾何約束。**

⟹ 「衝突固化到 LADD 上對別人好不好」的既有答案是 **好的**:生產者本來就沒有資訊
決定哪個對,而**消費者自己的約束會把它解掉**。強迫生產者先選,是要他回答一個他
答不了的問題。

**而用戶要的方向與現況相反**:local 該便宜隨便,published 該嚴。今天是 local 嚴、
全球鬆。

### 2.4 固化只固化「當下搆得到的」,而且從不回頭 —— pin 不傳播

**〔量〕同一支程式,拆檔方式不同,`c` 的命運不同:**

```
;; 情形 A:a/b/c 同一個檔
a: 1 / b: 2 / c: a + b
$ oo evolve a.n ; oo status  →  c: 3            ← evolve 當下就被固化

;; 情形 B:c 先,a 後
$ oo evolve s1.n   (b: 2 / c: a + b)
$ oo evolve s2.n   (a: 1)
$ oo status        →  c: Thunk { … }            ← 補上 a 之後也沒回頭固化
```

而在 Combo 封閉性底下,**拆檔應該是語義無關的**。

**〔量〕後果——pin 不傳播:**

```
$ oo evolve a.n                          (a:1 b:2 c:3)
$ oo evolve p.n --pin --grant pin        (a: 3)
$ oo status  →  a: 3   b: 2   c: 3       ← c 沒跟著動,期待是 5
```

反事實已做:**從未觀測過、直接 pin,`c` 仍是 3** ⟹ 固化點是 evolve,不是 observe。

而且**不可能靠再 evolve 修好**,因為 `3 & 5` 是 `_|_`。
⟹ **覆寫一個座標,等於必須覆寫每一個由它導出的座標。今天不會。**

### 2.5 其餘實測差異(用戶劇本 vs 現況)

| 用戶描述 | 實測 |
| :-- | :-- |
| `oo init` 帶 a.n | **沒有 `init`**,是 `oo evolve a.n` |
| `.oo` 之後獨立於 a.n | ✓ |
| `observe a` → `1`,`observe c` → `3` | ✓ 一字不差 |
| 寫 `a: 5` 得到 `_\|_` | **更嚴**:`Error: Evolution Conflict`,整個 evolve 被拒絕,宇宙原封不動 |
| 「特權模式」(覆寫而非交集) | ✓ **已存在**,拼法 `oo evolve p.n --pin --grant pin` |

**〔量〕非 REPL 那條路今天幾乎不存在**:`oo run --observe`(帶空檔)與 `oo eval`
都不讀 `.oo/staged`,一律回 `_`。能看見 staged 的只有 `oo status`,而它對未強制的
thunk 直接印 Rust `Debug`(既有掛帳)。

### 2.6 REAL_01 §2 控制面的 `nlang/commit` 與核心不合

| 面上寫的 | 核心的實情 |
| :-- | :-- |
| `"parents": ["hash:…"]` **陣列** | `Commit.parent: Option<ContentHash>` **單數**,結構上不可能有兩個 |
| `"sign": true` | `oo commit` 沒有 `--sign`;有的是 `oo refine` |
| `"author": "developer@example.com"` | 自由字串、不認證,而 `~/.oo/identity` 有真的 ed25519 |

第三列是 disc 025「兩層」的教科書例子:**commit 的作者住斷言層,而工作區裡明明有一個
自我認證層。**

### 2.7 Phase 44 的 `~%Diff`:形狀對,語義相反

`crates/interpreter/src/builtins/diff.rs`,25 個測試,**規格零字**。
問題是「§1.5.4 的重放機制是不是已經有一半」——**答案是否定的,而且比「不夠用」更糟。**

**〔量〕`patch` 是覆蓋,不是 meet:**

```
c: { x: 1 }   d: { x: 5 }
~%Diff./patch (c, ~%Diff./diff (c, d))   →   { x: 5 }      ;; meet 會是 _|_
```

原始碼對得上:`set_at_path` 走無條件 `insert_field`,葉節點直接 `return new_val`。

⟹ **`diff.patch` 在每個路徑上都是 pin 的語義** ⟹ **拿它當重放引擎,會把每一次
普通演化都靜默地變成一次 pin。** 而 pin 與普通演化的可分性(§1.7.3)正是那條日誌
存在的理由。它不是少功能,是**語義相反**。

它也**只讀 `path` 與 `to`,忽略 `from`**——沒有基底檢查。REDO 確實盲套 after-image,
但 DB 的 REDO 錨在 LSN 上;這裡**沒有錨**,套錯基底會靜默產生垃圾。

**三個缺陷:**

* **①〔量〕相同的輸入會報出差異。** `{x: 1|3}` 對 `{x: 1|3}` →
  `[{path:"x", from: 1|3, to: 1|3}]`。成因:`same_value` 只有
  `Top`/`Bottom`/`Atom`/`Combo` 四個分支,**`Union`/`Thunk`/`Blur`/`Range`/`Code`/
  `Ref`/`TopCaused` 全落到 `_ => false`**;加上巢狀欄位本來就存成未強制 thunk。
* **②〔讀〕所有 bottom 一律相等**:`(Bottom(_), Bottom(_)) => true` ⟹
  `#conflict` 與 `#fuel_exhausted` 對 diff 是同一個值。
  **與 `observation_result.md` 的主論旨正面衝突**(原因是第二條軸)。
* **③〔讀〕Atom 相等用 Debug 字串比**:`format!("{:?}", ka) == format!("{:?}", kb)`。
  與既有掛帳「`to_nlang` 用 `Debug` 印未強制 thunk」同一家族。

**可沿用的兩塊:**

* `is_compatible` 的 `deep_merge_values` **葉節點走 `oo.unify_internal`,那是真正的
  meet** ⟹「這兩個合得起來嗎」這個閘是誠實的,而那正是套用前該問的問題,
  **也正是 §1.7 判定 ⊑ 所需要的原語**。
* `/diff` 吐出的 `{path, from, to}` **`from` 是有的,只是 `patch` 不看** ⟹
  形狀對,修法局部:套用前比對 `from`、預設用 meet、**除非該筆條目標記為 pin**。

## 3. 已有的材料

`Commit` 的實際形狀〔讀 `crates/interpreter/src/value.rs:1765`〕:

```rust
pub struct Commit {
    pub parent: Option<ContentHash>,   // 單數 —— 鏈,不是 DAG
    pub root: ContentHash,
    pub meta: CommitMeta,
    pub kind: CommitKind,              // Standard | Refine | Pin | Squash
    pub refine_info: Option<RefineInfo>,
}
```

`.oo/` 只有單一 `HEAD` 檔,**沒有 `refs/`** ⟹ 沒有分支。

**全引擎唯一的「第二條邊」**:

```rust
/// Heads abandoned by `#rollback` and recorded on the *next* commit
pub abandoned: Option<Vec<String>>,
```

一個 commit 可以指向**多個**被放棄的 head——但本地 GC 弧已裁定**放棄邊不是根**。
⟹ n/ 確實長出了一種多親,而它被設計成**審計行裡的事實,不是值間關係**。

> **更正(2026-08-02):** 本文初稿把「放棄邊不是 GC 根 ⟹ 記下的 CAID 所指物件可被
> 回收」講成了懸空指標缺陷。**在 §1.5.6 的框架下它不是缺陷,是正確的**:
> 記下一個你放棄的 CAID 是**關於它的一句陳述**,不是**承諾供應它**。
> 與 REAL_02 §162 把「未持有 → `#not_found`(缺席)」和 conflict 分開,是同一個
> 形狀——誠實地說「我沒有」不等於「它壞了」。

**特權覆寫的歷史已經有一半**:`CommitKind::Pin` 與 `CommitMeta.privileged_effect`
都存在,SPEC_08 §6.2 也治了它。**缺的是把被覆寫掉的舊值留下來**,而不只是「這次
提交動用了特權」這個布林。

## 4. 開放問題

**不是十一件事,是三個弧加三件散的。**(2026-08-03 攤開依賴關係。)

### 4.1 弧 A ── ○ 層(必須一起做)

| | |
| :-- | :-- |
| **A1** | **○ 的樹住哪、怎麼耐久。** 今天 `.oo/staged` 只有一個,無序無樹;`.oo/` 只有單一 `HEAD`、無 `refs/`。 |
| **A2** | **`Commit.parent` 退場。** §1.7.7:**用「不再設定」而非「移除」,代價為零**,舊 CAID 全不動。 |
| **A3** | **日誌條目的正準形。** §1.5.4 已定兩件(REDO、必須帶視界參數);未定:操作詞彙表(`#pin` / `#evolve` / 還有什麼)、**是否記錄輸入來源**(狀態重算推得出「什麼變了」,推不出「哪個輸入造成的」)。 |
| **A4** | **`oo evolve <路徑>`。** 把**注入**與**固化**拆成兩個動作;今天 `oo evolve` 只吃檔案,`oo run --observe` 觀測但不記錄。**A3 的詞彙表取決於這一題。** |

**耦合理由:** A2 要 ○ 先存在(parent 是**搬家**不是刪除);A3 要 A4 先定操作有哪些;
commit 要把 ○ 歷史併進 ● ⟹ 需要 A3。**這一弧是本主題唯一動到已出貨耐久格式的**,
但 §1.7.7 之後它**不再是紀元級**。

### 4.2 弧 B ── 全球圖

| | |
| :-- | :-- |
| **B1** | **SPEC_10 §4.1.2 vs SPEC_13 §5.3,哪個對?**(傾向 §5.3) |
| **B2** | **鬆緊往哪修?** local 放鬆(像 jj)/ published 收緊(補「完整、可執行、多層檢查」)/ 兩邊都做。 |
| **B3** | **全球圖索引的是 commit CAID 還是 `root`?**(§1.7.6 ②——**這一題可能讓 A2 完全不必要**) |
| **B4** | **`DECLARED` 邊的信任根。** 誰的簽章算數?模式已存在(`affiliation_roots`)。 |

> **B1/B2 可以單獨先做,而且是十一條裡最便宜的一條**:純規格、不需要 ○、不需要
> 新格式,而且引擎今天已經不遵守 §4.1.2 ⟹ **改它是讓規格重新變成真的**,
> 與 §5.1.2「重放即複現之」那一弧同一個形狀。
> **也是唯一一條「修正既有假敘述」而非「往前加」的。**

### 4.3 弧 C ── 命名空間

**`~%Diff` → `~%Engine` 的搬家可以現在做**(零遷移成本,那些位置是空的);
但 `/checkout` `/rollback` `/log` 的**語義**要等弧 A。可沿用/不可沿用見 §2.7。

### 4.4 三件散的

* **`refine` 的「可執行 / 通過檢查」那一格要放什麼、誰跑?**(§1.2 的缺口)
* **REPL 的觀測 / 演化切換。**
* **pin 的傳播規則。** ⚠ **這一條可能在弧 A 之後自動消失**——若 §1.5.7 要求 ●
  全部固化,「固化到一半然後被 pin」這個狀態就不存在了。
  **先做 A 再看它還在不在,不要先寫規則。**

> **已結(不再是開放問題):**
> * *「操作日誌要不要?」* → 要。§1.5.4/§1.5.5 已給出形式(REDO log,住 `~%Version`,
>   斷言層),剩下的是正準形(上列 #6)。
> * *「savepoint 在 commit 之後存不存活?」* → 原則上不存活,但**可由 ● 記下的歷史
>   重建**。
