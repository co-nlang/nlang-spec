# n/ Language Specification - 態射與管道 (Morphism & Pipe)
## 1. 態射定義 (Logic)

態射（Morphism）是從輸入集合到輸出集合的映射。

*   **語法**：`/name: input -> output`
*   **同構與模式匹配**：
    當一個 Combo `{}` 被賦值給 Logic 欄位（以 `/` 開頭）時，引擎會將該 Combo 同構展開為一個「聯集（Union）」的態射集合。Combo 的 Key 是輸入約束，Value 是輸出結果。
    ```nlang
    /fib: {
        0: 0
        1: 1
        @int: /add (/fib ($ - 1)) (/fib ($ - 2))
    }
    ```

### 1.1 態射分派與特異性 (Dispatching & Specificity)

當一個態射被應用於輸入 $x$ 時，引擎執行以下 **分派演算法 (Dispatching Algorithm)**：

1.  **匹配過濾**：將 $x$ 與態射 Combo 中的所有 Key（輸入約束）進行合併嘗試。保留所有未產生 `_|_` 的分支。
2.  **特異性排序**：對所有匹配成功的分支，調用 **[SPEC_06](./SPEC_06_Unification_Logic.md) §1.5** 定義的「極小元素規則 (Minimal Element Rule)」進行篩選。
3.  **選擇與執行**：
    - **唯一匹配**：若存在唯一的極小元素（最特定匹配），則回傳其結果。
    - **多重匹配**：若存在多個互不可比（Incomparable）的極小元素，結果為這些分支結果的**格論聯集 (`|`)**。
    - **無匹配 (Empty Selection)**：若所有分支皆不匹配（交集皆為 `_|_`），則結果收斂為 **`_|_` (Bottom)**，標記 `%cause: #no_matching_branch`。
    - **優先序**：顯式的態射分支定義具有最高優先權，僅在所有顯式分支皆不匹配時，引擎才嘗試進行自動升寫（見 §3.4）。

#### 情境 A：層級匹配 (Poset Selection)
```nlang
/func: {
    1: 1
    @int: 0
}
;; 觀測 /func 1
;; 結果: 1 (因為 1 比 @int 更具體，它是唯一的極小元素)
```

#### 情境 B：不可比性與歧義 (Incomparability)
若兩個模式重疊但互不為子集，引擎會保留聯集結果，這被視為一種資訊不足的狀態。
```nlang
/func: {
    @{ @int & > 3 }: "A"
    @{ @int & < 7 }: "B"
}
;; 觀測 /func 5
;; 結果: "A" | "B" (因為 {>3} 與 {<7} 互不包含，皆為極小元素)
```

#### 情境 C：消除歧義 (Disambiguation)
開發者可以透過定義更精確的「交叉集合」來強制收斂至單一結果。
```nlang
/func: {
    @{ @int & > 3 }: "A"
    @{ @int & < 7 }: "B"
    @{ @int & > 3 & < 7 }: "C"
}
;; 觀測 /func 5
;; 結果: "C" (因為 {>3 & <7} 是其它所有匹配項的子集，成為唯一的極小元素)
```
這套機制確保了定義的合併（Merging）是穩定的，且不依賴程式碼的排列順序。

> [!TIP] **歧義管理與聯集態預警 (Ambiguity Management)**
>
> 雖然 `n/` 容許聯集態 (`A | B`) 作為有效的觀測結果，但過度的歧義會隨演化管道擴散並消耗大量的 `%max_branches` 配額。
> 1. **主動消除**：建議開發者在發現 `/logic` 產生多重極小元素時，定義更具體的交叉集合。
> 2. **靜態偵測**：IDE 或 `oo check` 應在偵測到態射定義中存在「重疊但互不為子集」的分支時發出警告。
> 3. **顯式收斂**：若聯集是預期的，但後續運算需要唯一值，可使用 `~%System./first` 或自定義篩選邏輯進行強行坍縮。

### 1.2 條件收斂語法糖 (Ternary Sugar `? :`)
為了簡化常見的二元分支觀測，`n/` 提供 `? :` 運算子作為模式匹配的縮寫。

*   **語法**：`Condition ? Success : Failure`
*   **展開規則**：
    ```nlang
    {
        #true: Success
        #false: Failure
    } Condition
    ```
*   **語義**：`Condition` 必須收斂至 `@bool`。若為 `#true` 則坍縮至第一分支，若為 `#false` 則坍縮至第二分支。

## 2. 應用與柯里化 (Application & Currying)
*   **Prefix 呼叫**：`add 2 4`（等同於 `(add 2) 4`）。
*   **Infix 呼叫**：`/` 開頭者支援 `2 /add 4`。
*   **結構化傳入**：支援 `add {x: 2, y: 4}`，會自動進行結構化統一（Structural Unification）。
*   **視界邊界保護 (`!field_start`)**：在進行連續的態射應用時，若遇到下一個欄位的定義起點（如 `key:`），解析器會自動終止當前運算。這使得 `n/` 不需要括號或逗號也能精準切分表達式與結構欄位（詳見 **[SPEC_14](./SPEC_14_Formal_Grammar.md)** §1 視界邊界保護）。

## 3. 演化管道 `|>` (The Pipe)
`|>` 是宇宙演化的核心，負責將靜態的 Combo 轉化為新的狀態快照。

*   **優先權**：**Level 13** (低於聯集 `|`，高於三元運算 `? :`)。
*   **結合律 (Associativity)**：**左結合 (Left-to-Right)**。多重管道 `a |> /f |> /g` 語義上等價於 `(a |> /f) |> /g`。
*   **聯集分布律 (Distributivity)**：管道演化對格論聯集具備分布性。
    - 公式：`(A | B) |> /f  ≡  (A |> /f) | (B |> /f)`。
    - 語義：當演化對象處於疊加態時，演化行為會平等地作用於所有分支。

### 3.1 演化形態
管道的右值（RHS）決定了演化的具體方式：

1.  **態射演化 (Morphism Pipe)**：`input |> /Logic`
    *   語法糖，等價於 `/Logic input`。支援鏈式呼叫：`data |> /f |> /g`。
2.  **結構演化 (Transformer Combo)**：`input |> { ~new: $.val + 1, ...$ }`
    *   最核心的用法。右側的 `{}` 是一個臨時轉換器，`$` 指向進入管道的完整結構。
3.  **原子演化 (Atomic Collapse)**：`input |> #success`
    *   強制將輸入與特定原子進行交集。若輸入不相容則收斂為 `_|_`。

### 3.2 上下文符號 `$` 與視界溯源 `^`
`$` 意象為觀測者在演化樹上的立足點。在 `n/` 中，視界是嵌套且具備穿透性的。

#### 3.2.1 符號全語境對照表
| 符號 | 語義 | 作用域 (Scope) |
| :--- | :--- | :--- |
| **`$`** | **當前輸入 (Context Anchor)** | 緊鄰左側管道 `|>` 的輸入值。在嵌套管道中，內層 `$` 會**遮蔽 (Shadowing)** 外層。 |
| **`^.`** | **當前視界** | 從當前 `$` 開始導航（阻斷外部提升）。 |
| **`^^.`** | **父層視界** | 穿透一層遮蔽，存取上一層管道的輸入。 |
| **`${}`** | **內插觀測** | 內插字串內部的路徑遵循當前最內層管道的導航規則。 |
| **`_.`** | **根宇宙** | 忽略所有嵌套，直接從系統根節點開始觀測。 |

#### 3.2.2 遮蔽與溯源綜合範例
```nlang
user: { name: "Alice", status: "Active" }

user |> {
    ;; Level 1: $ 指向 user
    greeting: "Hello, " + $.name
    
    action: "Login" |> {
        ;; Level 2: $ 被遮蔽，現在指向 "Login"
        ;; 內插字串內部的 $ 與外部一致，皆受最鄰近的管道支配
        msg: `Action: ${$}, User: ${^^.name}, Status: ${^^.status}`
        ;; 結果: "Action: Login, User: Alice, Status: Active"
        
        trace: {
            ;; Level 3: $ 指向 {} (空組合體)
            loc: "Level 3"
            p2: ^^.           ;; 指向 "Login" (Level 2)
            p1: ^^^.name      ;; 指向 "Alice" (Level 1)
            err: ^^^^.name    ;; 視界過度穿透 (Overshooting) -> _|_
        }
    }
}
```

#### 3.2.3 視界邊限與過度穿透 (Horizon Limits)
*   **遮蔽效應**：當新的 `|>` 建立時，舊的 `$` 進入「歷史視界」，只能透過 `^` 系列符號存取。
*   **過度穿透**：若 `^` 的數量超過嵌套層數（例如在只有兩層嵌套時使用 `^^^^.`），路徑將無法定位任何有效的演化輸入。
    *   **結果**：收斂為 `_|_` (Bottom)。
    *   **元資訊**：系統會自動標記 `%cause: #out_of_horizon`。其 `details` 應包含 `actual_depth` 與 `requested_depth` 以便診斷。
*   **內插一致性**：內插字串 `` `...` `` 僅僅是觀測的視窗，它**不具備**建立新視界的能力，因此內部的 `$` 語義與外部環境完全同步。

### 3.3 演化即提交 (Evolution as Commit)
每一次成功的管道演化在 `oo` 引擎中都被視為一個原子的狀態推進。
*   **原子性**：若管道內部的收斂結果為 `_|_`，則整個管道輸出 `_|_` 且不產生新的 Commit。
*   **不穩定狀態偵測**：利用子型別判定 `x <= _|_` 可以在管道內部建立邏輯防火牆，防止錯誤的演化被提交。

### 3.4 態射升寫與函子性 (Morphism Lifting & Functoriality)

當管道的輸入是一個容器（如 List、Tuple 或特定 Combo），而右側的態射並不直接接受
該容器型別時，引擎會嘗試 **將態射升寫（Lift）** ，使其作用於容器的內部元素。

這依賴於 Combo 的 `%fmap` 元資訊，它賦予了結構 **函子（Functor）** 的特性。

#### 觸發優先順序

引擎嚴格依照下列順序處理 `A |> /f`，**不跳步、不靜默**：

1.  **直接應用**：嘗試將 `A` 作為輸入直接收斂 `/f`。若成功，回傳結果。
2.  **邊界檢查**：若 `A` 為 **Cocoon `{{}}`** 且未顯式導出 `%fmap`，則立即終止，不進行自動升寫。
3.  **檢查 `%fmap`**：若非 Cocoon（或 Cocoon 已導出介面），檢查 `<A>.%fmap` 是否存在。
4.  **觀測升寫**：若 `%fmap` 存在，將呼叫轉化為 `<A>.%fmap ($, /f)` 並執行。
5.  **回傳 `_|_`**：若 `%fmap` 不存在，正常回傳衝突，`%cause: #conflict`。

**Cocoon 隔離原則 (Cocoon Isolation)**：
嚴禁 `%fmap` 自動穿透 Cocoon 邊界（例如 `{{ [1, 2, 3] }} |> /double` 會收斂為 `_|_`）。
- **理由**：Cocoon 象徵封閉且受保護的私有幾何。自動升寫會導致內部的複合結構被外部態射非對稱地觀測，破壞了封閉性保證。
- **繞過方式**：若需對內含物進行升寫，必須先透過 `...` 展開（Unbox）該內容至開放的 Combo 中。

步驟 1 失敗不等於升寫一定成功——升寫後仍可能因為容器元素不符合 `/f` 的約束而產生
`_|_`。這確保型別錯誤永遠不會被靜默吞掉。

#### 範例：List 升寫

```nlang
/double: x@int -> x * 2

[1, 2, 3] |> /double
;; 步驟 1：[1,2,3] 不符合 @int → 直接應用失敗
;; 步驟 2：<[1,2,3]>.%fmap 存在（List 是 Functor）
;; 步驟 3：升寫，等價於 [1 |> /double, 2 |> /double, 3 |> /double]
;; 結果: [2, 4, 6]
```

#### 巢狀容器與遞迴穿透 (Recursive Penetration)

`|>` 操作符具備**自動遞迴升寫**能力。當處理深層嵌套容器（如 `[[[1, 2]]]`）時，引擎遵循以下邏輯：

1.  **逐層觀測**：若當前容器層級不符合態射 `/f` 的約束，且具備 `%fmap`，則進行升寫並對內部元素重複此過程。
2.  **終止點判定**：遞迴在滿足以下任一條件時終止：
    - **匹配成功**：當前層級（可能是內部元素）符合 `/f` 的型別約束。
    - **觸及原子**：抵達無法進一步分解的原子值。
    - **燃料耗盡**：遞迴深度或計算量觸及視界邊限。
3.  **語義範例**：
    ```nlang
    /double: x@int -> x * 2
    [[[1, 2]]] |> /double
    ;; 引擎自動向下穿透三層 List，最終作用於 int 原子
    ;; 結果: [[[2, 4]]]
    ```

*   **資源消耗與深度限制**：
    為了防止惡意或意外的無限深層結構導致資源枯竭，引擎必須實作 **「預設觀測半徑 (Default Observation Radius)」**。
    - **`%max_lifting_depth`**：超過此深度的自動升寫將被截斷，並坍縮為 `#incomplete` (%cause: #max_lifting_exceeded)。
    - 每一次升寫與態射應用均會消耗全域觀測資源（`%fuel` 與 `%timeout`）。
    - **級聯坍縮與立即終止 (Cascading Collapse)**：管道演化遵循**強原子性原則**。在 `A |> B |> C` 鏈中，若任何中間步驟產生了不可恢復的 `_|_`，後續的所有步驟將被**立即中斷**。
    - **原理**：因為後續步驟的輸入視界 $ 已經坍縮為空集合，根據格論，空集合的任何變換結果仍為空集合。
    - **傳播**：最終結果固化為 `_|_`（含完整的 `%cause` 鏈）。這確保了錯誤不會在不穩定的狀態下繼續「演化」，從而保護了宇宙因果的清晰度。
*   **局部防火牆**：可利用 `x <= _|_` 在升寫態射內部攔截錯誤，將特定的衝突轉換為可接受的狀態（如返回預設值），從而防止單一元素的衝突中斷整個管道。


### 3.5 優先權與結合律 (Precedence & Ambiguity)

在 `n/` 的運算子層級中，管道演化（`|>`）的優先權高於態射定義（`->`）。這是一項刻意的設計，旨在確保態射體內部的演化邏輯不需要額外的括號。

#### 情境 A：態射內的演化 (預設行為)
```nlang
/f: x -> x |> /g    ;; 解析為 x -> (x |> /g)
```
這是最常見的模式，態射體自然地包含了其後的演化鏈。

#### 情境 B：演化中的匿名態射 (需明確界定)
若欲將演化對象傳入一個即時定義的態射，由於 `|>` 優先權較高，必須使用括號：
```nlang
data |> (x -> x + 1)    ;; 正確：將 data 應用於匿名態射
```
*註：在 `n/` 的最佳實踐中，更推薦使用 **結構演化 `{}`**（見 §3.1）來替代裸的匿名態射，因為其具備更清晰的視界語義與結構化能力。*

## 4. 邏輯即組合 (Logic as Combo)
由於「萬物皆 Combo」，所有的 Logic (態射) 皆可觀測為一個特殊的 Combo 結構
(詳見 **[SPEC_03](./SPEC_03_Combo_System.md)** 與 **[SPEC_05](./SPEC_05_The_Trinity_Isomorphism.md)**)。

### 4.1 高階邏輯 (Higher-order Logic)
態射可以作為另一個態射的輸入或輸出。傳遞時使用 **結構態引用 (`</f>`)**。
```nlang
/apply: (f: @morphism, x) -> f x
```
當 `apply` 進行 Unification 時，它會驗證傳入的 `f` 是否具備態射特質。

### 4.2 匿名態射語義 (Anonymous Morphism Semantics)

匿名態射 `(x -> x + 1)` 的完整語義定義：

#### 定義 1：匿名態射的本體
匿名態射 `(param -> body)` 等價於一個未綁定到路徑的 Logic Combo：
```nlang
(x -> x + 1)  ≡  { %kind: #logic, %morphism: #true, %rules: { x: x + 1 } }
```

#### 定義 2：匿名態射的應用
匿名態射可直接應用於參數：
```nlang
(x -> x + 1) 5  ;; 結果：6
```

#### 定義 3：匿名態射的賦值
匿名態射可賦值給欄位：
```nlang
f: (x -> x + 1)
f 5  ;; 結果：6
```

#### 定義 4：匿名態射的分支與聯集
匿名態射可透過 `|` 組合多個分支，實作模式匹配。
```nlang
(x @int -> x + 1 | x @str -> x + "!") 5     ;; 結果：6
(x @int -> x + 1 | x @str -> x + "!") "hi"  ;; 結果："hi!"
```
*   **語義**：`(A -> B | C -> D)` 是 **「態射聯集 (Morphism Union)」** 的語法糖，等價於兩個 Logic Combo 的格論聯集：`(A -> B) | (C -> D)`。
*   **分派規則**：引擎在應用時，會同時觀測所有分支，並根據「最特定匹配原則 (SPEC_06)」選擇最符合輸入條件的分支。若多個分支同時匹配且互不可比，則結果保持為聯集態。

#### 定義 5：匿名態射的柯里化
多參數匿名態射自動柯里化：
```nlang
(x y -> x + y) 2 3        ;; 結果：5
((x y -> x + y) 2) 3      ;; 等價於上一行
```

#### 定義 6：動態型別推導 (Dynamic Type Inference)
若匿名態射未顯式標註輸入型別（如 `x -> x + 1`），其輸入型別將由實際調用時傳入的參數動態決定。
*   **聯集型別態射 (Union Type Morphism)**：若該態射被多次以不同型別呼叫，在靜態分析與型別推導的視角下，它實質上等價於一個處理聯集型別的態射（類似泛型實例化）。

#### 限制
匿名態射**不具備**以下特性：
1. **無路徑名稱**：無法透過路徑引用自身（遞迴需使用具名態射）
2. **無 `%compat`**：不支援相容性宣告
3. **無 `%migration`**：不支援遷移態射

**建議實踐**：
- 簡單變換使用匿名態射（如管道中的臨時變換）
- 複雜邏輯或遞迴定義使用具名態射

### 4.3 態射合併的語義與衝突 (Morphism Merges & Conflict)

根據 **[SPEC_05: 三位一體同構](./SPEC_05_The_Trinity_Isomorphism.md)**，態射（Logic）本質上亦是 Combo，因此必須遵循格論的交集合併（`&`）運算。

#### 定義 1：合併公式
當兩個態射 $f$ 與 $g$ 進行合併（ $f \sqcap g$ ）時，其語義是尋找一個同時滿足兩者映射規則的新態射。
*   **公式**：對於任何輸入 $x$， $(f \sqcap g)(x) \equiv f(x) \sqcap g(x)$ 。
*   **本質**：態射合併是對輸出結果施加的 **「雙重約束」**。

#### 定義 2：對偶身份與部分應用
當一個態射被部分應用（柯里化）時，它在格論中被視為一個**已部分坍縮的幾何物件**。
*   **Logic 性質**：它依然具備可觀測性，等待下一個參數。
*   **Data 性質**：它可以與 Metadata 合併，成為一個「攜帶狀態的邏輯體」。
    ```nlang
    ~f: /add 1                      ;; 部分應用
    ~meta: { name: "incrementer" }  ;; 附加數據
    ~rich_f: ~f & ~meta             ;; 合併
    
    ~rich_f 5                       ;; 結果：6 (Logic 屬性)
    ~rich_f.name                    ;; 結果："incrementer" (Data 屬性)
    ```

#### 定義 3：邏輯衝突與精煉案例
若對於相同的輸入 $x$， $f(x)$ 與 $g(x)$ 的交集為空集合，則該合併態射在 $x$ 上的觀測結果立即坍縮為 **`_|_` (Bottom)**。

*   **案例 A：數值衝突 (Value Conflict)**
    ```nlang
    /f: x -> 1
    /g: x -> 2
    /h: /f & /g
    ;; 觀測 /h 10  -> 結果: 1 & 2 -> _|_ (%cause: #conflict)
    ```
*   **案例 B：型別精煉 (Type Refinement)**
    ```nlang
    /check_int: x -> @int
    /check_pos: x -> @{ $ & > 0 }
    /is_pos_int: /check_int & /check_pos
    ;; 觀測 /is_pos_int 5 -> 結果: 5 (滿足雙重約束)
    ```

#### 邊界案例：原子同構展開
根據 **[SPEC_06](./SPEC_06_Unification_Logic.md)**，態射與原子的合併（如 `/f & 5`）會產生一個既是態射又是數值的複合體。這在實作帶有標籤的邏輯或常數態射時非常有用。
