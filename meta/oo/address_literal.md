# 位址字面 —— 弧 D 第一項的提案

> 2026-08-19。`commit.md` §4.4 弧 D 的第 1 項。
> **§3 的拼法仍是提案；§4 的四個子問題用戶已裁（2026-08-19）。**
> 承重理由見 `commit.md` §1.9：**標準根之所以龐大，是因為語言沒有位址字面。**

---

## 0. 這一項要解什麼

〔量，v0.26.1〕語言裡**沒有任何寫法能指名一個位址**：

| 寫法 | 結果 |
| :--- | :--- |
| `@"hash:…"` / `<<hash:…>>` / `~"hash:…"` | parse error |
| `"hash:…"` | 只是字串 |
| `<</f>>` | 有效，但引用的是**名字**（回傳 `%code`／`%closure`） |
| `~%Discovery./fetch("hash:…")` | **取得到值**，但見 §1 |

⟹ 每一個庫只能靠名字取得；名字只能綁在唯一永遠都在的地方；**東西因此被吸回根裡**。

---

## 1. 為什麼不是「已經有 `fetch` 了」

`~%Discovery./fetch(caid).field` 今天就能組合〔量〕。缺的不是組合能力，是**三件別的事**：

1.  **靜態可見。** 位址藏在一個字串引數裡，**要跑起來才知道這個提交依賴誰**。
    而預取、`§6.8` 的「指名依賴」、以及認不得時的**具名拒絕**，三者都需要
    **不執行就掃得到**。
2.  **效果。**〔量〕經 `fetch` 取得之物使外層帶 `%effect: #io`，而效果自 v0.26.0
    起進位址 ⟹ **匯入會改變匯入者的身分**。而位址→值是確定性的
    （同一個 CAID 恆得同一個值），`#io` 這個標註本身可能就是錯的。
3.  **先有雞。** `fetch` 自己是個名字，得先有東西綁住它。

> **既有判例正是「宣告依賴」而非「呼叫」**：標準根今天由根裡一個
> **寫進雜湊的欄位**指名（`~%__nlang_system_digest`），REAL_03 §6.8.1 稱之為
> 「一個指名依賴的欄位」。**位址字面是把那個機制從引擎專用推廣到使用者可寫。**

## 2. 判準（全部由量測或既有裁定導出，非偏好）

| # | 判準 | 出處 |
| :-- | :--- | :--- |
| C1 | **必須能被投影**：`<位址>.Math./add` | SYNTAX_05 §50「交集即匯入」——匯入是**交集進路徑欄位**，故位址必須能當路徑的頭 |
| C2 | **必須靜態可見**，不執行就掃得到 | §1.1 |
| C3 | **必須有引號或界定符** | 〔量〕v2 CAID 長 190 字元，含 `+ / : _`；`/` 與 `:` 皆為運算子 ⟹ **裸寫不可能** |
| C4 | **不得是 `<< >>` 的變體** | `<< >>` 已佔住「以名字引用」；一個概念一種正準拼法 |
| C5 | **不得動前綴本體論** | 〔讀〕SYNTAX_05 的 `@ / ~ ~@ ~/ % ~%` 是「維度 × 隱藏」的二維格，**已滿**；而位址不是一個面向 |

**C5 的正面版本**：位址回答的是**「從哪裡起算」**，那是 **anchor** 的位置，不是 prefix 的。
〔讀〕`n.pest:186` `anchored_path = { (anchor_root | anchor_parent) ~ path_segments? }`；
`anchor_root = "_."`、`anchor_parent = "^"+ ~ "."`。**anchor 家族只有兩個成員，且都是
「符號 ＋ 點」。**

## 3. 提案：參數化的根 anchor

> **⚠ 2026-08-19 更新：`"…"` 的形式已因 `quoted_names.md` §4.1 出局。**
> Q1 裁「引號內即純粹的名字」⟹ `"…"` 專指名字，而位址不是名字 ⟹
> `_"…"` 是把一個記法用在兩個概念上。**候選改為 `_{…}`**，其兩個量到的代價
> 見 §7.2，仍待裁。**以下 §3 的論證（anchor 而非 prefix）不受影響**——
> 換的是界定符，不是位置。

```nlang
_"2da5b71371649291cfa5dc5d0cd019464d248e98645b3901938e1c08d2172c2c".Math./add
```

**語義一句話**：`_.` 是「**這個**宇宙的根」；`_"位址".` 是「**那個**宇宙的根」。

文法上是 `anchored_path` 多一個替代分支，**不新增運算子、不動前綴格、不動優先序**：

```pest
anchor_addr = ${ "_" ~ "\"" ~ caid_body ~ "\"" ~ "." }
anchored_path = { (anchor_root | anchor_parent | anchor_addr) ~ path_segments? }
```

### 3.1 為什麼是這個

*   **C1** ✓ 它在 anchor 的位置，`path_segments` 本來就跟在後面。
*   **C2** ✓ 位址是 AST 節點不是字串引數，`grep` 得到、掃描得到、預取得到。
*   **C3** ✓ 有引號。
*   **C4** ✓ 與 `<< >>` 無關。
*   **C5** ✓ 動的是 anchor 家族，前綴本體論一個字不改。
*   **語義精確**：`_` 在這個語言裡已經是「宇宙／Top」。`_"addr"` 讀作
    「位於該位址的那個宇宙」——**不是新概念，是既有概念的參數化**。

### 3.2 落選者與落選理由

| 候選 | 落選理由 |
| :--- | :--- |
| `@"…"` | `@` 是 Type 維度。位址不是型別約束（C5） |
| `#"…"` | `#` 是 tag。tag 是**符號**，位址不是（C5） |
| `%"…"` | 最接近的落選者。`%id` 確實回傳位址 ⟹ 讀作它的逆很自然。但 `%` 是 **Meta 面向**，而 `_"…"` 之物是**值本身**不是關於值的元資訊（C5）。**若用戶偏好此形，理由成立，只是把 `%` 的意義擴一格** |
| `<<"…">>` | 直接違反 C4 |
| 裸 `hash:sha256:…` | 違反 C3〔量〕 |
| 只用 `~%Engine./at(caid)` | 違反 C2；且見 §1.3 先有雞 |

## 4. 四個子問題（**用戶已裁，2026-08-19**）

### 4.1 ✅ 只寫摘要，**但演算法必須留**

**裁定（用戶）**：留 digest 即可；sketch 本來就只給 `<=` 用，**不抗碰撞**。

〔量〕證據支持刪 sketch 與版本：一個 **v2** 物件以 `v1:<digest>` 定址**取得到同一份
內容**；而物件在磁碟上的路徑是 `objects/sha256/<2>/<62>`——**masa_ref 與 sketch
都不在路徑裡**。⟹ **摘要單獨即可定位**，版本前綴對取回不承重。

**但用戶追問的「sha256 要不要留」——必須留，而且理由不是風格。**

*   〔讀〕REAL_03 §30：`<algo> ::= "blake3" | "sha256" | <ext_algo>`
    ——**演算法自始就不是固定的**，blake3 是對等項且留了擴充位。
*   **BLAKE3 的預設輸出也是 256 bit ＝ 64 個 hex**，與 sha256 逐字元同形
    ⟹ **裸摘要在 blake3 落地的那一刻起就是歧義的**。
*   〔讀〕REAL_03 §437 已經把這件事寫成通則：物件路徑裡的 `sha256/` 這一層
    **本身就是容器對演算法的宣告**。⟹ **這個系統從不讓演算法隱含**，
    字面帶著它是與既有機制一致，不是額外負擔。
*   〔量〕blake3 在引擎裡**尚未實作** ⟹ 歧義是未來的，不是現在的。
    **但字面一旦定版就是相容性承諾**，補救的代價遠高於現在多寫七個字元。

**⟹ 正準形**：

```nlang
_"sha256:426d518693561d9b17814ea8e2818ea7a8a12b4c9e87befdf7f54be1cef5f92b".Math./add
```

**C3（必須有引號）在短形下仍然成立**：`sha256:<hex>` 的唯一非英數字元是 `:`，
而 `:` 是欄位分隔符 ⟹ 裸寫的 `sha256:abc.Math` 會被讀成一個欄位定義。

### 4.2 ✅ 缺名字＝自動補並記錄；缺**位址**＝具名拒絕

**裁定（用戶）**：應按使用者意圖；具名拒絕過嚴，會逼使用者不斷走特權模式重鑄歷史。
自然的落點是**自動補歷史**。

**這與 §6.8 第三條 MUST 不衝突——兩者管的不是同一件事。** 該條逐字為：
「引擎讀到自己**不具備的標準根摘要**時，必須拒絕開啟該根……不得以自身的標準根
代入後繼續。」**它管的是解不開的「位址」，不是沒綁定的「名字」。**

| 情形 | 答覆 | 理由 |
| :--- | :--- | :--- |
| **名字未綁定**（`~%Math` 不在第二個提交裡） | **自動補進第二個提交並記錄** | 歷史裡有痕 ⟹ 位址仍由歷史決定、仍可重現。**不是靜默替代** |
| **位址取不到**（`_"sha256:…"` 不具備） | **具名拒絕** | 一個具體位址**在定義上無可代入**；代入即 §6.8 所防的「兩個宇宙、同一個位址」 |

**⟹ 特權模式的疑慮不成立**：需要重鑄歷史的只有第二列，而第二列是使用者自己
寫下一個具體位址、那個位址取不到——那時候該停下的理由與特權無關。

**未定（留給弧 D 第 2 項）**：自動補**發生在哪一層**（解析／演化／提交），
以及補進去的那一筆**是否需要使用者同意**。

### 4.3 ✅ 純；可得性不是效果

**裁定（用戶）**：傾向走「純」；拆開或許是對的方向，**甚至直接記在不同的路徑上**。

拆開的形狀：

| | 是什麼 | 住哪 |
| :--- | :--- | :--- |
| **確定性** | 同一個位址恆得同一個值 | **值本身；`_"…"` 為純** |
| **可得性** | 這個倉此刻有沒有那些位元組 | **不是值的性質**——是倉的性質 |

⟹ 取不到走 `⊥ #missing_key` 那條路，**不是 `%effect` 那條路**。

> **用戶「記在不同的路徑上」這個直覺與這棟樓的第 7 句同形**：
> 特權邊之所以必須留審計痕，是因為**「值不會記得」**（`commit.md` §1.7.3）。
> 可得性同樣是值記不住的東西——它隨倉而變，隨時間而變。
> ⟹ **它的家是審計行，不是值。** 這與 disc 027 的結論（撤回是審計行裡的事實，
> 不是值間關係）是同一個形狀的第三例。

### 4.4 ✅ 只在 RHS

**裁定（用戶）**：合理。

〔讀〕`n.pest:37` 註明 LHS 只收 `_.`；`^` 已於 SYNTAX_03 §4.4 Q3 廢除（caret handover）。
`_"addr"` 比照——**定義的左手邊是這個宇宙的座標，不是別人的**。

## 7. 拼法未定（用戶 2026-08-19 提出兩點）

### 7.1 前置項：`"…"` 該不該是「純粹的名字」——**原則已在規格裡**

**用戶的概念**：`"…"` 包住的是**純粹的名字**，不是用來拆分欄位屬性的前綴符號
⟹ `"~123"`（名字就叫 `~123`）與 `~"123"`（local `~`，名字叫 `123`）不同。

**挖 SYNTAX_ 章節的結果：原則已經是規範性的**——SYNTAX_03 §106 #8
「名字裡真的有點」必須用 `"a.b"`，**前者單一座標、後者巢狀**。
⟹ **引號內的字元屬於名字，不是結構分隔符。** 用戶要的區分就是這條原則
在前綴 sigil 上的同一句話。

〔量〕引擎對 `.` 與 `+` 兌現了它（`"a.b"`／`"a+b"` 皆為字面名），
**對前綴沒有**（`"~abc"` 落到 local 軸）。

**全部細節、三個缺陷與三題待裁見 `quoted_names.md`。**
（先前此處寫「讀取端是 parse error」為**判斷錯誤**：`x["a b"]` 有效，
中括號才是規格認可的讀取形式。）

### 7.2 `_{…}`：位置是空的，但有兩個量到的代價

**用戶的另一個想法**：既然 `@{}`、`#{}` 早就存在，`_{}` 其實也行，
而且**繞開 `"…"` 的複雜性**。

〔量〕位置確實是空的——`_{a: 1}` 今天解析得過但回 `_`（`_` 與 combo 並置）。
但有兩件事必須先知道：

1.  **空白會變成有意義，而且是靜默的。**〔量〕`@{1}` 有效而 `@ {1}` 是
    **parse error**——既有複合 sigil 的空白敏感**吵著失敗**。
    但 `_ {a: 1}` 今天**合法**（回 `_`）⟹ `_{` 會是第一個
    **加空白就靜默變成另一個意思**的複合 sigil。
2.  **`:` 在大括號裡已經有一個競爭讀法。**〔量〕`_{sha256:426d}` 今天
    **就是被讀成一個欄位為 `sha256` 的 combo**。⟹ `_{sha256:<hex>}` 對解析器
    不歧義（若定為 compound-atomic），但**對人眼是假的 combo**。

| | `_"sha256:…"` | `_{sha256:…}` |
| :--- | :--- | :--- |
| 內容詞法上惰性 | ✓ | 需定為 compound-atomic |
| 與 §7.1 的「純名字」規則 | **衝突**（`"…"` 將專指名字，位址不是名字） | ✓ 不衝突 |
| 空白加了會怎樣 | 同樣靜默（`_ "…"` 亦合法） | 同樣靜默 |
| `:` 的競爭讀法 | 無 | **有**〔量〕 |
| 與既有家族的一致性 | anchor 家族（`_.` `^.`）皆為「符號＋點」 | 複合 sigil 家族（`@{` `#{` `${`） |

**⟹ 未裁。** 兩者的取捨取決於 §7.1 先怎麼裁：**若 `"…"` 專指純名字，
`_"…"` 就是把一個記法用在兩個概念上**，那條線在本專案是紅線（一個概念一種正準拼法）。

### 7.2.1 並置的三分規則 —— 量測（2026-08-21），**規格無條文**

裁 §7.2 之前先量清楚 `_ {…}` 今天到底是什麼。**它不是 meet**：

```
_ & {a: 1}   →  { a: 1 }      ← _ 是 meet 的單位元（Top）
_ {a: 1}     →  _
```

〔量，v0.28.0〕整張並置表**不對稱**：

| 式 | 結果 |
| :--- | :--- |
| `_ {a: 1}` | **`_`** |
| `{a: 1} _` | `⊥ #conflict` |
| `1 {a: 1}` ／ `{a: 1} {b: 2}` ／ `{a: 1} 5` ／ `1 2` | `⊥ #conflict` |

⟹ 並置就是施用，而規則是三分的：**運算元是態射 ⟹ 施用之；確定不是態射 ⟹ `⊥ #conflict`；
未知 ⟹ `_`**。第三列在格上是對的（單調：`_` 收窄成真態射得真答案，收窄成非態射得 ⊥
⟹ 此刻能給的最不具資訊的答案就是 `_`），而且是**整張表唯一不是 ⊥ 的一列**。

**這一列沒有規格條文。**〔量〕`SPEC_07` §244 只寫了 `%fmap` 不存在時回 `⊥ #conflict`；
「運算元是未知」在核心規格中找不到。〔量〕conformance **0 個向量**施用 `_`
（全部 `_` 出現處皆為 `_ }`／`_ |`／`_ &`）。

**但它不是「沒人想到」——是有人用了三次沒寫下來**：

| 位置 | 逐字 |
| :--- | :--- |
| `flat_map_test.rs:102` | `apply_morphism(Top, 1) = Top`，`:103` 逐字「This test verifies Top identity behavior」 |
| `functor_test.rs:425` | 「Use Top as identity — `apply_morphism(Top, 5) = Top`」 |
| `functor_test.rs:435` | 「With Top predicate: `apply_morphism(Top, 5) = Top`」 |

三處都**用**它而**未斷言**它 ⟹ 若哪天它改了，這三支會紅在別的理由上，
而沒有人會知道一條性質退休了（與 v0.27.0 那條「改測試的輸入以迴避退休的性質」同族）。

**這對 §7.2 的裁定是承重的**：若採「收（不挖例外）」，`_ {addr}.Math` 回 `_` 的正當性
**完全靠這一列**。第二個實作若回 `⊥ #conflict`，它通得過現有全部向量，
而同一份源碼在兩個實作上得到兩種答案——與 Q-033 D1「一個名字兩種解析」同形。

⟹ **建議與 §7.2 同批處理，不另開弧**：一條 SPEC 條文（三分表）＋至少一個 L1 向量。

> 若不可接受，需要的是**第三個候選**，而不是回到 `_"…"`。

**先裁 §7.1（`"…"` 是不是純名字），再裁拼法。** 理由：§7.1 的答案直接決定
`_"…"` 是不是合法的候選，而 §7.1 本身**還有一個實作缺陷要修**（印不回去、
`"~abc"` 落到 local 軸），那個缺陷與拼法之爭無關、值得獨立處理。

## 8. 承重前提被量測推翻（2026-08-21）：`_: X` 今天是惰性的

弧 D 第 2 項（`init` 的形狀）討論到「複製的時機點」時，撞到一件比 `init` 更前面的事。

### 8.1 量測

〔量 2026-08-21，v0.28.0 真二進位，全部經 `oo run FILE --observe out`〕

| 源碼 | 結果 |
| :--- | :--- |
| 全新宇宙、無任何 import，`~%Math./add (1,2)` | **`3`** |
| 全新宇宙，裸名 `add (1,2)` | `_` |
| `_: ~%Math` 之後，`add (1,2)` | **`_`** |
| `_: ~%Math` 之後，`/add`／`_.add`／`_./add`／`sub`／`/sub` | **全部 `_`** |
| `_: ~%Math` 之後，`out: _` | **`_`** |
| `_: { k: 7 }` 之後，`k`（頂層） | **`_`** |
| `_: { k: 7 }` 之後，`_.k` | **`_`** |
| `c: { _: { k: 7 }, r: k }` 之後，`c.r`（巢狀） | **`_`** |
| 對照：`k: 7` 之後 `k` | `7` |

**而它照抄不誤**〔量，使用者根物件大小〕：`_: ~%Math` → **11,625 B**（對照空根 287 B），
且 `x: ~%Math`（普通欄位）**同樣 11,625 B，一個位元組不差**。

### 8.2 三句結論

1.  **能力一直都在。** 標準根是根**指名的依賴**，`~%Math./add` 從第一秒就通。
    ⟹ `_: ~%Math` **從來不是取得**。
2.  **`_: X` 今天什麼都沒有做。** 它想做的是「把 X 放進回退格，讓裸名解析得到」，
    而那件事沒有實作——對標準庫與使用者自訂皆然，頂層與巢狀皆然。
3.  **`_` 在複製這件事上完全不特別**（與 `x:` 逐位元組相同）；
    它特別的地方在 `lib.rs:3110` 的回退查找，而〔量〕**那條回退不在名字解析路徑上**。

⟹ **「交集即匯入」這個正典寫法，今天是一個純粹的複製動作，
複製完之後沒有任何一條路徑因此變得可達。**

### 8.3 這推翻了什麼

*   **`commit.md` §1.9 與 `WORK_QUEUE` §6 該列所記的用戶口述來歷**
    ——「不做任何預設態射、全部放到 `~%` 底下，理由是交集進路徑欄位本身就是
    `import` 的實踐（`_: ~%Math`）」——**其後半今天不成立**。
    前半（能力放在 `~%` 底下）成立且已由標準根依賴兌現。
*   **弧 D §4.2 的 A／B 兩條路同時塌掉一半**：A（引擎在 `init` 時塞進預期之物）
    想避免的「引擎替你決定」今天已是既成事實；B（等使用者 `_: ~%Math` 才引入）
    **今天沒有東西可引入**。兩者都在描述一個不存在的機制。

### 8.4 順序因此要倒過來 ⟶ **✅ 已答（2026-08-23，O72）：回退格不成立**

> **本節提的那個問題已經裁了，答案是「否」。** `_: X` 不是掛載點；匯入走 `...`
> （打開封閉之後的 meet，可交換、不覆寫、碰撞即 ⊥）。**O69 的核心一句因此撤回**，
> 弧 D 第 2 項解散。全文見 `STATUS.md` **O72** 與 `d2_what_underscore_means_brief.md` §7。
> 下面保留原文作為當時的推理紀錄。


**先裁「回退格該不該真的存在」**——即 `_: X` 是不是「解析不到的名字掉進 X」。

*   **若是**：`_` 才真的是 combo tree 裡最特別的一格，而「觀測時機」才有東西可談
    ——**查不到才往 `_` 找，找的時候才解引用**。配合引用式 import（O68／Q1），
    `_` 裡放的是一個位址，**複製的時機點問題整個消失**，因為沒有複製。
*   **若否**：`_: X` 應降格或除名——它現在是一個抄一萬多位元組然後什麼都不做的寫法。

裁完回退格，`init` 的答案幾乎是掉出來的：那時要塞的是幾十個位元組，
「要不要獨立一個 commit」只剩一個純粹的目的——**要不要讓那一步可以被替換**。

### 8.5 順帶：SYNTAX_05 §3 的範例自己跑不動

〔量〕該節逐字範例

```nlang
_: ~%Cond
total: ~%Math./sum xs
```

除了 `_: ~%Cond` 惰性之外，**`~%Math./sum` 不存在**——
`⊥ #missing_key`「Key '/sum' missing in closed Cocoon」，`/sum` 住在 `~%List`（〔量〕`~%List./sum [1,2,3]` → `6`）。
**這是與回退格無關的第二個缺口**，另記。

## 9. D-2 開單前的那一項量測（2026-08-23）＝ 讀相容是空集合，但問題換了一個

`WORK_QUEUE` §3 記著 D-2 尚缺一項量測：**「既有那些存了拷貝的宇宙，在 mount
語義之下會怎樣——那份拷貝今天是惰性的，改了之後會不會突然開始做事。」**
本節是該項量測。**答案分兩半，而第二半比第一半重。**

### 9.1 第一半：在野普查 ＝ 空集合

| 量 | 結果 |
| :--- | ---: |
| 超專案 `.n` 檔中以 `_` 為鍵者 | **0**／207 |
| 全機 `.oo/` 目錄（有 `objects/` 者） | 19,823 |
| 全機 CAS 物件（逐一 JSON 解析，0 個解不開） | 7,358 |
| **任意深度**含 `_` 鍵（`data` 或 `rules`）的物件 | **1** |

而那 1 個是本次量測前 90 秒自己建出來的（scratchpad `d2/u1`）。

⟹ **D-2 的讀相容破壞面是空集合。** 佇列上原記的那個顧慮可以劃掉：
沒有任何既存宇宙會因為 `_: X` 改成 mount 而「突然開始做事」，因為**沒有宇宙存過它**。

**成本側順帶複驗 O68**（三個真宇宙，各 evolve＋commit）：

| 宇宙 | objects 合計 |
| :--- | ---: |
| `_: ~%Math` ＋ `k: 7` | 148,333 B |
| `z: ~%Math` ＋ `k: 7` | 148,326 B |
| `k: 7` | 136,936 B |

三者的標準根物件（136,268 B）**逐位元組相同**（CAS 去重有效）；`_` 與 `z` 只差 **7 B**
⟹ 複驗「`_` 在複製上完全不特別」，且 ~11.4 KB 的拷貝在根物件**內部**，去重救不到。

### 9.2 第二半：`_:` 今天已經有一個能用的意思，而且不是 §8 量到的那個

〔讀 `lib.rs:3108–3113`〕把 combo 施用到引數時：

```rust
c.get_field(&ks).or_else(|| c.get_field("it")).or_else(|| c.get_field("_"))
```

〔量 v0.30.0〕`({ a: 1, b: 2, _: 99 }) "zzz"` → **99**；
無 `_` 的對照組 → `⊥ #conflict`；`it` 與 `_` 並存時 **`it` 贏**。

**§8 沒有量錯**——它量的是**名字解析**脈絡（`add`／`/add`／`_.add`／`_./add`），
在那個脈絡 `_: X` 確實惰性。§8.2 第 3 句已寫「那條回退不在名字解析路徑上」，
**但沒有說它在哪條路徑上**。它在**施用**路徑上，而且是活的。

### 9.3 三個現存依賴，各自認定 `_:` 是不同的東西

| 依賴 | 它認為 `_:` 是 | 斷言 |
| :--- | :--- | :--- |
| `dispatch_test.rs:76` `test_dispatch_wildcard_fallback` | **萬用分派分支** | `{ _: "any" } 42` → `"any"` |
| `cocoon_shape_probe_test.rs:182` `pin_user_underscore_field_survives` | **普通使用者資料**（逐字「a USER field named `_` is data, not scaffolding」，標為 Law 3 邊界） | `{_: 5}` 顯示時必須存活 |
| `collision_hint_lint_probe_test.rs:119` `pin_r6_merge_key_free` | 逐字「**`_` merge key repetition ＝ multi-import idiom**」 | `{ _: ~%Cond, _: ~%Math, v: 1 }` 的 R6 提示數 ＝ 0 |

**規格側**：`TAG_REGISTRY` §119（`#no_matching_branch`）的提示行逐字叫使用者
「增加 `_` 預設分支」；`SPEC_07` §89 的 `_` 是**值**（萬有集合）不是**鍵**。
**conformance：0 個向量**釘上述任何一種。

⟹ **這是 §2.5 的第二例**：引擎做了一件對的事（萬用分支），規格沒描述它，向量沒釘它，
而樹上已經有三處靠著它綠著——**而且三處各自以為它是別的東西**。

### 9.4 linter 已經祝福的那個 idiom，今天求值成 ⊥

〔量〕`{ _: ~%Cond, _: ~%Math, v: 1 }`：

```
{ _: _|_ (%cause: #missing_key)  ;; Key 'one' missing in closed Cocoon
  v: 1 }
```

兩個 closed cocoon 取 meet ⟹ `_` 槽是 ⊥；`v: 1` 存活；`keys` ＝ `["_", "v"]`（**重複鍵不保留兩份**）。
對照 `{ q: ~%Cond, q: ~%Math }` **逐字同形** ⟹ 重複鍵取 meet，`_` 在這一格同樣不特別。
而 `oo lint` 對該檔回報 **0 diagnostics**。

⟹ **linter 明文把一個今天會塌成 ⊥ 的寫法命名為「multi-import idiom」並保證不提示。**

### 9.5 兩個意思會撞，而且撞在同一個拼法上

〔量〕`({ _: ~%Math, v: 1 }) "zzz"` → **回傳整個 `~%Math`（49 個鍵）**。

*   **萬用分支**說：引數沒匹配到鍵，回傳 `_` 槽的值 ⟹ 整個 `~%Math`。
*   **mount（O69）**說：名字沒解析到，掉進 `_` 槽**去裡面找** ⟹ 應該找 `zzz`，找不到則 ⊥。

同一個拼法、同一個運算，兩個答案。**兩者不是同一件事的兩種說法**：
一個把 `_` 的值**當成答案**，一個把它**當成繼續查找的地方**。

### 9.6 D-2 的射程因此要改寫

1.  **讀相容不再是 D-2 的問題**（9.1，空集合）。這一項擋住 D-2 的理由消失。
2.  **換上來的是一個裁定題**：mount 與萬用分支要不要共用 `_:`。
    共用則須明文寫出兩個脈絡如何分（施用 vs 名字解析），且 9.5 那一格要有答案；
    分拼法則須裁新拼法，並處理 `TAG_REGISTRY` §119 那句已經寫給使用者的提示。
3.  **多重掛載須同批裁**：`_` 重複今天是 ⊥（9.4），而 linter 把它當 idiom。
    mount 落地時這一格必須有答案——meet、序列 overlay、或明文拒絕。
4.  **落地時必須同批補規格與向量**：上述四種意義今天 **conformance 零命中**，
    §2.5 的判別法對這一格是滿分命中。
