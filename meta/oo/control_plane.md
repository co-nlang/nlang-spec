# control_plane — 別的程式怎麼驅動 `oo`

## 0. 前提(先讀這四句)

1. **`.oo/staged` 沒有任何互斥**,並行寫入是 last-writer-wins 且**無聲**(§1.1)。
2. **「值層只有一個寫者」是使用假設,不是機制。** 沒有東西阻止第二個寫者;
   第二個寫者只是靜靜弄丟資料。而**控制面的存在目的就是製造第二個寫者。**
3. **端點表與令牌都排在寫入模型裁定之後。** 先決定「控制面能不能合法地並行寫」,
   再畫表。
4. **但那個裁定可能不是前置,是下游**——併發模型很可能是 `commit.md` 弧 A
   (savepoint 內容定址化)的副產品,而不是它的前提(§1.4.3)。

## 1. 承重結論(候選)

### 1.1 控制面的前提今天已經是假的

**〔量〕同一工作區 40 個並行 `oo evolve`,各加一個不同欄位:**

```
應有 41 個欄位 → 實得 2 個
遺失 39 個,零錯誤,每個行程都成功返回
```

**〔讀〕成因**(`universe.rs:500` `save_staged`):

```rust
let staged_path = base_dir.join(".oo").join("staged");
let json = serde_json::to_string(&self.staged)?;
std::fs::write(&staged_path, json)?;    // ← 無條件覆寫
```

讀-改-寫,**沒有鎖、沒有期望值比對、沒有 temp+rename**。而 `fs::write` 先截斷再寫,
所以並行讀者還會看到**半截 JSON**——那是**損壞**路徑,不只是遺失。

* **〔量〕全樹 0 個檔含 `flock` / `LockFile` / `try_lock`**
* **〔量〕全樹 0 處樂觀併發痕跡**(`optimistic` / `compare_and` / `expected_head`)
* **〔量〕`storage.rs` 全檔 `rename` / `create_new` 命中數 = 0**——
  **連物件寫入也是裸 `fs::write`**(`storage.rs:269`)

| SPEC_10 §4.1 說 | 引擎做 |
| :-- | :-- |
| 強原子性 (Strong Atomicity) | 行程級「寫完就算」 |
| 晚到者自動收斂 $C = HEAD \sqcap Staged_{incoming}$ | 晚到者**覆蓋** staged 檔 |
| 樂觀併發模型 | 樂觀不存在,悲觀也不存在 |

**因果鏈:**

```
今天:  人一次一個 CLI      → 單寫者「碰巧」成立
控制面:程式 / TCP / WS 多客戶 → 假設失效 → 靜默丟資料變常態
```

⟹ **這一條排在端點表之前。**

**嚴重性分級(誠實):** 今天暴露面低(人不會並行跑 `oo`),
但**類別是資料遺失與資料損壞,不是設計歧見**。控制面一開,暴露面與設計目的同向放大。

**順帶解釋了一則既有訊息:** 竄改測試中出現的
`#object_undecodable: object present … but cannot be decoded (integrity unknown)`
——**「integrity unknown」正是撕裂寫入的症狀**。引擎已有那條錯誤路徑,只是不知道
那是它的成因之一。

### 1.2 控制面是兩張臉共用一條線

**(a) CLI 投影**——遠端驅動引擎。**裁定方向(用戶,2026-07-27):
控制面是 CLI 的投影,不是平行 API,「他就類似 CLI 的另一種介面」。**

**(b) 語言智慧面**——REAL_01 §8.3/§8.4 的 hover / completion / 跳轉 / 譜系視圖 /
視界模擬 / 燃料儀表板,**沒有一個是 CLI 動詞**。

二者只因 **LSP 本身就是 JSON-RPC over stdio** 才停在同一協定上
(§2.1 傳輸層明列「標準輸入輸出(stdio):用於 LSP」)。

### 1.3 兩個面、兩種機制,REAL_01 §7.0 已經切好了

〔讀〕§7.0(2026-07-27 新增):

| 面 | 請求者 | 機制 | 狀態 |
| :-- | :-- | :-- | :-- |
| **本機面**(§1.1 CLI) | **操作者本人** | **每次呼叫出示能力**(§7.0.1)、SPEC_08 §6.1.4 能力格 | **已出貨** |
| **服務面**(§1.2 / §2 JSON-RPC) | **遠端方**,身分不等同工作區擁有者 | §7.1 令牌 + §7.2 生命週期 + §2.6 連線認證 | **規範完整,實作零** |

§7.0.2 明文:服務面未實作前 §7.1/§7.2 **不適用**,且**不得**為滿足形式而於本機面
引入令牌——**那將以較弱者取代較強者**(逐次出示的參數在行程結束即不存在;
24 小時令牌是一份可被複製的持有者憑證)。

⟹ **準確的說法是「服務面令牌是紙,本機能力閘不是紙」**,不是「§7.1 全是紙」。
(本節由模型 #3 指正,查證屬實。)

**而 §7.0.1 最後一條獨立佐證了 `dot_oo.md` §1.5.2:**

> 本機面之特權閘所防守者為**程式**(含取自對等點者),非防守操作者本人;
> **任何宣稱能約束操作者的本機機制皆為虛飾。**

### 1.4 lock-free 才是規格要的;鎖反而是偏離

**POSIX 本來就有 lock-free CAS**:`open(O_CREAT|O_EXCL)` 與 `link()`
在目標已存在時**原子地失敗**(EEXIST)。

**而 CAS + 重試逐字就是 §4.1 要的東西:**

```
讀當前 staged S_cur → 算 S_cur ⊓ S_mine → CAS 安裝 → 失敗就重來
                      ↑
        C_new = HEAD_current ⊓ Staged_incoming
```

⟹ **鎖給你的是「拒絕」或「阻塞」,而 §4.1 從沒要求那個——它要求的是合併。**

#### 1.4.1 重試為什麼安全:CvRDT 在這裡兌現

meet **交換、結合、冪等**(SPEC_01;conformance L1-28 測 `x ∨ x = x`)⟹
同一組更新、不同順序、重複任意次,收斂到同一狀態。

⟹ **`commit.md` §1.1.1「值層是 CvRDT」正是 lock-free 重試正確的理由。**
不是巧合——CRDT 的定義性質就是為了讓**無協調的重放**安全。

#### 1.4.2 但 `pin` 不行,而那條界線已經畫過

`pin` **不可交換**(`commit.md` §1.1.2)⟹ 重試會給出「取決於誰先重試成功」的答案,
**那是把權威換成時序**,正是 §1.1.4 拒絕的那筆交易。

| | 機制 | 為什麼 |
| :-- | :-- | :-- |
| **核心(meet 型演化)** | **lock-free CAS + 重試** | 重試安全 ⟸ 交換/結合/冪等;而重試**就是**晚到者收斂 |
| **外掛(`pin`)** | **真正的序列化** | 不可交換 ⟹ 結果由時序決定 |

⟹ **開放問題 (1) 不是一個問題,是兩個,而接縫就是 `commit.md` §1.1.6 的核心/外掛線。**

#### 1.4.3 而它可能是弧 A 的副產品,不是它的前置

今天可變狀態是**多個檔**:`staged` / `pin_pending` / `effect_pending`,
外加 `HEAD` 與 `abandoned`。**CAS 一個檔不會讓那一組原子**
——讀者可以看到新的 `staged` 配舊的 `pin_pending`。

⟹ 要 CAS,**必須先讓可變狀態變成一個可整體替換的物件**:
staged 內容定址進 `objects/`,`staged` 檔只放一個 hash,
`pin_pending`/`effect_pending` 變成該物件的欄位。

**而那正是弧 A 的 savepoint 設計。**

> **所以 (1) 可能不是需要先裁定的前置問題,而是弧 A 的副產品。**

#### 1.4.4 止血與修復是兩件事

模型 #3 建議「先加鎖止血,再做 OCC」。**但最小止血不是鎖,是 `temp + rename`:**

* 它消滅的是**損壞**路徑(半截 JSON),那比遺失更嚴重;
* 五行,**不需要決定任何併發模型**;
* 對物件寫入**無條件正確**,因為內容定址讓重複寫同一物件是冪等的。

而**鎖**在弧 A 近時是繞路(蓋了要拆,中間那段是規格沒有的「拒絕」語義),
在弧 A 遠時才是止血。**那是排程問題。**

⟹ **拆成兩件:「消滅損壞路徑」(現在就能做,零裁定)與「決定併發模型」(等弧 A)。**

### 1.5 借 git 的機制,不借 git 的衝突政策

**〔讀認識,非讀 git 原始碼〕git 的 ref 更新是三段**,不是裸 CAS:

1. `refs/heads/main.lock` 以 `O_CREAT|O_EXCL` 建立 → 已存在就**立刻失敗**(不阻塞)
2. 在鎖檔內讀當前值、**與期望的舊值比對**(`update-ref <ref> <new> <old>`)
3. `rename()` 蓋過去

網路層的同一件事叫 **`--force-with-lease`**。

**而 git 在衝突時的政策是「拒絕」**;合併是**更上一層由人做**的事。

⟹ **而那正是 `commit.md` §1.1 那條線的操作面顯影:
git 不能在這裡合併,因為它的合併不是函數;n/ 可以,因為 meet 是。**

> **鎖檔、舊值比對、rename 全部可照抄;
> 「失敗就回報」那一步要換成「meet 進去再試」。**

#### 1.5.1 值得借的四樣

1. **不可變/可變的切分**——git 每個 ref **只有一個可變的東西**(一個裝 hash 的檔),
   其餘全不可變 ⟹ **協調面積只剩一個指標**。n/ 今天有五個可變檔互不協調(§1.4.3)。
2. **響亮的失敗**——git 的鎖碰撞會印出檔名;n/ 今天完全無聲。
   **不管最後選哪個模型,這條要先立。**
3. **`--force-with-lease` 這個概念**——控制面一定需要:遠端客戶端得能說
   「我期望 HEAD 還是 X」,否則它連拒絕都做不到。
4. **reftable**(git 較新的 ref 儲存格式:log-structured、append-only、
   **把 refs 與 reflog 存在一起**)——見 §1.5.3。

#### 1.5.3 reftable:三個動機,只有一個是規模

用戶提出的顧慮成立:reftable 的規模動機(百萬 refs)不適用於 n/ 工作區。
**但它有三個動機,規模只是其中一個:**

| 動機 | 適用於 n/ 工作區? |
| :-- | :-- |
| **規模**(百萬 refs、檔案系統壓力) | **不適用**——一個 HEAD、無分支(branch 已被值語言吸收,`commit.md` §1.3) |
| **跨多 ref 的原子更新** | **適用**——今天五個可變檔之間沒有原子性(§1.4.3) |
| **refs 與 reflog 存在同一結構** | **適用**——弧 A 要的正是「一條指標 + 一條日誌」 |

**而「什麼情況會用到」有一個現成答案:n/ 已經用過一次了。**
**〔量〕`.oo/peers/directory` 就是 append-only 行 + 2× 壓實閘**
(`peers.rs:3` 檔頭註解、`:34` 壓實閘、`:400` `OpenOptions::append`)。

⟹ **那個設計是自己長出來的,不是借來的。** 所以問題不是「要不要引進一個新模式」,
是「**要不要把已經用在對等目錄上的模式,也用在 savepoint 鏈上**」。

**但有一個限制要先標:** git 的 reflog 記的是 `(ref, 舊值, 新值, 誰, 何時, 訊息)`
——**那是 physical logging(狀態轉移)**;而弧 A 要的是 **logical logging
(操作 + 視界參數)**(`commit.md` §1.5.5 的分野)。

⟹ **借容器,不借記錄形狀。** block/append/compaction 的結構可用;
reflog 的條目模型是錯的那一種。

**而規模那一條真的會出現的地方是 LADD 側**——`commit.md` §1.7.6 的 ⊑ 物化索引
可能是數百萬條邊。但那裡該用資料庫,不是 reftable。

#### 1.5.2 不該抄的一樣

git 的 `.lock` 是**建議性的**:行程崩掉留下殘檔會擋住之後所有寫入,要人手動刪。

而 n/ 有一個 git 沒有的選項:**因為 meet 是冪等的,過期的鎖可以被安全地搶走再重試**
——git 不敢那樣做,正是因為它的合併不是函數。**同一個性質,第二次付紅利。**

## 4. 開放問題

1. **控制面要不要成為合法的並行寫者?**
   * 若**不要** → 互斥 + **響亮的**錯誤(禁止靜默覆蓋)
   * 若**要** → OCC,而 §1.4 指出它該是 lock-free CAS + 重試,且 `pin` 要另外序列化
   * **而 §1.4.3 說這可能是弧 A 的副產品,不是前置。**
     ⟹ **先做的可能是 §1.4.4 的止血(temp+rename),而不是這個裁定。**
   * 裁定後須回頭改寫 `commit.md` §1.1.6 的前提句:
     **單寫者若要當前提,必須被機制強制。**
2. **控制面的認證,是不是能力系統的第二種出示方式?**
   ```
   能力格(SPEC_08 §6)
       ├── 本機出示:--grant / --privileged        (已出貨)
       └── 服務出示:§7.1 令牌 = 可序列化的能力快照  (未出貨)
   連線層(§2.6 mTLS 等)
       └── 回答「通道對端是誰」,不是「這次呼叫有哪些能力」
   ```
   **敘事上是三處,代數上應是一套。接線比發明第四套重要。**
3. **§2.6 的 mTLS「CN 欄位映射至 n/ 的觀測身份」是第幾個身分?**
   操作者、節點之外冒出的第三個詞,**從未過 REAL_01 §7.6 六問表**。
   候選(擇一,不要並列):CN → 操作者 / CN → 節點 /
   連線只做通道保密、身分完全由能力承載。
   **在過表之前,「觀測身份」不得當承重。**
4. **端點表:整個重畫成 CLI 投影,還是實作那六個?**
   依 §0 它不是第一件。**投影優先於考古**——實作舊端點若與 CLI 不對齊,
   會變成第四套。
