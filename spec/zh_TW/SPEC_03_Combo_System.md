# n/ Language Specification - 複合結構 (Combo System)
## 1. Combo 與 Cocoon

### 1.1 Combo (疊加態預設 `{}`)
**Combo** (源自 Combination，即開放容器) 是 `n/` 最核心的結構。它遵循「**疊加態預設 (Superposition Default)**」——未被提及的欄位處於所有可能值的量子疊加態（即 Top `_`）。
*   **特性**：未定義欄位預設為 `_` (Top)。這意味著一個 Combo 永遠可以被後續的平行定義擴張，如同量子系統在觀測前保持所有可能態的疊加。
*   **平行定義**：同一個 Key 可以分散在不同檔案定義，最終結果是所有定義的**合併 (`&`)** (詳見 **[SPEC_06](./SPEC_06_Unification_Logic.md)**)。
*   **重複鍵合併 (Repeated-Key Merge)**：同一字面量內重複出現的 Key 是平行定義的**退化形**——結果同為所有定義的合併 (`&`)，與書寫順序無關。例如 `{ a: 1, a: 2 }` 等價於 `{ a: 1 & 2 }` → `{ a: _|_ }`；路徑鍵亦同，`{ a: { x: 1 }, a.y: 2 }` 等價於 `{ a: { x: 1 } & { y: 2 } }` → `{ a: { x: 1, y: 2 } }`。這與展開碰撞合併（§3.1）同一律：欄位即約束，資訊單調遞增，任何位置都不存在「後者覆寫」。（2026-07-16 裁定入法；同字面量重複鍵屬可疑拼法——lint 提示已立：Tier 1 **R6**（2026-07-17，想法 D 儀器），對同字面量內重複全拼鍵與靜態可見之字面展開碰撞發 Warn；拼法保持合法。寧漏勿誤邊界：root 精化慣用形、具名展開源、路徑鍵部分重疊、`_` 合併鍵永不旗標。）

### 1.2 Cocoon (繭 `{{}}`)
**Cocoon** (繭) 用於需要絕對嚴謹邊界、**本徵態封閉 (Eigenstate Sealed)** 的場景——結構已被觀測固定為確定的本徵態，拒絕任何額外的量子漲落。
*   **特性**：遵循「**本徵態封閉**」語義。
*   **封閉語義 (Sealed Boundary)**：
    1.  **存取限制**：讀取未定義的欄位 $k$ 立即返回 `_|_`（如同試圖觀測一個不存在於本徵態中的量子數）。
    2.  **合併拒絕 (Merge Rejection)**：當 Cocoon $C$ 參與合併運算 $C \sqcap X$ 時，若 $X$ 包含 $C$ 未定義的任何**非 Top 欄位**，則合併結果立即坍縮為 `_|_$。
    3.  **效果隔離 (Effect Isolation)**：Cocoon 是一個**量子退相干屏蔽艙**。內部欄位的效果標籤（如 `#io`）**不會**自動向外傳染給 Cocoon 容器本身——這相當於將內部子空間與環境退相干隔離。外部觀測者看見的 Cocoon 標籤預設為 `#pure`（詳見 **[SPEC_08](./SPEC_08_Meta_and_Runtime.md)**）。
    4.  **與展開的區別**：合併 (`&`) 是「幾何疊加」，受限於封閉性與效果隔離；展開 (`...`) 是「顯式解封 (Unboxing)」，它搬運定義、丟棄封閉外殼，並**釋放**內部的副作用標籤。

#### 1.2.1 封閉性衝突 (Cocoon Conflict)

當一個已處於**本徵態**的 Cocoon 與包含「未定義欄位」的結構進行交集（`&`）時，將觸發封閉性衝突——這相當於試圖將一個已坍縮的量子態與不兼容的觀測結果強行疊加。

> **Note**：此處的封閉性衝突與 Peres-Mermin 方塊的 $H^2$ obstruction 共享同一代數結構——兩者都在說「四個 MASA 的循環無法同時賦值」。Cocoon 的 `{{}}` 正是這個 $H^2$ obstruction 在語言層的工程體現（詳見 SPEC_01 §2.5.1 的 $H^2$ 定義與 SPEC_06 §1.3.2 的上鏈格式）。

*   **案例**：
    ```nlang
    ;; 定義一個本徵態封閉的個人數據
    @StrictUser: {{ name: @str }}

    ;; 嘗試併入額外欄位 age
    result: @StrictUser & { name: "Alice", age: 30 }

    ;; 結果：_|_ (Bottom)
    ;; %cause: #missing_key (在 @StrictUser 的本徵態中找不到 age)
    ```

*   **設計理由**：本徵態封閉是進行靜態分析與「疊加態 → 本徵態」推導的重要邊界。它允許編譯器在確定的集合內進行窮舉與優化，如同量子計算中的**退相干保護**。

**範例對比：**
```nlang
~c: {{ b: 2 }}
~o: { a: 1 }

;; 1. 直接合併 (幾何衝突)
result_merge: ~o & ~c    ;; 結果: _|_ (%cause: #missing_key)

;; 2. 展開合併 (顯式解封)
result_spread: { a: 1, ...~c }  ;; 結果: { a: 1, b: 2 } (開放)
```

### 1.3 欄位存在性與預設值
在 `n/` 中，欄位的「不存在」並非一種狀態，而是對萬有集合 `_` (Top) 的一種觀測。
*   **疊加態預設**：在 Combo 中，任何未定義的 Key $k$ 滿足 $Combo.k = \top$。這代表該欄位處於所有可能值的量子疊加態，直到被顯式觀測（賦值）才發生坍縮。
*   **本徵態預設**：在 Cocoon 中，任何未定義的 Key $k$ 滿足 $Cocoon.k = \bot$。這代表該欄位在本徵態中不存在，任何試圖訪問或合併未定義欄位的操作都會導致衝突（坍縮為 Bottom）。
*   **同構性**：這種設計確保了「存取」操作本身是幾何良定义的，錯誤僅發生在強行將不兼容的量子態進行合併之時。

## 3. Combo 運算與動態鍵
*   **合併 `&`**：遞迴地合併兩個 Combo 的欄位。
*   **差集 `\` 與 補集 `!`**：對 Combo 進行差集或補集運算時，引擎會將其轉化為對特定欄位的「負向約束」。例如 `{a: @int} \ {a: 1}` 等價於對 `a` 欄位施加 `@int & !1` 的約束。

### 3.1 展開運算子 (Spread)：
將目標 Combo 或 Cocoon 的所有欄位「攤平」至當前 Combo 中。

*   **安全邊界規則 (Spread Isolation)**：展開運算子**僅能搬運**在當前「詞法作用域 (Lexical Scope) (Lexical Scope)」中**具備觀測權限**的欄位。
    - **私有保全**：若展開操作位於目標 Combo 外部，則目標中的 `~` 私有欄位將**不會**被包含在展開結果中。這防止了透過 `...` 運算子非法導出（Leak）內部私有狀態。
    - **顯式覆蓋例外**：若需「破繭（Break the cocoon）」獲取全部定義（含私有），觀測者必須位於目標的詞法內部，或具備特權模式。
*   **碰撞合併 (Collision Merge)**：當展開的欄位與目標容器中已有的欄位發生重疊（Key 碰撞）時，其行為必須是**交集合併 (`&`)**，而非覆寫。這確保了「資訊單調性」。例如：`{ a: 1, ...{a: @int} }` 等價於 `{ a: 1 & @int }`。
*   **解封特性 (Unboxing)**：若展開對象為 **Cocoon `{{}}`**，被搬運的欄位集合在進入目標容器後不再受到其原先的「**本徵態封閉**」約束。
*   **目標屬性保全 (Target Attribute Preservation)**：展開操作僅搬運欄位定義，**嚴禁修改目標容器本身的屬性**。
*   **前向引用與收斂時序(2026-07-19 收帳)**:展開源得為**前向
    引用**(欄位同時性/交換律,SPEC_03 L1-26/27 既有法)——展開
    於**觀測收斂時**擴張,源在檔內的定義位置**不得**影響結果;
    碰撞交集/⊥ 傳因/Blur 吸收諸律於擴張時一體適用。未定義源=
    開放 `_` → Top no-op(既有行)。循環展開照 `#divergent`
    (C4 機構)。
    *   若展開至 Combo `{}`，目標維持開放。
    *   若展開至 Cocoon `{{}}`，目標維持封閉。
*   **未擴張的展開結果仍是普通的值（MUST，2026-08-24 入法）**：由上款，
    擴張發生於**觀測收斂時**，故一個尚未擴張的展開結果會在其**身分之外**
    攜帶一件待辦。該待辦**不得**改變任何值層結果——`{ ...X } & { ...Y }`
    的可觀測結果**必須**與直接書寫 `X & Y` 相同，**含碰撞時塌陷為 `⊥`**。
    > **判例（實測，引擎 v0.20.0–v0.32.0）**：某實作的合一以「兩邊 CAID 相同
    > 就回傳其一」開場，而兩個未擴張的展開結果 digest 逐字元相同（待辦不進
    > 位址）⟹ `{ ...{a:1} } & { ...{b:2} }` 得 `{ a: 1 }`、換邊得 `{ b: 2 }`、
    > 而 `({ ...{a:1} } & { ...{a:2} }).a` 得 **`1`** 而非 `⊥ #conflict`。
    > **丟一個鍵是資料遺失，丟一個衝突是一個讀起來正常的錯答案。**
    > 一般條款見 **[REAL_03](./REAL_03_CAID_Protocol.md) §6.9**；
    > 與本節 `#blur` 條下 **O47 按語**（「CAID 保全靠的是一個巧合」）同族——
    > **那是同一件事的第一次發作，本次是第二次。** 向量 `L2-111`–`L2-114`。
*   **語義轉變**：展開 `{{a: 1}}` 至 `{}` 後，`a` 欄位變回「**疊加態**」；展開 `{{a: 1}}` 至 `{{}}` 後，`a` 欄位依然處於**本徵態封閉**（即該目標 Cocoon 依然拒絕未宣告的額外欄位）。
*   **異質展開規則 (Heterogeneous Spread)**：當展開對象非標準 Combo 時，遵循以下同構規則：
    - **List `[]`**：將其數字索引欄位攤平至目標（例如 `{...[10, 20]}` 產生 `{0: 10, 1: 20}`）。
    - **原子 (Atom)**：將其視為 `{ %val: v }` 展開（例如 `{...#ok}` 產生 `{%val: #ok}`）。
    - **Top `_`**：無效操作，不對目標增加任何欄位或約束。
    - **Blur `#blur`**：吸收。展開＝全座標讀取，視界後來源的欄位集合不可知——目標容器立即變為**該 `#blur` 原樣**（cause／CAID／視界參數保全；不得鑄新因、不得靜默 no-op＝視界抹除）。可由既有法導出：`{ b: 1, ...big }` ≡ `{ b: 1 } & unbox(big)`，視界後解封即 `#blur` 本身，再依合併吸收律收官。與 Bottom 條款同構（⊥ 傳因／blur 傳快照）、與 **[SPEC_08](./SPEC_08_Meta_and_Runtime.md)** §3.2.2 #5 座標吸收同律——視界不得因展開而靜默消失。與書寫順序無關、逐節點生效、目標為 `{}` 或 `{{}}` 皆同。分界：Top 展開 no-op 不動——「無約束」與「不可知」正是此行與上行的邊界。（2026-07-16 裁定入法。）
        **按語（2026-08-10，O47）**：「原樣」包含**局部收斂結果（`partial`）不得被改寫**。
        參考實作曾將另一側合併進 `partial`，該行為在 `partial` 進入 CHS（REAL_03 §7.3）
        之前**不可觀測**，因為當時的 CAID 看不見它——本款的「CAID 保全」是靠一個
        巧合而非靠實作滿足的。理由本款自己已寫明：**視界後來源的欄位集合不可知**，
        把已知的一側揉進快照，是在斷言一件你不可能知道的事。
        與 **[SPEC_08](./SPEC_08_Meta_and_Runtime.md) §3.2.2 #1**「`partial` 快照不參與後續運算」同律。
    - **Bottom `_|_`**：強制坍縮。目標容器立即變為 `_|_`，**因果傳播**：承載展開來源自身的 `%cause`（主因果，見 **[REAL_04](./REAL_04_Causal_Chain_Protocol.md)** §4）。（2026-07-16 修訂：原文「標記 `%cause: #conflict`」為 ⊥-meta 整流前舊文——展開一個 `#private_access_violation` 或資源類 `_|_` 時鑄新因即視界抹除。）
*   **循環展開保護 (Circular Spread Protection)**：嚴禁一個 Combo 展開其自身或其祖先節點（例如 `A: { ...A }`）。
    *   **語義**：此類定義被視為邏輯發散，引擎將其判定為 `_|_`，標記 `%cause: #divergent`。這防止了在收斂過程中產生無限展開的黑洞。

#### 3.1.1 碰撞合併與衝突解決
開發者習慣於傳統語言的「後者覆寫」直覺，但在 `n/` 中，`...` 始終遵循格論合併。
*   **視覺化範例**：
    ```nlang
    ~base: { status: #ok, priority: 1 }
    ~patch: { status: #error }
    
    ;; 結果不是 { status: #error, priority: 1 }
    ;; 而是 { status: #ok & #error, priority: 1 } -> { status: _|_ }
    result: { ...~base, ...~patch }
    ```
*   **解決策略**：若需覆寫效果，必須使用特權模式的 `#pin` 或在工程層調用 `oo merge --strategy favor_incoming`（詳見 **[REAL_02](./REAL_02_Ouroboros_Protocols.md)**）。

### 3.2 動態鍵 (Dynamic Keys)
在定義 Combo 時，可以使用匿名集合 `@{}` 作為鍵，這稱為動態鍵。動態鍵本質上是對輸入或查詢的「模式匹配條件」。
```nlang
{
    @{ @int & 4.. }: #true
    @{ @int & ..3 }: #false
}
```
這在構建複雜的邏輯態射（Logic Isomorphism）時非常強大。

## 4. 同構原理 (Isomorphism)
在 `n/` 中，「萬物皆 Combo」。所有的複合字面量都可以被觀測為特定約束下的 Combo 結構。

| 觀測對象 | 等價的 Combo 展開 |
| :--- | :--- |
| **Data `x: v`** | `{ %val: v, %kind: #data }` |
| **Type `@T`** | `{ %kind: #type, %name: "T", %super: @B }`（`%super` 衍生自 SPEC_09 §2.1 層次；`%predicate` 退場→R2，見 SPEC_05 §3.2） |
| **Logic `/f`** | `{ %rules: { ... }, %morphism: #true, %kind: #logic }` |
| **Tuple `(A, B)`** | `{ 0: A, 1: B, %len: 2, %kind: #tuple, %closed: #true }` |
| **List `[1, 2]`** | `{ 0: 1, 1: 2, %kind: #list, %state: #total_ordered }` |
| **Enum `#X`** | `{ #X: (), %kind: #enum, %state: #unordered, %order: {...} }` |
| **Cocoon `{{A}}`** | `{ A, %closed: #true }` | 本徵態封閉的量子退相干屏蔽結構 |

*註：**`%kind`** 標示了該 Combo 的主要本體論角色（如 `#data`, `#type`, `#logic` 等），其自動推斷規則詳見 **[SPEC_05: 三位一體同構](./SPEC_05_The_Trinity_Isomorphism.md#4-kind-的語義地位)**。*

## 5. 順序與數值 Combo (Ordered & Numeric)

在 `n/` 中，順序（Order）是結構的一種維度。List、Tuple 與 Enum 均透過 `~%Enum` 與 `~%List` 提供的語義進行同構。

### 5.1 Enum (偏序枚舉)
Enum 是對一組標籤（Tags）施加偏序關係的 Combo。
*   **定義**：`workflow: { #draft < #review < #publish }`。
*   **比較運算 `<=>`**：用於判定兩個標籤的先後關係，回傳 `#lt | #gt | #eq | #un` (Unordered)。
*   **錨點**：序位預設受 `#_|_` (Start) 與 `#_` (End) 約束。

#### 元資訊與收斂
*   **`%rank`**：該標籤在序位中的整數權重。若序位尚未完全決定，其值為一組可能的聯集或區間。
*   **`%state`**：反映序位的決定程度：
    *   `#unordered`：標籤間無關係。
    *   `#partially_ordered`：部分標籤有先後關係。
    *   `#total_ordered`：任意兩標籤均可比較，此時 `%rank` 坍縮為單一原子。

### 5.2 List (鬆散的數值 Combo `[]`)
List 是以非負整數為 Key 且預設為 `#total_ordered` 的 Combo。
*   **預設值**：所有非負整數索引預設皆為 `_` (Top)。這反映了 List 作為**疊加態結構**的本質：未定義的座標代表尚未觀測的可能性，而非錯誤。
*   **邊界觀測**：存取大於等於 `%len` 的索引將返回 **`_` (Top)**。這是**疊加態預設**的體現——超出當前觀測邊界的索引僅代表「尚未坍縮的潛在值」。

### 5.3 Tuple (本徵態的數值 Combo `()`)
Tuple 語法 `(A, B)` 是對 List 施加「長度與本徵態封閉」約束後的產物。
*   **特性**：具備固定 `%len`，且預設為 `%closed: #true` 與 `%state: #total_ordered`。
*   **邊界觀測**：由於 Tuple 等價於以數字為 Key 的 Cocoon，存取大於等於 `%len` 的索引將立即觸發 **`_|_` (Bottom)**，並標記 `%cause: #missing_key`。這是**本徵態封閉**的嚴格性體現——任何超出已定義本徵態的觀測都是不可能的。

### 5.4 投影與轉換 (Projection)
*   **隱性投影**：當 Enum 處於 `#total_ordered` 狀態時，可直接透過數字索引存取（如 `workflow[0]` 返回 `#draft`）。
*   **顯性轉換**：利用 `~%` 系統邏輯進行結構投影。
    *   `workflow |> ~%Enum./toList` $\rightarrow$ 產生一個對應的 List。
    *   `myList |> ~%List./toEnum` $\rightarrow$ 產生一個對應的 Enum 順序關係。

### 5.5 元資訊：長度 `%len`
對於數值 Combo，`%len` 是一個虛擬欄位，由引擎動態計算：
*   **計算公式**：`%len = max(index | Combo[index] != _|_) + 1`。
*   **語義**：它代表了當前 Combo 中「非衝突邊界」的範圍。若 List 為空，則 `%len: 0`。

> 結語：Combo 是量子疊加的開放宇宙，Cocoon 是本徵態封閉的繭。成繭以錨定坍縮之果，破繭以重尋疊加之源——兩者的辯證法，構成了 n/ 幾何的完整邊界。
