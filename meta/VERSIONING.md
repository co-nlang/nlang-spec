# VERSIONING — 版號政策

> 裁決:2026-07-11(使用者)。自 **v0.2.0(分水嶺)** 起生效;分水嶺之前的版號
> (`v0.1.0-genesis` ~ `v0.1.0-alpha.3`)不溯及既往。
> 里程碑錨點屬 ORDER_00(v0.500.0 委員會、v1.0.0 Epoch 0);本檔只管「號怎麼編」。

## 1. 三條版本軸

| 軸 | 載體 | 規則 |
| :--- | :--- | :--- |
| **規格版本** | nlang-spec(SPEC/SYNTAX/REAL/ORDER/GUIDE) | semver;權威版本表在 SPEC_00 §4.4 |
| **引擎版本** | nlang-tools(`oo`) | semver;與規格 **major.minor 對齊**(§2) |
| **格式版本 (fmt)** | CAID `<fmt_version>` 欄位 | 獨立整數軸(v1, v2, …);映射表在 SPEC_00 §4.4;凍結紀律見 §4 |

## 2. 對齊契約:共用 `major.minor`,patch 各自所有

- **`X.Y` = 語義對齊層**:引擎 `X.Y.*` 宣稱實作規格 `X.Y.*`。對應關係只看 `X.Y`。
- **patch 位各自所有**:
  - 規格 patch(`X.Y.z`)= **編輯性修訂**——錯字、措辭、排版、非語義勘誤。
    任何語義變更(文法、求值、格律、協定)**不得**走規格 patch。
  - 引擎 patch = 引擎自己的 bugfix/效能,與規格 patch 無對應義務。
- **為什麼不共用完整 triple**(記錄裁決理由):semver 中 `+build` 不參與排序且
  工具鏈視為同版(cargo 不接受並存);裸核發布後的引擎 bugfix 若不佔 patch 位
  即無處可去(`X.Y.Z-fix.1 < X.Y.Z` 非法)。共用 `X.Y`、放開 patch 是唯一
  同時滿足「一個號溝通」與「工具鏈零衝突」的切法。

## 3. pre-release 與裸核語義

- **引擎裸核(無 pre-release 尾巴,如 `0.2.0`)= 通過該 `X.Y` 對應的 REAL_05
  合規等級測試**。未達標一律掛 `-alpha.n` / `-beta.n` / `-rc.n`。
  門檻等級:引導期暫定 REAL_05 **Level 2**;v1.0.0 起 = Level 3
  (ORDER_00 §5.1.1 本就要求)。等級調整 = 修訂本檔,不動版號規則。
- **規格 pre-release**(`-draft.n` 等)可用於公開徵求意見的草案版;定稿去尾巴。
- `+build` 欄位:自由使用(日期、commit 短碼),**不承載任何語義**。

## 4. fmt 凍結紀律(分水嶺的最重承諾)

- **v0.2.0 起,合法差異窗口關閉**:alpha 期「bn_serial 位元改(合法差異,無既存
  宇宙依賴)」的豁免不再適用。
- 任何影響 CAID 位元的變更(序列化 tag、值正規化路徑、canonical 列印若其進入
  序列化)一律:**提升 `fmt_version`** + 更新 SPEC_00 §4.4 映射表 + 提供
  SPEC_10 `#refine` 遷移路徑。
- fmt 提升不必然帶動規格 minor(fmt 是獨立軸),但必須在 changelog 顯著標記。
- 引擎側守門:bn_serial 相關測試向量即凍結探針;動到 = 紅線。

## 5. Changelog 紀律

- **位置**:`spec/CHANGELOG.md`(與規格同住;2026-07-05 既有裁決)。引擎側
  沿用 nlang-tools 自己的記錄慣例,不強制同格式。
- **起筆**:v0.2.0。之前的歷史由 v0.2.0 條目做一次性策展總結,不逐版回填。
- **分類三檔**(對應 SPEC_00 §4.5 權威層級):
  - **破壞性(Layer 1)**——語義/文法/協定的不相容變更;
  - **增量**——向後相容的新增(新章節、新裁決落檔、新模組);
  - **編輯性**——措辭、修錯、重排(= 規格 patch 的全部內容)。
- **量測儀器條款**:ORDER_00 §5.1.4(v1.0.0 條件:Layer 1 連續 90 天無破壞性
  變更)**以本 changelog 的「破壞性」條目為判定依據**——空窗期從最後一筆
  破壞性條目的日期起算,機械可判定。
- 每筆條目附:日期、影響章節、對應引擎 commit/版本(若有)、fmt 影響(若有)。

## 6. 版本路線(現況)

```
v0.1.0-genesis → … → v0.1.0-alpha.2(已 push)→ [alpha.3 = 未發布之工作狀態]
→ v0.2.0【分水嶺:規格穩定、changelog 起筆、fmt v2 凍結、宣傳解鎖】
→ 0.3, 0.4, …(語義變更逐 minor)
→ v0.500.0【委員會產生,ORDER_00 §3.2】
→ v1.0.0【Epoch 0,ORDER_00 §5;引擎裸核門檻升 REAL_05 Level 3】
```

- v0.2.0 之後排程不受版號約束的工作(規格書 Combo 化、SPEC_17 等)照常進行,
  於各自完成時落入對應 minor。
- ORDER_00/ORDER_01 於 Epoch 0 前仍可修訂(引導期本質);修訂走一般規格變更
  分類入 changelog。

### 6.1 委員會錨點自 `v0.5.0` 改為 `v0.500.0` **[2026-07-29]**

原路線把委員會產生放在 `v0.5.0`,隱含「規格在此之前只會再走三個 minor」。
實際不然:v0.2.0 之後語義變更**逐弧發生**,minor 位是會被持續消耗的資源,而
委員會之產生取決於 ORDER_00 §3.2 的**條件**,不取決於走過幾個 minor。把錨點
移到 `v0.500.0`,是讓「還要幾個 minor」與「何時成立委員會」**互相脫鉤**——
兩者本來就沒有關係,是原路線把它們綁在一起。

### 6.2 引擎 v0.2.x 期間未正確遵循本政策 **[2026-07-29,誠實記帳]**

**事實**:引擎自 `v0.2.0` 走到 `v0.2.55`,期間規格側累積 **334 個提交**、
含 **7 筆破壞性(Layer 1)條目**,而規格版號始終停在 `v0.2.0`。

**這使版號說了一句假話**。共用 `major.minor` 是一個宣稱:`oo v0.2.55` 宣稱
「我實作的是規格 `0.2.x`」。它不是——它實作的是一份只存在於未發布分支上的
規格。該宣稱大約自 v0.2.10 起即已不真,而其後又走了四十餘版。

**成因非疏忽,是兩件事的疊加**:(a) 原設計預期「規格推動引擎」,實際運行為
**引擎推動規格**——本政策 §2「共用 `major.minor`、patch 各自所有」對兩個方向
皆成立,故方向本身不是問題;(b) **規格 patch 位按 §2 只裝編輯性修訂**,而期間
所有變更皆為語義,**沒有任何一個位置可以承接它們**,於是它們就地累積。

**修正**:規格與引擎同步進入 `0.3`——引擎 `v0.3.0`,規格 `v0.3.0-draft.1`
(§3 之公開徵求意見草案;定稿去尾巴)。**記此條而不追溯改號**:已發布的
`v0.2.x` 標籤是歷史事實,重寫它們會製造第二個謊。

> **教訓**:版號是本專案對外做的**唯一一個形式宣稱**。一個沒有位置可以承接的
> 變更不會消失,它會累積成一句愈來愈大的假話——而**「等到夠整齊再打版號」這個
> 推遲本身是有代價的,代價由版號在推遲期間付**。
