## 0. 要裁的一句話

**`_:` 是不是要同時當「預設分支」和「掛載點」？**

如果是，兩個脈絡怎麼分，而**碰撞格**要答什麼；如果不是，哪一個換拼法，換成什麼。

**碰撞格**〔量 2026-08-23〕＝ `({ _: ~%Math, v: 1 }) "zzz"`，今天**回傳整個 `~%Math`**（49 個鍵）。
① 說「引數沒匹配到鍵，`_` 的值就是答案」；② 說「名字沒解析到，進 `_` 裡面找 `zzz`」。
**同一個拼法、同一個運算、兩個答案。** 三個選項各自要對這一格給出答案。

## 1. `_` 這個符號今天扛了幾個角色

〔量 2026-08-23，v0.30.0〕

| 位置 | 拼法 | 意思 | 狀態 |
| :--- | :--- | :--- | :--- |
| 值 | `x: _` | Top／未知 | 實作、規格皆有 |
| 錨 | `_.` | 這個宇宙的根 | 實作、規格皆有 |
| 錨 | `_{sha256:…}.` | 那個宇宙的根（**O67**） | v0.29.0 已出貨 |
| **鍵** | `_: X` | **① 預設分支**（模式 `_` 匹配一切） | **實作了** |
| **鍵** | `_: X` | **② 掛載點**（名字解析不到就進 X） | **沒實作**（O69 要它成立） |
| 鍵 | `_: X` | ③ 純粹的使用者資料 | 實作了（顯示存活） |

③ 不是第三種意義，是「當它兩種都不是的時候」。真正要裁的是 ①②。

**另有一個同義拼法**：`it`。〔讀 `lib.rs:3108–3113`〕
`get_field(ks).or(get_field("it")).or(get_field("_"))`——`it` 也是預設分支，**而且贏 `_`**。
〔量〕`({ a: 1, it: 88, _: 99 }) "zzz"` → **88**。
〔量〕`it` 這個用法在規格全文 **0 命中**——它是引擎獨有的拼法。

## 2. 兩個意義都寫在規格裡，而且寫在**同一個程式碼區塊**裡

這是本題最硬的一塊證據。`SPEC_09` §5.2 的正典範例：

```nlang
_: ~%Cond  ;; 合併到當前根節點          ← ② 掛載／匯入

;; …

grade: /cond [
    { @score & 90..: (@any -> "A") }
    { @score & 80..: (@any -> "B") }
    { _: (@any -> "F") }                ← ① 預設分支
]
```

**相隔七行，同一個拼法，兩個意思，而且規格自己沒有察覺。**

各自的出處：

*   **①**：`SPEC_07` §89 逐字「`_`（萬有集合）作為**預設分支**」；
    `TAG_REGISTRY` §119（`#no_matching_branch`）的提示行逐字叫使用者「增加 `_` 預設分支」。
*   **②**：`SYNTAX_05` §3 第 60 行的範例逐字 `_: ~%Cond`，
    §3 第 75 點逐字「**沒有 import 關鍵字**……匯入即把 `~%` 標準庫物件**交集**進一個路徑欄位」。

〔量〕**conformance 對 ① 與 ② 都是 0 個向量。**

## 2.5 來歷（用戶口述 2026-08-23）與三次漂移

**這一節改變了本檔的結論，放在這裡是因為它必須先讀。**

用戶口述的來歷有三段，而三段之間各有一次漂移：

1.  **原型是 CUE 的 pattern constraint** ——「對所有命名鍵／欄位施予相同約束」。
    〔量 2026-08-23〕**n/ 今天沒有這個東西**：`{ _: @int, a: 1, b: "x" }` 的 `b` 仍然是 `"x"`
    （若是約束就該 ⊥；對照 `{ b: @int & "x" }` 確實 `⊥ #conflict`「Value is not an integer」）。
    `_` 只是一個放著型別值的普通鍵。
2.  **到 n/ 變成「直接拿 combo 做 pattern matching」**，而 `_` 是最像 default 的拼法。
    ⟹ **第一次漂移：全稱約束 → 預設分支。** 這是唯一被實作的那一個。
3.  **匯入最初想的不是「`_` 這個鍵」，是交集 `_.` 這個 root combo 本身**——
    `<root> & ~%Cond & ~%Math`，用戶當時的話是「一個 **open & closed & closed**」。
    ⟹ **第二次漂移：`_` 從「根」變成「根裡的一個鍵」。**

### 2.5.1 而那條 meet 鏈從來不能成立

〔量 2026-08-23，v0.30.0〕

| 式子 | 結果 |
| :--- | :--- |
| `{} & ~%Cond` | ✅ `["/cond", "/if", "/match"]` —— **只有空根才行** |
| `{ v: 1 } & ~%Cond` | **⊥** `Key 'v' missing in incoming closed Cocoon` |
| `~%Cond & { v: 1 }` | **⊥** `Key 'v' missing in closed Cocoon` |
| `{} & ~%Cond & ~%Math` | **⊥** `Key 'one' missing in closed Cocoon` |
| `{ a: 1 } & { b: 2 }` | ✅ open & open 正常合併 |

**成因不是 bug，是規格。**`SPEC_03` §15.2 逐字：「當 Cocoon $C$ 參與合併運算 $C \sqcap X$ 時，
若 $X$ 包含 $C$ **未定義的任何非 Top 欄位**，則合併結果立即坍縮為 `⊥`」。
〔量，逐字驗證那句話〕`{ v: _ } & ~%Cond` → `["/cond","/if","/match","v"]` **通**；
`{ v: 1 } & ~%Cond` → ⊥。**Top 欄位穿得過封閉性，已知值穿不過。**

⟹ **根只要有一個自己的已知欄位，第一個 meet 就 ⊥；兩個模組則互相 ⊥。**
換句話說：**在 meet 讀法之下，匯入只在一個什麼都還不知道的程式裡合法。**

**最尖銳的一句**：`SPEC_09` §5.2 那個正典範例的根上有 `result` 與 `grade`，
**在 meet 讀法之下整段是 ⊥**。

⟹ **`_: X` 被實作成一個靜默的拷貝，不是偷懶**——它要表達的那個 meet
**對任何非平凡的程式都是 ⊥**，而拷貝是唯一不會當場炸掉的寫法。

### 2.5.2 「把模組改成 open」不是選項（但**在使用端打開**是——見 §4.5）

封閉性不是實作細節。`SPEC_03` §23 逐字把它接到
**Peres–Mermin 方塊的 $H^2$ obstruction**：「Cocoon 的 `{{}}` 正是這個 $H^2$ obstruction
在語言層的工程體現」。⟹ **拿掉模組的封閉性等於拿掉語言的 $H^2$。** 這條路關著。

### 2.5.3 這反而替 mount 說話

用戶說「掛載點的概念反而像是 n/ 獨有」——量測給出了它為什麼獨有：
**mount 是 closedness 這個問題的解。** 查找不到才進去，**從不把模組 meet 進根**，
所以封閉性擋不到它。

而且 mount 沒有背叛 meet 的故事，它**延長**了它：

*   兩者都有定義的地方（空根＋單一模組）**給同一個答案**——三個鍵。
*   **它們分歧的地方，正是 meet 變 ⊥ 的地方**（根有自己的欄位／兩個模組）。

⟹ **mount 是 meet 故事在 meet 失敗區的保守延拓。**

**但用戶指出的衝突點是真的，要寫清楚**：meet 是**值層、急切、對稱**；
mount 是**查找時、惰性、有方向**（本地遮蔽掛載）。O69 裁「mount 不是 cp」的時候，
**同時也離開了 meet**——而離開是有代價的：`&` 的交換律在掛載這一格不再成立。
這正是 §5.1 多重掛載為什麼變成一個真問題（先掛的先找？後掛的先找？），
而在 meet 讀法裡它根本不是問題（meet 可交換）——只是那個讀法通不了。

## 4. 選項（A／B／C）與其後果（§4.5–§4.9，2026-08-23 補量）

### A. 共用 `_:`，用**脈絡**分

*   **施用**脈絡（`combo arg`，查的是一個**鍵**）⟹ ①：`_` 的值就是答案。
*   **名字解析**脈絡（裸名查找，查的是一個**名字**）⟹ ②：進去繼續找。

**要付的**：規格得明文寫出「施用」與「名字解析」是兩個不同的運算，
並各自給 `_` 一條規則。**碰撞格由 ① 拿走**（它是一次施用，不是一次名字解析）。

**好處**：兩處既有文字（SPEC_07 §89／SYNTAX_05 §3）都不必改，
`TAG_REGISTRY` §119 那句寫給使用者的提示也不必改。

**風險**：這是**一個拼法兩個概念**，正好是「一個概念一種正準拼法」的反面。
使用者要先知道自己在哪個脈絡才知道 `_:` 是什麼意思——而
`SPEC_09` §5.2 那個區塊證明**連規格作者都沒分**。

### B. 分拼法：① 留給 `_:`，② 換一個

**要付的**：一個新拼法，且 `SYNTAX_05` §3 與 `SPEC_09` §5.2 的範例都要改。

**候選 ＝ `...`（spread），而它比本節初稿說的多做了很多。**
⚠ **本段於 2026-08-23 稍晚全面改寫**：初稿寫「`...` 的語義是 cp，抵觸 O69『mount 不是 cp』」，
**那個判斷是錯的**——`...` 不是 cp，它是**打開封閉之後的 meet**。詳見 **§4.5**。

### C. 統一成一條規則：兩者本來就是同一件事

一句話寫成：**「要的鍵不在這裡 ⟹ 交給 `_`」**，而「交給」的意思由 `_` 的值決定——

*   `_` 的值**不是** combo ⟹ 它就是答案（① 的行為，`{ _: "any" } 42` → `"any"`）
*   `_` 的值**是** combo ⟹ 在它裡面繼續找（② 的行為）

**要付的**：一條型別導向的規則，而 n/ 別處很少這樣寫。
且會改變一個今天有答案的式子：〔量〕`({ _: ~%Math, v: 1 }) "zzz"` 今天**回傳整個 `~%Math`**，
C 之下會變成「在 `~%Math` 裡找 `zzz`」⟹ ⊥。

**爆炸半徑〔量〕：零。** 樹上三支用到 `_:` 的測試，**沒有一支**把 combo 值的 `_` 施用到引數；
`{ _: "any" } 42`（`dispatch_test.rs:76`）在 C 之下**不變**，因為 `"any"` 不是 combo。

**好處**：一個拼法、一個概念、一句話。`SPEC_09` §5.2 那個區塊**同時變成對的**——
`_: ~%Cond` 往裡找，`{ _: (@any -> "F") }` 就是答案。

**那個「是不是 combo」的判準已經量過了，而且乾淨**〔量 2026-08-23〕：

| 值 | `type_of` | `keys` | C 之下 |
| :--- | :--- | :--- | :--- |
| `~%Math`／`~%Cond`／`{{ a: 1 }}`／`{ a: 1 }` | **`#combo`** | 非空，可導航 | 往裡找（②） |
| `(@any -> 1)`／`~%Math./add` | **`#logic`** | `[]` | 就是答案（①） |
| `"any"`／`5` | `#str`／`#int` | — | 就是答案（①） |

⟹ **態射不是 combo**，所以 `/cond`／`/match` 的預設分支在 C 之下**完全不動**，
`dispatch_test.rs:76` 的 `{ _: "any" } 42` 也不動。**§4 C 原本標的那個洞已補上，C 過關。**

⚠ **實作陷阱（先寫在這裡）**：判準必須用 `type_of`，**不可以用 `is_cocoon`**——
〔量〕`is_cocoon (~%Math)` 與 `is_cocoon ((@any -> 1))` **兩者都是 `#true`**，
拿它當判準會把態射也當成掛載點。

### 4.5 `...` 就是活下來的那個 meet（量測，2026-08-23）

§2.5 說原初的 meet 讀法從來不能成立，成因是封閉性。**那一節漏了一件事**：
不必改模組，`...` **在使用端就把封閉打開了**。

| 式子 | 結果 |
| :--- | :--- |
| `~%Cond & ~%Math` | **⊥** `Key 'one' missing in closed Cocoon` |
| `{ ...~%Cond, ...~%Math }` | **52 個鍵**；`./if (#true,…)` → `"y"`；`./add (1,2)` → `3` |
| `~%Reflection./is_cocoon ({ ...~%Math })` | **`#false`**（`~%Math` 自己是 `#true`） |

⟹ **`...` ＝ 先開再 meet。** `SPEC_03` §69 早就明講它吃「Combo **或 Cocoon**」的所有欄位。
**meet 這件事一直都在，只是承載它的是 `...` 不是 `&`。**

**而且它保住了格：可交換、不覆寫、碰撞即 ⊥。**〔量〕
`{ ...~%Math, one: 99 }` 與 `{ one: 99, ...~%Math }` **給同一個 ⊥**
（`Incompatible types: 99 vs 1`）——**兩個順序、同一個答案**。

**初稿擔心的兩件事都不成立**：
*   **cocoon**：它已經處理了（打開）。
*   **效果**：〔量〕`(~%Math./random).%effect` 與 `({ ...~%Math })./random).%effect` **皆 `#nondet`**；
    `/add` 兩邊皆 `#pure`。逐欄位保留，容器那層由 cocoon 的效果隔離（SPEC_03 §16）擋著。

**它真正做不到的只有一件事：覆寫。**

**與 Q-035 的交互已驗**：〔量〕`lib: { ...~%Math }` 進使用者 `data` 之後
`lib./add (1,2)` = `3`，而憑空發明的名字仍得 `#unprojected_builtin`
⟹ **spread 進使用者資料不會自我授權**，兩件事乾淨地疊在一起。

⚠ **spread 在頂層仍是壞的**（不影響本裁定，但落地時要知道）：〔量〕程式頂層寫
`...~%Math`，`oo status` 顯示它落在一個叫 `"..."` 的鍵底下、**沒有展開**，
同一份源碼的 `out: /add (1,2)` 維持未求值；**巢狀 `{ }` 內正常**。已入 Inbox。

### 4.6 交換律與覆寫不相容 —— 為什麼多重掛載一定是 list

meet **可交換、冪等**；「近的贏」兩者皆非。
⟹ **一旦要覆寫，就必須說清楚誰比較近，而那個「比較近」就是一個序。**

用戶 2026-08-23 的直覺（先說 poset，隨即改口 total order）**是對的，而且改口也對**：
兩個掛載可能都持有同一個名字，無法保證它們可比 ⟹ 需要**全序**
⟹ `_: [A, B]` **不是實作選擇，是被逼出來的形狀**。

### 4.7 n/ 今天已經有一個 overlay，而它不在值語言裡

〔讀 `eval.rs:795–812`〕裸名解析**先查 `ctx.root`，查不到才查 `ctx.standard_root`**；
〔讀 `lib.rs:99`〕註解逐字 *"user coordinates therefore win"*。

⟹ **覆寫是存在的：引擎層、剛好一層深、而且寫不出來。**

**這改變了 D-2 要裁的那句話。** 問題不是「要不要有 mount」，是
**「要不要讓引擎那一層變成可以寫出來的東西」**：

*   **要** ⟹ 就是 mount，就要序，就是 list（§4.6）。
*   **不要** ⟹ `...` 已經夠了，`_:` 純粹留給預設分支
    ——**這樣選項 C 反而不必處理掛載，它只是把萬用分支寫清楚**。

### 4.8 第四條路：承認 n/ 是格，不覆寫

你 import 了 `~%Math` 又自己定義 `one`，那就是你跟庫對 `one` 不同意，**⊥ 是誠實的答案**。
覆寫是命令式命名空間的習慣，不是格的習慣。

**這條路把問題解消而不是解決。** 代價明確：**引擎那一層的既有覆寫（§4.7）
會變成規格必須解釋的例外，而不是可以推廣的規則。**

### 4.9 pattern matching 那條：n/ 已經有一半

用戶提到「有些語言用 pattern matching 的語法拆 closed 的屬性，還能順便對位」。
〔量〕**n/ 已經有位置軸的那一半**：`((x, y) -> x + y)`
——解構在**態射參數位**，`tuple_destructure_probe_test.rs` 釘著。
〔量〕綁定位沒有：`{ (a, b): (1, 2) }` 是 **parse error**。

缺的是**名目軸、在綁定位**（`{ /add, /sub } <- ~%Math` 那種形狀）。
它會給 spread 與 mount 都給不了的東西：**選擇性匯入**——兩者今天都是全有全無。

**但選擇性匯入今天已經寫得出來**：〔量〕`add: ~%Math./add` 之後 `add (1,2)` → `3`
（479 B，對照整包 11,625 B）。⟹ **缺的不是能力，是一次拿很多個名字的人體工學。**
### 4.10 兩個檔各匯入一個模組（用戶 2026-08-23 提的自然用例）—— **今天就通**

`a.n` 寫 `_: { ...~%Math }`，`b.n` 寫 `_: { ...~%Cond }`，兩次 `evolve` 進同一個宇宙。

〔量 2026-08-23，v0.31.0，真倉提交後讀 CAS 物件〕**座標 `_` 的 `rules` ＝ 51，
`add` 與 `if` 皆在**（Math 48 rules ＋ 1 data `one`，Cond 3 rules ⟹ 48＋3 ＝ 51 ✓）。
換成普通座標 `x` 結果**逐字相同**。

⟹ **多重匯入在值層今天就成立，而且不需要任何順序。** 同名同前綴重複賦值即交集
（SYNTAX_03 邊界 #2），`...` 已把兩邊打開，兩個 open combo 的交集正常合併。
**§4.6 的「覆寫需要序」仍然成立，但「多重匯入需要序」這個動機在此消失**——
只要你不要覆寫，meet 自己就處理完了，而且可交換。

**但是什麼都解析不到。**〔量，同一個宇宙〕

| 寫法 | 結果 |
| :--- | :--- |
| `q1: /add (1,2)` | **未求值** |
| `q2: add (1,2)` | **未求值** |
| `q3: _./add (1,2)` | **未求值** |
| `q4: _._./add (1,2)` | **`3`** |

⟹ 值**組好了、放對地方了、也拿得到**——**缺的只有查找那一步**。
這是 §8 的結論在兩檔案情形下的複驗，也是**支持「`_:` 必須做事」最強的一個證據**：
不是東西不在，是沒有人去看。

### 4.11 ⚠ 順手撞到的缺陷：`&` 在兩邊都是 spread 時**靜默丟資料**

〔量 2026-08-23〕

| 式子 | 結果 |
| :--- | :--- |
| `{ /f: 1 } & { /g: 2 }` | `{ /f: 1, /g: 2 }` ✅ |
| `{ ...{ /f: 1 } } & { ...{ /g: 2 } }` | **`{ /f: 1 }`** ❌ `/g` 不見了 |
| `{ ...~%Math } & { ...~%Cond }` | **49 鍵**（Math 獨有，Cond 的 3 個沒了） |
| `{ ...~%Cond } & { ...~%Math }` | **3 鍵**（反過來，Math 的 49 個沒了） |
| `{ ...~%Cond } & { a: 1 }` | 4 鍵 ✅（只有一邊是 spread 時正常） |

⟹ **兩邊都是 spread 結果時，`&` 回傳左運算元、靜默丟掉右邊**，
**不可交換、無警告、無 ⊥**。而 `{ ...{ /f: 1 } }` 與 `{ /f: 1 }` **顯示完全相同** ——
**兩個印出來一模一樣的值，meet 起來不一樣。**

〔量，四個真二進位〕**v0.20.0／v0.26.0／PRE(`ebc0a5a`)／v0.31.0 全部相同** ⟹
**至少自 v0.20.0 既有，與 Q-035 及本題皆無關。**

**它與 §4.10 的關係**：同一個邏輯運算，走 `evolve` 的座標合併**是對的**（51 鍵），
走 `&` 運算子**是錯的**（丟一半）。⟹ **兩條路徑對「交集」給出不同答案。**
已入 `WORK_QUEUE` Inbox，標 `interrupt-candidate`（§2.2 第 2 款：可造成資料遺失）。
