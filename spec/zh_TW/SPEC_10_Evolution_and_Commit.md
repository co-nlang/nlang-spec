# n/ Language Specification - 演化、提交與因果邊界 (Evolution & Causal Boundary)

本章節定義 `n/` 宇宙如何隨著時間演化，以及由 Commit 序列構成的**因果邊界 (Causal Boundary)** 內的狀態變遷規律。
因果邊界定義了「已固化事實」與「未發生可能性」的幾何邊界。

---

## 1. 核心模型：宇宙的格論序列

`n/` 的時間軸不是連續的，而是一個由 **Commit** 組成的離散序列。
每個 Commit $C_n$ 代表宇宙在特定時刻的完整不可變快照。

- **宇宙即序列**：$U = \{C_0, C_1, C_2, ...\}$。
- **演化即交集**：從 $C_n$ 到 $C_{n+1}$ 的演化過程，本質上是對當前宇宙施加一組新的定義約束（交集運算）。

### 1.1 歷史認識論：觀測快照之固化

在 `n/` 中，**「宇宙歷史由因果邊界固化，而非由真理固化」**。

1.  **坍縮態固化 (Collapsed Anchoring)**：一個 Commit 捕獲的是節點在特定物理視界下的 **「坍縮觀測結果」**。

    > **⚠ 射程更正（2026-08-28 裁定 D46，Q-013）**：本款**只適用於不可重現的格**。
    > 一個 `%effect: #pure` 的格，其強制求值後的值相對於它的定義**不是新資訊**
    > ——它可以被重算——故 Commit **不得**以答案取代定義。逐條規範見 §2.3.1。
    > 本款原文寫於觀測與注入尚未分開之時（D42），當時「Commit 捕獲坍縮結果」
    > 對每一格都成立。
2.  **#blur 的歷史地位**：若某節點在提交時處於 `#blur` 狀態，則其生成的 `CAID_blur` 將被作為該 Commit 的物理組成部分進行雜湊。
3.  **因果邊界不變性**：一旦 Commit 固化，該 `CAID_blur` 在該歷史節點中的語義即被鎖定。即使未來發現了精確真相 $E$，該歷史 Commit 的幾何內容（認識論事實）**嚴禁**發生改變。
4.  **因果隔離**：真相的精煉必須透過新的演化步進（新的 Commit）來顯式應用，而非隱式地回溯性修改歷史。這確保了內容定址的絕對穩定性。

### 1.2 快照語義的拼寫歸屬（暫定裁決）

「記住宇宙在*那一刻*的樣子」是合法的需求。惰性化之後普通路徑欄位（`x: v`）存 thunk、
觀測時才固化，且 `<<path>>` 這個唯一的引用拼寫已歸活引用（Stage 3 C 案：evolve 期只存
路徑幾何、觀測時對*當下*宇宙解引用），因此「evolve 期凍值」在語言表層目前無拼寫。

**裁決：快照 ＝ Commit／CAID，不新增 source-level 語法。** 宇宙在某刻的凍結像即該刻
Commit 的 CAID（§1、§1.1——不可變、內容定址、可 `#diff`）；引用歷史快照 ＝ 引用該
Commit（引擎／REPL 層操作：`~%Repl./commit`、於 Commit 上下文 `~%Engine./observe`、`#diff`）。
此結論不為同一概念開第二種拼寫，符合語法極簡原則（一字一義）；且快照本是一個 Commit
序列（格論 meet 單調鏈）中唯一的**非單調**需求——欲在 $C_{n+1} \sqsubseteq C_n$ 精煉之後仍取
$C_n$ 的較粗值，任何 meet 皆無法回復，唯有 CAID 釘選——CAID-pin 是其理論正位，非權宜。

**有意留白（重開條件）**：對 **Staged 中間態**（§3.2；未固化、尚無 CAID）的 source-level
快照，或將某歷史 Commit 之值嵌為 source 內的活座標，目前**無拼寫**。是否值得為此付一個
語法，與 observe／evolve／commit／collapse API 的人體工學屬**同一問題**（皆取決於首次真實
使用的體感），故一併留待**首次使用複審**（見 `meta/ROADMAP.md` §3）後再議——**在此之前
勿發明語法**。

## 2. 核心演化態射 (Core Morphisms)

演化是透過一組標準的系統態射（System Morphisms）來驅動的。這些態射定義了語言與 Ouroboros 引擎交互的邏輯邊界。

### 2.1 `~%Engine./observe` (觀測)
- **語義**：在當前 Commit 的上下文（`_`）中，對路徑節點進行收斂運算。
- **性質**：純粹觀測，不改變宇宙狀態。

### 2.2 `~%Engine./evolve` (演化)
- **語義**：將新的定義注入當前宇宙的 **Staged (暫存區)**。
- **邏輯公式**：$Staged_{new} = Staged_{old} \sqcap Definition$。

#### 2.2.1 演化邊界的衝突揭露 **[Core Requirement，2026-08-08 新增]**

$Staged_{old} \sqcap Definition = \bot$ 時，演化**不得**發生。這一半引擎向來如此；
本節規範的是**它必須說出什麼**。

理由與 §4.1.2 同源而更基本：**一個只說「失敗了」的 `_|_` 是一個位元，
而一個位元不是格上的答案**。演化的最小單位是座標，衝突揭露的最小單位也應當是座標。

*   **必須指出座標（MUST）**：回報**必須**指出 `_|_` 落在哪一個座標。
*   **必須到葉（MUST）**：所指座標**必須**是實際發生矛盾的那一個，而**不得**只是
    該次演化所寫入的頂層欄位。二者在巢狀結構下相差任意多層。
*   **必須含錯誤碼（MUST）**：回報**必須**含 **[TAG_REGISTRY](./TAG_REGISTRY.md)** 中
    該 `%cause` 的名稱（如 `#conflict`），而非實作內部的列舉拼法。
*   **不得洩漏實作表示（MUST NOT）**：座標**不得**以引擎內部資料結構之形式呈現。
    尤其**不得**含原始碼位元組偏移、AST 節點名稱、或宿主語言的除錯輸出格式——
    那些是**關於引擎的事實**，不是關於使用者的宇宙的事實。
    〔2026-08-09：**此條的理由不限於座標**，已升為通則，見
    **[REAL_01](./REAL_01_Ouroboros_Engineering.md) §1.3**。
    本條保留，因為它在演化邊界上是**更強的**：那裡連「哪一個座標」都是規範的。〕
*   **各回報面一致（MUST）**：引擎若有多個向操作者回報的面（批次演化、互動式階段、
    服務回應等），各面**必須**給出同一個座標。**回報面之間的資訊差是實作細節，
    不是語義。**

#### 2.2.2 並行注入 **[Core Requirement，2026-08-30 新增；裁定 D49]**

§2.2.1 開頭那句「$Staged_{old} \sqcap Definition = \bot$ 時，演化**不得**發生」
連同「這一半引擎向來如此」，**預設了單一寫者**——它寫於工作集是一個被反覆改寫的
格子的時候。當工作集是一個**集合**（§3 第 2 款本來就這樣定義），
兩個注入可以**各自**與當時所見的集合相容，而**合起來**為 $\bot$。

*   **循序情形不變（MUST）**：注入前與當前集合的 meet 為 $\bot$ 時，
    該次演化**不得**發生，回報依 §2.2.1 各條。**這一半不因並行而放寬。**
*   **並行情形（MUST）**：兩筆注入**各自**通過上述檢查而其**聯合** fold 為 $\bot$ 時，
    **兩筆都必須保留**，且工作集**必須**回報 $\bot$ **落在哪一個座標**（§2.2.1 各條同樣適用），
    **離開碼不得為零**。
*   **不得以丟棄化解（MUST NOT）**：實作**不得**藉由丟掉其中一筆來回到單值狀態。
    「較晚的那一筆」需要一個先後序，而集合沒有序；**以到達順序裁決等於讓答案取決於排程**。
*   **由操作者化解**：$\bot$ 的工作集依 D33 由操作者處置。
    **提交必須失敗**（§4.1 的原子性保證），而非把 $\bot$ 靜默寫入歷史。

> **為什麼是保留而不是拒絕**：拒絕較晚者需要序。序在這一層不存在，
> 而為了拒絕而引入序，就是把並行控制搬進注入——那屬於另一條線（`pin` 的序列化）。
> **保留兩筆並誠實回報，是唯一不需要序也不需要協調的答案。**

> **自陳（2026-08-30）**：本節要求回報「哪一個座標」，但**未要求**多重衝突時
> 回報**哪一個**。〔量，參考實作〕兩組獨立衝突並存時，回報的座標隨執行變動
> ——因為 fold 在第一個 $\bot$ 停下，而遍歷序由本地識別碼決定。
> **該非決定性不影響身分**（提交被拒，$\bot$ 進不了歷史），但它是本節的已知留白。

> **論證性量測（2026-08-08，參考實作 v0.11.1）**：一個四層深的工作區，矛盾在
> `app.db.opts.retries`（六個葉子中的一個）。引擎當時回報的是
> `Conflict at Path(Path { anchor: Bare, segments: ["app"], span: Span { start: 0, end: 3 } })`
> ——即**該次演化所寫的頂層欄位名**，以宿主語言的除錯格式印出；而互動式階段
> 回報的全文是 `Evolution Conflict: Conflict`，連欄位都沒有。
> 同時，直接呼叫合併運算可取得 `path = Some("app.db.opts.retries")`：
> **葉層座標早已被算出，只是在型別邊界上被丟棄。**
> 拿掉這個量測，上列各條就只剩斷言——尤其「必須到葉」與「不得只是頂層欄位」
> 之所以分成兩條，正是因為實測顯示二者可以同時看起來像在回報座標。

> **自陳缺口（2026-08-08）**：本節要求座標**可被指認**，但**未要求**它可被**導航**。
> 二者今日不等價：需要引號的鍵（含 `.` 或空白者）**寫得進去**（`"a.b": 1` 合法），
> 而路徑語法**沒有對應的拼法**——`cfg."a.b"` 不可解析，`cfg.a.b` 則靜默取得 Top。
> 於是 `{ "a.b": … }` 與 `{ a: { b: … } }` 兩個結構不同的宇宙，其衝突座標
> **在字串上不可分**。**此為路徑語法之缺口，不在本節射程**；本節不因此弱化，
> 因為「說不出精確的話」與「說錯話」不是同一件事。修訂歸 SYNTAX 側。

### 2.3 `~%Repl./commit` (提交)
- **語義**：將當前 Staged 的內容與當前 Commit $C_n$ 合併，產生新的不可變快照 $C_{n+1}$。
- **原子性保證**：提交操作必須是事務性的。若合併結果產生 `_|_`，則提交失敗，HEAD 維持不變，且 Staged 區自動回滾至提交前的狀態。

#### 2.3.1 提交時保留什麼 **[Core Requirement，2026-08-28 新增；裁定 D46]**

**判準是 `%effect`，而且只有 `%effect`。**

*   **`#pure` 的格（MUST NOT）**：提交**不得**以其強制求值後的值取代它的定義。
    強制求值一個純格所得到的東西**可以被重算**，把它寫進歷史等於把一個
    可計算的關係存成物件。
*   **`#io` ／ `#nondet` ／ `#state` 的格（MUST）**：提交**必須**捕獲其強制求值
    後的值，並依 [SPEC_08](./SPEC_08_Meta_and_Runtime.md) §4.2.4 將活動標籤轉為
    `#cached`。這些格**重跑會得到別的答案**，若只留定義，那次觀測即永久遺失。
*   **`_|_`（MUST）**：撞到 `_|_` 者仍**必須**寫入 `_|_` 與其 `%cause`（§4.1.2）。
    一個誠實標記的矛盾是事實，不是待重算的配方。
*   **判準不得含其他維度（MUST NOT）**：特別是**不得**取決於父 Commit 在該鍵上
    持有什麼。若取決於它，同一支程式只因提交次數不同就會得到不同的根
    ——歷史粒度會變成身分的一部分。

> **這一款堵的是一個量到的資料遺失**〔量 2026-08-28，v0.37.0〕：提交強制求值每一格，
> 而一個當下算不出來的定義因此變成 `_`。`_` 是格的單位元，於是它不是變成錯的，
> 是在下一次 meet 中**消失**——補上它缺的輸入之後，那個欄位已經不在根裡。

### 2.4 `~%Engine./collapse` (坍縮)
- **語義**：將動態運算結果固化為新的靜態定義並產生 Commit。遵循格論收斂。

### 2.5 `~%Engine./refine` (精煉)
- **語義**：宣告一個精確節點是對既有模糊節點的格論精煉。建立 CAID 間的自動重定向鏈。
- **成立條件 (Proof Obligation)**：精煉宣告必須滿足 **幾何單調性**。若宣告 $ID_{old} \rightarrow ID_{new}$，則在數學上必須滿足：
    $$ID_{new} \sqsubseteq ID_{old}$$
    這代表新物件提供的資訊量必須等於或大於舊物件，且兩者在邏輯上不可衝突。
- **跨演算法精煉 (Cross-Algorithm Refinement)**：
    `#refine` Commit 支援跨雜湊演算法與跨格式版本的精煉宣告。其物理結構必須包含：
    ```nlang
    ;; #refine Commit 範例
    {
        %id: "hash:sha256:v1:refine-commit-id"
        %tags: #refine
        ~%Refine.source_caids: "hash:sha256:v1:old-id" | "hash:sha256:v1:alt-id"
        ~%Refine.target_caids: "hash:blake3:v2:new-id"
        %authority: {
            signer: "hash:sha256:v1:architect-caid" ;; 建築師身份
            signature: b"..."                       ;; Ed25519 簽名數據
            timestamp: t"2026-04-02T12:00:00Z"
        }
    }
    ```
- **驗證義務與能階**：
    引擎對精煉宣告的驗證強度取決於其物理能力：
    1.  **完全驗證 (Total Verification)**：若引擎具備解析兩者內容的能力，則 **必須** 執行 $ID_{new} \sqcap ID_{old} = ID_{new}$ 判定。若判定失敗（即不滿足子集關係），引擎應將該精煉宣告視為無效，並回傳 `#refinement_conflict`。
    2.  **不透明驗證 (Opaque Trust)**：若引擎無法解析目標 CAID（如演算法不匹配），則將幾何一致性的保證權交由 `%authority` 簽署者。
    3.  **因果一致性義務**：引擎必須確保重定向後的物件在所有與舊物件相關的格論運算中，產生的結果與原意圖相容。
    4.  **權威簽署驗證**：`#refine` Commit 必須包含有效的 `%authority` 結構。
        - **簽署對象**：該 Commit 的 CAID（計算雜湊時排除 `%authority` 欄位本身）。
        - **權威判定**：`signer` 必須存在於當前紀元的 `~%Official.architects` 集合中。該集合**必須**經帶外通道供給（**[REAL_01](./REAL_01_Ouroboros_Engineering.md)** §7.2 公鑰白名單 / 工作區斷言層）。引擎**不得**自行鑄入任何本地金鑰以充實該集合——由被檢查者供給檢查名單者，其檢查恆真，是**會說謊的審計面**而非驗證（**[SPEC_08](./SPEC_08_Meta_and_Runtime.md)** §6.1.2 裁定 P1 之同形：權威不得自授）。
        - **引導期特殊性**：引導期（Epoch < 0）之 Commit 預設不具備 `%authority`。其身分承襲由 **[ORDER_00](./ORDER_00_Interim_Constitution.md)** 定義之「創世精煉」清單硬編碼解決。
        - **名單必須是可滿足的** **[Core Requirement，2026-07-27 新增]**：實作**必須**使「非空白名單」成為一個**可通過**的檢查。若引擎的簽署身分逐行程重生，則不存在任何可寫入名單而該引擎會出示之值——此時非空名單使 `#refine` 於**兩個方向皆被拒**（帶簽章者「簽署者不在名單中」，未帶簽章者「非引導期缺 `%authority`」）。**無法被滿足的名單不是比無法失敗的名單更嚴格,而是同一個檢查**：兩者皆為恆定值，只是常數不同。故本條之前提是 **[REAL_01](./REAL_01_Ouroboros_Engineering.md)** §7.5 的穩定操作者身分；操作者以該節所定介面取得自身公鑰，經帶外通道置入名單，方構成一次真正的宣告。
        - **未驗證必須留痕** **[Core Requirement，2026-07-27 新增]**：白名單為空（無人宣告權威）時，引擎**得**接受未經驗證之 `#refine` 並繼續，但**必須**於該 Commit 上記錄「未經驗證」之事實，且該記錄**必須**可與「已對非空白名單完成密碼學驗證」相區分。**空白名單下即使附有有效簽章亦記為未驗證**——無可比對之集合時，簽章證明的是「某人簽了」，不是「有權者簽了」。記錄落於 Commit 審計面（非值），且不得改變既有 Commit 之 CAID。**理由**：本條為 §6.2 審計可查驗性與 **[REAL_03](./REAL_03_CAID_Protocol.md)** §6.6 條款四之同一律——不可憑檢視區分的審計面不成其為審計面。

## 3. 狀態機與指標 (State Machine & Pointers)

1.  **HEAD**：指向當前「活躍」的 Commit 快照。
2.  **Staged**：存儲自上一個 Commit 以來新注入但未提交的定義集合。
3.  **History**：有向無環圖（DAG）結構的 Commit 鏈。
4.  **Savepoint（○）**：見 §3.1。

### 3.1 Savepoint **[Core Requirement，2026-08-28 新增；2026-08-30 修訂；裁定 D43／D47／D50／D51]**

**Savepoint 記錄的是「看了多深」，Commit 記錄的是「它是什麼」。**
兩者不是同一條管線的兩個階段，是兩條不同的軸——這正是 §2.3.1 把深度擋在
Commit 之外的理由：深度**必須有地方去**，而那個地方是 Savepoint。

*   **耐久（MUST）**：每一個 Savepoint **必須**在產生時即為持久，且**必須**
    在 Commit 之後繼續存在。**「持久」與「提交」是兩件事**：Staged 是工作集，
    Savepoint 不是。
*   **身分（MUST NOT）**：Savepoint 的身分**不得**為 CAID。它是本地鑄造的識別碼。
    Savepoint **永不旅行**——它是持有者自己的觀測深度，對第二方沒有內容，
    故自我認證在此無代價可言亦無價值可言。
*   **前驅（MUST）**：每一個 Savepoint **必須**記錄一個**前驅集合**（`parents`）。
    該集合可為空（尚無前驅）、單元素（常態）或**多元素（並行分叉之後的匯流）**。
    由 `parents` 導出的祖先關係**必須**可判定。
    **[2026-08-30 修訂，D50]** 本款原文為「Savepoint **必須**帶有一個可判定的**先後序**」，
    而那句話把**兩件不同的事**壓成一句：**前驅是一個函數**（本地宣告的邊，「這一顆從哪一顆來」），
    **可比是一個關係**（「任兩顆判得出先後」）。前驅蘊含可判定的偏序，但**不蘊含全序**；
    全序蘊含前驅，但**把並行的分叉壓成一條線，而那條線的先後由排程決定**。
    判別器是圖：**畫一張歷史圖要的是覆蓋關係（哪一條邊該畫），而裸的偏序只給可達性。**
    〔來歷〕`parent` 單數是從 `Commit` 隨欄位搬過來的，而**控制面（`REAL_01` §2）
    自始即宣告 `"parents"` 為陣列** ⟹ 單數從來只活在實作的一半。
*   **前驅不得由到達順序決定（MUST NOT）**：兩個並行的注入若各自看見同一個前驅，
    **兩者都必須記錄該前驅**，**不得**以先後到達把其中一個排在另一個之後。
    以到達順序裁決等於讓歷史取決於排程（同 §2.2.2）。
*   **產生判準（MUST）**：一個 Savepoint 產生，當且僅當
    **(a) 注入改變了宇宙在格上的位置**，或 **(b) 觀測真的化約了一個 thunk**，
    或 **(c) 覆蓋關係改變了——即候選的 `parents` 不是「當前唯一前驅」那一個單元素集合**。
    判準**不得**以「消耗了燃料」表述——〔量 2026-08-28〕觀測邊界的燃料是固定
    進場費，一個原子與一條兩百步的加法鏈在同一個門檻上，故該表述等價於
    「每一次觀測」，判不出差別。

    **[2026-08-30 新增 (c)，D51]** (a) 與 (b) 都是**值層**的判準，而
    **兩個寫者收斂到同一個值是兩件發生過的事**：格上的位置沒有移動，
    但歷史上多了一次匯流。只有 (a)(b) 時那次匯流不留任何痕跡
    〔量 2026-08-30：兩個並行注入同一個定義 → 注入 2 個檔、Savepoint **1** 顆〕，
    於是分叉**永遠不合流**——紀錄說「還在分歧」而值說「已經收斂」。
    **一般理由**：**meet 冪等是值層不需要協調的理由，而事件不冪等；
    格的性質不是事件的性質。**

    **⚠ (c) 不得被讀成「每一次成功的注入都產生 Savepoint」（MUST NOT）。**
    循序的重複注入，其候選的 `parents` 恰為當前唯一前驅 T、且其值與 T 所記者相同
    ——**它什麼都沒有加**，故**不得**產生 Savepoint。
    把 (c) 實作成「一律產生」會讓一個沒有回收機制的集合在重複的無效操作下**無界成長**。
*   **`_|_` 亦產生 Savepoint（MUST）**：觀測坍縮為 `_|_` 時**必須**產生 Savepoint。
    `%cause` 掛在那個值上;若失敗的觀測不產生任何東西，`%cause` 就沒有可指的對象，
    那次失敗即不可檢查。

## 4. 並發與平行收斂語義 (Concurrency & Parallel Convergence)

`n/` 採用基於格論與內容雜湊的樂觀併發模型。

### 4.1 演化的原子性與合併競爭
`#commit` 操作在 Ouroboros 引擎中必須具備**強原子性 (Strong Atomicity)**。

1.  **晚到者自動收斂 (Optimistic Merge)**：
    若多個觀測者平行提交，引擎對「晚到者」自動進行以下邏輯：
    $C_{new} = HEAD_{current} \sqcap Staged_{incoming}$
2.  **衝突揭露 (Conflict Disclosure)**【2026-08-06 拆解，見 §4.1.2】：
    若自動收斂產生 `_|_`，引擎**必須**停下並回報，且**必須**在 `%cause` 中揭露導致衝突的競爭 Commit 之 CAID。**是否固化，由操作者決定**。
3.  **語義 Rebase**：
    開發者面臨併發衝突時，必須透過 `undo` 修正其 Staged 定義，或切換合併策略（如 `#favor_incoming`）重新進行提交。

#### 4.1.2 為什麼是「回報」而不是「中止」 **[Core Requirement，2026-08-06 拆解]**

本條原文作「若自動收斂產生 `_|_`，**提交必須立即終止**」。該句把**兩件不同的事**
綁在一起，而拆開之後兩半的歸屬不同：

| | 誰的責任 | 規範 |
| :--- | :--- | :--- |
| 收斂撞到 `_|_` | **觀測** | **必須停下並回報**（保留） |
| 要不要固化 | **操作者** | **不由本條代決** |

這是 §1「演化 ＝ 觀測 ＋ 固化」的同一個拆法，套在提交上。**觀測遇到矛盾時
停下並說出來是對的；但「因此不准記進歷史」是另一個決定，而那個決定屬於人。**
歷史由**因果邊界**固化而非由真理固化（§1.1）——一個被誠實標記的矛盾，
是一則關於那一刻的事實。

*   **粒度更正（MUST）**：本條所稱之「提交」不是固化的單位。**固化的最小單位是
    savepoint**；`#commit` 是其後、另外的一個動作（見 §1.2 之快照歸屬）。
*   **回報的內容（MUST）**：引擎**必須**指出 `_|_` 落在哪些座標，而不僅回報
    「成功」。靜默地固化一個帶矛盾的狀態，等於讓操作者在不知情下做決定。
*   **本條之射程（MUST NOT）**：本條治的是 §4.1.1 之**自動收斂**路徑——
    亦即操作者未做任何決定、僅因並發時序而落入 `_|_` 的場合。
    **顯式地固化一個含 `_|_` 的內容不在本條射程內。**

> **論證性量測（2026-08-06）**：本條原文之「中止」在參考實作中**有實作卻抓不到
> 任何東西**——它只在合併結果不是 Combo 時觸發，而兩個 Combo 相 meet 恆為
> 一個帶 `_|_` 欄位的 Combo。且該實作合併的是行程內載入的根，**從不重讀 HEAD**，
> 故 §4.1.1 之「晚到者」半邊亦不存在。⟹ **該條治的場合到不了，不是被違反。**
> 拿掉這個量測，「拆解」就只是措辭偏好。

### 4.2 平行觀測與快取隔離
純粹的觀測 (`#observe`) 可無限平行展開。引擎必須以「(CAID, 視界參數)」為複合鍵進行快取隔離，防止不完全的觀測結果（`#incomplete`）污染全域快取。
