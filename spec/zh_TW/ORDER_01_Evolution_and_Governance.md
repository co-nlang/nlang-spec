# ORDER_01：演化、治理與時間 (Evolution & Governance)

> **Authority**: [Normative / 演化程序標準]  

## 1. 語義紀元 (Semantic Epochs)

`n/` 的演化以 **「紀元 (Epoch)」** 為物理基準，確保宇宙的 CAID 系統具備絕對穩定性。

### 1.1 創世起點與唯一 CAID
*   **創世 CAID ($C_0$)**：每個 Epoch 必須具備唯一的創世雜湊。
*   **產生邏輯**：$C_0$ 是在當前 Epoch 規範化規則下，標準庫原始碼與初始權威（Architects）集合的幾何指紋。
*   **Epoch 0 起點**：定於 **v1.0.0** 正式發布之物理時刻。達成條件與啟動程序詳見 **[ORDER_00](./ORDER_00_Interim_Constitution.md)** **§5**。
*   **不可向後相容的語義變更**：指任何會導致相同 CAID 在新舊引擎下產生不同格論觀測結果的變更。
    *   **範例**：改變 `&` 運算子的結合律、修改原子型別的位元寬度、或更動 **[SPEC_01](./SPEC_01_Foundation_and_Lattice.md)** 定義的極小元素公設。
*   **CAID 演化與 Epoch**：純粹的 `oo fmt` 規範化規則調整（`fmt_version` 升級）僅為 CAID 演化，不構成 Epoch 躍遷。
*   **物理原點**：創世時刻一旦確定，即為不可修改的歷史事實，任何未來的 Epoch 躍遷皆以此為物理原點。

### 1.2 Epoch 躍遷程序 (The Leap Ceremony)
跨 Epoch 躍遷被視為宇宙的「硬分叉」，必須滿足以下極嚴格條件：
1.  **RFC 義務**：必須通過標準 RFC 流程，且詳細說明遷移路徑。
2.  **超高共識**：獲得 **全體建築師 3/4 (75%) 以上** 權重之明確同意簽章。
3.  **遷移證明**：新 Epoch 的創世 Commit 必須包含完整的 `%migration` 態射，用於將舊 Epoch 的狀態自動坍縮至新語義中。
4.  **權威連續性證明 (Authority Continuity Proof)**：
    - 新 Epoch 的創世節點 **必須** 包含一份由上一個 Epoch 全體活躍建築師 **絕對多數 (2/3)** 簽署的 **因果完整性證明 (CIP)**。
    - **語義**：這建立了跨越物理紀元的治理因果鏈，確保觀測者能沿著因果邊界追蹤至創世奇點，而不受金鑰輪換的影響。

### 1.3 跨 Epoch 共存原則
*   **歷史保全**：舊 Epoch 的所有 Commit 仍可被對應版本的引擎觀測。
*   **引擎義務**：新 Epoch 引擎 **必須** 能夠解析舊 Epoch 的 CAID，並透過 `%migration` 態射將其坍縮至新語義。
*   **版本標識**：引擎必須顯式宣告其支援的 Epoch 範圍。

### 1.4 凍結時間表
*   **Layer 0 (數學基礎)**：永久凍結。
*   **Layer 1 (語言系統)**：5 年凍結。
*   **Layer 2 (系統法度)**：穩定演進（每 2 年重審）。

## 2. 決策與共識機制 (Consensus Model)

### 2.1 規格裁決權 (The Architects)
規格的最終解釋權歸屬於 **n/ 建築師群**。其核心職責為守護 5 大不變性。

### 2.2 演化流程：RFC (Request for Comments)
1.  **提案資格**：
    *   **初期階段 (Initial Phase)**：持有未被列入 `~%Official.blacklist` 之有效 GitHub 帳號者。
    *   **正式階段 (Formal Phase)**：具備 **穩定 CAID 身份** 且獲得至少一位現任建築師「保薦 (Sponsorship)」者。
    *   **穩定 CAID 身份**：指已發布至少一個公開 Commit 且該 Commit 已被 `~%Official` 或至少一位建築師之公開宇宙引用之觀測者。
    *   **保薦配額 (Sponsorship Quota)**：每位建築師之「尚未結案（Pending）之有效保薦」數量上限為 **3 個**。保薦配額於提案收斂（通過或被最終否決）後自動釋放。
    *   **階段切換條件**：當建築師群規模達到 **5 人 (含)** 以上，或 Epoch 0 凍結期滿時，自動廢止初期階段規則，全面進入正式階段。
2.  **草案提交**：於官方指定之 `@co-nlang/rfcs` 儲存庫提交 Markdown 格式之提案。
3.  **技術審查 (Review)**：由至少一位現任建築師將提案標記為 `Review` 後開始，為期至少 **14 天**。
4.  **最後決策 (FCP)**：為期 **7 天**。
5.  **收斂判定**：採用「懶惰共識」。若無建築師提出「不變性違規」之否決，則視為通過。
6.  **否決冷卻**：提案被否決後，**相同提案者** 針對 **解決相同問題** 所提交之提案，在 **30 天** 內不得重複提交。是否屬於「相同問題」由建築師群最終裁決。

## 3. 版本號與廢棄機制

### 3.1 版本即別名
版本號是同一個 Epoch 下特定規格 Commit 的語義別名。

### 3.2 廢棄策略 (%deprecated)
1.  **標記義務**：擬移除之特性必須標記 `%deprecated` 元資訊，包含建議替代路徑。
2.  **同紀元保證**：在同一個 Epoch 內，廢棄特性 **必須** 保持「仍可被引擎正確解析與觀測」之狀態，嚴禁物理移除。
3.  **物理移除**：廢棄特性僅能在跨 Epoch 躍遷（Spec Leap）且具備 `%migration` 態射時方可物理移除。

## 4. 緊急修補程序 (Emergency Patch Protocol)

針對安全缺陷或不變性矛盾，允許啟動快速修補流程：

1.  **發起條件**：任一建築師發布「緊急狀態宣告」。
2.  **快速審議**：跳過 Review 階段，直接進入 **48 小時加速 FCP**。若 48 小時內有建築師未回應，其沉默視為棄權（其權重不計入共識分母）。
3.  **生效門檻**：
    *   **簽章門檻**：獲得包含提案人在內至少 **三位 (3)** 建築師之共同簽章。
    *   **參與度防衛 (Quorum Guard)**：最終贊成簽章之權重總數，**不得低於參與投票（非棄權）成員總權重的 1/2**。
    *   **例外情況**：若建築師總人數少於 3 人，則需 **全體一致同意**。
4.  **修補限制**：嚴禁引入新功能，僅限於恢復語義對齊。

## 5. 官方別名管理政策

### 5.1 內容准入
**`~%Official`** 內容更新必須通過 RFC 流程。納入標準包含自洽性、公益性與技術合規性。

### 5.2 命名空間黑名單
建築師群維護 `~%Official.blacklist` 節點。
*   **決議**：黑名單之增刪需經全體建築師過半數 (> 50%) 同意。
*   **效力隔離**：
    *   **新內容禁令**：黑名單生效後，該身份產生的所有 **新 Commit** 在發現時預設坍縮為 `_|_` (%cause: #blocked_by_policy)。
    *   **歷史警告**：在黑名單生效前已存在的歷史 Commit 仍可解析，但引擎應附帶 `%warn: #blocked_source` 標記。
*   **權限限制**：被列入黑名單之 CAID 身份立即失去 RFC 保薦資格。

## 7. 信任自舉與共識幾何 (Trust & Consensus)

### 7.1 投票者結構與共識規則
*   **`~%Governance.@Voter` 結構**：
    ```nlang
    {{
        pubkey: b""        ;; 成員 Ed25519 公鑰
        weight: @int & 1.. ;; 投票權重（必須為正整數）
        alias:  @str?      ;; 人類可讀別名 (選填)
    }}
    ```
*   **信任根**：`~%Official.architects` 定義為 `@{ [@~%Governance.@Voter] }` (Voter 之集合)。
*   **Epoch 0 初始值**：預設所有建築師權重均等為 **1**，初始名單硬編碼於創世規格。

### 7.2 共識計算規則
`~%Governance.consensus_rule` 在 Epoch 0 預設為 **`#strict_2_3_majority`**。
*   **判定公式**：$\frac{\sum \text{Weights of Support}}{\sum \text{Weights of (Support + Oppose)}} \ge \frac{2}{3}$。
*   **失效判定**：若分母為 0（全體棄權或沉默），則共識判定為失敗。
*   **投票型別**：
    - **贊成 (Support)**：計入分子與分母。
    - **反對 (Oppose)**：僅計入分母，不計入分子。
    - **棄權/沉默 (Abstain)**：不計入分子與分母。
*   **否決權 (Veto)**：任何建築師可基於「不變性違規」行使否決權，否決後提案立即終止。
    - **否決義務**：行使否決權必須附帶書面理由，明確指出違反之幾何不變性。
    - **否決覆議**：若其他建築師認為否決不當，可於否決發布後 **7 天內** 提出覆議。若獲得 **除否決者外，其餘建築師總權重 2/3 以上** 之簽章支持，可推翻該否決。

### 7.3 利益衝突與中立性
*   **揭露義務**：若提案涉及成員之商業或財務利益，該成員 **必須** 於 FCP 階段前主動公開其利益關係。
*   **強制迴避表決**：其餘成員可發起子提案，以 **全體過半數 (> 1/2)** 權重決定是否強制該成員在該提案中迴避。
*   **利益迴避 (Self-exclusion)**：涉及自身權限變更之提案，受影響成員之簽章權重自動計為 `0`。

### 7.4 權威委任細則 (Delegation)
1.  **授權性質**：核心層授權特定子路徑（如 `~%Official.std`）之行政權。
2.  **委任成員結構**：被授權者必須滿足 `@Voter` 結構，其 `weight` 由授權 Commit 顯式定義。
3.  **限制**：授權不可轉讓且核心層隨時可發布新 Commit 撤銷。
4.  **期限**：除非顯式標註 `%expires`，否則委任於 **「發生跨 Epoch 躍遷（Spec Leap）」** 之時自動屆期。

### 7.5 治理自癒與死鎖恢復 (Self-Healing)
為了防止因建築師集體失能（如私鑰遺失或長期不活躍）導致的演化停滯，建立以下自癒程序：
1.  **活躍度監測**：連續 **12 個月** 未在以下場合留下有效簽章者，被自動標記為 `#inactive`：
    - RFC 投票（贊成、反對或顯式宣告棄權）。
    - `~%Official` 命名空間之 Commit 簽署。
    - 參與緊急修補程序（*註：緊急修補中的沉默不計入活躍簽章*）。

```nlang
;; 活躍度計算虛擬碼
/is_active: (member: @Voter, current_time: @timestamp) -> {
    last_sig: member.last_signature_timestamp
    (current_time - last_sig) < (12 * 30 * 24 * 60 * 60)  ;; 12 個月
}
```

2.  **門檻自動降解**：當 `#inactive` 成員權重總和超過全體 1/3 時，共識計算之分母自動排除 `#inactive` 成員，直至其重新發布簽章啟用。
3.  **急迫性干預**：若 **全體活躍建築師（非 #inactive）人數為 0**，則視為治理停擺，立即開放社區自舉程序，不受「6 個月全體 inactive」之時限限制。
4.  **社區自舉 (Bootstrap Ceremony)**：
    *   **發起門檻**：至少 **10 位** 具備穩定 CAID 身份之貢獻者聯名發起。若穩定 CAID 身份者總數不足 10 人，則需 **所有穩定 CAID 身份者** 全體一致同意方可重置。
    *   **投票範圍**：所有具備穩定 CAID 身份者皆可投票。
    *   **投票權重**：社區自舉投票中，每位穩定 CAID 身份者之權重均等為 **1**。
    *   **通過門檻**：獲得所有參與投票（非棄權）者 **3/4 以上** 權重同意。
    *   **新建築師產生**：RFC 提案中必須明確提名新建築師候選人名單與權重分配，該名單隨 RFC 一併表決通過。
