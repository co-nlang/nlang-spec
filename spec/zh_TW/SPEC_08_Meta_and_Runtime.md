# n/ Language Specification - 運行時與計算視界 (Runtime & Computational Horizon)

本章節定義 Ouroboros 引擎的核心行為：虛擬欄位機制、錯誤處理，以及由 **Kochen-Specker 定理** 所定義的**計算視界 (Computational Horizon)** 的物理收斂策略。

---

## 1. 虛擬欄位機制 (Virtual Fields %)

使用 `%` 前綴的欄位代表節點的 **元幾何特徵 (Meta Geometry)**。為了確保實作一致性，規格將其分為兩類：

### 1.1 自省屬性 (Reflection - 唯讀)
這些欄位由 Ouroboros 引擎在觀測時即時計算，反映節點的物理與邏輯狀態。使用者**嚴禁**對其進行賦值。
- **範例**：`%id` (CAID / 譜幾何指紋), `%len` (容器長度), `%cause` (正交衝突歸因)。
- **行為**：任何試圖對其賦值的行為，在收斂時會被引擎忽略或判定為 `#privileged_required`。
- **對偶性觀測**：`%cause` 自身具備對偶特質——`node.%cause` 坍縮為衝突標籤（如 `#type_mismatch`）；`<<node.%cause>>`（結構態觀測**整條路徑**，非僅 `node`）則可獲取詳細的衝突上下文（詳見 **[REAL_04：因果結構](./REAL_04_Causal_Chain_Protocol.md)**）。`<<node>>.%cause`（先結構化 `node` 再坍縮讀取）與 `node.%cause` 等價——皆回傳標籤，因為未加 `<<>>` 的 `.` 導航一律坍縮，無論其左側是否已結構化。
- **生成條件**：`%cause` 僅在 `%val` 坍縮為 `_|_` 時由引擎產生；否則讀取為 `_`（未受約束的預設疊加態，語義是「無事實可回報」，**非**新的衝突）。
- **溯源能力**：在複雜的合併中，`%cause` 應指向第一個導致空集合的原子操作，以協助開發者定位邏輯斷裂點。
- **實作建議**：為了節省儲存成本，引擎可將 `%cause` 實作為**惰性（Lazy）**的。僅當觀測者顯式查詢該元欄位時，才回溯計算完整的因果鏈；同時，實作可選擇性地限制因果鏈的深度。

### 1.2 特徵屬性 (Trait - 可宣告)
這些欄位定義了節點的代數行為與本體論角色。使用者**可以**顯式宣告這些欄位，以覆蓋引擎的預設推斷。
- **範例**：`%kind` (強制視角角色), `%fmap` (定義算子行為), `%bind` (定義單子行為), `%termination_proof` (手動終止證明), `%fuel` (觀測能量配額)。
- **行為**：引擎在執行態射應用或管道演化時，會優先查詢這些 Trait 欄位。

### 1.3 字典與授權
元資訊的完整字典與創世預設值請見 **[SPEC_09](./SPEC_09_Standard_Library.md)**。
*   **意象**：`%` 象徵 Ouroboros 纏繞在權杖上，代表系統的自省與自省後的自我轉化。
*   **特權介入**：在 `#pin` 模式下，特權觀測者可強制修改特定的自省屬性（詳見 §6）。

## 2. 錯誤處理：正交衝突與邏輯防火牆 (Orthogonal Conflict)

`n/` 採用非嚴格（Non-strict）的錯誤處理模型。當觀測導致子空間坍縮至零維（Bottom）時，發生衝突。

### 2.1 可觀測與可恢復的衝突 (Catchable Conflicts)
觀測者可以使用子型別判定 `x <= _|_` 或三元運算 `? :` 在邏輯層建立防火牆。

**可恢復範圍**：
- **`#conflict`**：因合併不同原子或不相交型別產生的邏輯衝突（正交子空間交集為零）。
- **`#missing_key`**：存取封閉結構（Cocoon）中不存在的欄位。
- **`#caid_mismatch`**：發現過程中的內容驗證失敗。
- **`#blocking`**：違反系統級合規性或安全性限制（見 **[REAL_05](./REAL_05_Compliance_and_MVP.md)**）。
- **`#type_mismatch`**：輸入值不符合態射或型別約束。

**不可恢復範圍 (Unrecoverable Physical Limits)**：
- **`#divergent`**：因偵測到發散遞迴而觸發的保護。
- **`#fuel_exhausted`**：因觸及計算視界燃料限制而導致的觀測中斷。
- **`#timeout`**：因觸及物理時間限制而導致的觀測中斷。
- **`#max_lifting_exceeded`**：超過最大態射升寫深度。
- **`#cocoon_isolation_violation`**：試圖穿透 Cocoon 邊界進行自動升寫。

**判定理由**：實體物理限制（燃料、時間）與發散屬於「宇宙觀測能力」的缺失，無法透過內部的幾何邏輯進行自我補償。

```nlang
;; 合法：攔截型別衝突
safe_val: (input & @int <= _|_ ) ? 0 : input
```

*註：`? :` 為模式匹配的語法縮寫，詳見 **[SPEC_07](./SPEC_07_Logic_and_Pipe.md) §1.2 條件收斂語法糖**。*

### 2.2 崩潰診斷與溯源 (`%cause`)

當一個節點收斂為 `_|_` 時，Ouroboros 引擎會保留導致衝突的**因果鏈 (Causal Chain)**，並透過 `%cause` 元欄位提供給觀測者。

*   **對偶性觀測**：`%cause` 自身具備對偶特質——`node.%cause` 坍縮為衝突標籤（如 `#type_mismatch`）；`<<node.%cause>>`（結構態觀測**整條路徑**，非僅 `node`）則可獲取詳細的衝突上下文（詳見 **[REAL_04：因果結構](./REAL_04_Causal_Chain_Protocol.md)**）。`<<node>>.%cause`（先結構化 `node` 再坍縮讀取）與 `node.%cause` 等價——皆回傳標籤，因為未加 `<<>>` 的 `.` 導航一律坍縮，無論其左側是否已結構化。
*   **生成條件**：`%cause` 僅在 `%val` 坍縮為 `_|_` 時由引擎產生；否則讀取為 `_`（未受約束的預設疊加態，語義是「無事實可回報」，**非**新的衝突）。
*   **溯源能力**：在複雜的合併中，`%cause` 應指向第一個導致空集合的原子操作，以協助開發者定位邏輯斷裂點。
*   **實作建議**：為了節省儲存成本，引擎可將 `%cause` 實作為**惰性（Lazy）**的。僅當觀測者顯式查詢該元欄位時，才回溯計算完整的因果鏈；同時，實作可選擇性地限制因果鏈的深度。

## 3. Ouroboros 引擎行為：計算視界與 KS 定理

收斂受限於觀測者的物理能量。這一限制的底層法理由 **Kochen-Specker (KS) 定理** 提供：

*   **非全域性公設**：KS 定理證明了在維度 $\ge 3$ 的 Hilbert 空間中，不存在一個全域截面（Global Section）能同時賦予所有非交換觀測量確定的真值。這意味著「上帝視角」在數學上是不存在的（詳見 **[APP_04](./APP_04_Mathematical_Foundations.md)**）。
*   **局部性必然性**：由於全域真值的不存在，觀測行為必然是**上下文相關（Contextual）**的。這為 `n/` 的 **Bohrification**（將量子本體投影至交換視角）提供了數學必然性。
*   **視界作為對價**：計算視界（`%fuel`）並非單純的工程限制，而是觀測者在特定視角下，為了將「潛在可能性」坍縮為「局部真實」所必須支付的**幾何代價**。當燃料耗盡，觀測者觸及的是該視角下的物理邊界（KS 定理所定義的觀測極限），而非技術瓶頸。
*   **視界的拓撲深度（Papers IV, XX–XXII）**：視界不只是 KS（$H^2$，全域截面不存在）的對價，它還有一個**確切的拓撲深度**。對稱／Pauli（雙線性）資料的互文性障礙*截斷於* $H^3$（Paper XXII arity-resonance ceiling），所以視界的幾何內容恰好封頂於 $H^3$ 一層、不再更深——**這一半（封頂）是定理**，且不依賴下述比較。另一半須誠實標記：**16-cell 關聯子斷層**（視界的幾何內容，見 **[APP_07](./APP_07_The_Obstruction_Ladder.md)** §5 L3 列）與 cross-context anticommutation 的 modulus $[n_a]$ 指向*同一個 $H^3$ 現象*（同一個 $n=4/n\ge5$ 邊界、同一台 nerve-collapse 機器），但「同一個類」目前是**現象級證據而非定理**：IV↔XX **comparison map**（Paper XX §future work 明文 deferred，含 Čech/$\mathbb{Z}$ 係數的 Dixmier–Douady lift）需要兩條垂直腿——五角星腿已由 **self-representation map** 接上 ambient 類（item 23，closed mod Kudo）；16-cell 腿仍 open（RESEARCH_FRONTIER items 1、7）。因此「視界深度 = $H^3$ 拓撲」的精確狀態是 **await**（等 16-cell 腿）；`%fuel` 量的是把 $H^3$ bulk 坍縮為局部真實所需的能量，其**封頂**照 $\hbar_{n/}$ ceiling 讀（**[APP_06](./APP_06_Unified_Field_Theory.md)** §6.5），該 ceiling 為定理級。（2026-07-03 修正：先前版本把 self-representation map 與 comparison map 當同一物、宣稱「已焊接、為定理」——兩者同名不同物：前者是垂直橋 $\partial\Delta^4\to BV$，後者是水平比較。）

### 3.1 視界半徑與物理防線

引擎遵循由元資訊定義的物理限制，這被視為觀測者的「視界半徑」。規格層僅定義元欄位的 **語義功能**，不強制要求統一的物理單位或預設值。

> **視界本質**：在 `n/` 宇宙中，視界是 **觀測精度的對價**。燃料的消耗量與目標幾何物件的 **結構複雜度** 成正比。觀測者必須投入與其 **幾何厚度** 相對應的能量，才能將其坍縮為確定的原子。詳見 **[COSMOLOGY/05](./COSMOLOGY/05_PHYSICS_Horizons_and_Uncertainty.md)**。

| 元欄位 | 語義定義 |
| :--- | :--- |
| **`%fuel`** | **空間資源控制**：限制單次收斂觀測涉及的節點展開與遞迴總量（MBU）。 |
| **`%timeout`** | **時間資源控制**：限制單次收斂觀測允許的最大觀測時長（毫秒）。 |
| **`%max_branches`** | **複雜度限制 (分支)**：防止聯集分支過度膨脹導致的狀態空間爆炸。 |
| **`%max_unification_depth`** | **複雜度限制 (深度)**：防止遞迴 Combo 合併或態射應用導致的堆疊溢位。 |
| **`%max_lifting_depth`** | **複雜度限制 (升寫)**：防止管道 `|>` 在處理巢狀容器時發生無限遞迴升寫。 |
| **`%max_pattern_nodes`** | **複雜度限制 (匹配)**：限制單次模式匹配涉及的 AST 節點總量。 |

**規格義務 (Specification Obligations)**：
*   **優先級判定 (Priority Axiom)**：
    - **`%fuel` 優先**：若觀測因耗盡燃料而中斷，引擎 **可以** 根據策略回傳具備決定論 CAID 的 `#blur` 快照。
    - **`%timeout` 降級**：若觀測因物理超時而中斷，引擎 **嚴禁** 回傳 `#blur` 狀態，必須回傳無 CAID 的 `#incomplete` 暫態。這確保了不同運算速率的硬體對同一路徑的觀測事實保持一致。
*   **一致性要求**：在相同的視界參數輸入下，引擎產生的 `#blur` CAID **必須**具備決定論（詳見 **[SPEC_13](./SPEC_13_Ouroboros_Discovery_Protocol.md)**）。
*   **規範化計費 (Standardized Billing)**：為了確保跨引擎的 CAID 決定論，實作者**必須**遵循 **[REAL_01](./REAL_01_Ouroboros_Engineering.md) §10** 定義的最小計費單位 (MBU) 進行 `%fuel` 扣除。
*   **配額異常處理 (Quota Validation)**：
    *   **無效配額**：若觀測者設定了非數值、負數或超過物理極限的 `%fuel` 或 `%timeout`，引擎**必須**將其視為 `0` (即立即中斷觀測)，並回傳 `#incomplete` 或 `_|_` (視 `%strategy` 而定)。
    *   **資源繼承**：在遞迴觀測或 `./fetch` 過程中，若未顯式覆蓋配額，子觀測**必須**繼承並共用父觀測的剩餘配額。嚴禁在子觀測中「非法獲取」額外的隱性燃料。
*   **燃料消耗時機 (Consumption Timing)**：僅在**觀測階段 (Observation)** 消耗資源。當觀測者引發格論收斂或態射應用時，引擎開始對涉及的遞迴、分派、驗證或展開操作進行計費。

#### 3.1.1 最小計費單位 (Minimum Billing Unit, MBU) **[Core Requirement]**

為了確保跨引擎的 CAID 決定論與 OODP 互通性，本節定義標準的燃料消耗表。引擎**必須**遵循以下權重進行 `%fuel` 扣除：

| 操作 | MBU 消耗 | 說明 |
| :--- | :---: | :--- |
| **原子合併 (`&`)** | 1 | 兩個原子值的基礎合併。 |
| **Combo 欄位對齊** | 1 + 0.1 × n | 欄位數 n（無前綴 + @ + % + / + ~ + ~%）。 |
| **態射應用 (`/f x`)** | 10 + 5 × (模式深度) | 基礎 10，每層嵌套模式 +5。 |
| **函子升寫 (`%fmap`)** | 5 × 容器深度 | 深度從 1 開始計算。 |
| **單子綁定 (`%bind`)** | 8 × 管道長度 | 管道中每個態射消耗 8 MBU。 |
| **聯集展開 (`\|`)** | 2 × n | n 為展開後的分支數。 |
| **譜幾何計算 (LADD)** | 50 + 100 × dim | dim 為投影算子維度（以 64 為單位）。 |
| **GPP 驗證 (STARK)** | 500 | 每次 STARK 證明驗證的固定開銷。數字基於舊複數電路估計；待 $\mathbb{F}_2$ 指紋電路（APP_02 §6）校準，預期下修。 |
| **外部 FFI 調用** | 100 + 50 × 參數量 | 基礎 100，每個參數 +50。 |
| **CAID 計算** | 20 + 5 × 節點數 | 規範化與雜湊計算。 |
| **Binary-n/ 序列化** | 2 × byte 數 | 將 AST 轉換為位元流。 |

##### 計費累積與溢出

- **累積原則**：所有操作消耗採用**無條件進位 (Ceiling)**，最小消耗為 1 MBU。
- **溢出判定**：當累積消耗 ≥ `%fuel` 時，觀測立即中止，回傳 `#fuel_exhausted`。
- **部分計費**：觸及視界時，已消耗 MBU **不會**退還。

##### 引擎差異容許範圍

由於硬體架構差異，實作允許以下容許範圍：
- **標準作業**：實際消耗必須在表中值的 ±10% 範圍內。
- **證明驗證 (STARK)**：實際消耗必須在 ±20% 範圍內（因 GPU/CPU 差異）。
- **報告義務**：引擎必須在 `~%Engine./profile` 中提供實際消耗統計，供開發者校準。

### 3.2 觀測狀態機 (Observation State Machine)

引擎在增量收斂過程中，必須遵循以下狀態變遷規律：

| 狀態 | 屬性 | 說明 |
| :--- | :--- | :--- |
| **未觀測 (Lazy)** | 潛在 (Potential) | 節點已定義但尚未被任何路徑抵達。不消耗燃料。 |
| **已收斂 (Exact)** | 穩定 (Stable) | 運算已終止，結果為原子、Combo 或 Cocoon。具備唯一 CAID。 |
| **衝突 (Conflict / `_\|_`)** | 終態 (Terminal) | 偵測到邏輯不相容或發散。具備帶有因果鏈的穩定 CAID。 |
| **不完全 (#incomplete)** | **暫態 (Transient)** | 觀測因觸及視界（燃料/時間耗盡）而中斷。**不具備 CAID**，嚴禁提交 (Commit)。 |
| **模糊 (#blur)** | **快照 (Snapshot)** | 視界截面。**具備決定論 CAID**，可參與發現與提交。代表特定限制下的觀測事實。 |

*註：`#incomplete` 僅存在於主動觀測的內存中。若引擎根據 `%strategy: #blur` 決定將中斷點轉化為可傳遞狀態，則該節點從 `#incomplete` 提升（Lift）為 `#blur`。*

#### 3.2.1 語義邊界：暫態與快照
*   **#incomplete (不完全)**：代表觀測精度的「掛起」。它不是一種數據，而是一種「計算請求的餘額」。由於其結果隨時會隨燃料增加而變動，因此不具備內容定址的合法性。任何將 `#incomplete` 標記為 Commit 內容的行為都必須導致 `#privileged_commit` 權限校驗或直接坍縮為 `_|_`。
*   **#blur (模糊)**：代表觀測精度的「凍結」。它是對「當前視界參數 + 局部收斂結果」的內容雜湊。在 LADD 協議中，`#blur` 扮演了真理的預留空間。
    - **CAID 計算義務**：`#blur` 的 CAID **必須**包含序列化後的視界參數（%fuel 等，見 **[REAL_03](./REAL_03_CAID_Protocol.md)**）。
    - **穩定性承諾**：一旦固化為 `#blur` 的 Commit，其語義不再隨物理環境變動。它代表「在特定限制下的觀測事實」。

#### 3.2.2 觀測狀態遷移邏輯 (Transition Logic)

引擎在增量收斂過程中，必須遵循以下狀態變遷規律：

1.  **`Lazy` → `Incomplete`**：首次觀測節點，但計算因觸及視界限制（`%fuel` 耗盡或 `%timeout` 超時）而中斷。
2.  **`Incomplete` → `Exact`**：後續觀測提供了額外燃料，且計算成功收斂至穩定值。
3.  **`Incomplete` → `Conflict`**：後續觀測提供了額外燃料，但偵測到邏輯矛盾（如正交子空間合併）。
4.  **`Incomplete` → `Blur`**：根據策略（`%strategy: #blur`），將掛起的不完全態轉化為具備決定論 CAID 的可傳遞狀態。
5.  **`Blur` → `Exact` / `Conflict`**：當更高精度的 Commit（精煉）被導入宇宙時，動態觀測視窗透過「自動重定向」轉化為精確態或衝突態。

**不變性要求**：
- **單調性**：一旦進入 `Exact` 或 `Conflict` 狀態，嚴禁退回 `Incomplete` 或 `Blur`（除非切換 Commit 歷史）。
- **快取一致性**：`Exact` 結果的優先權永遠高於 `Blur` 與 `Incomplete`。
- **固化隔離 (Commit Isolation)**：自動重定向**嚴禁**影響已固化歷史 Commit 中的節點語義。精煉僅作為一種「建議」，必須透過顯式的演化管道進入歷史。

#### 3.2.3 觀測視窗與重定向邊界 (Observation Window)

為了平衡「開發時的靈活性」與「歷史的不可變性」，引擎必須明確界定 **觀測視窗** 的生命週期：

*   **開啟時機 (Window Open)**：
    1.  進入演化管道 (`|>`) 的求值過程。
    2.  執行系統原語 `~%Engine./observe` 或 `~%Discovery./fetch`。
    3.  處於 REPL 的互動式暫存區 (Staged Area)。
*   **重定向特權**：在視窗開啟期間，引擎獲取 **「幾何重定向特權」**。若觀測到 $ID_{blur}$ 且系統已知其對應的 $ID_{exact}$，則在內存中執行靜默替換。這確保了觀測者總是能看到當前燃料下最精確的真實。
*   **關閉時機 (Window Close)**：
    1.  觀測結果被寫入 **Commit (固化)**。一旦寫入歷史，該節點的 CAID 即被凍結，不再受後續精煉影響。
    2.  觀測結果被返回給外部系統（如 FFI 或 CLI 輸出）。
*   **語義隔離義務**：引擎必須確保關閉後的靜態數據 **嚴禁** 發生追溯性的重定向。這保護了內容定址宇宙的因果一致性。

#### 3.2.4 視界邊緣的狀態坍縮 (Strategy)

當運算觸及視界邊緣（燃料耗盡、超時、或超過最大分支/深度限制）時，節點會根據 `%strategy` 進行語義選擇：

| 策略 | 行為 |
| :--- | :--- |
| **`#blur` (預設)** | 容許將 `#incomplete` 作為有效狀態傳遞，讓宇宙維持在「部分觀測」的聯集狀態。具備決定論 CAID，可參與發現與提交。 |
| **`#strict`** | 任何觸及視界邊緣的運算立即判定為衝突 `_\|_`，確保宇宙的絕對清晰度。適合需要嚴格確定性的關鍵路徑。 |
| **`#approximate` (近似收斂)** | 允許引擎在資源不足或分支過多時，切換至啟發式收斂策略，以犧牲部分幾何精確度換取在有限資源內的近似解答。具備決定論 CAID，但標記為 `#approximate` 以區別於 `#exact`。 |

*   **實作義務**：近似算法的具體細節（如隨機性種子與版本化）由環境層定義，詳見 **[GUIDE_02: 引擎優化指南](./GUIDE_02_Engine_Optimization.md)**。

#### 3.2.5 執行差異與 CAID 穩定性 (Execution Variation & CAID Stability)

**核心原則**：CAID 的決定論僅保證「結構身分」的穩定性，不保證「數值結果」的位元級一致性。

| 層面 | 決定論來源 | 是否受執行策略影響 |
| :--- | :--- | :--- |
| **結構身分（CAID）** | EML 樹/AST 的規範化結構（靜態） | ❌ 否 |
| **數值結果（觀測）** | 硬體浮點運算（動態） | ✅ 是（在容差內） |
| **譜特徵（Sketch）** | 投影算子的幾何特徵 | ⚠️ 穩定（誤差在量子化閾值內視為相同） |

**EML 執行範例**：

```nlang
;; EML 樹結構（靜態）
/ln: 2.0    ;; 語義上等價於 eml(1, eml(eml(1, 2.0), 1))

;; 觀測結果（動態）
#eml_native 策略: 0.6931471805599453    ;; 純 EML 計算，誤差較大
#expanded_opt 策略: 0.6931471805599453  ;; 硬體 log 指令，誤差較小
```

**重要區分**：
- 兩種策略產生的 **CAID 相同**（因為結構相同）
- 兩種策略產生的 **數值結果可能微異**（在 IEEE 754 容差範圍內）
- 這是預期行為，非錯誤

**數值比較語義**：
```nlang
/ln(2.0) == /ln(2.0)     ;; ✅ 結構相等（比較 CAID）
/ln(2.0) === /ln(2.0)    ;; ⚠️ 數值相等（可能因執行差異而 #false）

;; 推薦：使用誤差容忍比較
abs(/ln(2.0) - 0.693) < 1e-10   ;; ✅ 數值近似相等
```

**效果標記**：
- 引擎使用優化執行時，**應**標記 `%effect: #approximate`
- 這允許下游觀測者識別「數值結果可能因硬體/策略而異」的情況

### 3.3 增量收斂與視界快取

Ouroboros 維護有向無環圖（DAG）來追蹤視界內的依賴關係。
*   **局部無效化**：當視界內的某個定義改變時，僅重新觀測受影響的下游。
*   **惰性求值**：只有當觀測者試圖穿透視界看向某個節點時，該節點才會從「潛在狀態」坍縮為「觀測狀態」。

### 3.4 系統反映 (System Reflection)

除了虛擬元欄位 (`%`) 提供的靜態幾何自省外，Ouroboros 引擎透過**系統物件 (`~%`)** 向觀測者反映其當前的會話狀態、提示符與特權層級。

*   **語義區分**：`%` 欄位描述「節點是什麼」；`~%` 物件描述「引擎正在做什麼」。
*   **交互參照**：關於 `~%repl` 的詳細結構、環境合成 (%import) 以及控制介面的規格，詳見 **[SPEC_11: 反映與合成](./SPEC_11_Reflection_and_Synthesis.md)**。

### 3.5 Bohrification 投射 ($Q \dashv B$)

Bohrification 伴隨（Paper VI）描述了全域量子代數 $Q$ 與其古典語境 sheaf $B = \Gamma(\mathcal{C}(A))$ 之間的雙向投射。引擎提供兩個內建操作：

| 操作 | 方向 | 功能 | 對應 |
|:---|:---:|:---|:---:|
| `~%Engine./project_down` | $Q \to B$ | 將量子 Combo 投影到指定 MASA 語境，產生 `#blur` 局部截面 | Bohrification |
| `~%Engine./project_up` | $B \to Q$ | 從多個古典語境的局部截面重建全域量子疊加態 | L-S reconstruction |

**`project_down` 行為：**

```nlang
~%Engine./project_down {
    target: @Combo         ;; 要投影的量子態
    masa:   @caid          ;; 目標 MASA 的 CAID（REAL_03 v2 格式）
}
;; 結果：target 在 masa 語境下的局部截面（#blur）
```

**`project_up` 行為：**

```nlang
~%Engine./project_up {
    sections: [@Combo]     ;; 從多個 MASA 取得的局部截面
}
;; 結果：各截面的量子疊加態（#exact or union of #blur）
```

> **數學保證注意**：`project_up` 的理論基礎是 $Q \dashv B$ 伴隨的 left adjoint $\mathcal{Q}$，其顯式構造目前為開放問題（系列論文 Paper VI, Conjecture）。
> 當輸入截面來自不相容的量子態時，輸出可能為無物理意義的疊加——引擎應以 `#blur` 標記此類情況。此限制不影響向下操作的 `project_down`（其數學保證來自 Bohrification 的標準結果）。

**限制：**
- `project_down` 需要目標 MASA 的 CAID 具有 `<masa_ref>`（v2 格式）。
- `project_up` 的輸入截面必須來自不同的 MASA（同一 MASA 的多個截面無疊加意義）。
- 兩者皆受當前 `%fuel` 視界限制：`project_up` 需要至少 $2 \times$ 標準 meet 的燃料。

## 4. 代數效果系統 (Algebraic Effect System)

`n/` 的副作用追蹤基於格論聯集。效果（Effect）被視為一種特殊的標籤集合，隨觀測路徑向上傳播，追蹤子空間的干涉與糾纏。

### 4.1 效果的多重性與組合 (Multiplicity)

*   **基礎標籤**：`#pure` (預設), `#io`, `#nondet`, `#state`, `#cached`。
    - `#pure`：么正變換，不與環境糾纏。
    - `#io`：與外部子空間進行觀測交換。
    - `#nondet`：包含非決定性坍縮（如隨機數）。
    - `#state`：依賴或修改環境投影狀態。
    - `#cached`：曾有干涉結果已被固化為穩定 CAID 投影。

*   **組合矩陣 (Effect Composition Table)**：
    當兩個節點（或態射與參數）的效果進行組合時，結果標籤遵循「資訊疊加」原則。`#pure` 為單位元。

| & | #pure | #io | #nondet | #state | #cached |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **#pure** | #pure | #io | #nondet | #state | #cached |
| **#io** | #io | #io | #io \| #nondet | #io \| #state | **#io \| #cached** |
| **#nondet** | #nondet | #io \| #nondet | #nondet | #nondet \| #state | **#nondet \| #cached** |
| **#state** | #state | #io \| #state | #nondet \| #state | #state | **#state \| #cached** |
| **#cached** | #cached | #io \| #cached | #nondet \| #cached | #state \| #cached | #cached |

*註：`#io` 與 `#nondet` 為「活動副作用 (Active Effects)」，代表尚待物理執行的不確定性。`#cached` 為「固化副作用 (Solidified Effects)」，代表其歷史因果雖包含 IO，但結果已錨定於穩定 CAID。兩者組合時應並行標註，以利於引擎執行部分快取重用與增量收斂。*

*   **效果冪等律 (Effect Idempotency)**：效果標籤的組合遵循格論聯集性質。在任何觀測路徑下，$E \mid E = E$。引擎在合成 `%effect` 欄位時，必須對標籤集合進行去重化簡，嚴禁產生如 `#io | #io` 的冗餘描述。

*   **CAID 參與義務**：`%effect` 欄位被視為節點幾何本體的一部分，**必須**參與 CAID 的規範化計算。這確保了語義上不純的程式無法透過偽裝為 `#pure` 來獲取相同的內容標識。

*   **自訂效果標籤 (`#ext:`)**：為了支援特定實作或領域的需求，開發者可定義自訂標籤。
    - **格式**：`#ext:<identifier>` (例如 `#ext:file_write`, `#ext:db_query`)。
    - **處理**：引擎應將未知的 `#ext:` 標籤視為非純粹（Non-pure）效果，除非開發者透過特權模式顯式處理。

### 4.2 傳染與傳播規則 (Propagation)

1.  **結構傳染**：若 Combo 的任一欄位具備效果 $E$，則該 Combo 自身的 `%effect = parent.%effect | E$。這確保了外部觀測者在接觸容器時就能預知其內部的潛在副作用。
    *   **Cocoon 隔離 (Shield)**：若容器為 **Cocoon `{{ }}`**，則上述傳染規則在 Cocoon 邊界停止。Cocoon 自身的 `%effect` 保持為 `#pure` (或其定義層級的效果)，內部的副作用被「封印」在視界內，扮演量子退相干屏蔽。
2.  **態射傳染**：態射 $f$ 應用於 $x$ 時，結果的效果為 $Effect(f) \mid Effect(x)$。這防止了純態射在處理不純輸入時遺失效果標記。
3.  **解封傳染 (Unboxing)**：使用 `...` 運算子展開一個具色 Cocoon 時，其內部的效果標籤將立即污染目標作用域。
4.  **停止邊界與固化 (Solidification)**：
    - **轉化規則**：一旦數據被坍縮並獲得穩定 CAID，其 `%effect` 欄位中的 **活動標籤 (#io, #nondet, #state)** 必須在觀測結果中被轉化（固化）為 **#cached** 標籤。
    - **語義**：這象徵著該資訊的「不確定性」已被歷史固化。
    - **重新激活**：若一個 `#cached` 節點參與了新的態射運算，且該態射本身具備活動副作用，則結果將重新獲得活動標籤（見 §4.1 組合矩陣）。

### 4.3 效果遮蔽與處理 (Masking / Handlers)

為了讓帶副作用的程式碼能在純粹語境下安全運行，`n/` 提供以下機制：

*   **`~%Effect./runPure`**：這是一個特殊的系統態射，用於將特定的副作用「坍縮」為穩定數據。
    *   **授權條件**：此操作**僅能**在目前視界具備有效的 `%privilege_token`（即特權模式）時被呼叫。
    *   **語義固化**：它將傳入的含副作用節點強制執行，並將結果節點的 `%effect` 標籤「固化」為 `#pure`。這向引擎承諾：「此處產生的 `#io` 已被外部環境代理，對後續的格論觀測可視為純粹且決定性的數據」。此操作不影響原始定義的 CAID，僅影響觀測結果。
*   **靜態守護**：在預設的純粹上下文 (`#pure`) 中，若意外觸發了 `#io` 觀測，引擎將其阻擋並坍縮為 `_|_$ (含 `%cause: #effect_violation`)。

### 4.4 觀測配額預設行為 (Quotas Default)

若觀測過程中耗盡了 `%fuel` 或 `%timeout`：
*   **預設行為**：引擎採用 **`#blur`** 策略，返回一個包含已知資訊與 `#incomplete` 標記的聯集態。這能保證互動式環境（如 REPL）不會因為單個複雜節點而完全鎖死。
*   **生產建議**：在關鍵的業務路徑中，建議顯式設定 `%strategy: #strict`，確保只有完整收斂的結果才能被提交。

## 5. 外部邊界與 FFI 異常處理

`n/` 的格論模型與現實世界的互動是透過 **外部邊界 (External Boundary)** 實現的。外部世界（HTTP、SQL、傳統函式庫）被視為一種「不穩定的聯集來源」。

### 5.1 副作用的坍縮 (IO Collapse)

1.  **非決定性映射**：一個 `#io` 請求（如 HTTP GET）在 `n/` 中被視為對該 CAID 內容的觀測請求。
2.  **物理合成**：引擎負責進行物理層操作，並將回傳結果轉換（Synthesize）為 `n/` 的 Combo。
3.  **格論固化**：一旦結果進入 `n/` 視界並被觀測，該結果必須被 **坍縮 (Collapse)** 為一個帶有 CAID 的靜態定義，才能與其他節點進行交集合併。這防止了外部世界的變動破壞 `n/` 的不變性。

### 5.2 外接系統介面 (Foreign Interface)

*   **SQL 合成**：數據庫查詢結果被合成為包含數值索引的 List 或帶有 Key 的 Combo。
*   **HTTP 映射**：請求與回應模型被對齊為特定的型別邊界。

### 5.3 FFI 異常處理 (FFI Panic Handling)

外部邊界（FFI）是 `n/` 決定論宇宙的最脆弱點。

*   **純粹性與沙箱**：若外部函數標記為 `#pure`，引擎**必須**遵循 **[REAL_01](./REAL_01_Ouroboros_Engineering.md) §5.2.1** 定義的沙箱隔離義務，確保環境欄位與時間不影響觀測結果。
*   **物理崩潰 (Panic)**：若外部程式發生段錯誤 (Segfault) 或未捕獲的異常，引擎**必須**捕獲此崩潰，並將該觀測節點坍縮為 `_|_`，標記 `%cause: #ffi_panic`。
*   **惡意回傳 (Malformation)**：若外部程式回傳了與預期型別不符或物理格式錯誤的 Combo 結構，引擎將其判定為 `_|_`，標記 `%cause: #ffi_malformed`。
*   **安全性原則**：外部邊界的錯誤**嚴禁**導致 `n/` 引擎本身的程序退出（Exit）。引擎必須維持物理穩定性，僅讓發生錯誤的邏輯路徑坍縮。

## 6. 權限與特權模式 (Privileged Mode)

特權模式提供繞過格論約束的能力。為了守護宇宙完整性，其安全管理被視為**核心規格義務 (Core Requirement)**。

### 6.1 准入與安全義務

1.  **實體隔離**：引擎實作者**必須**保證特權指令與普通收斂指令在物理線程或內存空間上具備可審計的隔離。
2.  **令牌強制化**：執行特權操作**必須**提供有效的 `%privilege_token`。嚴禁進行任何「隱式」或「無令牌」的特權後門。
3.  **因果標記**：由特權操作產生的所有變更，其 `%cause` **必須**標記為 `#privileged_*` 標籤，以維持全域溯源透明度。

### 6.2 特權操作清單與審計

| 操作 | 說明 | 審計標籤 (%cause) |
| :--- | :--- | :--- |
| `#pin` | 直接覆蓋節點值，跳過收斂邏輯。 | `#privileged_pin` |
| `#commit`（含衝突）| 強制提交含有 `_\|_` 的 Staged 狀態。 | `#privileged_commit` |
| `#rollback` | 移動 HEAD 指標至任意歷史 Commit。 | 無 (由歷史鏈追蹤) |
| `#squash` | 壓縮並清除 Commit 歷史片段。 | `#privileged_squash` |
| `#effect_override` | 強制將含副作用節點標記為 `#pure`。 | `#privileged_effect` |

**語義保證**：
*   **CAID 一致性**：特權操作產生的節點與 Commit，其內容雜湊（`%id`）依然基於其最終的物理結構計算。特權操作改變的是「收斂過程」，而非「幾何指紋」。
*   **透明度**：由特權操作產生的 Commit 必須在元資訊中標註其干預性質，以便下游觀測者進行信任評估。

### 6.3 設計理由

特權模式的存在不是鼓勵繞過格論，而是承認現實：有時開發者需要強制修復一個引擎無法自動解決的邏輯衝突，或對已知正確的值進行直接注入（如從數據庫載入的快取）。

*   **安全管理**：特權 Token 的發放、生命週期與撤銷機制不屬於語言規格，詳見 **[REAL_02](./REAL_02_Ouroboros_Protocols.md)**。
