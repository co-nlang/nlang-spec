# n/ Language Specification - 態射與管道 (Morphism & Pipe)

> **態射與管道的分工（2026-07-20 語義梳理，編輯性；總綱見 SPEC_00 §1.2「靜與動」）**：
> 態射是轉換的**算子**（靜態規則物件，體在定義處捕獲自己的世界——裸名走詞法鏈、
> `^` 讀定義側容器鏈、呼叫點資料唯一通道是 `$`；§4.2.3），應用／管道是轉換的
> **行為**（演化即提交 §4.3；Kleisli bind §4.1 註）。「態射是轉換」讀作名詞，
> 不是動詞；態射體內 `^` 讀定義側（2026-07-19 裁定）由此是推論而非特例。

## 1. 態射定義 (Morphism)

態射（Morphism）是從輸入集合到輸出集合的映射。

*   **語法**：`/name: input -> output`
*   **同構與模式匹配**（2026-10-09 改寫，裁定 D95–D97）：
    有至少一個模式鍵 `@{ … }:` 的 Combo 是一張**分派表**——不論它是否被賦給 Logic 欄位（以 `/` 開頭）——它是**一個**態射：各分支在這一張表裡互比特定性（極小元素規則，§1.1）。**表不是它各分支箭頭的 `|`**：`|` 的成員不互比特定性，被施用時逐支分配（§5.2 定義 4，D104，2026-10-11；原文「同構展開為一個聯集的態射集合」與此相反，已改寫）。表內每個非 meta 鍵都是一個**輸入約束**：模式鍵是該模式、數字鍵是該整數、標籤鍵是該標籤、`_:` 是預設分支（§1.1.1）、其餘的命名鍵與引號鍵是該字串。**鍵依它拼出的座標讀**（D107，2026-10-13）：鍵是座標字串，表把它讀成剖析器讀這個記號時得到的原子；引號只用來拼出名字，不改變座標——`#a:` 與 `"#a":` 是同一個座標，在表裡都是標籤 `#a`，`"4":` 是整數 `4`，`"_":` 是預設分支。長得像別種原子的字串約束寫 `@{ "#a" }:`。（原文「命名鍵與引號鍵是該字串」在座標只是字串時與「標籤鍵是該標籤」不能同時成立——`{ #a: 2 }` 與 `{ "#a": 2 }` 同址，而 D101 要經 `&` 組出的表與字面表同一組位元組；已改寫。）Value 是該分支的輸出，分支值裡的 `$` 是被匹配的輸入（[SYNTAX_12](./SYNTAX_12_Pipe_Ternary_and_Context.md) §4 #5）。
    **裸 `@T:` 鍵永遠是座標 `T` 的型別面向**（[SYNTAX_05](./SYNTAX_05_Prefix_Ontology.md) §2 #1），不是分派約束；約束一律寫 `@{ @T }:`（D96）。本節範例原寫 `@int:`，於 2026-10-09 改為 `@{ @int }:`；原範例另用了 v0.27.0 已移除的頂層 `/add`，一併改為 `+`。
    ```nlang
    /fib: {
        0: 0
        1: 1
        @{ @int }: (/fib ($ - 1)) + (/fib ($ - 2))
    }
    ```

### 1.1 態射分派與特異性 (Dispatching & Specificity)

當一個態射被應用於輸入 $x$ 時，引擎執行以下 **分派演算法 (Dispatching Algorithm)**：

1.  **匹配過濾**：將 $x$ 與每一個分支的**模式**（輸入約束；§1.1.2）進行合併嘗試。保留所有未產生 `_|_` 的分支。
2.  **特異性排序**：對所有匹配成功的分支，調用 **[SPEC_06](./SPEC_06_Unification_Logic.md) §1.5** 定義的「極小元素規則 (Minimal Element Rule)」進行篩選。
3.  **選擇與執行**：
    - **唯一匹配**：若存在唯一的極小元素（最特定匹配），則回傳其結果。
    - **多重匹配**：若存在多個互不可比（Incomparable）的極小元素，結果為這些分支結果的**格論聯集 (`|`)**。
    - **無匹配 (Empty Selection)**：若所有分支皆不匹配（交集皆為 `_|_`），則結果收斂為 **`_|_` (Bottom)**，標記 `%cause: #no_matching_branch`。
    - **優先序**：顯式的態射分支定義具有最高優先權，僅在所有顯式分支皆不匹配時，引擎才嘗試進行自動升寫（見 §5.4）。

#### 1.1.1 `_` 作為預設分支（2026-08-24 明文化；裁定 O72 ⑥）

**規範內容只有一句：`_:` 作為鍵的意義是分派的預設分支，而且只有這一個意義。**

**`_:` 不是掛載點，也不是匯入。** 一個名為 `_` 的欄位就是一個普通欄位，
它把值放在**下一層**；匯入請用展開運算子 `...`
（**[SYNTAX_05](./SYNTAX_05_Prefix_Ontology.md)** §4 邊界 #6）。
覆寫**不進**值語言：同名即交集（**[SPEC_03](./SPEC_03_Combo_System.md)** §3.1 碰撞合併）。

其應有的行為由 §1.1 加上「`_` 是萬有集合（Top）」導出：`_` 與任何輸入合併皆不為 `_|_`，
故永遠留在匹配集合中；而它是格上的最大元，依「極小元素規則」永遠最不特定，
於是**僅當沒有任何其他分支匹配時**才被選中。

> **已兌現（2026-10-09，Q-076；2026-08-24 的兌現缺口註記結清）**〔量，參考實作 Q-076 交付〕
> 態射分派上的預設分支現已成立：`{ @{ @int & 4.. }: "A", _: "other" }` 施於 `"s"` 得 `"other"`（原為 `_|_ #conflict`「Rule has no %code」）、施於 `5` 得 `"A"`。
> 原註記指出的引擎獨有同義拼法 `it` **已退場**（D98）：`({ a: 1, it: 88, _: 99 }) "zzz"` 得 `99`——`it` 只是一個普通的鍵，不是預設分支，也不是綁定名。

#### 1.1.2 模式是值；分派表與依鍵查找（2026-10-09 新增；裁定 D95–D99；2026-10-10 補導航、正規形、印出，裁定 D100–D102）

**模式是一個值，與它的分支住在一起。** 分派表的模式鍵與 `->` 的左手邊，其模式皆以**值**存於 `%rules` 的該分支（`%pattern`），分支的名字是模式的位址（[REAL_03](./REAL_03_CAID_Protocol.md) §5.2 第 3 條）。**模式的印出字串永不被讀回成模式**（D95）——印出形不是單射：`@{ @int }` 與 `@{ @str }` 同印成 `"{...}"`，字串 `"4..6"` 與區間 `4..6` 同印。此前參考引擎正是以印出字串當鍵、再由字串**猜回**模式，猜不回者一律 Top：`{ @{ @int }: "A" } "s"` 得 `"A"`，兩個型別分支的表對一切輸入皆 `_|_`。

*   **`->` 的左手邊是模式**：`(@int -> 7) "s"` 無匹配；`(x @int -> x) 4` 得 `4`（`x` 綁定輸入，`@int` 是模式）；標籤、區間、聯集、字面同。**只有綁定名的箭頭**（`x -> …`、`(x y -> …)`、`((a, b) -> …)`、`_ -> …`）沒有模式、匹配一切，形如 §5.2 定義 1。
*   **沒有模式鍵的 Combo 被施用是依鍵查找**（D97）：只有**原子**引數有鍵（其印出名）；非原子引數落到 `_:`，再無則 `_|_ #no_matching_branch`。分派落空同為 `#no_matching_branch`。
*   **同一個約束出現多次是同一個分支，所有本體相交**——不論它們寫在同一個字面裡、經 `&`、還是經後續的演化聚在一起；本體**只在分派選中該分支時**才求值；兩個本體的衝突只屬於該分支，別的引數照常作答。同一分支的多個本體是一個**集合**：相交的先後、分組、重複不改變值的位址。
    > **D109（2026-10-14，Q-087）：「只在選中時求值」的射程，與未求值本體的身分。** 觀測一張表——印出、`=`、`run --observe`、提交——**不執行任何沒被選中的分支**，不論它的效應有沒有被預測到。**可能有所作為的本體是程式碼**：本體自由出現 `$`（它要等被匹配的輸入，[SYNTAX_12](./SYNTAX_12_Pipe_Ternary_and_Context.md) §4 #5）、可能帶效應、或施用了某個態射（一支箭頭的效應標記不說它的本體做什麼）——這樣的本體在選中之前不求值；它以程式碼定址、比 `=`、印源碼，身分像箭頭本體：表達式加它捕捉的名字，不是周圍每一框的全部。**封閉、純、且不施用任何東西的本體可以提前求值**，以值定址（`{ @{ 4 }: 1 + 1 } = { @{ 4 }: 2 }`）——是許可，不是義務。
    > **判例（〔量，v0.88.0；v0.78.0 同〕）**：`{ @{ @int }: 1, _: ~%Io./write_file (…) }` 在印出、`=`、提交時都寫檔；提交把 `k: { @{ @int }: $ * 10 }` 凍成 ⊥ `#no_context`（`_.k 5` 得 ⊥，就地 `50`），`$ + 1`、`$ * 2`、`$ * 10` 三表同根；`{ @{ @int }: $ + 1 } = { @{ @int }: $ * 2 }` 得 `#true`。第一輪修正以「預測帶效應」為判準，施用一支寫檔的箭頭（`f 1`）仍在觀測時寫檔——**預測是手段，判準是可能**。
*   **`it` 退場**（D98）：它不是鍵的特例，也不是綁定名；隱含綁定 `0` 同退場。
*   **舊引擎寫下的表不猜**（D99）：帶 `%morphism`、沒有 `%rules`／`%builtin`、以印出名為鍵的 Combo 被施用，答 `_|_ #pattern_not_kept`。
*   **表上的導航讀分支存著的值**（D100）：`t.k` 讀「鍵 `k` 所拼出的約束」那一支——鍵→約束對照與施用同一張（`.j` 是字串 `"j"`、`.1` 是整數 1、`._` 是 `_:` 那一支）；本體裡的 `$` 是該約束；同一約束的多個本體相交。**讀回的就是存著的值**：存的是箭頭或另一張表，讀回的就是那個箭頭、那張表，不把它施用在約束上——施用才施用（分派選中的分支存著箭頭，把它施用在輸入上：`{ @{ @int }: (x -> x + 1) } 5` 得 `6`）。沒有該分支 ⟹ `_`（開放世界），**不落到 `_:`**——`_:` 只有分派一義（§1.1.1）；導航問「這個座標存了什麼」，施用問「這個輸入答什麼」。**作用域面是同一條**：在表的作用域框裡以裸名找 `n`（[SPEC_04](./SPEC_04_Navigation_and_Duality.md) §2.1）就是讀 `.n`，故分支本體看得到兄弟鍵：`{ @{ @int }: n + 1, n: 5 } 3` 得 `6`。有模式鍵的箭頭依 D97 也是表：`("f" -> 7).f` 得 `7`；箭頭是封閉繭，沒有該分支時答 `#missing_key`（`(x @str -> 7).f`）。
*   **一張表只有一個正規形**（D101）：資料鍵是分支，同一分支的本體是以位址為鍵的集合；字面、`&`（兩向）、`|>`、展開 `...`、根的逐次演化，產生**同一組位元組**——同一個格元素一個位址（n/ 是 CvRDT，`meta/oo/commit.md` §1.1.6）。
    > **判例（2026-10-13，Q-084）：正規形是讀它的人看到的形。** 展開 `...` 帶進來的分支在落地之前不存在；**一個 Combo 是不是表、是不是態射、有哪些分支，必須在它的展開落地之後才讀**——不論它住在哪裡（頂層、欄位、提交後讀回）、從哪個入口被讀（施用、`|>`、`|>` 右邊聯集的成員、被選中的分支值）。〔量，v0.85.0；v0.75.0 起〕欄位以 thunk 存，強制它時展開未落地 ⟹ `{ t: { ...{ @{ @int }: 1 }, _: 0 } }.t 7` 得 `0`（應 `1`），選錯的分支照常執行；`=`、印出、導航卻都對——**兩個 `=` 相等的值分派不同，正是本款要防的**。
    > **判例（2026-10-22，Q-098）：逐次演化是同一組寫入。** 工作集一旦有模式鍵就是表，之後一次演化寫的資料鍵落成它的分支；那筆寫入必須照樣在工作集裡、照樣進提交的根——**同一組寫入不論分成幾次演化、寫在一檔或分檔，提交前的工作集與提交後的根相同**。〔量，v0.98.0；v0.79.0 起〕演化 `@{ @int }: 0`、再演化 `x: 3`：兩次退出碼 0，`oo status` 不列 `x: 3`，提交後 `_.x` 讀 `_`（寫在同一檔讀 `3`）；`@{ "b" }: 2` 再演化 `b: 3`，`_.b` 讀 `2`，而先後倒過來、同一檔、中間先提交皆為同一根、讀 ⊥。引擎依寫下的鍵回工作集找普通欄位以重建這次演化的記錄，表把它存成分支，找不到就丟了。
*   **表依約束印**（D102）：原子約束的分支以鍵的拼法印（`j: 5`、`1: "a"`、`#a: 1`、`_: 0`）——**只在裸拼法讀回同一個約束時**（D107）；字串約束 `@{ "4" }:`、`@{ "_" }:`、`@{ "#a" }:` 照原樣印，裸印會讀回整數、預設分支、標籤（[SYNTAX_02](./SYNTAX_02_Literals_and_Atoms.md) §4 #12）。其餘以 `@{ <模式的印出形> }:` 印（`@{ @int }: "n"`）；**表裡沒有任何一列會印成 `@{ … }:` 時，每一列都印 `@{ … }:`**（D108，2026-10-13）——`{ @{ 4 }: "f", @{ _ }: "z" }`、`{ @{ "j" }: 1 }`，因為沒有模式鍵的 Combo 讀回是依鍵查找的普通 Combo（D97），不是表；同一分支的多個本體**各印一列、鍵重複**（D109，2026-10-14；原文「以 ` & ` 相接」讀回是一個本體，已改寫）——`{ @{ 4 }: "g", @{ 4 }: "f" }`；摘要名只在耐久形。拼法不規範（D64）；印出形**永不讀回**（D95）。

> **邊界與未兌現（2026-10-09 誠實記帳）**〔量，Q-076 交付〕
> *   印出一張表再把文字貼回去，**不保證**得到同一張表——這是 D95 的直接後果：印出形不是耐久形（[SPEC_05](./SPEC_05_The_Trinity_Isomorphism.md) §3.3 `%code` 款同理）。〔量，Q-077 交付〕D102 之後，原子與型別約束的表貼回去相等（`{ @{ @int }: "n", j: 5 }`）；同一約束兩個本體印成 `k: 1 & 2`，貼回去是沒有模式鍵的普通 Combo，`=` 為 `#false`。
> *   `x @{ 4.. } -> …` 被剖析成施用而非型別註記，模式靜默成為 Top（匹配一切，`x` 未綁）；`x @(1 | 2) -> …` 正確。剖析器的缺口，已列佇列。
> *   `@int & 4..` 求值成 `4..`（`@int` 不見）、`@string`（不存在的型別名）與任何值合併成功——兩者使某些「看起來不同」的模式其實是同一個值。已列佇列。

> **已兌現（2026-10-10，Q-077；上方 2026-10-09 的「字面與 `&` 位址不同、導航不一致」一款結清）**〔量，參考實作 Q-077 交付〕
> 字面與 `&` 同一個根、`=` 為 `#true`；`.j`、`.k`、`.1`、`.cfg.a` 在字面、`&` 兩向、`|>`、`...`、根、提交後讀回皆同一答案；字面表的導航、作用域、印出恢復 v0.77.0 的讀數（v0.78.0 帶出去而 `CHANGELOG` 漏記的退化）。

#### 情境 A：層級匹配 (Poset Selection)
```nlang
/func: {
    1: 1
    @{ @int }: 0
}
;; 觀測 /func 1
;; 結果: 1 (因為 1 比 @int 更具體，它是唯一的極小元素)
```

> **已結（2026-10-09，D96）**：2026-08-24 記下本例 `/func 7` 得 `_|_`，因為裸 `@int:` 不參與匹配過濾。裁定 D96：裸 `@T:` **永遠**是型別面向，不是分派約束——落差不在引擎，在範例的拼法。範例已改寫為 `@{ @int }:`；〔量，Q-076 交付〕`/func 1` 得 `1`、`/func 7` 得 `0`。

#### 情境 B：不可比性與歧義 (Incomparability)
若兩個模式重疊但互不為子集，引擎會保留聯集結果，這被視為一種資訊不足的狀態。
```nlang
/func: {
    @{ @int & 4.. }: "A"
    @{ @int & ..6 }: "B"
}
;; 觀測 /func 5
;; 結果: "A" | "B" (因為 {4..} 與 {..6} 互不包含，皆為極小元素)
```

#### 情境 C：消除歧義 (Disambiguation)
開發者可以透過定義更精確的「交叉集合」來強制收斂至單一結果。
```nlang
/func: {
    @{ @int & 4.. }: "A"
    @{ @int & ..6 }: "B"
    @{ @int & 4..6 }: "C"          ;; 交叉集合直接寫閉閉區間
}
;; 觀測 /func 5
;; 結果: "C" (因為 {4..6} 是其它所有匹配項的子集，成為唯一的極小元素)
```
這套機制確保了定義的合併（Merging）是穩定的，且不依賴程式碼的排列順序。

> [!TIP] **歧義管理與聯集態預警 (Ambiguity Management)**
>
> 雖然 `n/` 容許聯集態 (`A | B`) 作為有效的觀測結果，但過度的歧義會隨演化管道擴散並消耗大量的 `%max_branches` 配額。
> 1. **主動消除**：建議開發者在發現 `/logic` 產生多重極小元素時，定義更具體的交叉集合。
> 2. **靜態偵測**：IDE 或 `oo check` 應在偵測到態射定義中存在「重疊但互不為子集」的分支時發出警告。
> 3. **顯式收斂**：若聯集是預期的，但後續運算需要唯一值，可使用 `~%System./first` 或自定義篩選邏輯進行強行坍縮。

### 1.2 條件收斂語法糖 (Ternary Sugar `? :`)
為了簡化常見的二元分支觀測，`n/` 提供 `? :` 運算子作為模式匹配的縮寫。

*   **語法**：`Condition ? Success : Failure`
*   **展開規則**：
    ```nlang
    Condition |> {
        #true: Success
        #false: Failure
        _: _|_
    }
    ```
*   **語義**：`Condition` 必須收斂至 `@bool`。若為 `#true` 則坍縮至第一分支，若為 `#false` 則坍縮至第二分支。`_` (萬有集合) 作為預設分支，確保非布爾值輸入收斂為 `_|_`。

## 2. 微分態射 (Differential Morphisms)

上同調障礙階梯中的 differential $d_r$ 在 `n/` 中對應為內建態射族 `/%differential.{1,2,3}`：

| 態射 | 對應 $d_r$ | 運算 | 行為 |
|:---|:---:|---|---|
| `/%differential.1` | $d_1$ | meet 收斂 `&` | 嘗試局部合併。若成功則繼續；若產生 $H^1$ 相位差則記錄於 `%cause` |
| `/%differential.2` | $d_2$ | 衝突分支 | 將不可調和的 $H^2$ 衝突分支保留為聯集（SPEC_06 §1.7 非嚴格性）|
| `/%differential.3` | $d_3$ | 視界擴展 | 遇 $H^3$ 障礙時請求更多 `%fuel`，擴大計算視界後重試 |

這些態射由引擎自動調用，不需要使用者顯式編寫。它們存在於規格中是為了讓引擎的收斂流程可以被觀察和除錯：

```nlang
;; 查詢當前狀態在第幾級 differential
~%Engine./state.differential
;; 可能結果：#d1_converging | #d2_branching | #d3_horizon

;; 引擎日誌中的 differential 記錄
%cause: {
  %differential: 2
  %obstruction_degree: #h2_sign
  %branches: 2
}
```

$d_4$ 及以上為預留，對應 Epilogue 的更高階障礙（女巫攻擊、信任隔離）。

## 3. 應用與柯里化 (Application & Currying)
*   **Prefix 呼叫**：`add 2 4`（等同於 `(add 2) 4`）。
*   **Infix 呼叫**：`/` 開頭者支援 `2 /add 4`。
*   **一個 Combo 引數**：`add {0: 2, 1: 4}`。**引數永遠是一個 Combo**——`add (2, 4)` 是本形的糖，鍵恰為 `0`、`1`。**態射綁定哪些鍵，由它自己的模式宣告**（見 [SYNTAX_09](./SYNTAX_09_Morphism_Application.md) §2）。

    > **⟵ 更正（2026-08-26，O76）。** 本行原文為「**結構化傳入**：支援 `add {x: 2, y: 4}`，會自動進行結構化統一（Structural Unification）」，自 Genesis（2026-04-01）起如此。**兩處都不成立**：（i）〔量，引擎 Genesis `71177b7`，2026-05-23〕`math.add` **逐字**取 `get_field("0")`／`get_field("1")`，`x`／`y` **從來不是引數鍵**（那是 Rust 區域變數名）；（ii）「結構化統一」作為一種**獨立於位置式之外的匹配機制****不存在**——今天以具名鍵取引數的七個內建走的是同一條路，只是鍵不叫 `0`、`1`。⟹ 慣例由三種收斂為**兩種**，差別在**鍵名由誰宣告**，不在匹配機制。
*   **欄位邊界保護 (`!field_start`)**：在進行連續的態射應用時，若遇到下一個欄位的定義起點（如 `key:`），解析器會自動終止當前運算。這使得 `n/` 不需要括號或逗號也能精準切分表達式與結構欄位（詳見 **[SPEC_14](./SPEC_14_Formal_Grammar.md)** §1 欄位邊界保護）。

## 4. 演化管道 `|>` (The Pipe)
`|>` 是宇宙演化的核心，負責將靜態的 Combo 轉化為新的狀態快照。

*   **優先權**：**Level 13** (低於聯集 `|`，高於三元運算 `? :`)。
*   **結合律 (Associativity)**：**左結合 (Left-to-Right)**。多重管道 `a |> /f |> /g` 語義上等價於 `(a |> /f) |> /g`。
*   **聯集分布律 (Distributivity)**：管道演化對格論聯集具備分布性。
    - 公式：`(A | B) |> /f  ≡  (A |> /f) | (B |> /f)`。
    - 語義：當演化對象處於疊加態時，演化行為會平等地作用於所有分支。
    - 右值是聯集時同樣分配：`x |> (/f | /g)  ≡  (x |> /f) | (x |> /g)`——右值不論是寫出來的、經路徑或欄位到達的（D104，2026-10-11；§5.2 定義 4）。兩側皆然：⊥ 的分支剪掉（`|` 的單位元）；全為 ⊥ 時取主因果、原樣傳出（`REAL_04` §4）。

### 4.1 演化形態
管道的右值（RHS）決定了演化的具體方式。**右值是哪一種，在它的展開落地之後才判**（Q-084）：`7 |> { ...{ @{ @int }: 1 }, _: 0 }` 是態射演化，得 `1`——v0.85.0 以前在落地前判，把它當結構演化去合併，得 `#conflict`。右值是聯集時，逐成員判。

1.  **態射演化 (Morphism Pipe)**：`input |> /Logic`
    *   語法糖，等價於 `/Logic input`。支援鏈式呼叫：`data |> /f |> /g`。
2.  **結構演化 (Transformer Combo)**：`input |> { ~new: $.val + 1, ...$ }`
    *   最核心的用法。右側的 `{}` 是一個臨時轉換器，`$` 指向進入管道的完整結構。
3.  **原子演化 (Atomic Collapse)**：`input |> #success`
    *   強制將輸入與特定原子進行交集。若輸入不相容則收斂為 `_|_`。

> **範疇論讀法（2026-07-06，docs/discussion/018）**：`|>` 是疊加 monad（值格上帶零的
> 自由 join-半格，效應分級）的 **Kleisli bind**；三形態實為**兩個嵌入**——態射＝Kleisli
> 箭頭（自由），轉換器＝精煉箭頭 `λx. x & t[$:=x]`（永不離開 ↓x；「賦值即交集」在箭頭
> 世界的唯一延伸），原子＝精煉箭頭的常數特例。§4 的「疊加態平等演化」「演化即提交」
> 即 bind 可加性與零吸收——定律表已全數引擎驗證（`pipe_laws_test.rs`；兩處引擎違規
> 2026-07-06 修復，ENGINE_SYNC #18）。密封容器 × 轉換器 → `_|_` 是精煉箭頭的定理而非
> 缺陷（SYNTAX_12 §4 #7）。

### 4.2 上下文符號 `$` (Context Anchor)

`$` 意象為觀測者在演化樹上的立足點——管道內部的臨時世界與外部宇宙之間的**唯一**橋樑。
（設計理由：`n/` 在格論下沒有真正的區域變數；「執行期臨時記憶體」的角色由 `|>` 承接——
管道中途的 Combo 皆為暫態，唯最終結果坍縮回 `_` root 樹。`$` 即區分管道內外的 this。）

> **2026-07-05 修訂（P1–P5 定案）**：舊版的「`^^` 跨管道溯源」與「裸 Combo 重綁 `$`」
> 敘述**作廢**（errata）；`^` 系列完全回歸路徑面（SPEC_04／SYNTAX_03）。

#### 4.2.1 規則（P1–P5）

1.  **P1 重綁點唯一**：`$` 只在**演化邊界**重綁——`|>` 與態射應用（apply ≡ 單步演化，§4.1）。
    裸容器（`{}`／`{{}}`／`[]`）**永不**重綁。
2.  **P2 管道不可穿透**：無跨管道溯源。取外層上下文一律**顯式傳遞**：
    ```nlang
    user |> {
        greeting: "Hello, " + $.name
        action: { act: "Login", user: $ } |> {
            msg: `Action: ${$.act}, User: ${$.user.name}`
        }
    }
    ```
3.  **P3 自由 `$` ＝ 開放項**：含自由 `$` 的表達式可定義、可儲存（不觀測不坍縮）；
    觀測時由**最近包圍演化**動態綁定；無綁定觀測 → `_|_`（`%cause: #no_context`）。
    開放項的 CAID ＝ 含 `$` 符號的語法幾何（身分穩定；觀測值依框架而變——value ≠ identity）。
    > **判例（2026-10-15，Q-088）：存起來的開放項就是它的定義。** 「可儲存」的意思是**存的是它的語法**，不是把它物化成「一個記錄、裡面放著沒綁定的 thunk」——開放項的定義（自由 `$` 不算箭頭本體、巢狀 `|>` 的右式、表的分支本體——後者的 `$` 是被匹配的輸入，D109）在演化與提交時都存成語法。**讀一個存起來的開放項，就是在讀它的地方求它**：在讀者的 `$` 底下，讀者沒有就沒有——與就地以名字讀同一個定義一字不差。**此外誰都不另外綁**：被交給演化的值（輸入、引數，以任何名字、在閉包裡、跨提交）照 [GUIDE_03](./GUIDE_03_Incremental_Convergence.md) §11.2 的強制規則（thunk 的 `context` → 觀測方的 `$` → `_|_ #no_context`），由強制它的一方綁；`|>` 右值的 thunk 帶該管道的 `$`（P1）。〔量，v0.89.0；v0.78.0 同〕`t: { a: $.b + 1 }` 提交後 `{ b: 1 } |> _.t` 得 `{ a: ⊥ #no_context, b: 1 }`（就地 `{ a: 2, b: 1 }`），兩個不同的模板演化後 `=` 為 `#true`；頂層 `t: $.b + 1` 在演化當下就坍縮成 ⊥。修正走了三個修補回合：「在讀到處蓋章」「在結果上綁」「以參數框分出被交給的」各自被恆等律 `(x -> x) v`、兄弟別名 `{ y: x, r: y }`、跨提交的閉包打穿——**被交給與被讀到是值與求值時機的事，不是讀取位置的事**；照本條與 §11.2 字面實作則一次成立。
    > **判例（2026-10-17，Q-091）：經過名字讀到也一樣。** `w: t`、`g: { m: t }` 時，`(x -> _.w)`、`(x -> _.g.m)`、`{ @{ @any }: _.w }` 在讀它的框架裡讀到 `t` 的定義，與 `(x -> _.t)` 同答；沒有框架時它仍是模板，之後的 `|>` 照樣綁它。〔量，v0.92.0〕`{ b: 1 } |> (x -> _.w)` 得 `{ a: ⊥ #no_context }`——讀到的配方被原封帶出框架，在沒有 `$` 的地方才被強制。
4.  **P4 `$` 只指輸入**：永不指涉轉換器自身構建中的欄位（sibling 用裸名，詞法溯源 SPEC_04）；
    tuple 輸入按同構以 `$.0`／`$.1` 存取。
5.  **P5 內插不建作用域**：`` `…${…}…` `` 內的 `$` 與字串外完全同步。

#### 4.2.2 正典範例：開放項與自我觀測

```nlang
s: "Logic" |> { a: $ }        ;; {a: "Logic"}
w: { x: $.s }                  ;; 開放項：自由 $，合法儲存
_: w.x                         ;; _|_ (%cause: #no_context)——無包圍演化
v: <<_.>> |> <<_.>>            ;; 銜尾蛇一行式：根宇宙以自身為轉換器
_: v.w.x.a                     ;; "Logic"——此框架下 w 的 $ 綁定為根宇宙
```

*   同一個 `w`、兩個觀測框架、兩個值、無全域截面——開放項是**觀測框架依賴的物件**，
    `$` 是語言在語法層的觀測者記號。
*   **路徑導向（惰性）觀測是語義要求，非最佳化**：根宇宙含 `v` 自身，`v` 的全量觀測
    必然自我迴歸、以 `%fuel` 視界收場（`#incomplete`）；`v.w.x.a` 這類路徑投影則有限收斂。
    引擎**必須**支援按需收斂（規範：**[SPEC_04](./SPEC_04_Navigation_and_Duality.md) §6**；工程施工圖：GUIDE_03 §11）。
*   **注入警覺**：誰 pipe 開放項，誰的上下文即綁定其 `$`。來自 LADD 的開放項是
    「等待上下文注入」的物件；信任層對策（如 `%open` 自省標記）屬 REAL／ORDER 排程。

#### 4.2.3 路徑上溯與過度穿透 (Path Ascent Limits)

`^` 系列為**路徑面**符號（容器上溯，SPEC_04／SYNTAX_03 §4.4；2026-07-17 三款裁定）：
容器鏈以**根宇宙**為最外層（二層深處 `^^` 即達 root）；`^.x` 為**嚴格座標**存取（該層無
`x` → 開放 `_`，不外溯）；`^` 僅得出現於 **RHS**（定義鍵位含 `^` 已廢止＝文法非法，
字面量局部性保全）。當 `^` 數超過容器嵌套深度（root 級 `^` 即是），**觀測**時 → `_|_`
（`%cause: #out_of_horizon`，details 含 `actual_depth`／`requested_depth`）。

**態射體內 `^`(裁定 2026-07-19)**:`^` 是**定義當下的路徑縮寫**,
非觀測時依當前路徑判讀——態射體內的 `^` 鏈=**定義側容器鏈到底**
([持有容器 → … → 根宇宙];體視同持有容器內一層,與巢內字面量
`c: {k:7, w: {q: ^.k}}` 讀 c 同構),於定義處捕獲,**不隨呼叫點
改變**;超深 → 觀測 `_|_`(`#out_of_horizon`)。呼叫點資料的唯一
通道=`$`(P1–P5 顯式傳遞)。三通道各一法:**裸名=詞法鏈**
(SPEC_04 §2.1)、**`$`=動態輸入**、**`^`=定義側嚴格座標**。
(語義梳理見本章卷首「態射與管道的分工」——藍圖屬於繪圖桌世界,
體內 `^` 讀定義側即其推論;本款只封走私動態通道。)

### 4.3 演化即提交 (Evolution as Commit)
每一次成功的管道演化在 `oo` 引擎中都被視為一個原子的狀態推進。
*   **原子性**：若管道內部的收斂結果為 `_|_`，則整個管道輸出 `_|_` 且不產生新的 Commit。
*   **不穩定狀態偵測**：利用子型別判定 `x <= _|_` 可以在管道內部建立邏輯防火牆，防止錯誤的演化被提交。

### 4.4 態射升寫與函子性 (Morphism Lifting & Functoriality)

當管道的輸入是一個容器（如 List、Tuple 或特定 Combo），而右側的態射並不直接接受
該容器型別時，引擎會嘗試 **將態射升寫（Lift）** ，使其作用於容器的內部元素。

這依賴於 Combo 的 `%fmap` 元資訊，它賦予了結構 **函子（Functor）** 的特性。

#### 觸發優先順序

引擎嚴格依照下列順序處理 `A |> /f`，**不跳步、不靜默**：

1.  **直接應用**：嘗試將 `A` 作為輸入直接收斂 `/f`。若成功，回傳結果。
2.  **邊界檢查**：若 `A` 為 **Cocoon `{{}}`** 且未顯式導出 `%fmap`，則立即終止，不進行自動升寫。
3.  **檢查 `%fmap`**：若非 Cocoon（或 Cocoon 已導出介面），檢查 `<A>.%fmap` 是否存在。
4.  **觀測升寫**：若 `%fmap` 存在，將呼叫轉化為 `<A>.%fmap ($, /f)` 並執行。
5.  **回傳 `_|_`**：若 `%fmap` 不存在，正常回傳衝突，`%cause: #conflict`。

**Cocoon 隔離原則 (Cocoon Isolation)**：
嚴禁 `%fmap` 自動穿透 Cocoon 邊界（例如 `{{ [1, 2, 3] }} |> /double` 會收斂為 `_|_`）。
- **理由**：Cocoon 象徵封閉且受保護的私有幾何。自動升寫會導致內部的複合結構被外部態射非對稱地觀測，破壞了封閉性保證。
- **繞過方式**：若需對內含物進行升寫，必須先透過 `...` 展開（Unbox）該內容至開放的 Combo 中。

#### 態射升寫決策流程 (Lifting Decision Flow)

當執行 `lv |> /f` 時，Ouroboros 引擎遵循以下遞迴決策路徑：

```rust
// 虛擬碼語義定義
fn evolve(lv, f) -> Value {
    // 步驟 1：嘗試直接應用 (Direct Application)
    // 檢查 lv 是否符合 f 的參數型別約束
    if lv.matches(f.param_type) {
        return f.apply(lv);
    }

    // 步驟 2：邊界檢查 (Boundary Check)
    // 嚴禁穿透 Cocoon 隔離邊界
    if lv.is_cocoon() {
        return _|_ (%cause: #cocoon_isolation_violation);
    }

    // 步驟 3：觀測函子性 (Functor Observation)
    // 檢查 lv 是否具備升寫能力 (%fmap)
    if lv.has_fmap() {
        // 對 lv 內部的每個元素 e 遞迴執行 evolve(e, f)
        return lv.map(|e| evolve(e, f));
    }

    // 步驟 4：最終衝突
    // 既不符合型別，也不具備函子性
    return _|_ (%cause: #type_mismatch);
}
```

**語義保證**：
1.  **最外層優先**：若容器本身符合 `/f` 的約束（例如 `/f` 專門處理 List），則執行直接應用，不觸發升寫。
2.  **遞迴深挖**：升寫是遞迴的。引擎會不斷向下穿透，直到找到能與 `/f` 合併的層級或觸及原子。
3.  **單調終止**：若所有層級皆不匹配且觸及原子，則收斂為 `_|_`。這確保了型別錯誤不會被靜默吞掉。

#### 範例：List 升寫

```nlang
/double: x@int -> x * 2

[1, 2, 3] |> /double
;; 步驟 1：[1,2,3] 不符合 @int → 直接應用失敗
;; 步驟 2：<[1,2,3]>.%fmap 存在（List 是 Functor）
;; 步驟 3：升寫，等價於 [1 |> /double, 2 |> /double, 3 |> /double]
;; 結果: [2, 4, 6]
```

#### 巢狀容器與遞迴穿透 (Recursive Penetration)

`|>` 操作符具備**自動遞迴升寫**能力。當處理深層嵌套容器（如 `[[[1, 2]]]`）時，引擎遵循以下邏輯：

1.  **逐層觀測**：若當前容器層級不符合態射 `/f` 的約束，且具備 `%fmap`，則進行升寫並對內部元素重複此過程。
2.  **終止點判定**：遞迴在滿足以下任一條件時終止：
    - **匹配成功**：當前層級（可能是內部元素）符合 `/f` 的型別約束。
    - **觸及原子**：抵達無法進一步分解的原子值。
    - **燃料耗盡**：遞迴深度或計算量觸及視界邊限。
3.  **語義範例**：
    ```nlang
    /double: x@int -> x * 2
    [[[1, 2]]] |> /double
    ;; 引擎自動向下穿透三層 List，最終作用於 int 原子
    ;; 結果: [[[2, 4]]]
    ```

*   **資源消耗與深度限制**：
    為了防止惡意或意外的無限深層結構導致資源枯竭，引擎必須實作 **「預設計算半徑 (Default Observation Radius)」**。
    - **`%max_lifting_depth`**：超過此深度的自動升寫將被截斷，並坍縮為 `#incomplete` (%cause: #max_lifting_exceeded)。
    - 每一次升寫與態射應用均會消耗全域觀測資源（`%fuel` 與 `%timeout`）。
    - **級聯坍縮與立即終止 (Cascading Collapse)**：管道演化遵循**強原子性原則**。在 `A |> B |> C` 鏈中，若任何中間步驟產生了不可恢復的 `_|_`，後續的所有步驟將被**立即中斷**。
    - **原理**：因為後續步驟的輸入作用域 $ 已經坍縮為空集合，根據格論，空集合的任何變換結果仍為空集合。
    - **傳播**：最終結果固化為 `_|_`（含完整的 `%cause` 鏈）。這確保了錯誤不會在不穩定的狀態下繼續「演化」，從而保護了宇宙因果的清晰度。
*   **局部防火牆**：可利用 `x <= _|_` 在升寫態射內部攔截錯誤，將特定的衝突轉換為可接受的狀態（如返回預設值），從而防止單一元素的衝突中斷整個管道。


### 4.5 優先權與結合律 (Precedence & Ambiguity)

在 `n/` 的運算子層級中，管道演化（`|>`）的優先權高於態射定義（`->`）。這是一項刻意的設計，旨在確保態射體內部的演化邏輯不需要額外的括號。

#### 情境 A：態射內的演化 (預設行為)
```nlang
/f: x -> x |> /g    ;; 解析為 x -> (x |> /g)
```
這是最常見的模式，態射體自然地包含了其後的演化鏈。

#### 情境 B：演化中的匿名態射 (需明確界定)
若欲將演化對象傳入一個即時定義的態射，由於 `|>` 優先權較高，必須使用括號：
```nlang
data |> (x -> x + 1)    ;; 正確：將 data 應用於匿名態射
```
*註：在 `n/` 的最佳實踐中，更推薦使用 **結構演化 `{}`**（見 §5.1）來替代裸的匿名態射，因為其具備更清晰的作用域語義與結構化能力。*

## 5. 邏輯即組合 (Logic as Combo)

> 本節探討態射在 Combo 結構中的表示方式。關於 Data/Type/Logic 三位一體的哲學基礎，請見 **[SPEC_05](./SPEC_05_The_Trinity_Isomorphism.md)**；關於態射分派與模式匹配的具體演算法，請見 **[SPEC_06](./SPEC_06_Unification_Logic.md)** §1.5。

由於「萬物皆 Combo」，所有的 Logic (態射) 皆可觀測為一個特殊的 Combo 結構
(詳見 **[SPEC_03](./SPEC_03_Combo_System.md)** 與 **[SPEC_05](./SPEC_05_The_Trinity_Isomorphism.md)**)。

### 5.1 高階邏輯 (Higher-order Logic)
態射可以作為另一個態射的輸入或輸出。傳遞時使用 **結構態引用 (`<</f>>`)**。
```nlang
/apply: (f: @morphism, x) -> f x
```
當 `apply` 進行 Unification 時，它會驗證傳入的 `f` 是否具備態射特質。

### 5.2 匿名態射語義 (Anonymous Morphism Semantics)

匿名態射 `(x -> x + 1)` 的完整語義定義：

#### 定義 1：匿名態射的本體
匿名態射 `(param -> body)` 等價於一個未綁定到路徑的 Logic Combo：
```nlang
(x -> x + 1)  ≡  { %kind: #logic, %morphism: #true, %rules: { x: x + 1 } }
```

#### 定義 2：匿名態射的應用
匿名態射可直接應用於參數：
```nlang
(x -> x + 1) 5  ;; 結果：6
```

#### 定義 3：匿名態射的賦值
匿名態射可賦值給欄位：
```nlang
f: (x -> x + 1)
f 5  ;; 結果：6
```

#### 定義 4：匿名態射的分支與聯集
匿名態射可透過 `|` 組合多個分支，實作模式匹配。
```nlang
((x @int -> x + 1) | (x @str -> x + "!")) 5     ;; 結果：6
((x @int -> x + 1) | (x @str -> x + "!")) "hi"  ;; 結果："hi!"
```
*   **語義**：態射聯集 (Morphism Union)——`(A -> B) | (C -> D)` 為兩個 Logic Combo 的格論聯集。**分支必須各自括號**：裸寫 `A -> B | C -> D` 因 `->`（L15）鬆於 `|`（L12）會解析為 `A -> ((B | C) -> D)`，非本意（2026-07-05 釘死，SYNTAX_11 §4.1）。
*   **施用規則**（2026-10-11 改寫，D104）：態射的 `|` 就是 Combo 的 `|`——每支箭頭是它自己的 Logic Combo（定義 1；轉換見 [SYNTAX_11](./SYNTAX_11_Morphism_Definition.md) §2 #6），聯集的成員各以自己被施用，結果取聯集：`(A | B) x  ≡  A x | B x`。與導航遇聯集（`({ a: 1 } | { a: 2 }).a` ⟹ `1 | 2`）、引數是聯集時的逐支演化（§4）是同一條規則；兩側都是聯集時每一對都在。⊥ 的支剪掉；全為 ⊥ 時取主因果、原樣傳出（`REAL_04` §4）。
*   **特定性只在單一成員內比**：一張表的各分支互比特定性（§1.1 極小元素規則），`|` 的成員**不比**。要跨分支比特定性，寫成一張表：
    ```nlang
    ((x @int -> "int") | (5 -> "five")) 5    ;; 結果："int" | "five"
    { @{ @int }: "int", 5: "five" } 5         ;; 結果："five"
    ```
    原文此處的分派規則寫「引擎在應用時，會同時觀測所有分支，並根據「最特定匹配原則 (SPEC_06)」選擇最符合輸入條件的分支。若多個分支同時匹配且互不可比，則結果保持為聯集態。」——那是跨成員比特定性，與 D104 相反，已改寫。原掛的兌現缺口註記（本定義兩例皆得 `_|_ #conflict`，2026-10-09）隨 Q-080 兌現而移除。

#### 定義 5：匿名態射的柯里化
多參數匿名態射自動柯里化：
```nlang
(x y -> x + y) 2 3        ;; 結果：5
((x y -> x + y) 2) 3      ;; 等價於上一行
```

#### 定義 6：動態型別推導 (Dynamic Type Inference)
若匿名態射未顯式標註輸入型別（如 `x -> x + 1`），其輸入型別將由實際調用時傳入的參數動態決定。
*   **聯集型別態射 (Union Type Morphism)**：若該態射被多次以不同型別呼叫，在靜態分析與型別推導的視角下，它實質上等價於一個處理聯集型別的態射（類似泛型實例化）。

#### 限制
匿名態射**不具備**以下特性：
1. **無路徑名稱**：無法透過路徑引用自身（遞迴需使用具名態射）
2. **無 `%compat`**：不支援相容性宣告
3. **無 `%migration`**：不支援遷移態射

**建議實踐**：
- 簡單變換使用匿名態射（如管道中的臨時變換）
- 複雜邏輯或遞迴定義使用具名態射

### 5.3 態射合併的語義與衝突 (Morphism Merges & Conflict)

根據 **[SPEC_05: 三位一體同構](./SPEC_05_The_Trinity_Isomorphism.md)**，態射（Logic）本質上亦是 Combo，因此必須遵循格論的交集合併（`&`）運算。

#### 定義 1：合併公式
當兩個態射 $f$ 與 $g$ 進行合併（ $f \sqcap g$ ）時，其語義是尋找一個同時滿足兩者映射規則的新態射。

*   **定義的合併**（2026-10-12，D105）：`f ⊓ g` 是**一張表**——兩邊的列取聯集，同一約束是同一分支、本體相交（**被選中時**各以自己的綁定名求值，§1.1.2），施用時照常依極小元素分派（§1.1）。**只有綁定名的箭頭是約束為 Top 的一列**（`@{ _ }:`，[SYNTAX_11](./SYNTAX_11_Morphism_Definition.md) §2 #6）；**沒有列的態射**（內建、部分施用，如 `~%Math./add 1`）是約束為 Top、本體為「施用它」的一列。相交的先後與分組不在位元組裡（D101）。
    ```nlang
    ((x -> x) & (x -> 5)) 5                 ;; 結果：5（同一個 Top 列，兩個本體皆得 5）
    ((x -> 1) & { @{ @int }: 2 }) 5         ;; 結果：2（較特定的列勝出）
    ((x -> 1) & { @{ @int }: 2 }) "s"       ;; 結果：1
    (~%Math./add 1 & { @{ 5 }: 99 }) 6      ;; 結果：7
    ```
    這是 §5.2 定義 4（D104）的對偶：`|` 讓成員各自施用、不比特定性；`&` 把它們熔成一張表、比特定性。原掛的待裁註記（2026-10-09：表 `&` 是分支聯集，與下列公式兩讀）以本款結清。
*   **公式**：對於任何輸入 $x$， $(f \sqcap g)(x) \equiv f(x) \sqcap g(x)$ ——**在 $f$ 與 $g$ 的約束相同時成立**（例如兩邊都只有綁定名；本節定義 3 的案例 A、B 皆屬之）。約束不同時，較特定的列在它匹配之處勝出（上款）。
*   **本質**：在同一個約束上，態射合併是對輸出結果施加的 **「雙重約束」**。

#### 定義 2：對偶身份與部分應用
當一個態射被部分應用（柯里化）時，它在格論中被視為一個**已部分坍縮的幾何物件**。
*   **Logic 性質**：它依然具備可觀測性，等待下一個參數。
*   **Data 性質**：它可以與 Metadata 合併，成為一個「攜帶狀態的邏輯體」。
    ```nlang
    ~f: /add 1                      ;; 部分應用
    ~meta: { name: "incrementer" }  ;; 附加數據
    ~rich_f: ~f & ~meta             ;; 合併
    
    ~rich_f 5                       ;; 結果：6 (Logic 屬性)
    ~rich_f.name                    ;; 結果："incrementer" (Data 屬性)
    ```

#### 定義 3：邏輯衝突與精煉案例
若對於相同的輸入 $x$， $f(x)$ 與 $g(x)$ 的交集為空集合，則該合併態射在 $x$ 上的觀測結果立即坍縮為 **`_|_` (Bottom)**。

*   **案例 A：數值衝突 (Value Conflict)**
    ```nlang
    /f: x -> 1
    /g: x -> 2
    /h: /f & /g
    ;; 觀測 /h 10  -> 結果: 1 & 2 -> _|_ (%cause: #conflict)
    ```
*   **案例 B：型別精煉 (Type Refinement)**
    ```nlang
    /check_int: x -> @int
    /check_pos: x -> @{ $ & !(..0) }   ;; 嚴格正性 = 正交補（稠密域無閉區間拼法）
    /is_pos_int: /check_int & /check_pos
    ;; 觀測 /is_pos_int 5 -> 結果: 5 (滿足雙重約束)
    ```

#### 邊界案例：原子同構展開
根據 **[SPEC_06](./SPEC_06_Unification_Logic.md)**，態射與原子的合併（如 `/f & 5`）會產生一個既是態射又是數值的複合體。這在實作帶有標籤的邏輯或常數態射時非常有用。
