## 1. 承重結論(候選)

### 1.1 有兩個 `.oo`,同名、不同義、不同根

〔量〕全樹掃描(未截斷)`join(".oo")` 共 21 處,得出:

```
~/.oo/                              <workspace>/.oo/
├── identity   ← 操作者身分         ├── objects/sha256/<2hex>/<rest>  ← CAS
└── nodes/                          ├── HEAD   format   staged
    ├── <sha256(工作區絕對路徑)>     ├── pin_pending   effect_pending   abandoned
    │     ← 節點金鑰                ├── architects.json   discovery.n
    └── <同上>.affiliation          ├── peers/directory
          ← 歸屬聲明                └── routing/
```

出處〔讀〕:`value.rs:1848`(operator identity)、`value.rs:2008`(`node_key_path`)、
`value.rs:1985`(`resolve_node_home`,可由 `OO_NODE_HOME` 覆寫)、
`storage.rs:86/109/233/297/310`、`universe.rs:501/511/521/633`、
`discovery_config.rs:25`(`CONFIG_FILE = "discovery.n"`)、
`peers.rs:87`(`PEERS_DIR = "peers"` / `PEERS_FILE = "directory"`)、
`oodp.rs:608`(`{node_key_path}.affiliation`)。

**一個名字,兩個尺度**:HOME 側是「這個人在這台機器上的 n/ 身分」,
工作區側是「這個宇宙」。**其中一個裝著私鑰。**

**〔量〕把 HOME 當工作區會怎樣**(以 `HOME` 重導至暫存目錄實測,未觸及真實 HOME):

```
~/.oo/
├── format   objects/   staged     ← 工作區的宇宙
└── nodes/<hash>                   ← 全機器的節點金鑰登記處
```

**檔名沒有一個相撞,所以它「能用」。危險在刪除語義**:
`rm -rf ~/.oo` 想重置一個工作區,結果連這台機器上所有節點金鑰(與 `identity`)
一起銷毀。**「重置這個工作區」與「銷毀我在這台機器上的全部身分」變成同一個命令。**

**裁定(用戶,2026-08-04):要拆,HOME 側改名 `~/.nlang/`。**
理由(本文補):HOME 側裝的東西**沒有一樣屬於某個引擎實例**——那是**專案範圍**,
不是引擎範圍。而 `nlang` 已是專案的既定拼法(`nlang-spec` / `nlang-tools` /
`co-nlang.org`),`oo` 是 CLI 與引擎的名字。**改名是把每個名字放回它自己的尺度。**

### 1.2 節點身分由檔案系統路徑決定——而那是裁定過的

**〔量〕搬移工作區會換掉節點身分:**

```
原地    node id …6ae9d364e41dad8950002594d466364564b53f445be5724ff73d47df8e7a29c1
mv 之後 node id …f570d9f104bd9a58d8e30df142c3baa26ff804045ca58daf531971acf50917a6
```

**〔讀〕這不是意外,REAL_02 §4.1.1 明文寫了代價:**

> 引擎**無法**區分「工作區被搬移」與「工作區被複製」——它只觀察到路徑改變——
> 故令路徑參與身分,使**複製在結構上即為另一個節點**,無需偵測、無需啟發式、
> 無需詢問操作者。**代價是搬移工作區即更換節點身分,此為明知之取捨。**

同節另有兩條:節點金鑰**不得**置於 `.oo/` 內(該樹是設計來被取用與複製的成品);
節點金鑰**不得**與操作者金鑰同一把。以及 §4.1.1 的一句好理由——

> **讓宇宙可聯邦的性質,恰好取消它作為節點位址的資格**——
> 內容定址回答「是什麼」,節點位址回答「眾多持有者中的哪一個」。

⟹ **本文初稿把 `mv` 的後果當成「意外」呈現,不對。它是被看見、被權衡、被接受的。**

#### 1.2.1 但 savepoint 框架給了一個更乾淨的拆法(候選,**未裁定**)

§4.1.1 的論證前提是「引擎無法區分」——**但那說的是自動偵測**。
而金鑰**本來就不在工作區裡**(同節明文禁止),所以:

> **複製之所以拿不到身分,是因為金鑰不在被複製的樹裡——與路徑怎麼當鍵無關。**

路徑鍵化實際只做一件事:**查找**。於是:

| | 今天 | 拆開之後 |
| :-- | :-- | :-- |
| 複製工作區 | 新路徑 → 無金鑰 → 新節點 ✓ | **一樣** ✓ |
| 搬移工作區 | 新路徑 → 無金鑰 → **變成別人** | **更新索引 → 還是同一個人** |

代價是要有人說「我搬家了」。**而那不是啟發式,是一句斷言**——正是斷言層的用途,
與信任根那一弧同形(**操作者宣告,引擎不猜**)。

⟹ **路徑今天是「定義」,應該是「索引」。** 而 §4.1.1 的 惰性 條款(首次網路使用時
才產生)已經把身分放在 published 那一側了,**只差沒把查找方式與身分定義分開**。

> **對照(用戶提出):** agent harness(如 Claude Code)把專案資料放
> `$HOME/.<harness>/projects/-home-gali-nlang/`,路徑編碼進目錄名,搬家要手動改。
> **但那是快取,搬錯了頂多失去歷史;n/ 這個是身分,搬錯了等於變成另一個人。**
> 同一個設計,**代價差一個量級**;harness 敢這樣做正因為它可以接受重建。
> ⟹ n/ 不該照抄,**不是設計不好,是放錯了層**。

### 1.3 工作區 `.oo/` 裡有三種威脅模型,只用檔名區分

| 檔 | 是什麼 | 層(`commit.md` §1.8) | 誰寫 |
| :-- | :-- | :-- | :-- |
| `objects/sha256/**` | CAS | **自我認證** | 引擎 |
| `routing/` | DHT 路由表 | **可重算**(由 `peers/` 重建) | 引擎 |
| `HEAD` `format` `staged` `pin_pending` `effect_pending` `abandoned` | 引擎自己的狀態 | 斷言 | 引擎 |
| `architects.json` | 誰能 refine 這個宇宙 | 斷言 · **信任根** | 帶外 CLI |
| `discovery.n` | 歸屬信任根 | 斷言 · **信任根** | 帶外 CLI |
| `peers/directory` | 對等點目錄 | 斷言 · **內容來自網路** | 引擎 |

⟹ **`.oo/` 裡只有 `objects/` 是自我認證的。** 其餘十項全在斷言層,
而權威來源天差地別:**引擎自己的暫態 / 人類設定的信任根 / 遠端餵進來的資料**。

而 SPEC_08 §6.3 的儲存邊界對這三者**一視同仁**地把語言層擋在外面。
那個閘是對的,但**它把「不可寫」當成唯一的軸**——`peers/directory` 是唯一內容來自
遠端的,卻跟 `HEAD` 躺在同一層。

**裁定(用戶,2026-08-04):三類可以分開。**(怎麼分未定。)

### 1.4 點不是隱藏,是命名空間保留

〔讀〕`fs_guard.rs:167`:

```rust
fn path_has_dot_oo_component(path: &Path) -> bool {
    path.components().any(|c| matches!(c, Component::Normal(s) if s == ".oo"))
}
```

閘比對的是**任何位置上、恰好等於 `.oo` 的路徑元件**。

⟹ 改成 `oo/` 之後,**任何一個剛好叫 `oo` 的普通目錄都會被語言層拒絕存取**。
`.oo` 這個拼法**保留了一個沒人會不小心用到的名字**;`oo` 不是。
**點在這裡不是隱藏,是命名空間保留——那是 lock 的前提,不是 lock 的替代。**

**但「格論底下沒什麼好藏的」(用戶)有道理,而且有一個具體的不對稱撐著:**

> 在 git 裡 `.git/` 是**簿記**,內容在工作樹。**在 n/ 裡反過來——`.oo/` 就是宇宙本身**
> (`commit.md` §2.5 量過:evolve 之後 `.oo` 獨立於 `a.n`),`.n` 檔比較像投遞管道。

⟹ **點在語義上說了一句假話(「這是內部細節」),但在工程上做了兩件真事**:
shell 誤刪防護 + 命名空間保留。

**裁定:留著點,但把理由寫對。** 並同時記下:**藏不等於鎖,而 n/ 的鎖是分開的**——
SPEC_08 §6.3 是無條件拒絕,**沒有任何能力可以解開**。
**點擋 shell,閘擋程式**,兩者擋的不是同一個對手,不是冗餘。

### 1.5 信念面與發言面

(用戶 2026-08-05 提問:`.oo/` 內各檔的竄改/偽造,跟 `mv` 是不是同一個概念?
既有的立場是「你要亂改是你自己的事,引擎做好校驗即可」。)

**〔量〕竄改各檔的實測:**

| 動的東西 | 結果 | 傷到誰 |
| :-- | :-- | :-- |
| `objects/**` 加一個位元組 | **`#object_undecodable`**「present … but cannot be decoded (integrity unknown)」 | 自己 |
| `HEAD` → 不存在的 CAID | **`CAID not found in local store`** | 自己 |
| `HEAD` → 另一個**存在的** commit | **接受,無聲**(那本來就是 checkout) | 自己 |
| **`architects.json` 塞入自己的公鑰** | **完全無聲**,`status`/`log` 都不說 | **自己**(你會開始承認不該承認的 refine) |
| `peers/directory` 偽造一列 | **簽章驗證,壞的列被移除**(`peers.rs:483` `verify_loaded` → `verify_stored_ad`) | — |

⟹ **「你自己的事」是對的,但它只被驗證在一個面上。** 上表五列的傷害全部關在自己身上。

**而有第二個面,那句話從沒在上面被檢驗:**

| | 決定的是 | 壞了傷誰 |
| :-- | :-- | :-- |
| **信念面** | **我相信什麼**——`objects` `HEAD` `staged` `architects.json` `discovery.n` | 自己 |
| **發言面** | **我對別人說什麼**——**節點金鑰**、以及**由路徑導出的身分** | **別人** |

動節點金鑰 ⟹ 你用別人的名義簽章。`mv` ⟹ 你變成另一個節點,別人的對等目錄指向
一個不存在的身分,為舊 `node_id` 簽的歸屬聲明全部孤兒化。

> **軸不是「自我認證 vs 斷言」,是「這決定我相信什麼,還是我說什麼」。**

(歸屬聲明 `<node_key>.affiliation` 也在發言面,但**受節點簽章保護**
——「只壞聲明」這個狀態不存在,是歸屬弧的代修結論。故不在本類。)

#### 1.5.1 `mv` 與竄改的差別,精確地講

**竄改有意圖;`mv` 沒有。** 上表每一列都是有人刻意編輯 `.oo/` 裡的檔案;
`mv` 是一個完全普通的檔案系統操作,**沒有任何改變身分的意圖**——它就是改變了身分。

⟹ **真正的概念不是「竄改」,是:**

> **身分被一個「會因為不相干的理由而改變」的東西決定。**

這使它成為**可檢查的類別**:找所有**在發言面上、卻由引擎完整性傘之外的東西導出**
的項目。**今天恰好只有一個:工作區路徑。**

#### 1.5.2 這也把 §6.3 的角色說清楚了

SPEC_08 §6.3 那個無條件的儲存邊界,**保護的是信念面、防的是程式**
——一支惡意的 n/ 程式改不了你的 `architects.json`。那個閘是對的。

**而發言面沒有任何東西防「操作者自己的檔案系統操作」。** 這通常沒問題,
因為操作者就是權威;**但 `mv` 正是那個例外:操作者做了一個動作,
而那個動作的意義不是他選的。**

⟹ **缺的不是更多完整性檢查,是「身分不該是任何『操作者為了別的理由而動的東西』
的函數」**——正是 §1.2.1 的「路徑是索引,不是定義」。

**`mv` 那個發現與竄改這個問題,指向同一個修正。** 而這也說明 §1.2 那句
「明知之取捨」為什麼值得重看:**當初權衡的是「複製 vs 搬移」,沒有權衡到
「發言面不該由無意圖的操作決定」——軸選錯了,不只是不方便。**

### 1.6 `oo node <verb>`:那句斷言的介面

(用戶 2026-08-05 由 `rm` / `git rm` 的差異想到。)

**類比比表面更強。** `git rm` 是**可選**的——`rm` 之後 `git add -A` 效果一樣,
因為 git 能靠比對工作樹與索引推出「刪除」。而 §4.1.1 明文說引擎**無法**推出「搬移」。

> **git 有 `git rm` 是為了方便;oo 需要它是因為那是那個事實唯一的通道。**

**但它不可能是強制的**——人會在 shell 裡 `mv`、在檔案管理員裡拖、
`git clone` 到別的路徑、在容器裡掛到別的掛載點。**永遠無法要求工具被使用。**

**而 §1.2.1 的索引設計正好讓那沒關係:**

| | 索引設計底下 |
| :-- | :-- |
| 用了指令 | 更新索引 → **身分保住,無損** |
| 沒用(shell `mv`) | 新路徑無索引項 → **退回今天的行為,鑄新身分** → **安全,只是有損** |

⟹ **索引讓「沒用工具」的退路安全,工具讓「用了」的路徑無損。缺一不可**
——所以這個指令不能單獨做,得與 §1.2.1 同行。

**名字:** `git mv` 搬的是倉庫裡的檔案,這裡搬的是工作區本身,同名不同尺度。
而用戶設過的判準是「核心動詞留 flat,**非工作樹之物收進名詞命名空間**」,
**節點身分正是非工作樹之物**,且 **`oo node` 已存在**(`serve`/`id`/`advertise`/…)。
⟹ 應為 `oo node <verb>`,不是 `oo mv`。**這是那個被擱置的 CLI 形狀決定的第一個具體案例。**

**裁定(用戶,2026-08-05):後置。** 搬完再認領,如
`oo node adopt --from <舊路徑>`;中間那段時間你是一個新節點,
但**檔案系統狀態已經是真的**,斷言描述的是既成事實而非預告。

#### 1.6.2 為什麼是後置——與 WAL 相反的那一半

用戶的直覺是「這很像 REDO/UNDO log 的一致性問題,而這個一致性還上升到斷言層」。
**方向對,但理由是相反的那一半:**

**WAL 的原則其實是前置**(log 先寫、再動資料)。它敢前置,是因為**日誌是權威**
——崩了可以照日誌把資料推成真的。

**而這裡檔案系統是權威。** 引擎推不動它:`mv` 失敗救不回來,`mv` 沒發生也變不出來。

> **方向取決於「你能不能強迫另一邊跟上」。WAL 能,所以前置;
> `oo node adopt` 不能,所以後置。**

**而「上升到斷言層」正好接在這裡:** 資料庫裡日誌與資料**都在它的控制內**,
一致性是**機制**問題;這裡有一邊在外面,一致性就變成**斷言**問題
——操作者說發生了什麼,而**沒有任何東西可以拿來對照驗證**。

**失效模式也因此不同:** WAL 的缺口可以重放補回;
**未被認領的搬移不會報錯,它只是靜靜地變成一個新節點。**

⟹ 這正是 §1.6「缺一不可」的理由:**既然無法保證那句斷言會被說出來,
沒說的那條路必須自己就是安全的。**

#### 1.6.1 `oo copy` 是問錯的那一個;缺口在反方向

複製**本來就該**拿到新身分(§4.1.1 的全部重點),而且今天免費成立
⟹ `oo copy` 會是換了名字的 no-op。

**真正沒有的是刻意的身分繼承:換機器。** 今天路徑與 HOME 都變
⟹ **不可能在新機器上還是同一個節點**,除非手動把 `~/.oo/nodes/<舊hash>`
複製到新機器的 `<新hash>`——**做得到,但沒有文件、沒有指令、不可能被發現。**

⟹ **換筆電 = 失去網路身分。** 而這暴露一個不對稱:

> **§4.1.1 花了力氣讓「複製」不繼承身分,卻從沒提供任何「刻意繼承」的路徑。
> 防偽造做了,支援遷移沒做。**

## 2. 圖與現況對不上的地方

### 2.1 REAL_01 §4.2 的參考佈局幾乎是虛構的

規格畫的:`objects/{objects.idx, refs.idx, pack/, 00/}`、`refs/heads/main`、
`refs/HEAD`、`staged`、`config.n`、**`audit.log`**、**`wal/`**。

**〔量〕實際只有 `objects/` 與 `staged` 名字對得上**:
`refs/` 不存在(HEAD 是平的)、`config.n` 不存在(是 `architects.json` +
`discovery.n` 兩個)、`objects.idx` / `refs.idx` / `pack/` 都沒有、
分片是 `objects/sha256/<2hex>/<rest>` 而非 `00/`。

**而最值得注意的是缺的那兩個:**

> **`audit.log`** 與 **`wal/`** —— **規格早就把 `commit.md` 弧 A 缺的兩塊命名了,
> 而引擎兩塊都沒蓋。**

`commit.md` §1.5.4 的 REDO log 就是 `wal/`;§1.7.3 那條「值不會記得所以必須留痕」
就是 `audit.log`。**幾輪推導出來的東西,REAL_01 §4.2 早就寫在那裡。**

**裁定(用戶,2026-08-04):弧 A 就用這兩個既有的名字。**
⟹ 那會把規格裡的虛構變成事實,而不是再發明一組。

### 2.2 儲存邊界的保護方式,正是 §4.1.1 明文禁止依賴的那一種

REAL_02 §4.1.1 保管條款:

> 必須在語言層路徑邊界之內,且**該保護不得依賴路徑恰好含儲存目錄名之元件**。

而 §1.4 的 `path_has_dot_oo_component` 做的正是那件事:**節點金鑰之所以受保護,
唯一的原因就是它的路徑含 `.oo` 這個元件。**

⟹ **規格明文禁止依賴的東西,就是引擎今天唯一依賴的東西。**
(本條是對該條款的閱讀,不是條文自陳;若讀法有誤請糾正。)

**後果:** §1.1 的 `.nlang/` 改名**不是引入新風險,是會讓一個既有的不合規顯形**
——今天沒炸,只因為兩邊剛好同名。改名時**必須**同時處理這個閘,
否則 `~/.nlang/identity` 對任何 n/ 程式變成可讀。

### 2.3 `nodes/` 只增不減

**〔量〕** 本機 `~/.oo/nodes/` 目前 **166 個金鑰檔**——每一個曾經跑過 `oo` 的路徑
都鑄了一把(含本次對話開的每個暫存工作區),**而沒有任何東西會回收它們**。

金鑰是為「首次網路使用」而生(§4.1.1 惰性),但實測顯示**純本地操作也會鑄**。
⟹ 兩個問題各自獨立:**鑄得太早**,以及**從不回收**。
